## 四、D23 最终拍板（用户 2026-05-28）

### 拍板：**worker_threads**

### 拍板理由

1. **启动 + IPC 双线胜出 4-5x**：cold-start 优势显著；pre-warm 后差距消减但 fallback 场景保持；worker pool 启动时延迟低
2. **同环境双栈兼容**：worker_threads 在 Electron + 纯 Node 都能跑（POC 用 `node` 直接跑通）；CI 集成测试 / 性能基线脚本可不依赖 Electron 跑（spec §七 测试矩阵收益）
3. **cancel 不构成 utilityProcess 胜出依据**：worker_threads 17.91ms / utilityProcess 2.32ms — 两者都远低于 1s 阈值，且 A4 chunked 10w/chunk 业务阈值 cancel < 5s 更宽松
4. **OS 资源占用更小**：worker_threads 同进程 V8 线程；utilityProcess 独立 Electron Helper 子进程 + V8 isolate
5. **内存隔离需求弱**：worker 内只跑 SQL + 算法，无第三方 native 代码，不需要 utilityProcess 提供的进程隔离
6. **API 一致性**：两者 `parentPort.on/postMessage` 几乎一致；utilityProcess child message event payload 在 Electron 36 实测时是 raw 而非 `{ data }` 包装（详 §六 surprise #2），需要兼容代码；worker_threads 无此问题

### utilityProcess 不作为备选保留

- POC 已验证两种方案对 DatabaseSync 均无障碍
- 未来若发现 worker_threads 与某第三方 native 模块冲突，可重新评估
- Phase 1 不实现双栈支持（防过度设计 + 资金红线）

## 六、POC 中发现的 6 个 surprise

| # | 发现 | 影响 | Phase 1 处理 |
|---|---|---|---|
| 1 | `ExperimentalWarning: SQLite` 每个 worker 启动都打印 | worker pool 启动会刷屏 stderr | 写 worker 时加 warning filter |
| 2 | utilityProcess child message payload 不一致（spec 示例 `{ data }` 实测 raw） | 选 worker_threads 后可忽略 | N/A |
| 3 | worker_threads cold-start 仅 11ms（spec 预测 100-200ms 偏保守） | pre-warm 策略可放宽 | spec §2.1.1 后续可优化 |
| 4 | utilityProcess 启动 53ms 比 worker_threads 高 5x，但仍 << 200ms | Windows 低配机型可能接近 200ms | 选 worker_threads 后无 Windows 风险 |
| 5 | PRAGMA `synchronous=NORMAL` 返回 int 1 不是字符串 | PRAGMA verify 代码需注意类型 | Phase 1 T06 worker 入口实现时按 int 断言 |
| 6 | DatabaseSync 在两种 worker 容器内都能正常工作 | D24=a 方案基石验证通过 | Phase 1 T06 直接按 spec §2.2.1 实施 |
