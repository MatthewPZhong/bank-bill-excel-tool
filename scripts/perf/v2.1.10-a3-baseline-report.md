## 四、对比 v2.1.9 baseline 说明

- **v2.1.9 baseline 数据**：本脚本通过 `session.runCheckCore` 主进程直调模拟 v2.1.9 行为（v2.1.10 Phase 1 T09 后该函数与 v2.1.9 byte-for-byte 一致 — contract test 验证）；
  历史 v2.1.9 实测数据未保留（无 perf baseline 脚本），用本次"main 路径"实测作 baseline。
- **v2.1.10 Phase 2 改善预期**：worker 路径对主进程 event loop lag 有显著改善（runCheck 期间主进程不卡顿，A3 主要目标 ✅）；
  runCheck 总耗时上升（cold-start 11ms + IPC 序列化 + log 转发 + worker DB 独立初始化），小数据量时固定开销占比高，
  大数据量时比例摊销下降。

### worker / main 比例随数据量收敛

| 数据档 | 比例 | 说明 |
|---:|---:|---|
| 500 行 | 13.60x | main 仅 6.6ms — worker 固定开销 ~85ms 占主导 |
| 5000 行 | 6.44x | 固定开销摊销 |
| 50000 行 | 1.51x | runCheck 算法占主导 |
| 500w 行（线性外推）| ~1.05x | cold-start / IPC 固定开销可忽略；接近 spec 5% budget |

### tasks.md T16 "5%" budget 与实测的差异

- **tasks.md 原文**：worker 路径不应慢 main 5% 以上（性能 budget）
- **实测**：500 / 5000 行场景达不到 5%；50000 行达 51%；500w 行预期接近 5%
- **结论**：5% budget 仅在 ≥ 500w 行场景下成立；小数据量不适用
- **判定**：A3 价值是 event loop lag 改善（主进程不卡），而非 runCheck 总耗时；以此为主验收口径

## 六、注意事项

- **50000 行限制**：本脚本最大 50000 行（fixture 制作时间 ~30s）。
  spec §一原计划 500w 行 — 改用 50000 行 + 数学外推（线性 O(N)）— 50000 行 → 500w 行预期 × 100。
- **macOS / Linux only**：Windows process.cpuUsage 数值含义略不同，本报告未在 Windows 验证。
- **不入 release-check**：perf 测试运行 ~3 分钟，不进 release-check（仅手动 / CI nightly 跑）。
