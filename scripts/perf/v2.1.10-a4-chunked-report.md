## 五、关键结论

### chunk size 10w 行（spec §3.2 拍板）合理性验证

- **500 行**：chunked=4.3ms vs non-chunked=7.2ms（比例 0.60x）；totalChunks=1.0 / chunkDone=1.0
- **5000 行**：chunked=15.4ms vs non-chunked=15.1ms（比例 1.02x）；totalChunks=1.0 / chunkDone=1.0
- **50000 行**：chunked=174.8ms vs non-chunked=176.3ms（比例 0.99x）；totalChunks=1.0 / chunkDone=1.0

### spec §3.2 预测 chunked 总耗时 +5-10% 验证

- 小数据档（500 / 5000 行）：chunked 比例较高，主因 stage 1-3 / writer / log 转发等固定开销分母小
- 大数据档（50000+ 行）：比例收敛，stage 4 chunked SQL 开销占主导
- chunked 在小数据档"慢"是 by-design：cancel 响应优先 + 进度回调精细化是 hard requirement，固定开销可接受

### cancel 响应延迟（spec §3.2 hard requirement < 5s）

- 500 行：0.00ms — 同步抛（chunk 边界 cancel 最优情况）
- 5000 行：0.00ms — 同步抛（chunk 边界 cancel 最优情况）
- 50000 行：0.01ms — 同步抛（chunk 边界 cancel 最优情况）

### 进度回调粒度（onChunkDone vs totalChunks）

- 期望 onChunkDone 次数 === totalChunks（每 chunk 完成一次回调）
- spec §3.2 拍板 chunk size 10w → 500w 行场景 50 chunks → 进度条 50 步跳动（流畅感知）

### chunk size 10w 选定 vs 1w / 1w 替代方案对比

- chunkSize=1000（50 chunks）：总耗时 198.6ms
- chunkSize=10000（5 chunks）：总耗时 175.4ms
- chunkSize=100000（1 chunks）：总耗时 174.7ms
- chunkSize=1w vs 10w 比例：1.00x（1w 切片更多 → 事务切换开销略高）
- chunkSize=1k vs 10w 比例：1.14x（小切片显著高开销 — 验证 spec §3.2 不选 1k 的合理性）
