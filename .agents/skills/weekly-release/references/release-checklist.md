# weekly-release 执行 Checklist

本文件是每周发版步骤的唯一维护正文，配合上级 `SKILL.md` 使用。它是可复制的空白执行模板，不代表已经完成一次发布。沿用原流程的范围冻结、review、测试、PR、正式标签及发布核验；本版增加“从上一正式版本分模块开发、已集成后接手”的明确入口。

**推荐使用方式：模块开发与合并由你先完成；调用 Skill 后从 B 接手，核对已有成果，再继续 C—G。A 仅在尚未准备本轮分支时执行。**

## A．周内准备与模块集成（已完成则仅核验）

- [ ] **A1 确定稳定基线**：确认上一版确已发布，记录正式 tag 对应的 commit SHA；不把 `package.json.version`、文件夹名或仍可能前进的旧 release 分支末端直接当成发布基线。
- [ ] **A2 建立本轮分支**：仅在本轮 release 尚不存在时，从该基线创建 `release/<目标版本>`；独立模块分支从同一基线创建。依赖其他模块时明确依赖及起点，不意外带入未纳入的改动。下一轮另建 release，不继续向上一轮 release 累积新功能。
- [ ] **A3 完成单项准入**：模块目标、范围、验收依据明确；已完成相关 review 和必要验证；影响发布的重要未知项、设计冲突与人工复核已处理，文档适用且可用。
- [ ] **A4 按依赖集成**：把已达到准入条件的模块提交合入本轮 release，处理冲突并验证受影响行为。记录合并的具体 SHA；未完成、被排除或缺依赖的模块顺延，不因为“本周做过”就合并。

**本地与远端：**开发、集成可先在本地完成。需要协作、远端验证或开 PR 时推送同名 release；推送该分支不等于把它合入远端 main，也不等于正式发布。

## B．Skill 接手、冻结范围与基线核验

- [ ] **B1 核对任务与工作区**：确认目标版本、分支、窗口、操作范围；运行 `git status --short`，检查相关差异、暂存、未暂存与未跟踪文件。保留用户改动；发布候选须有明确已提交状态，不能把未提交改动当成将被发布的内容。
- [ ] **B2 核对远端与发布配置**：fetch 实际远端，检查真实分支状态、当前构建/发布 workflow 和适用保护规则。不为“对齐”执行破坏性 reset、强推或覆盖；本地 main 有独有提交时保留并说明，可直接使用已获取的远端引用核验。
- [ ] **B3 接手已有 release**：记录本轮 release 当前 SHA、上一发布基线与已有验证证据；已有分支保持原状，只补尚缺的已授权工作。源分支已合入时不重新合并，也不从 main 重新创建覆盖它。
- [ ] **B4 冻结清单**：逐项标注纳入/顺延/阻塞、源分支和选定 SHA、依赖及验证依据。对照 release 的实际差异，确认纳入内容存在、未被后续冲突处理或 revert 移除，且没有混入被排除的内容；不要只依赖分支名或时间范围。
- [ ] **B5 检查最新 main**：检查最新 `origin/main` 是否已包含在 release 历史中。main 若新增 hotfix 或其他必要更新，核对后合入 release 并重验受影响内容；若新增内容不能进入本轮，先解决发布范围冲突，不能声称已验证最新组合。不要重置已有 release 来“刷新基线”。

## C．版本、文档与最终候选验证

- [ ] **C1 更新版本文件**：在 release 上将项目版本更新到目标稳定版本，同步实际存在的锁文件/版本元数据；已正确则不重复升版。使用 npm 时先核对生命周期脚本，再用 `npm version <版本> --no-git-tag-version`，此阶段不创建正式 tag。[2]
- [ ] **C2 同步发布文档**：更新 `CHANGELOG.md`、`docs/VERSION_FEATURE_HISTORY.md`、`docs/USER_GUIDE.md`；既有 spec/TechDoc 直接引用，需要存放或补齐时使用 `versioned-docs`，不改写其他版本的需求。
- [ ] **C3 固定候选内容**：review release 相对已核对 main 的最终差异，确认范围、集成行为和文档一致；按授权提交本轮修改，记录候选 SHA。记录里只保存真实结果，不预填通过。
- [ ] **C4 执行必要验证**：完成受影响的局部/回归验证和 `npm run release-check`；复用仍适用的证据，不额外重复无关测试。检查所需构建、打包、界面与平台验证是否有证据。
- [ ] **C5 完成人工/专项检查**：按实际风险完成专项审查和必要人工验收；不适用项写明原因，资金损失红线不能以自动检查代替人工复核。
- [ ] **C6 确认候选可交付**：本轮造成的失败已修复并复验；验证期间产生的有效改动已纳入提交，证据覆盖最终候选。受阻时保持未完成、说明原因；不为周一窗口带病放行。

## D．远端 release 与 PR

- [ ] **D1 推送正确分支**：在授权范围内推送本轮 release 到远端同名分支，核对远端 head 等于候选 SHA。已有相同提交则复用；不要 `push main` 或一次性推全部标签。
- [ ] **D2 创建或复用 PR**：来源为 `release/<版本号>`，目标为 `main`；已有对应 PR 则更新，不重复创建。PR 中说明范围、顺延项、依赖、验证与人工检查结果。
- [ ] **D3 Review 与 CI 通过**：核对所需 review、状态检查、平台构建和适用审批实际通过，且对应本次 PR head/合并候选。没有配置状态检查不等于已经验证；本地通过也不能冒充远端 CI。
- [ ] **D4 合并前再次核对基线**：检查 main 是否推进、PR 是否产生新提交；有变化则回到 B5/C/D 受影响项，更新分支与证据，再检查合并条件。

## E．合并、确认最终 main 与正式标签

- [ ] **E1 建立发布锁定窗口**：与协作者协调，从 release PR 合并开始到发布结果核验结束，暂停 main 的无关合并；开发可继续在其他分支。它是协作约定，除非实际配置并核实了技术限制，否则不声称已由系统自动锁定。
- [ ] **E2 合并正确 PR**：在授权与保护规则允许范围内合并；已合并则核对事实而不是重复操作。记录 GitHub 最终合并提交 `M`，不用 release 合并前的 SHA 代替。
- [ ] **E3 核对最终提交检查**：fetch 后确认当前 `origin/main` 等于 `M`，并确认该最终提交对应的必要检查通过；不拿 PR 旧 head 的绿灯冒充最终 main 检查。如 main 已推进，暂停打 tag，重新明确发布目标与证据。
- [ ] **E4 创建附注标签**：核对 `M` 中的项目版本等于目标版本，正式标签为 `v<版本号>`；检查本地/远端标签是否已存在。不存在时在 `M` 上创建附注标签；已有相同且正确的附注标签则复用，有冲突则停止，不移动或覆盖。[3]
- [ ] **E5 推送且核验标签**：推送前再次核对远端 main 仍是 `M`，只推该标签，核对远端标签解析后的 commit 为 `M`、对象为附注 tag。远端标签已存在则转到发布状态核验，不靠删除重推触发。

当前项目 `.github/workflows/release-windows.yml` 会在 tag push 后重新 fetch main，并要求稳定版本、标签名匹配版本、附注标签、tag commit 等于检查时的 main 当前提交。因而“本地核对无误”不能消除 main 后续推进的竞争；锁定期不能只到标签 push 结束。该条件须在实际发版时按真实 workflow 再核对。[4]

## F．正式发布与产物核验

- [ ] **F1 核对 workflow 状态**：定位此次 tag 对应的发布运行；确认必要审批/运行已结束且成功。等待审批、排队、失败或取消均不是发布完成。
- [ ] **F2 核对产物集合**：按当前 workflow 核对安装包、便携包、安装包 blockmap 和 `latest.yml` 等预期产物，不硬编码其他版本名称。检查 `latest.yml` 的版本、安装包引用与 SHA512 证据，不以附件存在代替一致性验证。[4]
- [ ] **F3 核对对外 Release**：tag、版本、发布名称/说明一致，正式 Release 不是 draft 或 prerelease；对应安装/启动/升级及业务抽查按本轮条件有实际验证证据。未验证项说明原因，仍属必要项时不得宣布闭环完成。
- [ ] **F4 形成发布结论**：记录 Release、workflow、产物/日志位置及核验结果；成功后解除发布锁定窗口，进入 G；失败先按下表处理。

## G．收尾与下一轮

- [ ] **G1 建立可追溯记录**：记录基线 tag/SHA → 纳入模块 SHA → release 候选 SHA → PR → 最终 main `M` → 正式 tag → 发布产物与验证结果。无需重复复制 spec/TechDoc。
- [ ] **G2 处理顺延与故障**：每项未纳入/失败内容有原因、状态和后续归属；未发布则明确“未发布”，已发布但未验证则明确“待核验”，不要都称成功。
- [ ] **G3 准备下一轮**：下一轮从本次成功发布的正式 tag 对应提交开始；本地 main 无独有改动且可快进时才更新。旧 release/模块分支按保留约定归档；删除须有授权，不强删未合并分支。

### 失败与续做

| 发生阶段 | 处理方式 | 续做位置 |
|---|---|---|
| 模块、集成、review 或测试失败 | 修复并验证受影响项，或顺延；不机械重做已完成的无关步骤 | A/B/C/D 的受影响项 |
| main 在冻结/合并前推进 | 核对增量并纳入 release，重新验证组合 | B5 起 |
| 合并后、标签推送前 main 推进 | 停止打标签，重新确认发布目标；不把标签悄悄改到未经验证的新 head | E1/E3 起 |
| 标签已推送，尚未发布，workflow 失败 | 保留标签，调查失败阶段。只有不改源码且确认可安全重试的环境问题才重跑原提交；需改代码则通过新修复 PR 和新版本处理 | E/F 对应项 |
| Release 已存在或发布后验证失败 | 不覆盖 Release 产物，不移动正式标签；记录影响，使用新的修复版本，必要暂停分发由有权限人员处理 | 修复版本流程 |
| 环境、权限或人工复核阻塞 | 保留证据和已完成项，暂停受影响步骤；不声称任务会在后台自行完成 | 获得条件后续做 |
