# Unknowns First

先明确计划建立在哪些事实、假设和未知上，再决定是否提问、查证或继续实施。不要把普通探索结果包装成确定事实。

## 工作流

1. 把任务整理为 `Goal / Context / Constraints / Done when`；缺失项能从仓库查证的先查证。
2. 读取仓库规则、相关 spec、当前 diff、入口代码、测试和配置。
3. 建立事实清单。每条代码事实附文件、符号、测试或命令证据。
4. 使用 [preflight-template.md](references/preflight-template.md) 建立 Unknowns Register。
5. 按影响、可逆性和现有证据给每个未知选择 `BLOCK`、`PROBE` 或 `ASSUME`。
6. 优先消除最可能推翻数据模型、公共契约、资金安全或主要用户流程的未知。
7. 按风险消除顺序输出计划，而不是按代码书写顺序排列。
8. 实施期间使用 `$implementation-notes` 记录假设、决策、偏差和证据；计划改变时显式反向同步 spec。

## 决策规则

### BLOCK

仅当答案会实质改变以下内容时停下来询问用户：

- 数据模型、公共接口或外部数据契约
- 资金、权限、安全或隐私边界
- 不可逆迁移、删除或历史数据回填
- 主要用户流程或验收口径
- 会形成明显不同架构的互斥方案

一次只问最能改变方案的一个问题。先提供已确认事实、选项差异和为什么必须由用户决定。

### PROBE

可以用低成本证据澄清时，不询问用户，先执行最小验证：

- 查入口、调用链、测试、日志、配置或历史实现
- 写一次性 spike 或运行单条真实数据链路
- 用现有样本做只读回放
- 对隐性偏好或契约形态使用 `$prototype-first`
- 对跨模块盲区使用 `$blindspot-pass`
- 对清结算、对账、金额或幂等风险使用 `$reconciliation-blindspot-pass`

记录验证命令、结果和结论。失败的 probe 仍是证据，不要静默丢弃。

### ASSUME

仅对低影响、易回滚且符合现有惯例的歧义作保守假设：

- 写明假设及其依据
- 选择不扩大行为面、不新增隐式 fallback 的方案
- 保留回滚路径
- 在最终报告中知会用户

不得用 `ASSUME` 越过资金、安全、迁移或公共契约问题。

## 计划要求

每个非机械步骤至少写清：

- 要消除的未知或要保护的不变量
- 成功证据
- 失败是否会推翻后续计划
- 回滚或收缩方式

典型顺序：关键主键/所有权 -> 状态和幂等 -> 最小端到端切片 -> 公共契约 -> 完整实现 -> 验证与可观测性 -> 清理。

## 输出要求

输出应包含：

1. `Goal / Context / Constraints / Done when`
2. 已确认事实及证据
3. Unknowns Register
4. `BLOCK` 问题（如有，只列真正阻断项）
5. 已执行或建议执行的 `PROBE`
6. 保守假设
7. 风险优先实施计划

不要为了显得完整而制造未知，也不要在尚未查代码时直接向用户抛出可以自行查证的问题。
