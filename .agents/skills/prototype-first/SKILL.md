# Prototype First

原型用于回答一个明确问题，不用于提前搭建生产实现。默认不接真实写入、不迁移数据、不引入正式依赖。

## 工作流

1. 写出要消除的未知和决策人，例如“用户是否更重视信息密度”或“调用方是否能稳定提供幂等键”。
2. 定义判断证据：看到什么结果就选择、否定或继续调查某个方向。
3. 选择最低保真度：静态样例优先于交互原型，纯函数 spike 优先于完整服务，临时表结构优先于正式迁移。
4. 如果未知是偏好或互斥设计，制作 `2-4` 个决策维度真正不同的方案；不要只改颜色、名称或细枝末节。
5. 如果未知是技术可行性，只制作能证明关键约束的最小 spike，不凑多个方案。
6. 展示每个方案验证什么、牺牲什么，以及哪些部分故意没有实现。
7. 用户或证据选定方向后，把决定写入 spec；丢弃原型，再按生产标准实现。

## 可用原型

- UI 页面、弹窗、报表和导出样例
- API 请求/响应和错误样例
- 数据库表、索引和迁移草图
- 配置 DSL、规则表达式和模板
- CLI 命令及失败提示
- 小规模数据回放、解析或性能 spike

## 约束

- 原型必须易删除、与生产代码边界清晰。
- 不因“反正以后可能用”把原型扩成正式框架。
- 不在方向确认前大规模接后端、迁移或公共接口。
- 涉及资金、安全、删除或真实外部写入时，只做隔离或只读试验；需要真实写入则先取得授权。

## 输出

对每个原型写明：

```markdown
- 验证的未知：
- 核心差异：
- 判断证据：
- 有意省略：
- 丢弃方式：
- 结论：待选 / 采用 / 否定
```
