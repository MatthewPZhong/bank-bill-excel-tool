# Reconciliation Blindspot Pass

先读取 [reconciliation-risk-checklist.md](references/reconciliation-risk-checklist.md)，再按当前改动的数据流选择相关章节。不要机械输出整张清单。

## 工作流

1. 明确输入文件/订单、规范化模型、匹配引擎、修改字段、审计输出和持久化边界。
2. 画出关键标识和金额字段从来源到输出的血缘，标出转换、默认值、模糊匹配和 fallback。
3. 从 spec、代码、测试和真实样本分别取证；业务口径不能只靠变量名推断。
4. 检查正常、重复、缺失、冲突、多候选、部分失败、重跑和历史兼容场景。
5. 对每个候选问题区分事实、推断和未知，并选择 `BLOCK`、`PROBE` 或 `ASSUME`。
6. 命中资金红线时标注 `⚠️ 资金红线，请人工复核`，不得仅凭自动测试宣布安全。

## 必须保护的不变量

- 不少记、不多记、不重复记，不把一条业务事实静默归到另一账号、主体或币种。
- 借贷方向、原币/目标币、手续费、汇率和精度语义在转换前后可解释。
- 重推、补推、任务重跑和并发执行不会产生不可见重复或覆盖错误。
- 已修改、未修改、异常说明、未命中和跳过数据的去向可审计，关键集合满足行数守恒或有明确例外。
- 全量跳过、零输出、模糊命中、多候选和部分失败必须可观测，不得静默成功。
- 输出标黄、命中明细、异常说明和实际字段修改保持一致。

## 输出格式

按风险排序，每项包含：

```markdown
### [Critical/Important/Minor] 标题
- 场景：
- 事实与证据：
- 推断/未知：
- 资损或审计影响：
- 最便宜验证：
- 处置：BLOCK / PROBE / ASSUME / 已覆盖
```

结尾给出：

1. 资金红线人工复核项
2. 建议新增的自动化测试
3. 必须使用真实数据或人工确认的口径
4. 已被 spec 明确证明为有意设计的候选问题

不要把所有不熟悉的业务都判成缺陷；没有触发条件、数据样例或代码证据时，保留为未知并给出验证方式。
