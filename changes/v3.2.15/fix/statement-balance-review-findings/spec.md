## 1. 背景

深审在当前生产路径（legacy Main 链路）复现了以下问题，本分支修复：

| 编号 | 问题 |
| --- | --- |
| F01 | 直接映射 Balance 时映射值先拼成字符串，清洗删掉负号，负余额翻正 |
| F02 | 跨目录同名或改名同内容的文件选“覆盖旧记录”后进入大账号选择，续跑只按新路径删会话记录，旧记录留下，交易重复 |
| F03 | 账单日期有值但不是有效日期（如 2026-11-31）时被清空，该笔留在明细，余额计算与种子静默跳过 |

| F05 | 账单里的余额模式下，永久附加值只在每次导入的首日生效，第二天起丢失，结果取决于一次导入覆盖多少天 |
| F07 | 直接映射的高精度余额在推导期末余额时被舍入至两位，余额表与种子丢失精度 |
| K1 | KBANK-VN：表头含合并单元格占位的中间空列（借方占 G:I、余额占 K:O 等），模板匹配与账号识别的表头定位都先删掉全部空项再按连续列比较，匹配不上；模板包导入也删掉空项 |
| K2 | KBANK-VN：账单日期列为「Tổng / Total」、借贷列为全表总额的合计行，被 F03 判为无效账单日期而整份拒绝 |

## 3. 功能规则

### 3.1 余额保号（F01）

- Balance 映射值按带符号金额清洗（与收付金额拆分的有符号金额同口径：仅识别前导 `+`/`-`，去掉千分位等非数字字符）。
- Credit / Debit 的清洗口径不变。

### 3.2 无效账单日期（F03）

- 映射时记下 BillDate 原值非空、却无法识别为日期的源行；映射完成后，若这些行有收入或支出金额，整份文件拒绝：`FILE_READ`，提示“账单日期存在无效值：第 N 行「原值」[等 M 行]，请修正后重新导入”，明细逐行列出（最多 20 行，超出时附总数）。
- 不拦截：收付金额均为空或 0 的行（本就不进明细，如“合计”说明行）；BillDate 为空的行；ValueDate 无效（行为不变，仍为空）。
- 合计行例外（D7）：带金额、且实际生效的 BillDate 列（账单拆分不复用主映射时取拆分映射）整格等于合计标签的行，按合计行跳过，不进明细、不计入收支拆分与账单拆分统计，记为 `summary-row-skipped`（该行映射时产生的其他提示一并撤回）；导入提示写“已跳过 N 条账单自带的合计行”，报错文件逐行列出行号与原值。
  - 是否带金额：普通模板看主映射或收支拆分规则的金额；账单拆分看拆分展开后的金额。
  - 标签：`Tổng / Total`、`Tổng cộng / Total`、`Tổng`、`Tổng cộng`、`Total`、`Grand Total`、`合计`、`总计`；比较时忽略大小写、多余空格、`/` 两侧空格与 Unicode 组合形式，只做整格相等，不做包含（如 `Total payment` 仍按 D1 拒绝）。
  - 无金额的合计标签行保持原路径（按收支为空过滤）。
- 网银账单模块专用（`buildMappedRows` 只服务本模块）；共享日期规范化函数 `normalizeDateExportValue` 不改。

### 3.3 大账号续跑沿用覆盖身份（F02）

- 待选择上下文保存重复提示中确认覆盖的旧路径（`selectionResult.replacePaths`）。
- 续跑（手动选择、已保存顺序自动命中、多模板分组）按“确认覆盖的旧路径 ∪ 本次输入路径”删除会话旧记录；后者保持原同路径覆盖行为。

### 3.4 导出全部余额完整性（F04）

- 循环生成各模板组后，补录与断档确认仍先处理；随后任一组带 `balance-generate-failed` 时返回错误（`EXPORT_EMPTY`），提示“余额账单未导出：N 个模板组的余额生成失败，导出全部会缺少这些组的账户余额，请处理后重新导出”，明细为“模板名：原因”，不合并、不导出。
- 从“导出全部”触发的补录 / 不补录重算后，若仍有组生成失败，不缓存缺组的全部余额；再次导出全部时重新生成并按上条阻断。
- 模板已删除的组沿用原行为（导出并提示数据不完整）。

### 3.5 账单里的余额附加值（F05）

- 每天：期末余额 = 账单推导的原值 + 截至当日的附加值累计额（多个生效日累加）。
- 同日多候选余额用上一日的账单原值推导，不受附加值影响。
- 本次导入首日即有多候选、需用种子推导时：生成的种子（账单里的余额、通过发生额计算）是输出值，已含截至种子日的附加值，先扣回；人工录入的种子按账单原值。后者与发生额计算“以人工种子为起点、叠加全部附加值”的现有口径一致（见 6 节人工复核）。
- 一次导入多天与分次导入结果一致。

### 3.6 精度（F07）

- 直接映射余额：单一候选、多候选推导都返回原值（12 位口径）；种子同值写入。
- 叠加附加值后按 12 位口径收敛浮点误差（两种余额方式一致）。

### 3.7 模板表头中间空列（K1 / D6）

- 表头候选口径（`buildExpectedHeaderCandidates`）：先用只裁首尾空项、保留中间空项的完整结构按位置比较（空项只匹配空单元格），起始行与起始列偏移照旧搜索；找不到再用去掉全部空项的旧口径。命中的口径同时决定截取宽度与重复表头判定，取值下标与物理列一致。
- 模板匹配、按文件名映射的表头校验、明细映射（`readRowsWithMetadata`）与账号识别的表头定位（`findHeaderRowNumbersInRawRows`）共用该口径；账号扫描窗口仍为表头前最多 10 行。
- 模板包导入的表头与 `extractHeaders` 同口径：保留空项位置，只去末尾空项。
- 表类型识别器（`table-type-detector`）的内置签名锚点不跟随，仍去空（含中间空列的表用空列前的连续锚点段）。

## 4. 非目标

- B32、B35、深审 F06（多模板覆盖导入中途失败的会话与输出回滚）不在本分支。
- 括号负数 `(100.25)`、尾随负号 `100.25-`、`CR/DR` 后缀等余额格式不新增识别（与有符号收付金额同口径）。
- BillDate 为空但有金额的行仍不进余额计算（行为不变）。
- 不回溯、不改写已生成的历史余额表与种子。

## 5. 验收标准

- 负余额（含正负跨日）经 CSV、文本 xlsx、数值 xlsx 生成后，余额表 `cell.v` 与种子保持符号；高精度余额保持原值。
- 永久附加值 +10、第三日再 -3.5：三天结果为原值 +10、+10、+6.5；一次导入与分两次导入的余额表、种子一致。
- 首日多候选：以生成种子或人工种子为起点都能推导出正确余额。
- 含 `2026-11-31` 等无效账单日期且有金额的文件被拒绝并列出行号与原值，不产生明细、余额与种子。
- 跨目录同名、改名同内容、同一路径三种覆盖经大账号续跑后，会话只保留替换后的记录。
- 导出全部余额：第一 / 中间 / 最后一组及全部失败均阻断并列出失败组；补录后重算仍有失败组时不缓存缺组文件。
- KBANK-VN 结构（表头 C11:P11、14 列含 7 个中间空项、F6 账号）：模板样本建的模板能匹配原始账单；账号精确识别并解析到维护币种；第 73 行合计行被跳过并列出；60 笔交易的借、贷、余额与原始列逐行一致，借贷合计等于合计行。已用真实账单与模板样本在本机以代码路径验证（不含 GUI）。
- 模板有中间空项而账单没有这些空列、表头带前导空项、模板包导出再导入三种情况都能匹配。

## 6. 数据与资金影响

- 不改表结构、不改迁移；余额输出值、种子值在负余额、高精度、带附加值的场景下发生变化（恢复契约）。
- ⚠️ 资金红线，请人工复核：
  - 已生成的历史余额表与种子可能带错（负余额为正、精度两位、账单里的余额第二天起缺附加值）；升级后重新生成同期数据结果会不同。是否核查、通知或重出历史文件由业务决定。
  - 历史上写错的“账单里的余额”种子（负余额写成正、第二天起缺附加值）若被后续首日多候选推导使用，扣回附加值后对不上账单原值，会触发“请导入上一个账单日余额”提示（不会静默算出错误余额）。
  - 3.5 中人工录入种子按账单原值（未含附加值）的口径，与 B32 待确认的种子口径相关，须业务确认。
  - F03 拒绝范围：若真实账单在日期列放“合计”等文字且该行带金额，此前会作为空日期交易进入明细，现在整份拒绝；须用真实样本确认。
    - 2026-11-06 KBANK-VN 真实样本确认属于此类（「Tổng / Total」，借贷两列均为总额），按 D7 改为跳过并提示。合计标签清单只做整格匹配；新增标签或其他银行的合计行写法须用真实样本确认后再加。
  - K1/K2 修复后的 KBANK-VN 实机导入（GUI，打包版）未做，见 backlog。
