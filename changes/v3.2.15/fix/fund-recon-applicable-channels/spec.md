## 1. 背景

场景管理中自带写死场景（`builtin-fixed`）可通过【管理】选择适用银行渠道，空列表（界面全选时保存为空）表示全部。R2 dispatcher 按此逐行过滤，但 R4 资金性质校验与 R5 场景4「中台退款订单回填」在编排器中独立分桶执行，直接接收全部银行行：用户排除的渠道仍会被改写 FundType、仍会产出退款 `SUCCESS` 回填行。

## 2. 已确认决策

| 编号 | 决策 | 来源 |
| --- | --- | --- |
| D1 | R4 各子场景、退款回填只处理 matchedChannel 在其适用列表内的银行行；空列表 = 全部 | v2.1.13 PRD D-3；用户，2026-11-05（按建议定） |
| D2 | 与 R2 同口径：行→渠道按 Channel + 地区查渠道；限定列表下未匹配到渠道的行不适用；无渠道仓储（单维调度）时不过滤 | R2 dispatcher 现有实现 |
| D3 | canonical 调拨回填（`fund-transfer-backfill`）保持固定全渠道，不受影响 | v3.1.1 spec |

## 3. 功能规则

- `scenario-dispatcher` 抽出 R2 现有的行→渠道映射（`buildRowMatchedChannelMap`）与适用渠道过滤（`filterRowsByApplicableChannels`），R2 改用同一函数，行为不变。
- R4：编排器按子场景（`config.subCategory`）计算可处理的银行行；规则只在这些行里找同对账ID候选。排除渠道的行对该规则不可见：不改写、不消费、不产生不匹配告警，仍可被其他子场景（若适用）处理。同名子场景以最后一条为准（与规则表一致）。
- 退款回填：只把适用渠道内的银行行交给引擎，其余银行行不产出回填行与未匹配行。
- 行→渠道映射在首次需要时建立一次（只在有场景限定渠道时查库）。各轮不改写 Channel / 地区字段，映射与 R2 一致。

## 4. 非目标

- R3.5 DBS-Charge 资金校验、R5 场景3 中台入金清理同样独立分桶、可配置适用渠道，本分支未改；是否同样过滤待定向核验（登记 backlog）。
- 不回溯已导出的历史结果。

## 5. 验收标准

- R4 Ach Return 只适用渠道 A 时：A 的出账改为 `Ach Return`，B 与未登记渠道的行 FundType 不变、无 R4 告警；改为只适用 B 后反之；清空列表两者都改。
- 两个 R4 子场景分别限定不同渠道时各自生效。
- 退款回填只适用 A 时，回填文件只含 A 的 `SUCCESS` 行；清空列表时含全部。
- 真实仓储保存适用渠道 → 编排器（真实 channels 仓储）→ 退款 writer 写出回读，结果同上。

## 6. 数据与资金影响

- 不改表结构、不改迁移、不改匹配与金额规则；只缩小 R4 / 退款回填的候选银行行。
- ⚠️ 资金红线，请人工复核：此前配置过排除渠道的用户，其历史运行中 R4 可能改写过排除渠道的 FundType、退款回填文件可能含排除渠道的 `SUCCESS` 行；须在授权范围内抽查受影响配置下的处理记录。
