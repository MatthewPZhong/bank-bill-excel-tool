# v3.1.6 Spec - VCC财务OP校验

> status: `implemented`（严格系统财务OP模板、当前有效数据导出、删除状态生命周期、自动化与 self-review 已完成；人工资金复核待完成）

> target-version: `3.1.6`

## 1. 目标

新增「VCC财务OP校验」模块。系统根据当月 VCC 财务核算单据和移除归档 Pending 数据计算各主体、各币种发生额，以前月已归档的财务 OP 期末余额作为本月期初余额，得到本月计算期末余额，并与系统财务 OP 期末余额比较。

用户确认计算结果后，将本月计算期末余额归档，供下月作为期初余额使用；同时支持导出财务 OP 校验结果表。导入明细必须按业务主键幂等，重复导入不得造成发生额重复计算。

## 2. 页面与流程

### 2.1 主页面

前端结构沿用「收单单据币种校验」模块，并调整按钮：

- 【导入流水表】改为【导入文件】。
- 【导入单据表】改为【开始运行】。
- 【开始运行】改为【导出校验结果表】。
- 【导出差异】改为【数据管理】。
- 【导入文件】和【导出校验结果表】按钮使用白色样式。
- 【导入文件】与【开始运行】固定等宽，并以状态框的垂直中线左右对称排列。
- 点击【导入文件】后打开「选择导入账期」。页面结构沿用「业务OP数据核对 → 选择业务OP所属日期」：年份和月份使用两个横向排列的单选下拉框，移除日期下拉框；年份枚举为系统当前年份前一年、当前年、后一年，月份枚举为 1 至 12 月。
- 「选择导入账期」没有可沿用的最近操作账期时不预选，用户必须明确选择年份和月份；已有最近操作账期时回显该账期。【确定】在左，【取消】在右；确定后仍向导入链路提交 `YYYY-MM`，不改变后端账期契约。
- 点击【开始运行】后打开「选择运行账期」。页面不显示“月份账期”文本，仅保留已导入账期单选下拉框；下拉框宽度为原整行可用宽度的 25%，左边界与标题“选择运行账期”左边界对齐；下拉框下方的操作区上边线相对原位置下移 15px。

### 2.2 数据管理

- 页面结构沿用「平盘对账数据模块」的数据管理页面，移除【归档】和【导入】按钮；右下角固定按【删除】【导出】【返回】排列。
- 页面左上角标题固定为「数据管理」；左侧导航的宽度、间距、导航项尺寸及选中态与「平盘对账数据处理 → 对账数据管理」保持一致，导航文字左边界与页面标题「数据管理」的左边界对齐。
- 左侧导航从上到下为：结果表、校验表、校验原表。
- 三个导航页面的右侧表标题分别为「结果表」「校验表」「导入记录」，与「月份账期」在同一水平线上；标题左边界统一与下方表格首列表头对齐，其中「导入记录」与下方「账期」左边界对齐。
- 数据状态（归档状态）枚举为：未处理、已归档；不展示行数据量。该字段属于「账期 × 表类型」的有效数据集，不属于单次导入记录。
- 「校验表」的生成时间取该账期、该表当前有效数据最近一次实际新增完成时间。首次新增时生成，后续有新增有效行或新增系统 OP 主体快照时刷新；全量幂等跳过、失败导入、计算和确认归档不得改写。旧数据库升级时优先以最近一次 `inserted_count > 0` 的成功类导入完成时间回填，不得把归档导致的状态更新时间误当生成时间。
- 每个账期的有效表数据初始状态为未处理。用户确认归档当月财务 OP 后，本次参与计算的有效表数据统一变为已归档。
- 用户点击主页面【数据管理】后，在左侧选择【校验原表】，右侧直接进入「导入记录」列表，不再增加中间页面。
- 导入记录列表按导入时间倒序展示，表头固定为：账期、导入批次、原表类型、来源文件、导入时间、导入状态、操作。
- 「来源文件」单文件显示文件名，多分片显示「N 个文件」；点击或进入明细后可查看全部文件名。
- 「导入状态」属于单次原表导入记录，枚举为：导入成功、成功（含幂等跳过）、全部幂等跳过、失败（幂等冲突）、失败（校验异常）、已删除。失败记录不得被显示成成功或参与计算；「已删除」只表示该成功类记录关联的有效原表已被后续删除。
- 数据状态与导入状态是两个独立字段。确认归档只把当月有效数据集的数据状态改为已归档，不修改任何历史导入记录；删除可按本节规则叠加「已删除」生命周期展示，但不得覆盖数据库中的原导入结果。导入记录本身不使用未处理/已归档枚举。
- 「导入记录」列表上方提供一个「月份账期」单选下拉框。枚举值仅取已导入校验原表的月份账期，格式为 `YYYY-MM`，如 `2026-05`；按月份从新到旧排列，默认选中最新月份。
- 用户选中某个月份账期后，列表只展示该月份的校验原表导入记录，不提供「全部月份」枚举。尚未导入任何校验原表时，下拉框禁用并显示「暂无已导入账期」，列表显示空状态。
- 每行操作列提供【查看导入明细】。明细弹框包含「导入汇总」「幂等跳过」「幂等冲突」「其他异常」四个页签；可查看并导出同键同内容跳过、空幂等键、同键异内容、格式错误等数据。不得只展示数量或只在日志中记录。
- 导入完成后不弹出导入记录框。主页面状态框直接展示账期、实际新增行数、幂等跳过行数；系统财务OP必须与普通明细分开显示为「N 行币种数据（M 个主体快照）」，不得把一个九币种主体快照写成“新增 1 行”，也不得将快照数与普通明细行数直接相加。存在失败记录时追加待处理异常记录数和「数据管理 → 校验原表」查询路径。完整导入记录和逐行明细仍按上述路径持久化查询。
- 失败导入记录只有在用户填写处理说明，并明确勾选「保留当前有效数据集，本次失败导入不参与计算」后，才能标记为已处理。该操作只解除运行门禁，不会写入失败数据、覆盖旧数据或改变原导入状态。
- 「结果表」同时展示指定账期的计算/归档记录及人工期初初始化记录。期初记录至少包含账期、主体、九币种余额、初始化时间和核对说明，应用重启后仍可查询。

#### 2.2.1 删除数据

- 点击数据管理右下角【删除】，打开「删除数据」页面；页面结构参考「资金对账数据处理 → 链接表管理 → 删除」。「月份账期」和「目标表」两个单选下拉框平行排列：月份账期在左，宽度为恢复后的原整行下拉框宽度的 25%，其左边界与上方标题「删除数据」对齐；目标表在右，宽度保持原整行下拉框的 40%，其下拉框左边界与月份账期下拉框右边界固定相距 10px。右下角提供【删除】和【取消】。
- 「目标表」固定为：VCC充值清退明细、VCC费用及换汇明细、VCC通道明细、VCC_移除归档Pending账单、系统财务OP。
- 删除粒度固定为「月份账期 × 目标原表」。删除所选原表的当前有效数据及其对应校验表数据；原表与校验表是同一份有效事实的两种展示，不得出现只删一侧的状态。
- 删除任一目标原表时，该账期全部未归档计算结果同步失效并删除，防止旧结果继续展示或被归档；人工初始化期初余额保留。
- 导入批次、导入记录、幂等跳过、幂等冲突、其他异常及其本次/对比数据必须永久保留。删除当前有效数据前，系统须固化被引用有效行或系统快照的对比证据，删除后仍能在导入明细中查看和导出。
- 已归档账期禁止删除；存在活动导入或其他 VCC 财务OP后台任务时禁止删除。页面预检后，进入删除事务时必须重新校验门禁，并在提交前校验有效数据、数据集状态和未归档结果均已按预期清理，避免状态变化或静默部分删除。
- 删除操作为单事务：审计证据固化、有效数据删除、数据集状态删除、未归档结果失效及删除审计记录必须全部成功或全部回滚。不得留下原表、校验表、结果表或审计引用的部分状态。
- 当前选择没有可删除的有效数据时【删除】禁用。删除页面本身作为本次不可逆操作的确认页面，点击其中【删除】后直接执行，不再弹出第二次确认。
- 删除在后台 worker 执行。执行期间禁用目标表、月份、删除、取消和关闭入口，并禁用主面板其它 VCC 财务OP操作；完成或失败后恢复，防止用户误以为任务已停止或重复发起。
- 删除成功后回到原数据管理页面并刷新当前账期；月份账期枚举继续来自历史导入记录，因此删除有效数据不会让该月的导入审计入口消失。
- 删除提交时，与所选「月份账期 × 目标原表」关联、原结果为导入成功/成功（含幂等跳过）/全部幂等跳过且尚未标记删除的记录，须在同一事务内记录删除时间和删除审计 ID，列表状态显示为「已删除」。原始 `status`、统计数、异常和幂等证据继续保留，并在详情展示原导入结果。失败记录未形成被删除的有效原表，继续显示原失败状态；删除后重导产生的新记录显示正常导入结果，旧记录保持「已删除」。

#### 2.2.2 导出数据

- 点击数据管理右下角【导出】，打开「导出数据」页面；「月份账期」与「目标表」沿用删除页的左右双列、10px 间距和标题对齐。月份账期保持 25%，目标表占满剩余宽度，完整表名不得因沿用删除页 40% 宽度而被截断。
- 「目标表」下拉分为「校验原表」和「校验表」两组。校验原表组包含五类当前有效原表；校验表组包含四类派生校验表和系统财务OP。系统财务OP的校验表与原表内容一致，但在分组中分别提供，避免类型歧义。
- 导出只读取确认导出时仍有效的数据，不包含失败、回滚、幂等跳过或已删除的数据。当前选择无有效数据时【导出】禁用；归档数据仍属于有效事实，允许只读导出。
- 校验原表按正式模板完整表头和原列顺序导出持久化显示值；长编号、前导零和文本型业务键不得被数值化。该功能是数据级恢复，不承诺还原原上传文件的样式、公式、隐藏行列、非业务 sheet 或文件字节。
- 派生校验表按下表导出，派生字段直接读取导入时校验并持久化的值，不在导出时重新解释金额、币种或方向规则：

| 目标校验表 | 导出列 |
|---|---|
| VCC充值清退明细_校验表 | 订单号、BillDate、业务部门、对手部门、业务子类型、出入方向、公司主体、我方币种、我方到账金额、发生额 |
| VCC费用及换汇明细_校验表 | 订单号、BillDate、业务部门、业务子类型、出入方向、公司主体、我方币种、我方到账金额、发生额 |
| VCC通道明细_校验表 | 渠道订单号、账单日期、部门、通道名称、MID、交易金额、交易币种、清算金额、清算币种、借贷方向、billdate、结算币种、实际到账金额、公司主体、统计币种、发生额 |
| 移除归档Pending账单_校验表 | PendingBizId、主体、对账类型、channel、金额、币种、流水_币种、流水_对账金额、Pending发生额、流水_发生额、是否错币 |
| 系统财务OP | 与正式 16 列校验原表完全一致 |

- 输出为 `.xlsx`，sheet 使用目标表名；超过 Excel 单 sheet 上限时，每个 sheet 最多写 1,048,575 条数据行并自动续表。使用临时文件和原子替换发布，生成或校验失败不得留下半文件，也不得破坏目标路径上的已有文件。

### 2.3 业务流程

1. 选择目标账期后导入校验原表：VCC充值清退明细、VCC费用及换汇明细、VCC通道明细、移除归档Pending账单、系统财务OP。VCC通道明细必须逐文件确认公司主体；系统财务OP主体固定取正式模板的「主体」列，不得从文件名或用户输入覆盖。
2. 先执行表头、数据格式及第 3.2 节幂等校验，再生成对应校验表。
3. 校验当月所需校验表的完整性；校验通过后计算各币种发生额。
4. 当月计算财务OP期末余额 = 上月已归档财务OP期末余额 + 当月发生额。首次启用且某主体没有上月归档时，必须先为该账期、该主体一次性人工初始化九币种期初余额并填写核对说明；禁止默认 0，也禁止自动使用系统财务OP代替期初。
5. 弹出财务OP确认框。币种列从左到右固定为：AUD、CAD、CNH、EUR、GBP、HKD、JPY、SGD、USD。系统财务OP中的 CNY 映射为 CNH。
6. 确认框展示三行：当月计算财务OP期末余额、系统财务OP财务余额、差异。差异 = 系统财务OP财务余额 - 当月计算财务OP期末余额。
7. 确认框右下角提供【确认归档】和【关闭】；【确认归档】为蓝色。存在未解决的导入冲突、完整性错误或计算异常时，禁止确认归档。
8. 归档成功后返回主页面，状态框显示「YYYY-MM 财务OP校验结果表可导出」。YYYY-MM 取参与校验数据的账期。
9. 点击【导出校验结果表】，另存为当月财务OP校验结果表。

账期一经确认归档即冻结：不提供撤销归档、反归档或原地重算。归档后仅允许同键同内容的重放被幂等跳过；任何会新增或改变当月有效事实、系统快照或归档余额的操作均失败关闭。

## 3. 校验表转换与导入幂等

### 3.1 校验表转换

五类校验原表模板位于 `assets/VCC财务OP校验/`。系统财务OP使用 `系统财务OP.xlsx`，其校验表即校验原表。

导入 VCC通道明细后弹出主体确认框：逐个列出文件名及「公司主体」输入框，右下角提供【确认】和【关闭】；确认后将输入值赋给对应文件的全部有效行。

幂等键虽然不直接参与金额公式，仍属于必须读取并保留的数据血缘字段。

| 校验表名称 | 对应校验原表 | 取数字段 | 新增字段及取值逻辑 |
|---|---|---|---|
| VCC充值清退明细_校验表 | VCC充值清退明细 | 订单号、BillDate、业务部门、对手部门、业务子类型、出入方向、公司主体、我方币种、我方到账金额 | 发生额：`in` 为我方到账金额；`out` 为负的我方到账金额。 |
| VCC费用及换汇明细_校验表 | VCC费用及换汇明细 | 订单号、BillDate、业务部门、业务子类型、出入方向、公司主体、我方币种、我方到账金额 | 发生额：`in` 为我方到账金额；`out` 为负的我方到账金额。 |
| VCC通道明细_校验表 | VCC通道明细 | 渠道订单号、账单日期、部门、通道名称、MID、交易金额、交易币种、清算金额、清算币种、借贷方向、billdate、结算币种、实际到账金额 | 按第 4.1.2 节确定统计币种和金额，再按借贷方向生成有符号发生额。 |
| 移除归档Pending账单_校验表 | VCC_移除归档Pending账单（文件名可为「移除归档Pending账单」） | PendingBizId、主体、对账类型、channel、金额、币种、流水_币种、流水_对账金额 | Pending金额：`VCC_clearing_credit` 为负金额，`VCC_clearing_debit` 为正金额。流水金额：`VCC_clearing_credit` 为正的流水_对账金额，`VCC_clearing_debit` 为负的流水_对账金额。币种等于流水_币种时是否错币为 FALSE，否则为 TRUE。 |

#### 3.1.1 系统财务OP正式模板契约

系统财务OP按完整表头及列顺序严格识别，表头固定为以下 16 列：

`账单日期、主体、业务部门、币种、OP发生额、发生额（入）、发生额（出）、本期移除Pending金额、调账金额、OP期末余额、pending余额、费用项、财务余额、主体变动发生额、财务主体余额、创建时间`

- 表头允许位于前 220 个非空逻辑行内；sheet 名不作为识别条件。表头单元格首尾空白沿用其他校验原表的规范化规则忽略，除此之外缺列、多列、重名、改名或调换顺序均拒绝，不做别名、模糊匹配或旧格式回退。错误提示必须列出期望模板、实际列数及首批差异列，并明确指向 `assets/VCC财务OP校验/系统财务OP.xlsx`。
- 正式导入必须再次校验同一完整表头。同一工作簿出现多张系统财务OP表，或同时出现系统财务OP与其他可识别校验原表时，因歧义整体拒绝。
- 旧版按币种横向展开、以 `YYMMOP` 定位后续「系统」余额行的工作簿不再属于支持格式；必须先转换为正式 16 列模板，禁止静默沿用宽松结构识别。
- 每条数据的账期取「账单日期」，主体取「主体」，业务范围取「业务部门」，原始币种取「币种」，比较余额取「财务余额」的 Excel 显示值。目标账期数据的「业务部门」必须为 `VCC`；空主体、非法日期、非 VCC 数据、未知币种或空/非法余额均使本次系统财务OP导入整体失败。
- 文件可包含其他有效月份，但只读取用户所选账期；无法解析账单日期的非空行仍按格式错误拒绝。所选账期至少存在一个主体，同一文件可包含多个主体。
- 每个主体必须且只能提供 AUD、CAD、CNY/CNH、EUR、GBP、HKD、JPY、SGD、USD 九个币种各一行；CNY 在比较键中映射为 CNH，同时保留原始 CNY 行。CNY 与 CNH 同时出现视为归一化后重复币种并拒绝。
- 一个主体的九条原始行、各自行号、显示值和底层值必须共同写入快照血缘；持久化导入统计对完整主体按形成的快照数计算，以维持幂等与分类守恒，但用户可见的新增、跳过、冲突和回滚数量必须同时展开为九币种原始行数与主体快照数。文件在形成任何完整快照前发生格式错误时，该文件按一个格式错误输入单元计数。同文件其他主体格式错误导致整次失败时，已完整形成的主体快照必须记为事务回滚并保留九行血缘，不得无审计丢弃。

计算发生额前，当月至少必须存在 VCC充值清退明细_校验表、VCC费用及换汇明细_校验表和 VCC通道明细_校验表。缺少任一必需表时停止计算并明确列出缺失项。

### 3.2 四类明细原表幂等键

四类明细按下表建立独立的业务键命名空间。不同原表之间不互相判重；同一原表内跨文件、跨导入批次、跨账期统一判重。

| 原表类型 | 幂等字段 | 逻辑唯一约束 |
|---|---|---|
| VCC充值清退明细 | 订单号 | 同一原表类型内唯一 |
| VCC费用及换汇明细 | 订单号 | 同一原表类型内唯一 |
| VCC通道明细 | 渠道订单号 | 同一原表类型内唯一 |
| VCC_移除归档Pending账单 | PendingBizId | 同一原表类型内唯一 |

系统财务OP是期末余额快照，不进入上述四类明细业务键命名空间。其唯一范围为「账期 × 模板主体」：同范围同九币种余额时幂等跳过；同范围任一币种余额不同、或同一批次内出现不同快照时按冲突整体失败，不覆盖既有快照。同一失败批次内同时存在既有快照的精确重放和异内容快照时，精确重放仍单独记为幂等跳过，只有异内容快照记为冲突。系统财务OP中的 CNY 只在比较口径映射为 CNH，文件内同月、同主体的归一化币种必须唯一且九个目标币种必须完整。

若四类数据落在同一张明细表，数据库约束使用 `UNIQUE(source_type, idempotency_key)`；若每类数据独立建表，则各表使用 `UNIQUE(idempotency_key)`。不得仅依赖应用层查询判重。

### 3.3 幂等键读取与规范化

- 幂等字段必须按文本读取，禁止先转为 JavaScript `Number`；不得丢失前导零或超过安全整数范围的数字位。
- 仅去除值首尾空白。不得改变大小写、删除内部空格、截断、科学计数化或做模糊匹配。
- 原始键值、规范化键值、原文件名、sheet、原始行号、导入批次和账期必须保留，保证重复与冲突可追溯。
- 幂等字段为空、仅含空白或无法无损读取时，该逻辑原表本次导入失败并整体回滚；异常明细必须包含文件、sheet、行号、字段和原因。

### 3.4 重复导入处置

对同一原表类型和规范化幂等键，按以下规则处理：

| 场景 | 处理 |
|---|---|
| 首次出现 | 写入有效原表数据集，参与一次计算。 |
| 同键且原始业务内容一致 | 视为重复导入，跳过新增，不覆盖既有行，不再次参与计算；计入「重复跳过」。 |
| 同键但原始业务内容不一致 | 视为幂等冲突，不以新值静默覆盖旧值；本次逻辑原表导入整体回滚，阻止开始运行和确认归档，进入异常明细等待人工处理。 |
| 同一批次的多个文件出现相同键 | 使用同一规则比较；不得因文件顺序形成「先到先得」或「后到覆盖」。 |
| 并发或失败重试 | 由数据库唯一约束和事务共同兜底；最终只能存在一条有效业务事实。 |

「原始业务内容一致」比较范围为该原表全部原始业务字段，不包含文件名、sheet、原始行号、导入时间、批次号和派生计算字段。比较所用内容摘要及其版本必须持久化，后续规范化规则变更不得静默改变历史判重结果。

每个逻辑原表以一次用户导入操作为原子事务。解析、校验、去重、落库及导入统计必须一起成功；任一步失败时不得留下部分可参与计算的数据。大文件可以使用临时库或 staging 表，但只有完整校验通过后才能原子提升为有效数据。

### 3.5 导入审计与行数守恒

一次用户导入操作生成一个父导入批次；该批次每识别出一种原表类型，就在读取首行数据前预先生成一条原表导入记录。因此一次操作同时导入四类明细时，列表中显示四条同批次记录；VCC通道明细的多个分片合并为同一条原表导入记录。用户在文件选择器中取消且导入尚未开始时不生成记录；一旦提交导入，即使在第一类原表读取前取消、某类运行异常导致后续类型尚未开始，所有已识别类型也必须分别保留失败记录并说明没有数据进入有效数据集。

每个逻辑原表的导入结果必须展示并保存：

- 原始读取行数。
- 新增有效行数。
- 重复跳过行数。
- 空键/非法键行数。
- 同键异内容冲突行数。
- 其他格式错误行数。
- 事务回滚行数。

「幂等跳过」页签必须逐条展示被跳过的数据，而不是只展示汇总数量。每条至少包含：

- 原表类型和规范化幂等键。
- 本次被跳过行的全部原始业务字段、文件名、sheet、原始行号、导入批次和导入时间。
- 已保留有效行的全部原始业务字段、文件名、sheet、原始行号、首次导入批次和首次导入时间。
- 比较结论「同键同内容」和处置结果「幂等跳过，未参与重复计算」。

「幂等冲突」页签以相同结构并排展示既有行与本次行，标识存在差异的原始字段。四个页签均支持按原表类型、幂等键、文件名和账期筛选，并可按原表头导出完整明细；导出的审计元数据追加在原表字段之后。

必须满足：

`原始读取行数 = 新增有效行数 + 重复跳过行数 + 空键/非法键行数 + 同键异内容冲突行数 + 其他格式错误行数 + 事务回滚行数`

同一行只能归入一个最终处置类别。异常或重复行不得进入校验表和发生额计算；用户必须能从数据管理中的导入记录回溯到原文件与原始行。幂等跳过及冲突审计必须持久化，应用重启和业务数据归档后仍可查询、导出。

### 3.6 历史数据与唯一约束启用门禁

- 在启用跨账期唯一约束前，必须对已持久化历史数据执行同口径全量扫描。
- 历史空键、重复键或同键异内容不得自动删除、自动合并或任意保留一条；必须生成冲突清单并由人工确认处置。
- 历史扫描未通过时，不得建立唯一索引、不得把迁移标记为成功，也不得开放本模块归档。
- 唯一约束及迁移必须可重复执行；中途失败后重启应可继续或安全回滚，不得留下「约束已启用但数据未完成迁移」的中间态。

## 4. 发生额取数逻辑

`当月发生额 = 非通道明细发生额 + 通道明细发生额 + 移除归档Pending账单发生额`

所有参与计算、人工期初和系统财务OP的金额必须是可精确表示的十进制数，最多 2 位小数且最多 15 位有效数字。系统财务OP按工作簿单元格显示值读取，以隔离 Excel 底层浮点尾差；任何输入或汇总结果超出边界均整次失败，不自动四舍五入或截断。

### 4.1 财务核算单据发生额

#### 4.1.1 非通道明细发生额

- 校验表：VCC充值清退明细_校验表、VCC费用及换汇明细_校验表。
- 统计币种：我方币种。
- 非通道明细发生额：按主体、统计币种汇总有符号发生额。

#### 4.1.2 通道明细发生额

校验表：VCC通道明细_校验表。

通道名称不等于 CITI：

- `billDate > 当月最后一个自然日`：统计币种 = 清算币种；基础金额 = 清算金额。
- `billDate <= 当月最后一个自然日`：统计币种 = 结算币种；基础金额 = 实际到账金额。

通道名称等于 CITI：

- 统计币种 = 交易币种；基础金额 = 交易金额。

再按借贷方向生成有符号发生额：`in` 为正基础金额，`out` 为负基础金额。通道明细发生额为全部通道有符号发生额按主体、统计币种汇总后的合计。

### 4.2 移除归档Pending账单发生额

校验表：移除归档Pending账单_校验表。

Sheet2 的 J:K 列为「币种、差额」汇总表，4.2 的移除归档Pending账单发生额就是该表 K 列的差额：

1. 当前币种集合为 `流水_币种` 与 `币种` 的非空并集，每个币种只输出一行。
2. 流水金额汇总 = `SUMIF(流水_币种 = 当前币种, 流水_发生额)`。
3. Pending金额汇总 = `SUMIF(币种 = 当前币种, Pending发生额)`。
4. `差额 = 流水金额汇总 + Pending金额汇总`。
5. 移除归档Pending账单发生额按主体、币种取上述差额；同一 `PendingBizId` 最多参与一次。

## 6. 性能与可靠性

- 单次导入批次合计必须支持 500 万数据行，可由多个 `.xlsx` 分片组成；单个工作表仍受 OOXML/Excel 行数上限约束。处理引擎可复用「收单单据币种校验」的大表导入能力。
- 同一逻辑原表的全部分片必须进入同一判重范围，尤其要能识别跨分片重复键和冲突键。
- 大表路径与普通路径必须使用完全一致的幂等键、内容摘要、异常分类、金额和币种语义。
- 不允许为节省内存而降级为全量载入；应使用流式读取、分批写入和 staging/临时库。
- 中途取消、进程退出、磁盘不足或写入失败后，不得留下可参与计算的部分导入数据；重试不得重复计数。
- 同账期仍存在未结束导入批次时，计算和确认归档必须失败关闭；不得仅依赖前端按钮禁用或进程内任务锁。
- 每个文件只允许识别出一张对应业务表；同一工作簿存在多张同类型表时必须因歧义而拒绝，不得按 sheet 顺序任选一张。表头允许位于前 220 个非空逻辑行内，且识别与正式导入必须使用同一范围。
- 已归档账期使用账期级门禁：即使某类可选数据在归档时为空，归档后首次补导该类数据也必须拒绝。相同历史事实的精确重放仍按幂等跳过保留审计。

### 6.1 真实样本验证证据

2026-08-02 使用生产导入路径在临时数据库完成以下只读样本回放；测试结束后临时库均已清理，未写入正式应用数据库：

- 强制终止 worker 后执行启动恢复：已提交到 staging 的 100,000 行全部转为事务回滚审计，新增有效事实 0，恢复收口 1 条失败记录。

## 7. 验收标准

### 7.1 幂等与审计

- 四类原表分别按第 3.2 节业务键建立数据库唯一约束。
- 同一文件连续导入两次，第二次新增有效行数为 0，发生额及校验结果完全不变。
- 同一次多选文件及跨次导入出现同键同内容时只保留一条有效事实，并准确统计重复跳过数。
- 数据管理可逐条查看并导出幂等跳过明细；每条能够关联本次被跳过行和已保留有效行，且原始字段、来源文件、sheet、行号和批次完整。
- 从主页面【数据管理】进入【校验原表】后，无需经过其他页面即可在「导入记录」中单选已导入的月份账期，并查看该月全部原表记录；导入成功、全部幂等、冲突和回滚记录均可查询。
- 删除某类当前有效原表后，同账期、同原表类型的成功类导入记录显示「已删除」；详情仍展示原导入状态、删除时间、删除审计 ID、统计和逐行证据。失败记录保持原失败状态，删除后重导的新记录不继承旧删除状态。
- 同键异内容、空键、超长数字键、前导零键和跨分片重复均有自动化测试。
- 同键异内容不得覆盖，必须阻止计算和归档，并能从异常明细定位两侧来源。
- 失败重试及并发导入后，数据库有效行仍满足唯一约束和行数守恒。
- 历史唯一性扫描及冲突人工处置完成前，不得开放正式归档。

### 7.2 金额、币种与输出

- 非通道、CITI、非 CITI 两个日期分支和 Pending 差额公式均有正常、零值、负值、空值、未知方向及精度边界测试。
- CNY 到 CNH 的映射只作用于系统财务OP比较口径，原始币种值仍可追溯。
- Sheet2 J:K 每个币种只输出一行，K 列与第 4.2 节重算结果一致。
- 输入有效行均有且仅有一个最终去向；输出为零、全量跳过或存在冲突时必须给出用户可见提示。
- 数据管理「校验表」必须展示非空且语义稳定的生成时间；实际新增会刷新，全量幂等跳过和归档保持原值，旧库回填不使用较晚的归档状态更新时间。
- 数据管理可按「月份账期 + 目标表」导出五类当前有效校验原表或五类校验表；失败、回滚、幂等跳过和已删除数据不得进入文件。原表的完整表头、列顺序、前导零和长文本键，以及校验表实际参与计算的持久化派生字段均有自动化回读验证。
- 导出数据为零、原始字段血缘损坏、系统九币种不完整/重复或 Pending 错币标记不是 0/1 时失败关闭；超过单 sheet 行数上限时自动续表，任一写入、校验或数据库收口失败不得覆盖目标路径上的已有文件。
- 系统财务OP按账期和正式模板「主体」列唯一；同内容重导跳过、异内容重导及同批异内容均展示双方来源和差异币种。
- 导入单主体九币种系统财务OP时，主状态框显示“新增 9 行币种数据（1 个主体快照）”；导入详情的新增、幂等跳过、幂等冲突和回滚指标同时显示行数与快照数，普通明细仍只按原始行统计。
- 首月期初只能由用户一次性录入九币种余额；相同内容重试可跳过，不同内容禁止改写，并可在「数据管理 → 结果表」回查。
- 已归档月份禁止新增、改写、撤销和再次计算；下月已有人工期初时，禁止再归档上月以形成双重期初来源。
- 归档前由业务人员使用真实样本复核主体、币种、方向、金额、账期和差额；该项属于资金红线人工门禁。

### 7.3 工程门禁

- 相关单元、集成、smoke 和 `npm run release-check` 通过。
- 以多分片合计 500 万行执行导入完成性能、内存峰值、跨分片判重、取消和失败恢复测试。
- 在真实数据库副本上以不少于 400 万条通道有效行执行一次数据管理导出，核对耗时、峰值内存、临时磁盘、自动续 sheet、Windows Excel/WPS 打开及应用退出后的临时文件清理；该人工发布门禁不能由小规模自动化替代。
- 修改 `src/**/*.js` 后按 `rules/important-variables.md` 汇报关联功能；提 PR、版本 bump 或合并受保护分支前执行 `npm run scan:vars` 和 `npm run check:vars`。

## 8. 非目标与上线门禁

- 本 spec 不改变其他模块既有链接表或 Pending 模块的导入语义。
- 本 spec 不使用「备注」替代幂等键、方向、金额或币种字段。
- 本版本不提供归档撤销、归档后补数或历史月份原地重算；如未来开放，必须新增独立审计流程并重新评审跨月余额血缘。
- 若真实历史数据证明任一业务键会被合法跨期复用，应停止使用全历史唯一范围并反向更新本 spec；不得静默把账期、主体或其他字段拼入联合键。
- 当前可访问的 2026-06 样本已完成全量唯一性扫描，但上线前仍须由业务提供全部历史数据完成第 3.6 节门禁，并人工复核真实主体、币种、方向、金额、账期和归档衔接。自动测试不能替代该资金门禁。
