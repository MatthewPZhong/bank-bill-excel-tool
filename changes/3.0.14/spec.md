# bank-bill-excel-tool 3.0.14 Spec

> 目标版本：`3.0.14`
> 状态：实现、自动验证与技术 Review 完成，待人工资金复核
> 更新时间：2026-07-12
> 适用仓库：`bank-bill-excel-tool`

## 0. 迭代目标

3.0.14 包含两项用户可见变更：

1. 银行对账单处理只对“至少一个字段实际发生变化”的命中行校验并输出 `异常说明`。
2. 新增 `前置资金对账` 模块。3.0.14 只交付 `缺网关账单` 场景：导入标准银行对账单，联合临时网关账单和现有网关账单按“对账 ID + 渠道 + 金额 + 币种”做严格 1:1 对账，并按渠道导出资金对账结果。

实现、自动测试和技术 Review 完成后，已将版本号和三份发布文档更新为 3.0.14；人工资金复核仍是合并/发布硬门禁，不能由自动测试代替。

## 2. 需求一：仅实际改值行校验异常说明

### 2.1 “命中”的唯一判定

一行至少有一个用户字段满足 `oldValue !== newValue`，才是本需求中的“命中行”。以下行为不算命中：

- 场景条件成立但赋值结果与原值相同；
- 行被 dispatcher 锁定但没有实际字段变化；
- 仅检测到多对多候选或其它人工判断信息；
- 只有 `异常说明`，没有字段变化。

### 2.2 异常说明校验范围

- 多对多检测器及其它 `异常说明` 生成逻辑只接收实际改值行。
- 未改值行不执行异常说明检测，也不能因为生成了异常说明而被提升为命中行。
- `命中场景` sheet 只保留实际改值行。
- 实际改值行若同时存在异常说明，必须保留异常说明；改值列继续按既有规则标黄。
- 锁定但 no-op 的行继续保持调度语义，但最终进入 `未命中场景（导入前请删除）`。

### 2.3 不允许改变

- 不改 R2 first-match-wins 锁定语义。
- 不改 R5/C3 等引擎的匹配和赋值规则。
- 不改总输入行在命中与未命中结果之间的行数守恒。
- `manyToManyRows` 仍是只读检测产物，不得反向修改银行数据。

## 4. 标准银行对账单导入

### 4.1 输入契约

- 使用项目既有标准银行对账单 46 列表头契约。
- 支持项目现有标准账单文件类型和读取方式。
- 导入仅建立当前运行会话，不写入主业务链接表。
- 新导入成功后替换当前模块中上一次选择的银行文件，并使旧运行结果失效。

### 4.2 行级校验与派生

对每一行：

1. `Credit Amount` 与 `Debit Amount` 均非零：整次运行失败，并返回文件名、Excel 行号和两个金额。
2. 两者均为空或数值为零：跳过，并计入可见统计。
3. 仅一侧非零：有效银行行，金额为 `abs(Credit Amount - Debit Amount)`。
4. `ReconciliationId` 为空：不参与匹配，不计为缺网关账单，计入可见告警。

方向和姓名/卡号派生：

| 条件 | 交易类型 | name | cardNo |
|---|---|---|---|
| `Credit Amount` 非零 | `CREDIT` | `Drawee` | `Drawee Account` |
| `Debit Amount` 非零 | `DEBIT` | `Payee` | `Payee Account` |

### 4.3 渠道账单 16 列映射

| 输出列 | 标准银行列 / 规则 |
|---|---|
| channelName | `Channel` |
| merchantId | `MerchantId` |
| reconciliationId | `ReconciliationId` |
| channelOrderNo | `ChannelOrderNo` |
| name | 按收支方向派生 |
| cardNo | 按收支方向派生 |
| currency | `Currency` |
| requestAmount | 空 |
| receiveAmount | `abs(Credit Amount - Debit Amount)` |
| extraFee | `Extra Fee` |
| 清算网络 | `清算网络` |
| createTime | `BillDate` |
| finishTime | `ValueDate` |
| additionInfo | `Extra Information` |
| remark | `Remark-description` |
| COriginalId | `OriginBillId`；为空时使用 `文件名 + Excel 行号` 生成稳定追溯 ID |

## 5. MPT 网关账单导入

### 5.1 文件类型

3.0.14 只接受：

- `MPT_INBOUND_GATEWAY*.txt` / `.gz`
- `MPT_OUTBOUND_GATEWAY*.txt` / `.gz`

`MPT_CHANNEL_OTHERS` 必须明确提示“3.0.15 支持”，不得按网关账单误解析。

### 5.2 解析和强校验

- 编码：UTF-8，允许 BOM。
- 分隔符：`|$|`。
- 首行包含账单日期、批次号、声明明细数；白皮书和实样顺序不完全一致，因此日期与批次号按值形状识别，不能只依赖固定位置。
- INBOUND 和 OUTBOUND 实样均为 33 个字段；每行字段数必须与对应 schema 一致。
- 校验文件名前缀、文件名日期/批次、首行日期/批次、字段数、数值类型和声明行数。
- 一个文件作为一个原子批次：任一结构校验失败，该文件不得部分入库。
- 多文件选择沿用项目既有“逐文件成功/失败汇总”模式；单个失败不回滚其它已成功文件。

### 5.3 规范字段

统一为临时网关行至少保存：

- sourceType
- sourceBatch
- sourceDate
- sourceFileName
- sourceFileSequence
- sourceRowNumber
- reconciliationId
- date
- channel
- merchantId
- orderId
- billReconId / ReconBillBizId
- currency
- amount
- tradeType
- name
- cardNo
- realChannel
- clearingNetwork
- rawJson
- fingerprint

INBOUND 金额/币种：

- `currency`
- `amount`

OUTBOUND 金额/币种按以下优先级成对选择：

1. `bankDebitCurrency` + `bankDebitAmount`
2. `targetCurrency` + `targetAmount`
3. 原始 `currency` + `amount`

不得把不同优先级的币种和金额交叉拼接。

### 5.4 批次幂等与替换

- 临时网关数据跨应用重启保留，直至用户手工删除批次或全部清空。
- 不同 `sourceType + sourceBatch` 追加保存。
- 同一批次的新文件按文件序号判断新旧；更新文件使用单事务原子替换旧批次。
- 同文件名且内容 hash 相同：幂等 no-op。
- 同文件名但内容 hash 不同：拒绝，提示文件身份冲突。
- 低于当前批次文件序号的旧文件：拒绝，防止回退覆盖。
- 临时数据写入独立 run-data side DB；不得写入或覆盖主库 `linked_gateway_bill`。
- `MPT_INBOUND_GATEWAY` 和 `MPT_OUTBOUND_GATEWAY` 共用按账单月划分的物理 side DB，但批次和明细均以 `sourceType` 标识。两类文件必须使用各自 schema 独立解析和落库，不得跨类型替换批次或混用字段映射。

### 5.5 链接表管理（临时表库）

主面板 `链接表管理` 打开的管理首页，与 `资金对账数据处理 -> 链接表管理` 使用相同页面结构、样式和控件顺序：

- 标题为 `链接表管理`；
- 表格固定为 `表库名 / 数据日期范围 / 表库更新日期` 三列；
- 固定显示两行 `临时中台入金网关账单表库`、`临时中台出金网关账单表库`；每行只按自身 `sourceType` 计算最小/最大账单日期和最近导入日期，无数据时显示 `—`；
- 底部仅显示 `删除 / 导入 / 退出`，不显示 `账户映射管理`；
- `导入` 是临时 MPT 网关账单的唯一页面入口，可一次选择两类文件；每个文件按文件名识别为 INBOUND 或 OUTBOUND 后分别走对应 schema 和 `sourceType` 落库，复用既有进度和逐文件错误汇总能力；
- `删除` 打开的页面与 `资金对账数据处理 -> 链接表管理 -> 删除` 使用相同 card、表单结构、字段顺序和按钮布局；
- `目标表` 下拉固定为 `临时中台入金网关账单`、`临时中台出金网关账单`；标题随所选目标变化，并提供 `起始日期 / 结束日期 / 删除 / 取消`。

支持：

- 按所选 `sourceType` 和账单日期闭区间删除临时批次；命中批次的判据为 `sourceType 相同 AND start <= sourceDate <= end`，批次及其全部明细整体删除；另一逻辑表库的数据必须保留；
- 删除框本身是唯一确认页，与既有链接表删除框一致，不再增加批次选择或二次确认页；
- 日期范围有效且预统计成功后才启用删除；预统计和实际删除必须使用同一日期字段与闭区间口径；
- 旧的单批删除、全部清空后端接口保留兼容与自动化测试，但 3.0.14 新页面不展示；
- 操作期间与导入、运行互斥；
- 单个月侧库内使用事务保证批次和明细原子删除；跨月范围涉及多个 SQLite 文件，不承诺分布式原子性，中途失败必须报告已删除批次/行数，同一范围可幂等重跑；
- 不展示、修改或删除现有持久化网关账单链接表。

上述隔离只约束导入、管理、汇总和删除。执行 `缺网关账单` 对账时，两类临时网关明细仍按稳定顺序共同进入“临时网关账单”候选池，并统一使用第 6 节的四字段平账条件。

## 6. 1:1 对账算法

### 6.1 主键规则

只有以下四项全部相同才判定为平账：

```text
trim(银行 ReconciliationId) === trim(网关 reconciliationId)
AND trim(银行 Channel) === trim(网关 channel)
AND decimal(银行 abs(Credit Amount - Debit Amount)) === decimal(网关 amount)
AND trim(银行 Currency) === trim(网关 currency)
```

- 对账 ID 必须非空；空 ID 双方均排除并告警。
- 对账 ID、渠道和币种只去首尾空格，大小写敏感。
- 金额使用精确十进制规范值比较，`1`、`1.0`、`1.00` 视为相同，不使用 JavaScript 浮点近似。
- 不做 includes、模糊匹配、日期拼接、日期窗口或其它兜底。
- 对账 ID 相同但渠道、金额或币种任一不同，不判平账，也不得消费该网关候选；银行行进入不平结果，网关候选继续留给后续银行行并最终计入未使用统计。

### 6.2 网关联合池顺序

同一完整匹配条件下的候选顺序固定为：

1. 临时网关账单；
2. 现有网关账单；
3. 各来源内部保持稳定导入/数据库顺序。

银行侧保持输入行顺序，每行只消费同时满足对账 ID、渠道、金额和币种的一个网关候选，形成严格 1:1。来源优先级只在满足完整匹配条件的候选之间生效。

### 6.3 重复处理

银行侧：

- 永不去重。
- 相同 `ReconciliationId` 的每一行仍按自身渠道、金额和币种独立参与 1:1 匹配。
- 候选耗尽后的银行行判为缺网关账单。

网关侧仅折叠“完全重复记录”。指纹由以下 10 个规范字段构成：

1. date
2. channel
3. merchantId
4. orderId
5. billReconId / ReconBillBizId
6. currency
7. amount
8. tradeType
9. realChannel
10. clearingNetwork

规范化规则：

- 字符串只 trim，大小写敏感；
- 日期统一 `YYYY-MM-DD`；
- 金额按十进制数值等价比较；
- 同 `reconciliationId + fingerprint` 的记录折叠为一个候选，并输出重复折叠告警；
- 同 `reconciliationId` 但 fingerprint 不同的记录全部保留并参与 1:1。

### 6.4 结果守恒

对有效且对账 ID 非空的银行行：

```text
银行有效参与行数 = 平账行数 + 缺网关账单行数
```

另行统计：零金额跳过行、空对账 ID 行、非法双边金额行、网关空 ID 行、网关完全重复折叠行。所有统计必须在运行结果中可见。

## 7. 导出契约

- 模板：`assets/资金对账导出不平.xlsx`。
- 用户选择一个目录。
- 按银行账单 `Channel` 拆分，每个渠道生成一个文件。
- 文件名：`资金对账不平_{渠道名}_{本机实际导出日YYYY年MM月DD日}.xlsx`。

## 8. 兼容、性能与状态

### 8.1 C4 文件读取兼容

`readReconIdFixFile(file, 'gateway')` 必须同时接受：

- 旧格式：4 个 sheet，`对账结果` 19 列；
- 新格式：5 个 sheet，`不平结果` 20 列，含可选 `平账结果`。

读取器当前不消费结果 sheet 数据时，应只做结构兼容并安全忽略新增首列，不改变订单修复/网关账单读取语义。

### 8.2 大文件约束

- MPT 实样规模约 10 万行，必须流式解压、逐行解析、分批写 side DB；不得把完整 `.gz` 或全部对象同时放入内存。
- 现有网关链接表可能达到百万级，匹配时按必要字段迭代/投影读取，不调用会一次性物化全表的接口。
- 结果先落 run-data side DB，再流式写 Excel。
- 临时 MPT 与运行结果必须使用不同 side DB 模块：临时批次跨重启保留；运行候选池/结果只服务当前进程最后一次 run，新 run 或重启时整文件回收，避免重复运行导致月库无界增长。
- 导入、运行、删除批次和链接表变更使用共享互斥锁或一致的版本快照；数据源变化后旧运行结果和导出资格立即失效。

### 8.3 数据落点

- 主库仅保存轻量 run 镜像（对外 run ID、状态、汇总、side DB 相对路径）和模块设置；不保存批量明细。
- 临时网关批次元数据/明细放入 `pre-fund-reconciliation` side DB；匹配池、平账结果、不平结果放入独立的 `pre-fund-reconciliation-results` side DB，均由 `src/backend/run-data-store.js` 管理。
- side DB 内部 run ID 与主库镜像 ID 分属两个命名空间；UI/IPC 对外只返回主库镜像 ID，导出内部使用 side run ID。
- 新 run 开始时旧成功镜像标记 `superseded` 并删除旧结果 side DB；应用重启时旧成功镜像标记 `expired` 并删除结果 side DB。临时 MPT side DB 不受影响。
- side DB 模块名、DDL、清理和主库 runs 元数据必须满足 `rules/run-scoped-data-policy.md`。

### 8.4 失败语义

- 文件结构错误：该文件原子失败，输出明确原因和行号。
- 数据库写入失败：事务回滚，旧批次保持可用。
- 用户取消导出：不改变运行结果。
- 导出中途失败：删除未完成临时文件，不报告成功路径。
- 数据源在运行或导出前发生变化：拒绝使用旧快照，要求重新运行。

## 10. 验收标准

### 10.1 功能验收

- no-op 命中行不再产生异常说明，也不进入命中 sheet。
- 实际改值且有异常说明的行保留，改值列标黄。
- MPT 两类文件可导入、重启后仍可见、按批次删除/清空。
- `MPT_CHANNEL_OTHERS` 被明确拒绝并提示后续版本。
- 银行与网关严格按非空对账 ID、渠道、金额和币种 1:1；重复、空 ID 和未消费候选统计可见。
- 每个银行渠道生成一个 5-sheet 文件；0 不平仍生成。
- 导出列、sheet 顺序、来源枚举、姓名卡号和时间字段完全符合本 spec。
- 旧、新两类资金对账文件都可被 C4 读取器接受。

### 10.2 自动化验收

- 新增/更新单元测试覆盖解析、金额优先级、四字段完整匹配、错渠道/错金额/错币种不消费、重复折叠、1:1 消费、空 ID、输出映射和异常说明口径。
- 新增 side DB parity、批次幂等和原子替换集成测试。
- 新增真实规模的合成大文件性能/内存回归测试，不把真实业务文件提交仓库。
- `npm run test:unit` 通过。
- `npm run test:integration` 通过。
- `npm run smoke` 通过。
- 最终 `npm run release-check` 通过。

### 10.3 人工资金复核

以下项目必须人工复核后才可合并发布：

- 对账 ID、渠道、金额、币种四字段精确匹配及 1:1 消费顺序；
- 网关重复折叠指纹；
- OUTBOUND 金额/币种优先级；
- 银行 CREDIT/DEBIT 金额、姓名、卡号派生；
- 不平结果只包含缺网关的银行右单边；

- 按渠道拆分后的文件内容不串渠道。
