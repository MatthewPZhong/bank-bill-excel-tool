# Implementation Notes — v3.1.0

## Baseline

- Goal/spec：[`spec.md`](./spec.md)
- Initial plan：用户批准 v3.1.0 平盘资金性质校验完整方案，并补充清结算银行账户识别规则。
- Done when：[`test-spec.md`](./test-spec.md) 自动验证完成，资金人工复核项明确记录。

## Decisions

| 决定 | 原因 | 影响 |
|---|---|---|
| 业务明细进入独立持久侧库 | 主库 bulk 禁令；银行/链接表需跨重启 | 主库只保留既有轻量设置 |
| 原始值与工作值分离 | 用户明确原始银行表不可被覆盖 | 确认只改工作值和状态 |
| 清结算银行账户表仅筛正常状态 | 最新业务口径 | 非自有账户也进入链接表 |
| 三类账户场景只看双方账户币种 | 最新业务口径替换旧调拨匹配 | 不使用 ReconID、金额、方向或付款状态 |
| 严格 1:1 与差异审计 | 防止资金误改 | 多候选不抢占 |
| 第一阶段只保留一个全局待确认草稿 | 避免两个草稿共享同一银行行或链接候选后产生确认顺序冲突 | 新运行必须显式使旧草稿失效 |
| 同币种来源保留为内部证据 | 只保存 FX 候选会无法证明原有 `&FX` 应被移除 | 管理页和链接导出不展示，匹配引擎可读取 |
| Inbound 移除 `&FX` 要求三币种一致 | 空原始币种不能证明未换汇 | 银行币种、订单币种、原始出金币种任一不明即转人工 |
| 差异只展示有效草稿与已确认运行 | 失效/被替换草稿无法合法导出 | 避免差异页出现永久不可操作的“待确认”记录 |
| 侧库业务 JSON 严格解析 | 损坏数据回落为空对象会伪装成普通未命中 | 银行、链接或草稿损坏时直接阻断 |
| 首次 bootstrap 与主库/侧库 checkpoint 绑定 | 仅靠侧库 marker 或自动接管无法证明主库和侧库来自同一数据批次 | 主库先保存 generation 0 bootstrap；已有侧库无绑定或仅有旧 marker 时拒绝接管 |
| 主库与侧库共享 checkpoint 和待完成操作 | 仅靠父链无法区分真实崩溃窗口与“只恢复旧主库” | 主库写前登记基准 checkpoint+operation token；侧库历史同时记录父 token 与 operation token，二者吻合才追平 |
| 平盘操作全局互斥并校验 token 所有权 | 两个重叠 IPC 会覆盖同一个待完成记录 | 第二项操作直接拒绝；checkpoint 同步和清理只能由当前 operation token 执行 |
| 运行 envelope、明细和当前来源交叉校验 | 语法合法但共同伪造来源、结果或冲突计数可绕过 stale、审计及消费判断 | 每行保存完整性 hash；来源、结果、差异、消费和当前银行/链接记录逐项重算并 fail-closed |
| 已确认订单来源持久消费 | 单次运行 1:1 不能阻止跨月份或来源重建后的重复消费 | 侧库保存来源三元组与银行 BizId 的双向唯一关系 |
| 银行全局 revision | FundTransfer-in 会读取运行范围外的 out 银行行 | 任一银行导入、删除或确认都会使依赖历史 out 的草稿失效 |
| 输入使用带 SHA-256 证据的私有不可变暂存副本 | 仅复用同一路径或 stat 不能证明解析与存档是同一字节版本 | 复制后记录 snapshot/size/SHA，解析后、写库前、恢复前和正式存档时逐层复核 |
| side DB 同事务记录输入文件提交凭证 | operation 级 generation 只能证明“本次操作至少提交过一次”，不能证明多文件中具体哪些文件已提交 | 银行、普通来源、账户确认和回导在业务事务中写入文件证据；恢复只取 pending 与已提交凭证交集 |
| 有预期 SHA 的存档重试以内容身份为准 | 同字节恢复副本可能因复制或重建产生新的 inode/mtime/ctime | 历史 stat 不再作为阻断条件；仍要求当前读取前后稳定、大小一致和 SHA 精确一致 |
| source changed 重试能力由 artifact 证据决定 | 批次级错误码无法区分安全替代源和必须重跑业务 | controller 读取内部摘要能力但不向 renderer 暴露；替代路径仍由 ArchiveService 完整验真 |
| 恢复后立即回收 prepared 未提交输入 | B 正确排除存档后若只等过期清理，会延长敏感输入保留 | checkpoint 与 pending 完成后计算差集，并复用全局保护集清理 staging 子目录 |
| 草稿绑定规则版本 | 仅绑定数据 revision 无法发现代码口径升级 | 规则版本变化后旧草稿自动失效 |
| 平盘存档采用独立即时批次 | 运行批次内存关联跨重启丢失，且重复导出只留首份 | 每次成功输入、导出和回导均独立可追溯 |
| 存档建批增加持久文件 outbox | 主存档数据库不可用时，仅返回 warning 会丢失跨重启重试证据 | 业务返回前必须形成正式批次或原子 outbox；启动后重放成正式批次 |
| 未解决人工差异不消费来源 | 人工保留不等于确认某条订单配对 | 只有唯一成功匹配血缘可写来源消费 |

## Assumptions

- 货币和账号均 trim 后大小写敏感。
- 第一阶段无业务数据可归档，归档按钮只提示。
- 原始表成功但派生为 0 行，仍视为来源已导入。

## Deviations

| 原计划 | 实际 | 原因 | 影响 |
|---|---|---|---|
| 相交范围可分别保留待确认草稿 | 第一阶段全局只保留一个待确认草稿 | 同一银行行和链接候选的确认顺序需要唯一 | 用户每次新运行前会看到替换确认 |
| 只派生涉及换汇的调拨、测试付款和入账链接行 | 同币种行以 `visible=0` 留在侧库作内部证据 | 否则只能添加 `&FX`，无法可靠移除错误 `&FX` | 管理页和导出仍只显示涉及换汇的数据 |
| 草稿替换先废弃旧结果再生成新结果 | 废弃和创建在一个事务内完成 | 新草稿写入失败不得同时丢失旧草稿 | 失败后旧草稿保持待确认 |

## Blindspot Fixes

- Excel 日期对象加入稳定指纹，避免同主键但日期不同的来源行被误判为完全重复。
- 差异页隐藏失效/被替换草稿，已确认批次支持继续导出 49 列差异。
- 回导修改前后状态严格按“待确认 → 人工修改后确认”流转；最终值回到原值时不生成“原值 → 原值”命中明细。
- 混合来源批次保持选择顺序，确保存档中心不会把失败文件冒充为成功输入。
- position side DB 的关键 JSON 损坏时 fail closed，不降级为空数据继续匹配。
- 引擎输出 BizId 集合执行精确守恒校验，拒绝重复、未知或缺失结果。
- 已确认的订单来源跨月份和来源重建后不可重复消费；同 BizId+同来源可幂等复核，同 BizId 改配其它来源转人工。
- 银行导入检测其它范围的 BizId 冲突后才写入，避免“先删后报错”；银行导出也拒绝实际零行的交叉范围。
- 订单类删除要求明确月份，清结算银行账户表才允许整表删除；取消账户快照确认会立即回收 token。
- 差异导出严格限定运行、Channel、地区、月份和状态，合法回导同步刷新最终 outcome 和结果统计。
- side DB 保留 Excel 日期对象并拒绝损坏日期标记；结果回导兼容已知 Excel 时区往返，同时仍拒绝真实时分秒篡改。
- 生成五类正式链接模板和四类规范原始表模板；保留旧“中台调拨订单.xlsx”兼容别名，打包排除 Office/WPS 锁文件与 `.DS_Store`。
- 修复两个管理按钮将浏览器 click 事件误当成 preview 数据的问题；真实点击现在会调用 IPC 读取并打开对应管理页。
- 对账数据管理底部“导入”使用蓝色主按钮、“返回”使用白色次按钮；无归档数据提示改为白色“返回”，关闭提示后保留管理页。
- 差异页将功能和月份移到表格上方；月份默认最新并单选过滤，行级导出仍使用汇总行保存的月份，避免隐藏列后导出串月。
- 差异页两个筛选框直接复用主页面 `template-select main-panel-select-control` 样式层，不维护第二套圆角、箭头和焦点视觉。
- 差异页首列改为“银行渠道”，直接使用银行原始快照中的 `Channel-地区`；汇总和行级导出都增加地区维度，避免同一 Channel 的不同地区混在一行或一次导出中。
- 链接表管理移除静态“未归档”标签；可见链接数据按月份展示范围，链接表导入、删除或映射重建后记录表库更新日期。
- 链接表管理移除逐行操作栏；导出入口迁移到底部，通过目标表选择框继续传递明确的 `sourceType/tableName`，避免全局按钮误导出第一张表。
- 主页面“导出文件”改为“结果确认”，仅调整入口文案；结果确认页内的文件导出、结果回导和最终确认动作保持原契约。
- 链接原始表同步移除行数和逐行操作栏；底部导入入口改为蓝色导出，先选择原始表再调用既有导出 IPC，返回按钮保持白色。
- 银行 BizId 即使在同批同时替换多个范围，也禁止从旧 Channel+月份迁移到新范围。
- Inbound 只有银行币种与订单币种一致、且两者不同于原始出金币种时才判定涉及换汇；三种币种互不相同时转人工。
- 原始表、链接表和结果模板的 ID/账号/卡号/ReconID 等列固定为文本格式，避免 Excel 将长整数转为科学计数或丢前导零。
- 文本格式同时写到 Excel 列定义，保证零数据模板和运行时空表导出也保留标识符文本语义。
- 静态模板生成器和 Excel 测试改为复用运行时文本列判定，补齐 `CustomerRef`、`客户编号`、`客户号`、`accountReference` 等不能只靠窄正则识别的标识符。
- 银行导入、账户快照确认和结果回导改用私有不可变暂存副本；存档完成后清理，存档失败保留到重试成功或批次删除。
- 平盘输入、每次结果导出和结果回导改为独立即时存档；业务 IPC 在本次存档完成或形成可重试失败记录后才返回，不再遗留“业务已返回、任务仍只在内存尾队列”的窗口。
- 普通退出先禁止新业务并等待活动业务、worker 和存档队列排空，再关闭侧库。
- 银行、来源、链接、结果行及各去向血缘 JSON 均校验结构；语法合法的空对象也不能降级继续。
- 运行范围、来源集合、消费冲突计数、快照和汇总结构与实际运行明细交叉校验；主库预登记 operation token 与侧库 checkpoint 历史共同识别缺失、空库、旧主库单独恢复、合法旧库回滚、同 generation 分叉和更高 generation 分叉。
- 结果确认页补充“不适用/人工修改”统计，并明确未解决差异不认领来源；原唯一匹配被人工修改时保留来源血缘。
- 增加链接原始表、来源删除和运行范围三个实际渲染 preview；来源导入失败透传文件级 `detailLines`。
- 三份发布文档统一说明平盘成功输入、每次结果导出和结果回导均为独立即时存档，并将现行主模块数量更新为 12。
- 存档 artifact 成功或批次删除后按受控路径释放平盘暂存副本；失败/中断 artifact 的源路径进入启动清理保护集，保证跨重启重试不会被 7 天回收提前破坏。
- 源路径释放前重新读取全库未完成 artifact；跨批次共用同一路径时，只有最后一个 pending/failed 引用解决后才允许清理；替代源重试成功时同时检查被替换的旧路径，避免只保留不误删却永久泄漏。
- 主进程业务成功后的目录级清理再次读取未完成引用并过滤目标；保护集不可用时保守保留，禁止绕过 ArchiveService 的源释放判断。
- 存档中心重试、删除、另存为、锁定和保留期写操作纳入统一业务退出闸门，普通退出和升级安装会等待这些操作排空。
- 平盘银行导入、对账数据管理、链接原始表和链接表管理的恢复错误均展示经 HTML 转义的 `detailLines`。
- 首次侧库绑定改为主库预存 bootstrap；已有现代侧库无主库绑定、仅旧 marker、空库或残缺库均不再自动接管。
- 平盘 IPC 改为全局互斥，待完成记录写入、checkpoint 同步和清理均校验 operation token 所有权，避免并发操作互相覆盖。
- 运行行增加完整性 hash 和显式来源消费标记；确认前验证 FundType 是唯一可变业务字段、差异精确集合、结果去向、血缘及当前银行/链接引用。
- 存档控制器增加原子文件 outbox。正式建批失败时保留持久重试意图；启动恢复同时识别侧库推进、业务成功标记和已发布输出，纯导出也不会因异常退出漏档。
- 已确认运行读取时由 `consumes_source + lineage` 反推完整消费关系，并与持久消费表双向校验；确认事务在提交前执行同一校验，消费缺失、额外或错配均阻断。
- 消费关系由历史运行持有时，额外验真 owner 已确认且 owner 运行行的完整性 hash 与血缘确实对应同一银行 BizId、来源、业务主键和腿序号；保留同一银行 BizId 重导后的合法幂等。
- 存档恢复判定复用于同一进程的失败返回；结果文件已发布但导出状态落库失败时先登记 outbox，再允许同步 checkpoint。outbox 重放形成部分失败正式批次时仅释放已解决且无其它引用的源文件，失败 artifact 的源文件继续受保护。
- 正式建批、正式追加及 outbox 重放共享 artifact 完整性门禁；任一文件缺少正整数 artifact ID 时写入或保留同一 operation key 的 outbox，后续可在原正式批次补齐。正式批次与 outbox 同时失败时不得宣称可重试，也不推进 checkpoint。
- 清结算银行账户表单独导入的 prepare 结果显式标记 `archiveDeferred`；待用户确认期间不视为已提交业务，不建立空存档批次，apply 后再按正式输入存档。
- 将平盘 pending/checkpoint 完成步骤、存档结果结算和输出发布证据判定抽为可注入 helper，行为测试覆盖 prepare、apply、已发布输出 outbox 恢复及正式存档/outbox 双失败。
- service 初始化清理暂存前合并主库 pending `archiveFiles` 与存档中心保护集；pending 存在但文件数组缺失、非数组，input 缺合法 `filePath/sourceSnapshot/sizeBytes/SHA-256`，或 output 缺 `beforeSnapshot` 字段时，不再降级为空保护集。恢复登记与同进程 lifecycle 在任何 archive 状态早退或 checkpoint 同步前都复用同一解析器；损坏清单会保留 pending、阻断 checkpoint 且不产生错误 outbox。outbox 也拒绝非字符串和空白路径。保护 provider 返回非数组或抛异常时同样保守不清理。
- 业务错误页透传 `detailLines`；Excel 文本列补齐 `Account Reference`、`大额行号` 和 `VA`。
- 外部 final review 复核确认：旧实现只绑定暂存路径/stat，可能出现 side DB 解析版本 A、存档凭证版本 B。现已将解析时 snapshot/size/SHA-256 贯穿银行/来源/回导 token、主库 pending、operation tracker、controller、outbox 和 ArchiveService；恢复不得重新信任当前 input 快照，内容变化在 outbox 登记前 fail closed。
- 第二轮 review 发现 operation 级 checkpoint 无法证明普通来源多文件中的逐文件提交边界。side DB 现以同一业务事务记录每个已提交输入，异常恢复只存档 pending 与提交凭证交集；未提交文件排除，孤立或冲突凭证直接阻断。
- 第二轮 review 发现 ArchiveService 在 SHA 校验前比较历史 inode/mtime/ctime，会拒绝合法同字节恢复副本。已有预期 SHA 时现改为当前读取稳定性、大小和 SHA 三重校验；旧 artifact 无 SHA 时保留严格 snapshot 兼容路径。
- 第三轮 review 发现 controller 仍把所有 `ARCHIVE_SOURCE_CHANGED` 视为不可重试。现已接通文件选择、preload/IPC 参数和 service `sourcePaths`，有业务摘要时可安全恢复，无摘要仍要求重跑业务；错误副本返回明确提示。
- 第三轮维护建议指出多文件恢复排除的 prepared 输入可能滞留。恢复现于存档意图持久化、checkpoint 同步和 pending 清除后，复用未完成引用保护清理差集 staging。
- BillDate/ValueDate 不再一律降为日历日比较；纯日期仍接受等价 Excel 日期，包含时分秒时执行完整比较，仅兼容固定库时区偏移和最多 2ms 的 Excel 浮点误差。
- Self-review 发现 SheetJS 数组模式会在跳过空白行后丢失物理行号；读取器改用非空行的 `__rowNum__` 元数据恢复真实 Excel 行号，避免保留大段空白行造成内存膨胀。
- Self-review 发现混合存档重试可能部分成功但 Renderer 在整体失败时不刷新；controller 补充尝试/成功/失败计数，Renderer 对所有已发起重试统一在结束阶段刷新批次、详情和统计。

## Evidence
