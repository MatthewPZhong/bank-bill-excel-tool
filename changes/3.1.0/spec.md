## 0. 任务摘要

- Goal：将「平盘对账数据处理」从前端占位升级为可持久运行的「平盘资金性质校验」第一期。
- Context：v3.0.24～v3.0.26 只交付主页面占位；本次增加银行表库、五类链接表、严格匹配、差异审计、49 列结果、回导与确认。
- Constraints：批量明细不得进入主库；用户导入的 Excel 原文件和原始行快照不可覆盖；资金匹配必须有血缘、严格 1:1 和单一去向。
- Done when：本规格 AC、`test-spec.md`、版本文档、重要变量、release-check、启动性能与资金盲区复核完成。
- 主页面原“导出文件”入口显示为“结果确认”；按钮 ID、位置、可用状态和打开结果确认页的业务逻辑不变。结果确认页内真正生成文件的按钮仍显示“导出文件”。

## 1. 范围

- 仅实现 `position-fund-nature-check`。
- `position-data-info-backfill`、`position-order-writeoff` 和平盘交易对账单继续显示“后续版本开放”。
- 确认结果只将银行批次状态改为“已校验性质”，不执行业务归档。
- 存档中心自动保存成功输入和成功输出；存档中心文件与业务表库状态相互独立。

## 2. 页面契约

### 2.1 对账数据管理

- 导航：未归档、已归档、差异数据。
- 未归档固定两行：平盘银行对账单、平盘交易对账单。
- 银行行显示整体日期范围、状态计数和“导出 / 删除”；操作范围为一个/全部 Channel + 一个/全部月份。
- 底部按钮：归档、导入、返回。第一期归档提示无符合条件数据。
- 差异页按功能、银行渠道、月份、运行批次汇总；银行渠道固定显示为银行行 `Channel-地区`。状态为待确认、人工确认保留、人工修改后确认；操作为导出。
- “功能”和“月份”不占用表格列，改为表头上方横向排列的两个单选下拉框。第一期功能固定为“平盘资金性质校验”；月份取现有差异月份、按倒序排列并默认选择最新月份，切换月份后只显示该月汇总。
- 两个筛选下拉框复用主页面单选下拉框的视觉样式，包括 48px 高度、圆角、边框、下拉箭头和焦点状态；仅宽度按筛选内容调整。
- 差异表格列固定为银行渠道、运行批次、状态、差异数、操作；同一 Channel 下不同地区必须拆成不同汇总行。导出同时携带当前汇总行的 Channel、地区、真实月份和状态，不得串入同渠道其它地区的数据。

### 2.2 链接表管理

- 固定五行：中台调拨平盘对账单、中台测试付款对账单、中台网关入账对账单、中台网关出账对账单、清结算银行账户表。
- 页面不显示“未归档”分区文字；列表只保留链接对账单名、数据日期范围、表库更新日期三列，不显示操作栏。
- 数据日期范围按可见链接数据的最早月至最晚月显示；同月只显示 `YYYY-MM`，跨月显示 `YYYY-MM ~ YYYY-MM`，无日期显示“—”。
- 表库更新日期只显示 `YYYY-MM-DD`；成功导入、删除或账户映射重建链接表时刷新，无历史更新记录显示“—”。
- 底部左侧：链接原始表、账户映射管理；右侧依次为删除、导入、导出、返回。仅导入使用蓝色主按钮，其余按钮为白色次按钮。
- 点击底部“导出”后先选择一张链接对账表，再沿用现有另存为流程导出；空表仍可导出仅含表头的模板。
- 链接原始表页只显示原始表名、日期范围和更新时间，不显示行数及逐行操作栏。底部只保留蓝色“导出”和白色“返回”；点击“导出”后先选择目标原始表，再沿用既有另存为流程。
- 平盘账户映射独立于资金对账映射；保存后重建调拨派生并使待确认草稿失效。

## 3. 存储与生命周期

- 批量业务数据写入 `{userData}/run-data/position-reconciliation/position-data.sqlite`，主库不得新增银行/订单/账户批量明细表。
- 侧库持久保存银行批次/行、原始导入/行、链接行、账户映射、运行草稿/行、差异、revision，以及每次 operation 中已经与业务数据同事务提交的输入文件证据。
- 侧库额外保存已确认的订单类链接记录消费关系，订单来源、来源业务主键、腿序号和银行 BizId 均可追溯。
- 主库保存平盘侧库 checkpoint，包含实例身份、单调 generation 和事务随机 token。首次初始化时，主库必须先持久保存 generation 0 bootstrap，再允许创建与其完全一致的侧库；磁盘已有侧库但主库没有 checkpoint/bootstrap、仅有旧 `initialized` 标记、文件缺失或空库均 fail closed，禁止静默接管或补成空库。
- 每次可能写侧库的 IPC 在执行业务前，主库先持久登记“基准 checkpoint + 本次 operation token”；侧库业务事务原子推进 generation/token，并只追加保存 `generation/token/parentToken/operationToken` 历史链。侧库领先时，必须同时证明主库 checkpoint 是父链祖先，且全部领先事务属于主库登记的同一次待完成操作，才允许异常退出后追平；仅恢复旧主库、缺少待完成操作、身份不同、generation 回退、同 generation token 不同或父链分叉均阻断。
- 平盘 IPC 全局串行执行；待完成记录、checkpoint 同步和清理必须校验 operation token 所有权，禁止并发请求覆盖或清理另一项操作。
- 备份与恢复必须把主库及 `run-data/` 作为同一批次处理，禁止只恢复 `tool-data.sqlite` 后继续使用平盘功能。
- 银行、链接表或映射变更递增对应 revision；运行绑定 snapshot，过期草稿禁止导出、回导和确认。运行来源集合必须由运行行的原始 FundType 重新推导，已确认消费冲突数必须由逐行血缘重新统计，不能只信任 snapshot/summary 中可共同修改的字段。银行任一范围导入、删除或确认还会递增全局银行 revision，确保 FundTransfer-in 引用的范围外 out 行变化后草稿失效。
- 草稿跨重启保留。第一期全局只允许一个待确认草稿；任何范围的新运行都必须先确认使旧草稿失效，不按 Channel+月份并存多个草稿。
- 替换运行在同一事务内完成“旧草稿失效 + 新草稿落库”；新草稿写入失败时旧草稿保持可用。
- 用户输入原文件不修改；侧库保存 `original_json` 与 `original_fund_type`。确认只更新工作值和审计值。
- 银行、来源、链接、运行和血缘 JSON 损坏时阻断操作并提示侧库数据异常，不得降级为空行或普通未命中。运行范围、快照和汇总即使语法合法，也必须具备完整字段并与运行明细计数、范围和来源一致。
- 每条运行行保存覆盖索引字段与 JSON 的完整性 hash，并校验原始行、结果行、FundType 唯一允许变更、结果去向、差异精确集合、来源消费标记、血缘和当前银行/链接记录。已确认运行还必须由 `consumes_source + lineage` 反推来源消费关系，并与持久消费表双向核对；消费关系由更早运行持有时，仅在 owner 运行已确认且其完整运行行血缘可证明同一关系时允许幂等复核。缺失、额外、错配、无关 owner 或指向未来运行均 fail closed。旧草稿缺少完整性字段时只允许空运行继续读取，非空旧草稿 fail closed。
- Excel 日期对象序列化后必须恢复为 `Date`；日期标记损坏同样阻断。
- 平盘输入、结果导出和结果回导在业务成功返回前完成存档，或持久写入可跨重启重放的文件 outbox。待完成操作保存业务完成状态、文件清单、输入解析时 `sourceSnapshot + sizeBytes + SHA-256` 证据和输出写入前快照；无论是异常退出，还是同一进程内发生“文件已发布/侧库已推进但后续状态更新失败”，只要侧库已推进、业务已标记成功或输出文件已发布，就必须先恢复持久存档意图，再同步 checkpoint 和清理待完成操作。正式存档与 outbox 都无法登记时返回明确失败并提示业务可能已完成，禁止用户直接重试。
- 每个已写入 side DB 的输入文件必须在同一业务事务内写入 `operation token + sourceType + role + 暂存路径 + snapshot + size + SHA-256` 提交凭证。多文件普通来源导入发生部分成功后异常退出时，恢复存档集合固定为主库 pending 文件与该 operation 已提交凭证的交集；尚未提交的文件不得进入存档。pending 有文件但无凭证时排除该文件；凭证存在但 pending 无对应文件、同一路径重复或双方任一证据不一致时 fail closed，禁止登记 outbox、同步 checkpoint 或清理 pending。
- 正式建批、向正式批次追加文件及 outbox 重放都只有在每个文件已形成带正整数 artifact ID 的正式记录后，才可认定存在正式持久重试能力。批次已创建但任一附件在元数据登记前失败时，必须将完整文件清单写入同一 operation key 的 outbox；outbox 写入也失败时保持 pending、禁止推进 checkpoint。正式失败 artifact 与 outbox 的未完成引用共同决定暂存文件是否可释放。
- 单独识别清结算银行账户表但尚待用户确认时，只保存内存确认 token，不视为业务已提交，也不建立空存档批次；本次 prepare 的主库 pending 正常清理。用户确认后的 apply 操作才写侧库并存档不可变输入副本。
- 平盘 pending、存档持久化和 checkpoint 清理使用同一可测试状态机；正式存档、持久 outbox 和二者同时失败三条分支必须保持确定行为，禁止仅靠源码接线断言。
- 启动清理暂存目录前，保护集必须同时包含正式失败 artifact、outbox 以及主库平盘 pending 的 `archiveFiles`。input 项必须同时包含非空 `filePath`、合法解析时 `sourceSnapshot`、一致的 `sizeBytes` 和 64 位 SHA-256；output 项必须包含写出前 `beforeSnapshot` 字段。任一保护来源缺失、损坏或不可用时，保守跳过本次过期清理。恢复流程与同进程 checkpoint 完成流程必须复用同一校验；无论 `archiveRequired` 或 `archiveState` 为何，文件清单损坏都必须保留 pending、禁止写入错误 outbox、禁止推进 checkpoint。恢复 input 时必须复用 pending 中的解析时证据并重新校验当前暂存字节，禁止重新抓取当前文件快照作为可信基准；不一致时保留 pending、checkpoint 不推进且不登记错误 outbox。outbox 自身也必须拒绝非字符串及空白路径，并完整保存预期 SHA-256。
- 存档中心按失败 artifact 的内部证据区分恢复方式：普通可重试错误沿用原路径；`ARCHIVE_SOURCE_CHANGED` 且存在合法预期 SHA-256/大小时显示“选择原文件并重试”；缺少该证据时只能提示重新运行业务。页面和 preload 不得获得摘要值，替代路径最终仍由 ArchiveService 校验普通文件、大小、读取前后稳定性、读取字节数和 SHA-256。
- 存档中心批次重试可能部分成功；controller 必须返回本次尝试、成功和失败计数，Renderer 在任何已发起重试结束后都刷新批次、详情和存储统计，再显示全成功或部分失败结果，禁止把后台已成功附件继续展示为失败。
- 多文件异常恢复中，pending 有但 side DB 无提交凭证的 prepared 输入不得进入存档。恢复意图持久化、checkpoint 同步且 pending 清除后，立即计算 `pending inputs - committed inputs`，再通过正式失败 artifact、outbox 和全局未完成引用保护集清理对应 staging 子目录；不得直接删除文件或越出平盘 staging 根目录。

## 4. 导入

### 4.1 银行

- 支持 `.xlsx/.xls`，严格识别“渠道对账单”46 列或平盘 49 列。
- 49 列导入时清空前三个审计字段，作为新银行数据。
- `BizId` 非空且在本次选择中唯一；Channel 非空；BillDate 可解析为本地日历月份。
- 数据区空白行允许忽略，但不得压缩后续行的 Excel 物理行号；错误提示、来源行号和运行血缘必须继续指向原文件中的真实行号。
- 同一 BizId 已存在于其它 Channel+月份范围时整次导入拒绝，不得先删旧范围或静默迁移 BizId。
- 用户确认前先将所选文件复制到应用私有不可变暂存区；复制完成后以有界分块读取生成 `sourceSnapshot + sizeBytes + SHA-256`。解析完成后及每次修改 side DB 前均重新校验同一暂存副本，存档服务复制时再次核对预期 SHA-256。银行、链接原始表、账户快照和结果回导均遵守该契约；原路径文件随后被覆盖不得改变本次导入内容。暂存字节不一致时返回 `position-staged-input-changed`，不得修改 side DB 或推进 generation。存档重试已有预期 SHA-256 时，历史 inode/mtime/ctime 变化本身不阻断同字节副本；必须以本次读取前后 stat 稳定、大小与预期一致且 SHA-256 精确一致共同证明身份。没有预期 SHA-256 的旧 artifact 继续使用严格历史 snapshot 校验。
- 暂存副本仅在对应文件成功存档或用户删除失败存档批次、且全库存档 artifact 已无未完成引用后释放；多个批次共用同一路径时，任一 pending/failed 引用都必须阻止提前清理。重试改用新源路径时，旧、新路径都进入同一受控释放检查。主进程业务成功后的目录清理必须再次读取相同保护集，查询失败时保守保留，不得绕过服务层门禁。失败或中断批次可跨重启继续重试，启动清理不得删除仍被未完成存档引用的副本。
- 全部文件校验完成后，按 Channel+月份原子替换；取消确认不写入。

### 4.2 链接原始表

- 按严格表头自动识别：清结算银行账户表、中台调拨订单表、中台测试付款全量信息表、中台网关原始入账订单、中台网关原始出账订单。
- 内置规范模板使用“中台调拨订单表.xlsx”；既有表类型识别仍保留“中台调拨订单.xlsx”兼容模板，不改变旧入口。
- 业务主键分别为：无（账户快照）、调拨单号、付款单号、`bizId`、业务单号。
- 业务主键、日期、关键金额或必需币种非法时整份文件拒绝并报告文件/sheet/行号/字段。
- 原始表数据区空白行允许忽略，但错误提示及 `source_row_number` 必须保留原 Excel 物理行号，不得使用删除空白行后的数组下标。
- 同文件完全相同的主键重复行折叠；内容冲突拒绝整份文件。重复指纹必须包含 Excel 日期对象的实际时间值，不得把不同日期视为相同。
- 同批跨文件主键冲突时拒绝后续文件，已成功文件保留；后续独立导入按主键更新。
- 同批结果顺序与用户选择文件顺序一致，存档中心只保存实际成功的对应文件。
- 需要确认的账户快照同样从应用私有不可变暂存副本解析、写库和存档。
- 清结算银行账户表是全量快照，仅派生 `账户状态=正常`；不限制账户性质和是否参与对账。
- 正常账户须有币种、非空账户性质，且银行账号/系统账号至少一个非空。过滤后为 0 行时拒绝覆盖旧快照。
- 订单类来源删除必须明确选择至少一个月份，不接受空月份或整表删除；只有清结算银行账户表允许二次确认后整表清空。

## 5. 链接表字段

| 链接表 | 字段 |
|---|---|
| 中台调拨平盘对账单 | ReconID、MerchantId、Currency、Amount、FundType、调拨单号、调拨状态、交易时间、付款币种、收款币种、换汇渠道 |
| 中台测试付款对账单 | ReconID、付款单号、付款状态、源金额、源币种、目标金额、目标币种、付款渠道、创建时间、银行流水号 |
| 中台网关入账对账单 | ReconID、MerchantId、Currency、bizId、billDate、tradeType、channel、originOutboundCurrency |
| 中台网关出账对账单 | ReconID、MerchantId、Currency、业务单号、账单日期、交易类型、渠道名称、原始币种、原始金额、银行扣款币种 |
| 清结算银行账户表 | 既有 40 列，只有账户状态正常的行 |

- 调拨订单付款币种与收款币种不同才显示为可见链接数据；同币种订单保留为内部证据，用于把银行原有错误 `&FX` 校正回基础类型。每单派生 out/in 两腿，账户先应用平盘独立映射，未映射时保留原账号。
- 测试付款要求源金额/源币种有效且源金额非 0；源币种不同于目标币种时显示为可见链接数据，同币种行保留为内部证据。
- 入账管理页只显示 `Inbound-VA/WireReturn` 且 `currency != originOutboundCurrency` 的 FX 链接数据；同币种记录保留为内部证据。Inbound 只有银行币种、订单币种和原始出金币种三者均明确且相同时才可移除 `&FX`，任一币种为空或证据冲突均转差异。
- 出账保留全部合法候选，FX 在银行匹配阶段判定。

## 6. 通用匹配

- 除账户识别三场景外，银行任一非空 `ReconciliationId/ChannelOrderNo/CustomerRef` 与 ReconID trim 后大小写敏感精确匹配。
- 不同标识命中不同链接行、多候选、候选复用均转差异；订单类匹配在单次运行及所有已确认运行之间执行全局双向严格 1:1。
- 已确认的链接来源记录不得被其它银行 BizId 再次消费；已确认的银行 BizId 不得改配到其它来源记录。同一银行 BizId 重导后复核同一来源记录允许幂等通过。
- 未解决差异的人工确认只表示保留人工结论，不代表认领某条链接来源；没有唯一成功匹配血缘的差异不得写入来源消费表。
- 入账方向：Credit 非 0 且 Debit 为空/0；出账方向相反；Test 仅要求 Debit 非 0。
- 调拨银行金额为 `abs(方向金额) + signed Extra Fee`；空手续费按 0，非法值或负合计转差异。
- 金额使用十进制字符串运算并精确到分，不使用 JavaScript 浮点数。
- 仅实际修改 FundType 的单元格标黄；同值消费不标黄；选中银行行必须单一去向。

## 7. 场景规则

- Inbound / Wire Return：分别使用 `Inbound-VA / WireReturn`，按 ReconID+MerchantId，不比较金额；依据订单币种、原始出金币种和银行币种判断基础/FX。Inbound 仅在三种币种均非空且相同时判为基础类型；无法明确则差异。
- outbound / Ach Return：Ach 仅 `AchReturn`，普通 outbound 排除 AchReturn；按 ReconID+MerchantId，不比较金额；只有精准/模糊 FX 条件成立时加 `&FX`，其余转差异。
- FundTransfer-in/out：仅付款成功；按 ReconID、对应腿账号、币种、含手续费金额匹配，付款/收款币种不同即 FX。
- FundTransfer-out 的 BillDate 不早于交易日；FundTransfer-in 还不早于同一调拨单唯一 out 银行日，out 从全部未归档银行数据查找。
- Test：不校验账户和金额；按 ReconID、Debit 和银行币种/目标币种判断；非成功合法状态为模糊命中。

### 7.1 Others / Revenue Clear / From TREASURY FUND

- 不使用调拨链接表，不校验 ReconID、金额、方向或付款状态。
- 在 Payee CardNo、Drawee CardNo、MerchantId 中，以“银行字段包含完整银行账号或系统账号”识别正常账户；trim 后大小写敏感。
- 先唯一识别 `账户性质=自有` 的逻辑账户；排除命中该账户的字段后，从剩余字段唯一识别账户性质非空且不等于“自有”的逻辑账户。
- 银行账号和系统账号是同一账户的别名；共享任一非空别名的行归为同一逻辑账户。
- 重复行只有唯一币种时折叠；多币种、多账户性质、别名冲突、缺失或多候选转“需人工判定”。
- 两账户币种不同改为对应 `&FX`，相同改为基础类型；唯一完整识别为精准命中，不产生模糊命中。

## 8. 结果、回导与确认

- 模板：`assets/平盘银行对账单.xlsx`；文件名：`YYYYMMDDHHmm_平盘资金性质校验结果.xlsx`；sheet：渠道对账单；固定 49 列。
- 前三列为命中明细、命中类型、匹配命中详情；其后为标准 46 列。
- 命中类型：精准命中、模糊命中、未命中、需人工判定、不适用、人工修改。
- 回导严格校验 49 列和完整 BizId 集合；行序可变。只允许在原基础/FX二元组内修改 FundType，并可同时修改详情；禁止仅改详情或改其它字段。
- 回导对除 FundType 和审计详情外的字段执行严格防篡改校验。BillDate/ValueDate 原值为纯日期时允许等价纯日期文本或 Excel 日期单元格；原值包含业务时分秒时必须完整一致。所有日期时间只接受原值、最多 2ms 的 Excel 浮点误差或 ExcelJS→SheetJS 已知固定时区往返等价值；同日修改小时、分钟或秒、跨日、非法日期文本和 Invalid Date 均拒绝。
- 合法回导后重新计算最终修改数、差异数、精准/模糊数、不适用数和人工修改数，结果确认页必须显示回导后的最终统计。
- 成功导出或合法回导后才允许确认。
- 回导修改后、最终确认前，差异状态仍为“待确认”；确认事务根据最终结果更新为“人工确认保留”或“人工修改后确认”。
- 确认原子更新工作 FundType、审计、差异状态和批次状态；未解决差异可确认为人工确认保留。
- 结果确认页必须明确提示未解决差异不会认领或消费链接来源。
- 差异页只展示 snapshot 仍有效的待确认批次和已确认批次；失效或被替换草稿不显示。差异导出严格按运行批次、Channel、地区、月份和差异状态过滤，已确认批次仍可导出对应 49 列数据；所选范围为 0 行时明确拒绝。
- 草稿快照绑定平盘规则版本；规则版本变化后旧草稿自动失效并要求重新运行。
- 结果、链接表和原始表导出在列级固定业务 ID、账号、卡号、ReconID、CustomerRef、客户编号等标识符为文本格式；静态模板生成器与运行时 writer 必须复用同一判定，即使零数据、只有表头，也必须保留长整数和前导零。

## 9. 验收标准

- AC-01：五类原始表可识别、派生、导出、删除，坏行和冲突不会部分写入单文件。
- AC-02：银行 46/49 列可导入，Channel+月份替换原子，原 Excel 和原始快照不变。
- AC-03：十组 FundType 规则、跨已确认运行的双向严格 1:1、方向、日期、Extra Fee 和单一去向符合本规格。
- AC-04：清结算银行账户表只筛正常状态；三类账户场景按自有/非自有唯一账户币种判定。
- AC-05：结果固定 49 列，修改标黄，零数据标识符列仍为文本格式；纯日期与已知 Excel 日期时间往返兼容，同日时分秒等真实篡改拒绝，确认原子且草稿可跨重启。
- AC-06：差异按 Channel+月份+运行+状态汇总并保留原因和血缘，导出不得串范围。
- AC-07：主库不出现批量明细；银行输入、链接原始表、回导文件和每次成功导出的结果均独立立即接入存档中心，不依赖进程内批次关联；业务 IPC 返回成功前，本次存档登记与文件处理必须完成或落成可重试失败记录，不能只排入进程内尾队列。
- AC-08：存档重试、删除及另存为均进入统一业务退出闸门；应用退出或升级必须等待进行中的存档写操作完成。
- AC-09：并发平盘操作不得覆盖待完成记录；运行行、结果去向、差异和来源消费无法通过共同篡改绕过完整性校验；异常退出后的已完成业务或已发布输出必须恢复成正式存档批次或持久 outbox。多文件部分提交恢复只存档 side DB 同事务凭证可证明的已提交文件，未提交文件不得混入。
- AC-10：版本、文档、完整数据目录备份说明、重要变量、release-check、侧库 parity、preview 和启动性能完成。
