## 1. 背景

### 1.1 为什么要做

- 用户从 3.0.26 升级到 3.2.11 后**每次启动都失败**。启动失败对话框显示 `biz-op-v327：[BIZOP_ACTIVATION_RESOURCE_UNAVAILABLE] 业务 OP 升级需要 1024 MiB 后台内存预算，当前可用 4096 MiB（预算上限 4096 MiB）……`（[S01](baseline-evidence.md#s01)）。
- 文案自相矛盾（“可用 4096”大于“需要 1024”），用户按提示关闭程序、重启都无效；开发侧也无法从文案或日志判断真实原因（[S04](baseline-evidence.md#s04)）。
- 排查中还复现出另一个确定存在的启动阻断：从 v3.1.10 及更早版本升级、带有旧业务 OP 月度文件的用户，会稳定地报 `BIZOP_LEGACY_SCHEMA_INCOMPLETE`（[S09](baseline-evidence.md#s09)、[S11](baseline-evidence.md#s11)）。

### 1.2 用户与业务价值

- 受影响的用户完全无法打开软件，所有模块都不可用；启动失败也让自动更新送不到他们手上（[S12](baseline-evidence.md#s12)）。
- 本次修复要让：资源错误能说清真实原因，短暂占用可以自行恢复，旧格式月度文件不再阻断升级。

### 1.3 当前问题

| 编号 | 问题 | 状态 |
| --- | --- | --- |
| P-RES | 升级预检“立即拒绝、零等待”；拒绝原因被丢弃；文案显示的是记账余额和写死的 1024 MiB | 机制已确认；用户机器上的具体阻塞项**未知**，本地 5 组场景均未复现 |
| P-SCHEMA | 第一轮旧数据扫描要求旧月度文件 6 张表齐全，v3.1.10 及以前创建的文件只有 4 张 | 已确认，本地稳定复现 |

## 2. 代码现状（必须有出处）

- **相关文件**：`src/main-process/biz-op-v327/upgrade-main.js`、`phase-admission.js`、`upgrade-legacy.js`；`src/main-process/background-execution/resource-governor.js`、`memory-admission.js`、`memory-activity.js`；`src/main-process/archive-center/controller.js`；`src/backend/startup-failure.js`；`scripts/biz-op-v327/verify-windows-app.js`。
- **当前行为**
  - 升级预检以 `lowMemoryBehavior:'reject', timeoutMs:0` 申请 `EXPORT_IO_RESOURCES`。失败时丢弃原错误，用调度器的 `available`/`budgets` 拼文案，“1024 MiB”写死（`upgrade-main.js:199-217`，[S04](baseline-evidence.md#s04)）。
  - v3.2.11 起生产环境固定装配内存准入。x64 上该预检实际申请 384 MiB（低内存档 128 MiB），存在任何增长未知的活动或租约就直接拒绝（[S03](baseline-evidence.md#s03)、[S05](baseline-evidence.md#s05)）。
  - 预检失败会聚合为启动失败，业务窗口不会创建（[S06](baseline-evidence.md#s06)）。首次升级的那次启动会预检两次：owner 阶段一次，post-outbox 阶段续跑时再一次（[S13](baseline-evidence.md#s13)）。
  - 失败明细在三处丢失：
    - 内存准入和调度器只返回布尔判定，错误不带原因，超时错误也不带候选额度（[S14](baseline-evidence.md#s14)）；
    - 错误处理时的现场可能已经变化（[S15](baseline-evidence.md#s15)）；
    - post-outbox 入口不透传明细（[S13](baseline-evidence.md#s13)）。
  - 第一轮扫描（非 quiescent）对旧月度文件要求 6 张表齐全（`upgrade-legacy.js:73`）。随后由原 provider 补齐旧文件结构，第二轮严格扫描才授权清理（[S11](baseline-evidence.md#s11)）。
- **已知限制**：业务 OP 的其他阶段已经使用统一准入 `acquireBizOpPhaseLease`（不可能满足立即拒绝、暂时占用最多等 5 秒，`phase-admission.js:5-46`），唯独升级预检没有接入。
- **事实依据**：见 [baseline-evidence.md](baseline-evidence.md)。

## 4. 功能点

### 4.1 F1：资源拒绝的准确诊断

- **说明**：升级预检被拒绝时，启动失败对话框的“处理明细”和活动日志都能看出真实原因。
- **输入**：
  - 调度器错误 `details` 中的判定记录（R2 新增，判定时采集）；
  - 调度器快照、内存活动清单和系统可用内存（拒绝后采集）。
- **输出**：外层错误码保持 `BIZOP_ACTIVATION_RESOURCE_UNAVAILABLE`，`message` 不再写死额度。`detailLines` 依次包含：
  1. 内部原因码（预算不足或等待超时）；
  2. helper 已有的 4 行：动作；兼容请求额度、本次预算、记账剩余；槽位；“本阶段尚未开始”。稳定上限拒绝时，另有调度器原因和实际上限；
  3. **判定记录**：
     - 判定次数、最后一次判定的时间、入队时前方的排队数；
     - 每个实际候选（如普通档 384 MiB、低内存档 128 MiB）的拒绝原因和相关数值，例如按来源计数的增长未知活动、判定时的系统内存采样和需要量、额度占用；
     - 一直没有轮到本申请时，如实写明；
  4. **拒绝后现场**，明确标注“错误处理时采集，可能已变化”：
     - 按种类计数的增长未知活动，以及清单是否已封存；
     - 活动租约：数量，以及前 3 项的 actionKey、执行档（或“未登记”）和额度；
     - 队列长度；
     - 系统可用内存。
- **边界**：
  - 判定记录只做记录，不改变判定分支、返回值和错误码。
  - 阻塞原因以判定记录为准。
  - 不记录路径、ownerKey、任务 ID 或业务数据；原错误挂在 `cause` 上。
  - owner 入口与 post-outbox 入口的弹窗和日志采用同一格式。
  - 对话框连同存档控制器加的首行，总共不超过 20 行；日志保留全部明细。
- **验收标准**
  - AC1.1：生产内存策略下，有一个未退出的载体，等待超时后，判定记录列出两个实际候选（384 / 128 MiB）：普通档的原因是“存在增长未知的活动”，来源计数为“载体 1”；低内存档的原因是“低内存档需要独占，但有其他重任务”。
  - AC1.2：装配了内存准入、但未匹配资格（走兼容上限）且上限不足时，明细中出现调度器原因 `stable-limit` 和实际上限，并且立即返回、不等待。未装配内存准入的调度器则由 helper 预检，立即返回预算不足（见 AC2.3）。
  - AC1.3：明细不包含以 `/` 或 `\` 开头的路径，也不包含 ownerKey。
  - AC1.4：使用同一 helper 的其余 5 个业务 OP 阶段，错误码、取消和关闭语义不变，明细只增不减。调度器的错误码和判定结果不变，新增信息只在 `details.decision`。
  - AC1.5：活动租约明细标注执行档（已登记的 profileId，或“未登记”），据此能看出哪些是增长未知的阻塞租约。
  - AC1.6：owner 入口和 post-outbox 入口的资源拒绝，启动失败对话框和日志都包含内部原因、判定记录和拒绝后现场。
  - AC1.7：申请一直没轮到（队首阻塞）时，判定记录写明判定 0 次和入队时前方的排队数。即使拒绝后现场已经变化（例如队首已消失、新租约已授予），判定记录也不受影响。

### 4.2 F2：升级预检的有界等待

- **说明**：升级预检改用现有的 `acquireBizOpPhaseLease`。
- **输入**：原 ownerKey、actionKey、operationKey 和 `EXPORT_IO_RESOURCES`。
- **输出**：获批后照原逻辑继续；否则抛出 F1 定义的错误。
- **边界**
  - 资源充足：立即获批，不强制等待。
  - 不可能满足（超出固定预算，或兼容/硬上限稳定拒绝）：立即拒绝，不排队。
  - 暂时不满足：在调度器内排队最多 5 秒，期间按调度器原有机制每秒重查内存；超时后撤掉自己的排队项。
  - 取消、调度器关闭等错误保持原类型，不改写成资源错误。
  - 已 ACTIVE 的用户不做预检，行为不变。
- **验收标准**
  - AC2.1：暂时占用在 5 秒内释放后获批，后续流程照常执行。
  - AC2.2：等满 5 秒后失败；之后才释放的容量不会被迟到授予，也不会泄漏租约；其他请求的排队不受影响。
  - AC2.3：不可能满足的预算立即失败（0 等待）。
  - AC2.4：首次升级和续跑两个入口都适用。

### 4.3 F3：旧格式月度文件兼容

- **说明**：第一轮扫描（`quiescent:false`）接受只缺 `biz_op_recon_dataset_heads` 和 `biz_op_recon_month_end_copy_intents` 的旧格式月度文件。之后照原流程由原 provider 补齐结构，第二轮严格扫描。
- **输入**：`run-data/biz-op-recon/month-YYYY-MM.sqlite` 及其 `-wal`/`-shm`。
- **输出**：第一轮通过；第二轮严格扫描，规则不变。
- **边界**
  - 只放宽“缺这两张表”这一项。未知表、外键、未知触发器、`quick_check`、文件身份与哈希、数量上限等检查全部保持。
  - 第二轮（授权清理）仍要求 6 张表齐全；原 provider 补不齐时仍然失败并阻断。
  - 主库的旧表校验不变。
- **验收标准**
  - AC3.1：v3.0.26 加旧月度文件的 userData 用本分支启动，升级到 ACTIVE，窗口正常创建，旧月度文件被回收。
  - AC3.2：旧 4 表文件第一轮通过；若第二轮前未被补齐，第二轮仍报 `BIZOP_LEGACY_SCHEMA_INCOMPLETE`。
  - AC3.3：含未知表或未知触发器的月度文件，第一轮仍然失败。
  - AC3.4：v3.1.11 及以后格式的月度文件（现有 CI 验收数据）行为不变。
  - AC3.5：G1 场景进入持续门禁：`npm run test:integration` 中的集成测试，以及 Windows 正式包验收脚本，都覆盖 G1 月度文件。断言内容为：到达 ACTIVE（正式包另断言窗口正常）、旧文件按约回收、非目标数据保留。任何失败都让命令以非零退出。

### 4.4 完成标准

- AC1–AC3 全部有自动化证据，其中 AC3.5 由持续门禁承担。
- `npm run test:unit`、`npm run lint`、`npm run release-check` 通过。
- Windows x64 正式包验收通过（`build-windows.yml` 中的 `verify-windows-app.js`，已含 G1 场景）。结果单独记录，不以本地 macOS 复现代替；实机验收作为补充。

- **对外接口影响**：

- **兼容性影响**：v3.1.10 及以前的旧月度文件可以完成升级；其他格式不受影响。

## 6. 技术决策

- **方案**
  - 复用现有 `acquireBizOpPhaseLease`，不另写等待逻辑；
  - 诊断以“判定记录”为准：内存准入和调度器增加可选的记录参数，不重构判定流程；另附标注过的“拒绝后现场”；
  - post-outbox 入口在存档控制器的包装处透传明细；
  - F3 只放宽第一轮，G1 场景进入集成测试和 Windows 正式包验收。
- **为什么不用其他方案**
  - 只把 `timeoutMs` 改成 5000、保留 `reject`：没有排队，等于没等。
  - 只做拒绝后快照（R1 方案）：超时路径拿不到实际候选额度，快照也可能不是判定时的现场（[S14](baseline-evidence.md#s14)、[S15](baseline-evidence.md#s15)）。
  - 重构为结构化判定结果（`AdmissionDecisionV1`）：要改返回类型和队列模块，作为诊断包，风险和工作量都偏大。本分支只加记录，不改判定。
  - 让启动失败对话框递归读取 `cause`：会改变所有启动失败的展示方式。
  - 扫描前给旧文件补表：会在“只读检查”阶段写旧文件，违反“先检查、再允许原 provider 打开”的设计。
  - 启动恢复窗口（B 阶段）：对“每次必现”的用户不能恢复可用性，而且要改动启动和退出主链路。
- **可能风险**
  - 判定记录改动了调度核心的两个模块。只加记录，原有行为由现有测试锁定。
  - 拒绝后现场可能与判定时不同；明细中已标注，判读以判定记录为准。
  - 有界等待最多让启动多等 5 秒。
  - 详见 [TechDoc §六](techdoc.md#六兼容回滚与风险)。

## 7. 数据／状态／安全影响

- **数据结构**：不变。
- **状态流转**：不变。预检失败仍然发生在创建迁移任务之前（首次路径）或推进 stage 之前（续跑路径）。
- **权限 / 安全**：诊断（包括判定记录）不输出路径、ownerKey 或业务数据。
- **回滚策略**：只回退源码和测试。F3 放行后，原 provider 补齐了月度文件的结构，旧版本也能识别这种结构（v3.1.11 起的版本平时就是这样打开旧文件的）。
