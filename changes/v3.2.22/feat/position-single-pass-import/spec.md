## 1. 背景

平盘对账数据处理模块导入大文件很慢，使用体验差；银行对账单单文件最大 1.2GB。用户要求：

- 原始账单需要存档，仅存一次和一份，需要有版本号。
- 对账单仅存数据交互用的字段值，仅存一次和一份，需要对应原始账单的版本号。
- 数据处理流程中的扫描、哈希校验、预存、预检，能去掉的尽量去掉。

改造前实测（2026-11-23，100 万行 × 46 列、173MB、解压后 1.7GB 的银行对账单，本机）：

| 阶段 | 耗时 |
| --- | --- |
| 暂存复制 + 文件哈希 | 0.3 秒 |
| 预检（第一次全量解析 + 逐行摘要 + 账本登记 + 账本封存） | 29 秒 |
| 写入（文件再哈希 + 第二次全量解析 + 逐行摘要 + 回查账本 + 写库） | 41 秒 |
| 提交 | 29 秒 |
| 合计 | 107 秒 |

侧库与临时文件峰值占盘 8.8GB。链接原始表同样两遍：100 万行网关出账订单（146MB）改造前 139 秒，其中预检 41 秒、写入 83 秒、提交 5 秒，峰值占盘 4.85GB。纯解析只需 10 秒（现用扫描器）/ 4.4 秒（只取 15 列的字节级扫描器），其余时间花在重复解析、逐行哈希、账本、整行 JSON 序列化与小缓存下的写库和提交。

## 2. 已确认决策

| 编号 | 决策 | 来源 |
| --- | --- | --- |
| D1 | 结果导出、银行数据导出只含审计列 + 交互字段 + 原始账单版本号与行号，不再输出完整 46 列 | 用户，2026-11-23 |
| D2 | 版本号按每份导入文件递增；同渠道 + 月份重导时，旧版本原件保留在存档中心可追溯，行数据只保留当前版本 | 用户，2026-11-23 |
| D3 | 保留「覆盖确认」，但不二次解析；仅在会覆盖已有数据时弹出 | 用户，2026-11-23 |
| D4 | 平盘没有需要保留的正式数据，侧库直接换新结构，不做旧数据迁移 | 用户，2026-11-23 |
| D5 | 侧库 checkpoint 链与运行结果行的 `integrity_hash` 保留；解析口径（日期、金额、长 ID）不变；B53 / B54 / B36 不在本次范围 | 计划审批，2026-11-23 |

实现采用的技术调整（不改变 D1–D5 的结果，依据见 techdoc §2）：

- A1：保留一次「复制到模块暂存目录并顺带计算 SHA-256」。这份副本是存档中心的入库来源，也是崩溃恢复时的文件凭证；此后不再对文件做任何二次哈希。计划中「直接解析用户原文件、由存档中心事后复制」的做法在「侧库已提交、存档未完成时崩溃且原文件被移动」的情况下会丢失原件，且需要改动整套以 SHA-256 为凭证的恢复链路，风险高、收益小（复制 + 哈希实测 0.3 秒 / 173MB）。
- A2：分步交付。第一步只换银行对账单导入引擎（单遍、无账本、无行哈希）；第二步换存储结构（版本号、交互字段、导出列）；第三步来源链路；第四步清理。

- A3：链接原始表的记录身份沿用现行契约（`changes/v3.1.3/position-reconciliation-large-table-import/spec.md` D-16：内容相同折叠为一条，业务单号相同但内容不同各自保留），但「内容」只按保存下来的必用列计算。计划里「同业务单号重复行按交互字段相等判定合并或拒绝」中的「拒绝」未采用：拒绝会让现有能导入的文件导不进来，属于未经确认的业务规则变化。
- A4：运行结果行保留一份交互字段快照（已确认的历史运行在银行数据被替换后仍要能导出），去掉结果整行副本。

进度（2026-11-23）：四步全部实现并验证。遗留项见 `knowledge/backlog.md` B143–B146。

## 3. 功能规则

### 3.1 原始账单存档与版本号（D2）

- 每份成功导入的原始文件登记一条版本记录：版本号（模块内自增，界面显示 `V<n>`）、类型（银行对账单 / 各链接原始表）、原始文件名、大小、SHA-256、sheet、行数、状态（当前 / 已被替换）、导入时间、存档批次引用。
- 原始文件在存档中心只存一份；内容相同的文件再次导入时复用已有存档内容，不存第二份，但仍分配新版本号（版本号标识一次导入）。
- 行数据只保留当前版本：同渠道 + 月份被新文件覆盖后，旧行删除，旧版本记录标为「已被替换」，其原件按存档中心保留策略留存。
- 链接原始表按文件累加：某个版本的行全部被后续导入替换或被删除后，该版本标为「已被替换」；清结算银行账户表每次确认整表替换，旧版本即标为「已被替换」。
- 界面：「对账数据管理 → 未归档」与「链接原始表」各有一列「原始版本」，只列当前版本（如 `V5、V3`，超过 3 个显示「等 N 个」，悬停可见文件名）。
- 导入暂存副本在原件进入存档中心、任务收尾后立即删除；待确认的账户表保留到确认或取消。

### 3.2 对账单只存交互字段（D1）

- 银行对账单行只保存：`BizId`、`Channel`、`BillDate`、`地区`、`MerchantId`、`Currency`、`Credit Amount`、`Debit Amount`、`Extra Fee`、`ReconciliationId`、`ChannelOrderNo`、`CustomerRef`、`Payee CardNo`、`Drawee CardNo`、`FundType`，以及原始版本号与原始行号。清单由匹配引擎、金额校验、逻辑账户与差异汇总实际读取的字段确定。
- 链接原始表行只保存各表的必用列（`SOURCE_REQUIRED_FIELDS`）与原始版本号、行号；链接表保持现有派生列。清结算银行账户表的链接表只含 5 个必用列（账户状态、币种、账户性质、银行账号、系统账号）。
- 链接原始表的记录标识由必用列内容算出，入库时算一次，之后不再复核。两行只在非必用列上不同，现在视为同一条记录（改造前算两条）；标识相同但必用列内容不同的情况直接报错中止。
- 运行结果行不再保存整行副本，只保存结果资金性质、审计信息、血缘与完整性摘要。
- 导出（结果导出、差异导出、银行数据导出、链接表 / 原始表导出、异常数据报告）只含上述字段 + 审计列 + 原始版本号 / 行号。结果回导只比对这些列。

### 3.3 单遍导入与覆盖确认（D3）

| 情形 | 规则 |
| --- | --- |
| 正常导入 | 选择文件后一次读取、校验并写入；不再有预检遍和写入遍 |
| 不覆盖已有数据 | 读取完成后直接生效，不弹确认 |
| 会覆盖已有渠道 + 月份 | 读取完成后弹出确认，列出将被替换的渠道 / 月份与行数；确认即生效，取消则本次导入全部作废、库内数据不变 |
| 文件存在非法行（BizId / Channel / BillDate 缺失或无法解析） | 整批拒绝，库内数据不变，提示文件与行号 |
| 同一批文件内 BizId 重复 | 整批拒绝，提示两处行号 |
| BizId 与未被本次覆盖的其他渠道 / 月份数据冲突 | 整批拒绝，提示冲突位置 |
| 读取过程中取消、程序退出或子进程异常 | 库内数据不变 |
| 等待确认期间 | 模块其他写操作（运行、删除、导入、映射保存）提示先确认或取消当前导入 |

### 3.4 链接原始表与账户表导入

| 情形 | 规则 |
| --- | --- |
| 一次选择多份文件 | 一个导入进程、一次读取、一个事务；整批只生效一次（改造前是每份文件各自生效一次） |
| 某份文件表头不识别、结构不符、读取出错 | 只拒绝该文件，其余文件照常导入；结果逐文件列出原因 |
| 数据库错误、取消、侧库状态异常 | 整批作废，库内数据不变 |
| 行被过滤（状态不符、必填缺失等） | 记入异常数据并出一份异常报告；整批一份报告，不再按文件或大小分片 |
| 过滤行与同批其他文件的正常记录是同一业务单号 | 含该过滤行的文件按现行规则拒绝，其余文件照常导入 |
| 异常报告写不出来 | 含过滤行的文件不导入，其余文件照常导入 |
| 全部文件被拒 | 不生效、不产生版本号与存档 |
| 清结算银行账户表 | 先只统计有效行数并提示「旧 N 行 → 新 M 行」；确认后重读同一份暂存文件整表替换。确认前文件或行数发生变化即拒绝 |
| 导入进行中 | 模块其他写操作直接提示导入进行中，不排队等待 |

### 3.5 去掉的环节

预检遍、导入账本库、逐行内容摘要的跨遍比对与防碰撞摘要、写入前的文件再哈希、写入前的独立结构迁移进程、整库 `quick_check` 与外键全表检查、异常报告分片。保留：一次暂存复制时的文件 SHA-256（存档与恢复凭证）、链接原始表每行一次的记录标识、侧库 checkpoint 链、运行结果行完整性摘要。

## 4. 非目标

- 不改匹配规则、资金性质判定与差异口径。
- 不改日期 / 金额解析口径；B53（数字日期时区）、B54、B36 另行处理。
- 不改存档中心的保留策略与界面。
- 运行（资金性质校验）搬到子进程不在本次范围。

## 5. 验收

- 同一 100 万行样本端到端导入耗时降到改造前的 1/3 以内。实测：银行对账单 107 秒 → 19 秒，链接原始表 139 秒 → 26 秒（techdoc §1）。
- §3.3 各情形有自动化回归；库内数据在任何失败 / 取消路径下不变。
- 行可追溯：任一银行行、来源行能对应到原始版本号与行号；版本记录能对应到存档中的原件。
- 单测、集成测试、lint 通过；PR-ready 前 `npm run release-check` 通过。
- 对账专项审查结论与资金红线项交人工复核。
