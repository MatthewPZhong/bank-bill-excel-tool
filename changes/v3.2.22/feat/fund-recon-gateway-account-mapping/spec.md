## 1. 背景

「中台调拨订单对账ID回填」（R5 场景2）有两种数据来源，由场景配置「对账数据来源为中台调拨单表」二选一：

- 勾选（默认）：调拨对账单来源（R5s2-recon）。派生调拨对账单时，`big_account` 先按「账户映射管理」由中台调拨单账户号换成清结算系统银行账号（v3.0.12）。
- 取消勾选：网关来源（R5s2）。直接比较网关 `merchantid` 与银行 `MerchantId`，不经过映射。

部分用户用网关对账单里的调拨单回填，网关账户号与清结算银行账号不一致时对不上，而映射管理只覆盖中台调拨单。

用户表述为「网银账单生成模块」；代码中链接表管理、账户映射管理、带「网关对账单修复」入口的场景管理都属于「资金对账数据处理」（`#bankStatementModulePanel`），按该模块实施。

## 3. 规则

### 3.1 共用映射 helper

`engine-utils.js` 新增 `resolveMappedAccount(accountMappingMap, rawAccount)`：归一化 → 非 Map 按空表 → `get ?? 原值`。调拨派生 `buildFundTransferReconRows` 与 R5s2 网关、检测器网关侧共用。映射非空且账号含 `_xHHHH_` 写法时返回空串（转义护栏，D16）。

### 3.2 R5s2 网关匹配

`runRound5FundTransferBackfill(gwRows, bankRows, { accountMappingMap })`：每条网关行在扫描银行池前算一次 `resolveMappedAccount(map, gw.merchantid)`（不建按行数增长的缓存），要求 `=== normalizeCellValue(bank.MerchantId)` 且两侧非空；匹配账号属本方向映射目标账号集合时另需 `gw.Channel`、`bank.Channel` 归一化后非空且相同；`options.channelMissingDiagnosticGwRows` 为池外诊断行，只告警不匹配（D9）；返回 additive `directionsValid`。币种、金额（含 Extra Fee）、方向、日期两阶段、严格 1:1、多候选 tie-break 与 warning 不变。

### 3.3 注入

- `runReconciliation({ fundTransferAccountMappingMap, fundTransferChannelMissingDiagnosticSource })` 缺省空 Map / null，都只传给 R5s2 网关分支；该分支实际运行且 `directionsValid` 时才传给多对多检测器做映射补跑（补跑的网关池过滤在银行门控之后逐行判断）。
- `bank-statement:run`：经 `prepareRunFundTransferReconDerivation` 在调拨对账单重派生前读一次映射（D4），经 `rebuildFundTransferReconDerivation({ accountMappingMap })` 供派生；之后才按渠道读网关池，网关来源开启时用同一份 Map 在同一次扫描暂存池外诊断候选（D9，只存 id 与键摘要；R5 运行时按 id 回读），再把 Map 与诊断读取器传编排器；mid-allocation 导入入口仍由派生函数自行读取。
- worker：`evidence-provider` 读 `getMappingMap(snapshot.db)`，映射 entries 进入证据签名；启用调拨派生消费方时派生证据须带 `accountMappingSignature` 且与快照一致；网关来源开启时同口径在读池的同一次扫描暂存候选、在同一快照事务内按 id 回读，并提供 `r5ChannelMissingDiagnosticSource`；`service.js` 透传。
