## 0. 本次迭代总目标

3.0.13 包含 6 个实施项：

1. **导入文件目录记忆**：所有业务导入入口点击导入后，文件选择框默认进入上一次导入文件所在目录。
2. **网银账单生成大账号识别失败拦截**：识别不到大账号，或识别到但当前模板未维护时，必须提示并阻断，不允许静默取其它维护账号。
3. **中台调拨单派生过滤**：导入中台调拨订单后，生成调拨对账单时仅处理 `调拨状态 = 付款成功` 的源行。
4. **银行对账单结果表异常说明迁移 + 纯 no-op 行过滤**：
   - 不再生成 `异常-人工处理` / `异常-人工判断` 独立 sheet；
   - 将原异常 sheet 的 `异常说明` 移到 `命中场景` sheet 的 `命中明细` 右侧；
   - `命中场景` 只保留“有用户可见处理信息”的行：实际字段变更行，或有 `异常说明` 的人工判断行；过滤既无字段变更、又无命中明细、又无异常说明的纯 no-op 行。
5. **C3 网关赋值候选选择修复**：C3 `gateway-recon-join` 多候选时，若银行被赋值字段旧值非空，且候选中存在同值网关候选，优先选择该同值候选，避免把已有正确 `ReconciliationId` 错覆盖。
6. **版本与文档同步**：升级 `package.json` 版本并同步 `CHANGELOG.md`、`docs/VERSION_FEATURE_HISTORY.md`、`docs/USER_GUIDE.md`。

## 2. Req1：导入文件默认进入上一次导入目录

### 2.1 需求

所有业务导入入口，只要用户打开文件选择框，下一次点击同类或相关导入时，应默认进入上一次选择文件所在目录。

规则：

- 用户取消选择时不更新目录。
- 用户选择文件后，即使后续业务校验失败，也更新为刚选择文件所在目录。

- 上一次目录不存在或不可访问时，静默回退 Electron 默认目录，不弹错。
- 同 scope 优先读自己的目录；没有 scope 目录时可 fallback 到 global 最近目录。

```js
      : undefined;
```

## 3. Req2：网银账单生成大账号识别失败时禁止误取其它账号

### 3.1 问题

当前大账号识别链路在以下场景可能静默误选：

- 文件中识别不到大账号；
- 识别到大账号，但该大账号未在当前模板的大账号库维护；
- 识别结果为空或不唯一，却被后续逻辑兜底成大账号库里的其它账号。

用户要求：无法识别或未维护时必须提示，不允许用错账号继续生成。

### 3.2 Codex 定位指令

先 grep 以下关键词，定位实际自动识别 / 自动选择分支：

```bash
grep -R "__MULTI_BIG_ACCOUNT__\|selectedBigAccount\|completeBigAccountSelection\|extractBigAccountOrder\|allowManagedMerchantWithoutSelection\|template_big_accounts\|getWithOwn\|groupBigAccountRows" -n src tests
```

重点关注：

- `src/main.js`
- `src/main-process/statement-generation.js`
- `src/backend/file-service.js`
- `src/main-process/statement-session.js`
- `src/backend/database/template-repository.js`
- `src/backend/database/utils.js`
- renderer 大账号选择弹窗逻辑

### 3.3 行为规则

新增纯函数，建议命名：

```js
resolveRecognizedBigAccount({
  extractedMerchantId,
  extractedCurrency,
  maintainedBigAccounts,
  sourceFileName,
  templateName
})
```

返回：

```js
{ status: 'ok', selectedBigAccount }
{ status: 'needs-selection', candidates, message }
{ status: 'failed', code, message, detailLines }
```

规则：

1. `extractedMerchantId` 归一化后为空：
   - 返回 `failed`。
   - code: `BIG_ACCOUNT_NOT_RECOGNIZED`。
   - 文案：`未识别到大账号，请检查导入文件或先在“维护大账号”中维护后重新导入。`
   - 不允许 fallback 到 `maintainedBigAccounts[0]`。

2. `extractedMerchantId` 非空，但维护表无同 merchantId：
   - 返回 `failed`。
   - code: `BIG_ACCOUNT_NOT_MAINTAINED`。
   - 文案：`识别到大账号「${id}」，但当前模板的大账号库未维护该账号，请先维护后重新导入。`
   - detailLines 包含文件名、识别值、模板名。

3. 同 merchantId 只有一个维护项：
   - 返回 `ok`，使用该维护项。

4. 同 merchantId 有多个币种：
   - 若 `extractedCurrency` 非空且能唯一匹配币种，返回 `ok`。
   - 若币种无法唯一确定，返回 `needs-selection`，复用现有大账号选择弹窗，让用户选。
   - 不允许自动取第一个。

5. 用户已经在弹窗显式选择 `selectedBigAccount` 时：
   - 保持既有逻辑，不要再次错误拦截。
   - 但可以校验所选项仍存在于当前模板维护列表；不存在则提示重新选择。

### 3.4 接入点

在“自动识别并准备生成文件”的路径中，在调用 `prepareGeneratedFiles` / `generateStatementFiles` 前执行校验。

不要在 `buildMappedRows` 中简单拒绝所有未映射 `MerchantId`，因为普通账号映射流程仍可能允许原值透传。本需求只针对“维护大账号 / 自动识别大账号”的误兜底路径。

错误返回应走现有用户侧错误体系，至少包含：

- `status: 'failed'`；
- `step: '识别大账号'`；
- `errorCode: 'BIG_ACCOUNT_NOT_RECOGNIZED' | 'BIG_ACCOUNT_NOT_MAINTAINED'`；
- 用户可读 `message`；
- 状态框可见；
- 如项目当前错误报告机制会生成 txt，则继续生成。

### 3.5 测试

新增大账号识别单测：

1. 维护表有 `B002/USD`，文件识别为空：返回失败，不生成文件。
2. 维护表有 `B002/USD`，文件识别为 `A001`：返回失败，不选择 `B002`。
3. 维护表有 `A001/USD`，识别为 `A001`：成功选择 `A001/USD`。
4. 维护表有 `A001/USD`、`A001/EUR`，识别账号为 `A001` 但币种未知：返回 `needs-selection`。
5. 维护表有 `A001/USD`、`A001/EUR`，识别账号 `A001` 且币种 `USD`：成功选择 USD。
6. 用户显式选择 `A001/EUR` 后重新生成：不被识别失败逻辑拦截。

## 5. Req4：银行对账单处理结果表布局调整 + 纯 no-op 命中行过滤

### 5.1 当前代码事实

当前 `writeBankStatementOutput` 输出：

- `未命中场景` sheet；
- `命中场景` sheet，第一列为 `命中明细`；
- 如果 `manyToManyRows` 非空，会追加 `异常-人工判断` sheet，表头为 `[异常说明, ...BANK_STATEMENT_FIELDS]`。

用户说的 `异常-人工处理` 与代码当前 `异常-人工判断` 语义相同。本次验收中，两个名称都不应再出现在输出工作簿中。

同时，同事补充 spec 指出：旧输出中 `命中场景` 会混入大量“被 R2 场景锁定但没有实际字段变化”的 no-op 行。这类行表现为：

- `命中明细` 为空；
- `_modifiedColumns.size === 0`；
- 无黄色修改单元格；
- 没有 `异常说明`。

这些纯 no-op 行不应进入 `命中场景`。

### 5.2 目标语义

#### 5.2.1 `命中场景` 的权威语义

3.0.13 起，`命中场景` sheet 不再表示“所有被场景锁定/消费的行”，而表示“有用户可见处理信息的银行行”。

一行进入 `命中场景` 的条件：

```text
有实际字段修改 OR 有异常说明
```

具体为：

- 有实际字段修改：该行 `_rowId` 在 `modColsByRowId` 中存在，且对应修改列 Set 可为空以外的实际改动来源记录。
- 有异常说明：该行 `_rowId` 出现在 `manyToManyRows[].row._rowId` 中，并且 note 非空。

#### 5.2.2 过滤规则

必须过滤：

```text
无字段修改 AND 无异常说明
```

这类行即使被 R2 dispatcher 锁定，也不写入 `命中场景`，应落入 `未命中场景`，以保持行数守恒。

必须保留：

- 有字段修改的行；
- 无字段修改但有 `异常说明` 的人工判断行；
- R2 命中后又被 R4/R5 实际改写的行，且应继续嫁接 R2 `_hitScenario*` 元数据；
- R4/R5-only 改写行。

### 5.3 关键冲突处理

同事 no-op 过滤 spec 中“只有字段被实际修改的银行行才进入 `命中场景`”这句话不能直接照抄为实现，因为 3.0.13 第 4 项要求把 `异常说明` 从独立 sheet 移入 `命中场景`。

最终实现必须以本规则为准：

```text
命中场景 = 实际字段修改行 ∪ 有异常说明的人工判断行
```

也就是说：

- 纯 no-op 行过滤；
- 但有异常说明的 no-op 人工判断行仍保留，并在 `异常说明` 列显示 note。

### 5.4 修改 `reconciliation-orchestrator.js`

文件：

`src/main-process/reconciliation-orchestrator.js`

当前 `buildOutputRows(bankRows, modColsByRowId, r2HitByRowId)` 的判定类似：

```js
const isHit = (r) => modColsByRowId.has(r._rowId) || r2HitByRowId.has(r._rowId);
```

需调整为可接收可见异常行集合。推荐改签名：

```js
function buildOutputRows(bankRows, modColsByRowId, r2HitByRowId, visibleReviewRowIds = new Set()) {
  const hasChangedColumns = (r) => modColsByRowId.has(r._rowId);
  const hasReviewNote = (r) => visibleReviewRowIds.has(r._rowId);
  const shouldGoToHitSheet = (r) => hasChangedColumns(r) || hasReviewNote(r);

  const modifiedRows = bankRows
    .filter(shouldGoToHitSheet)
    .map((r) => {
      const out = { ...r };
      const r2hit = r2HitByRowId.get(r._rowId);
      if (r2hit) {
        for (const k of Object.keys(r2hit)) {
          if (k.startsWith('_') && !META_EXCLUDE_KEYS.has(k)) {
            out[k] = r2hit[k];
          }
        }
      }
      out._modifiedColumns = new Set(modColsByRowId.get(r._rowId) || []);
      return out;
    });

  const unmatchedRows = bankRows.filter((r) => !shouldGoToHitSheet(r));
  return { modifiedRows, unmatchedRows };
}
```

在 `runReconciliation()` 中：

1. 先跑完 `detectFundTransferManyToMany(...)` 得到 `manyToManyReviewRows`。
2. 构造 `visibleReviewRowIds`：

```js
function buildReviewRowIdSet(reviewRows) {
  const ids = new Set();
  for (const rv of Array.isArray(reviewRows) ? reviewRows : []) {
    const row = rv && rv.row;
    if (!row || row._rowId === undefined || row._rowId === null) continue;

    if (note.trim() === '') continue;
```

## 6. Req5：C3 网关赋值场景优先选择同值赋值候选

### 6.1 问题

C3 `gateway-recon-join` 场景中，当一条银行行同时匹配到多条网关行，且其中一条网关行的赋值字段已经等于银行行当前被赋值字段时，系统仍可能选择另一条排在前面的网关候选，把银行行已有正确值覆盖成其它值。

典型场景：

- 场景：`outbound-2`
- C3 assign：网关 `reconciliationid` → 银行 `ReconciliationId`
- 银行当前 `ReconciliationId = RC-SAME`
- 多候选：
  - `gwOther.reconciliationid = RC-OTHER`
  - `gwSame.reconciliationid = RC-SAME`
- 若网关顺序为 `[gwOther, gwSame]`，当前逻辑 `matched[0]` 会选择 `gwOther`，造成错误覆盖。

### 6.2 当前根因

文件：

`src/main-process/scenario-engines/c3-gateway-recon-join.js`

当前流程：

1. 过滤网关条件、银行条件。
2. 对每条银行行，从未消费网关行中找出所有满足 `reconFields` 的候选。
3. 排除赋值字段为空的候选。
4. 如果候选数大于 1，发 `multi-gateway-match` warning。
5. 直接取：

```js
const chosen = matched[0];
```

问题：`matched[0]` 只反映网关行导入顺序，不考虑银行当前被赋值字段已有值。

### 6.3 目标行为

仅对 direct assign 模式生效。

当一条银行行匹配到多条可用网关候选时，如果：

```text
assign.mode !== 'custom'
AND bankRow[assign.bankField] 归一化后非空
AND 存在候选 x，使 normalizeCellValue(x.row[assign.gwField]) === normalizeCellValue(bankRow[assign.bankField])
```

则优先选择这条同值候选。

如果不存在同值候选，则保持现有行为：选择 `matched[0]`。

custom mode 不适用：

- custom mode 新值来自 `assign.customValue`，不是网关字段；
- 不存在“网关赋值字段同值候选”的概念；
- 仍按现有 custom mode 行为。

### 6.4 保留行为

不改变：

- `conditions` 过滤口径；
- `reconFields` 匹配口径；
- `发生额绝对值` 虚拟字段口径；
- Extra Fee 匹配与写盘口径；
- 候选数大于 1 时继续产生 `multi-gateway-match` warning；
- 匹配成功后仍 lock 银行行；
- `usedGwRowIdx` 仍消费最终 `chosen` 的那条网关行；
- 1v1 单向消费模型。

### 6.5 实现方案

在 `c3-gateway-recon-join.js` 内新增纯函数，建议使用带语义的名字，避免未来误认为通用排序器：

```js
function chooseC3MatchedCandidatePreferExistingAssignValue(matched, bankRow, assign, isCustom) {
  if (!Array.isArray(matched) || matched.length === 0) return null;
  if (isCustom) return matched[0];
  if (!assign || !assign.gwField || !assign.bankField) return matched[0];

  const oldValue = normalizeCellValue(bankRow && bankRow[assign.bankField]);
  if (oldValue === '') return matched[0];

  const sameValue = matched.find((x) =>
    normalizeCellValue(x && x.row && x.row[assign.gwField]) === oldValue
  );

  return sameValue || matched[0];
}
```

替换：

```js
const chosen = matched[0];
```

为：

```js
const chosen = chooseC3MatchedCandidatePreferExistingAssignValue(matched, bankRow, assign, isCustom);
```

`chosen` 理论上不会为 null，因为前面已 `matched.length > 0`，但可防御：

```js
if (!chosen) return;
```

### 6.6 warning 文案

保留 warning code：`multi-gateway-match`。

可以选择不改 warning 文案，减少测试抖动。

如果增强文案，建议只追加说明，不改 code：

- 命中同值候选：`bankRow 在网关账单中匹配到 2 行可用 gw，优先取赋值字段同值候选（数据脏）`
- 未命中同值候选：沿用 `取第一条（数据脏）`

### 6.7 测试

文件：

`tests/unit/main-process/scenario-engines/c3-gateway-recon-join.test.js`

必测：

1. 同值候选在后时仍优先选择同值候选：
   - 银行 `ReconciliationId = RC-SAME`；
   - 网关顺序 `[gwOther(RC-OTHER), gwSame(RC-SAME)]`；
   - 银行最终仍为 `RC-SAME`；
   - `modifications.length === 0`；
   - `lockedRowIds` 包含该银行行；
   - `multi-gateway-match` warning 仍存在。

2. 同值候选在前时行为不变。

3. 没有同值候选时沿用第一条候选：
   - 银行 `ReconciliationId = RC-OLD`；
   - 网关 `[RC-1, RC-2]`；
   - 最终 `RC-1`；
   - 产生一条 `ReconciliationId: RC-OLD -> RC-1` modification。

4. 银行旧值为空时沿用第一条候选。

5. custom mode 不走同值候选优先，仍写入 `customValue`。

6. Extra Fee 回归：
   - 同值候选在后；
   - `extraFee.enabled = true` 且 `amount` 有效；
   - 选择同值候选后，`ReconciliationId` 不变；
   - `Extra Fee` 仍按现有规则写入相反数并产生 modification；
   - lock + 消费网关行仍发生。

7. 1v1 消费回归：
   - 两条银行行共享两条网关候选；
   - 第一条银行行因同值优先消费 `gwSame`；
   - 第二条银行行只能消费剩余网关行；
   - 不允许同一网关行被两条银行行重复消费；
   - 最终 `usedGwRowIdx` 行为与“消费 chosen 候选”一致。

### 6.8 风险与边界

这是 C3 多候选脏数据下的选择规则变更。历史逻辑完全按网关行顺序取第一条；新逻辑在“银行旧值非空且存在同值候选”时优先同值候选。

这会改变部分历史多候选脏数据的输出结果，但目标是避免把已经自洽的银行对账 ID 错改成另一条网关对账 ID。

本修复不解决“为什么同一银行行能匹配多条网关行”的数据质量问题；多候选 warning 必须继续保留。

## 11. 验收标准

1. 任意业务导入入口首次选择某目录文件后，再点同入口导入，文件框默认打开该目录。
2. 取消导入不会覆盖记忆目录。

4. 识别到未维护大账号时，不会使用其它维护账号，并提示用户先维护。
5. 中台调拨单只有 `调拨状态=付款成功` 的源行会派生调拨对账单；每条成功源行仍生成 in/out 两行。

7. `命中场景` sheet 第 1 列是 `命中明细`，第 2 列是 `异常说明`，第 3 列开始保持原银行对账单字段顺序。
8. `异常说明` 内容来自原 `manyToManyRows[].note`，按 `_rowId` 写入对应命中行；一行多 note 用 `; ` 拼接。
9. `命中场景` 不包含“命中明细为空、异常说明为空、无标黄修改列”的纯 no-op 行。
