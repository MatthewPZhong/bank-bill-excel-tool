## 1. 目标与完成标准

### 1.1 目标

修复中台调拨单和中台测试付款单因少量、可明确识别的异常行导致整份文件 0 行落库的问题。

新流程固定为：

`链接表管理 → 导入原始表 → 文件解析/校验 → 发现过滤行并自动过滤 → 写数据库`

过滤不需要用户在数据库写入前确认。正常行自动落库并参与后续平盘资金性质校验，异常行不进入原始表和链接表，但必须通过过滤墓碑、异常报告和存档记录保持可追溯。

### 1.2 完成标准

- 第一条可过滤异常不再中断文件扫描；同一文件的全部数据行均完成分类。
- 正常行自动写入 `position_source_rows` 并按现有规则派生链接行。
- 可过滤异常行不写入原始表、不生成链接行、不参与资金匹配或消费占用。
- 用户无需作出过滤确认；写库完成后能看到过滤数量并导出完整异常数据。
- 异常报告可立即导出，也可后续从“存档中心 → 平盘对账数据处理”下载。
- 文件内每个非空物理数据行均有唯一、可解释的处理去向。
- 不修改 ReconID、商户、金额、币种、方向、日期、FundType 或严格 1:1 匹配规则。
- 六份真实异常文件完成回放；业务人工复核作为正式发布前资金门禁保留。

## 2. 范围与非目标

### 2.1 本期范围

仅改造以下来源：

- 中台调拨订单表（`fund-transfer`）。
- 中台测试付款全量信息表（`test-payment`）。

### 2.2 非目标

- 网关入账、网关出账和清结算银行账户表继续使用 3.1.3 的校验与落库契约。
- 不把所有行级错误统一改成过滤；只有本 Spec 白名单中的错误允许过滤。
- 不改变平盘资金性质匹配算法、候选优先级、消费规则或结果确认门禁。
- 不恢复以业务单号作为技术唯一键；继续使用 3.1.3 的 `row_hash/sourceRecordKey` 身份。
- 不要求用户在资金校验前再次确认“来源数据不完整”。
- 不在校验结果页顶部增加持续缺失警告。

## 3. 行分类与过滤白名单

### 3.1 互斥行去向

每个非空物理数据行只能进入以下一种去向：

- `accepted`：校验通过，写入原始表并派生链接行。
- `filtered`：命中过滤白名单，不写原始表和链接表，写入过滤墓碑和异常报告。
- `duplicate-collapsed`：完整规范内容及 `row_hash` 相同，沿用 3.1.3 规则折叠。
- `file-rejected`：文件命中硬错误，当前文件不发生数据库修改。

成功处理的文件必须满足：

`物理数据行数 = accepted + filtered + duplicate-collapsed`

文件被拒绝时，所有行统一计入 `file-rejected` 文件结果，不得同时提交其中的正常行。

### 3.2 调拨单可过滤异常

只有同时满足以下条件时允许过滤：

1. `调拨单号`存在且合法；
2. `交易时间`可解析；
3. `调拨状态`不是`付款成功`，包括但不限于`付款失败`、`已提交渠道`和`剔除`；
4. 付款/收款金额为空或不是合法金额，或者付款/收款币种为空。

稳定错误码：`FT_NON_SUCCESS_EVIDENCE_INCOMPLETE`。

`付款成功`行缺少金额、币种等证据时仍整文件拒绝，禁止通过过滤掩盖可能有效的调拨入腿或出腿。

### 3.3 测试付款单可过滤异常

只有同时满足以下条件时允许过滤：

1. `付款单号`存在且合法；
2. `创建时间`可解析；
3. `源金额`为空或不是合法金额，或者`源币种`为空。

稳定错误码：`TEST_PAYMENT_SOURCE_EVIDENCE_INCOMPLETE`。

目标金额、目标币种及其他字段异常不在本期白名单内，继续整文件拒绝。

### 3.4 始终整文件拒绝

- 文件损坏、表头无法识别或存在多个可识别业务 Sheet。
- 业务键为空、日期无法解析。
- 行内容或行哈希证据冲突。
- 导入期间源文件内容、大小或哈希发生变化。
- 不属于第 3.2、3.3 节白名单的其他校验错误。
- 过滤行的业务单号与当前数据库中的正常记录冲突。
- 同一文件内，过滤行与正常行使用同一业务单号。
- 同批文件中，过滤行与其他待提交正常行使用同一业务单号。

## 4. 自动过滤与导入交互

### 4.1 主流程

1. 用户在“链接表管理”选择“导入原始表”并选择文件。
2. 现有流式导入任务完成文件识别、解析、规范化、校验、去重和行分类。
3. 没有过滤行的文件按 3.1.3 既有流程提交。
4. 有过滤行且没有硬错误的文件，系统自动排除过滤行并直接提交正常行。
5. 同一文件事务内写入正常行、派生链接行、过滤墓碑、来源 revision 和审计证据。
6. 提交完成后，在现有导入结果中显示正常行数、过滤行数、重复折叠数和链接行数。

本期不增加数据库写入前的异常确认弹窗，也不提供以下前置按钮：

- `过滤异常行并继续导入`
- `跳过含异常文件`
- `取消本次导入`

现有导入进度弹窗的取消能力保持不变：扫描、校验及提交前允许取消；进入不可取消的提交阶段后继续沿用 3.1.3 的服务端拒绝取消规则。

### 4.2 导入完成提示

导入结果不是独立页面，仍显示在“链接表管理”的现有导入结果流程中。

存在过滤行时，文件结果必须明确显示：

> 导入完成，已自动过滤异常数据：总数据 N 行，正常落库 A 行，过滤 F 行，重复折叠 D 行，生成链接 L 行。

同时提供：

- `导出异常数据`：调用保存对话框复制本批次异常报告。
- `关闭`：返回链接表管理。

`导出异常数据`为可选操作，不影响已经完成的数据库提交。用户关闭后仍可在存档中心下载相同报告。

没有过滤行时不显示异常导出入口，仅显示现有正常成功结果。

### 4.3 全量过滤

若某文件全部数据行均命中过滤白名单且不存在硬错误：

- 允许提交过滤墓碑和异常报告，但原始表与链接表新增 0 行。
- 文件结果必须使用强提示：`导入完成，但有效落库数据为 0 行，已过滤 N 行`。
- 不得显示为普通“导入成功 N 行”。
- 后续资金校验若本次所需来源在目标月份有效数据为 0 且存在活动过滤记录，必须阻断运行。

### 4.4 多文件与失败语义

- 保持普通来源“整批预检、逐文件独立事务”的 3.1.3 契约。
- 某文件因硬错误或同业务单号碰撞而拒绝，不回滚其他已经成功提交的文件。
- 每个文件结果必须明确标记为正常成功、过滤后成功或失败。
- 报告生成、哈希验证或归档意图失败时，所有含过滤行的文件均禁止写库；不含过滤行的文件可继续沿用既有流程。
- 单文件数据库事务失败时，该文件的正常行、链接行、过滤墓碑和 revision 整体回滚，不影响此前已提交文件。
- 含过滤行的多文件批次必须为各文件建立可独立恢复的密封报告引用；批次汇总报告只能在其覆盖的输入文件均已提交时进入成功存档。部分提交恢复不得保留含未提交文件数据的报告。

## 5. 身份、碰撞与过滤墓碑

### 5.1 业务单号碰撞

3.1.3 已证明同一业务单号可能对应多条不同的合法记录，因此禁止按业务单号删除所有旧原始行或链接行。

过滤行的业务单号若已存在一条或多条正常记录：

- 当前文件返回 `position-filtered-key-collision`；
- 当前文件不提交正常行、过滤墓碑或 revision；
- 现有原始行和链接行保持不变；
- 结果提示用户修正原文件，或先通过现有范围删除能力清理明确范围后重新导入。

禁止采用“保留旧链接并继续过滤”的隐式 fallback，防止资金校验继续使用可能过期的记录。

### 5.2 过滤墓碑

新增只读审计用途的过滤墓碑，至少记录：

- 来源类型、业务单号、ReconID、业务日期和月份。
- 稳定错误码、中文原因。
- 源文件名、Sheet、Excel 行号、`row_hash`。
- 导入操作标识、异常报告文件引用和报告哈希。
- 创建时间、解除时间和解除原因。

墓碑不得进入链接派生、候选匹配、多候选判断或消费占用。

### 5.3 生命周期与幂等

- 相同 `source_type + row_hash` 的异常再次导入时，关闭旧活动墓碑并创建本次审计记录，保证同一精确异常只有一条活动墓碑。
- 不同 `row_hash` 即使业务单号相同，也不得未经证据自动认定为同一记录的替代版本。
- 后续合法正常记录导入成功时，解除同来源、同业务单号的活动墓碑；历史记录不删除。
- 墓碑变化与正常来源数据在同一文件事务内提交。
- 成功过滤、正常导入、墓碑解除和范围删除均提升对应来源 revision；失败、查看和导出不提升 revision。
- 即使某来源某月原始表为 0 行，只要存在活动过滤墓碑，“链接表管理 → 删除”仍必须展示该来源和月份，允许用户按范围解除墓碑，禁止形成只能靠重导才能退出的阻断状态。

## 6. 异常报告与存档中心

### 6.1 报告内容

每个成功包含过滤行的导入批次生成一份供正常导出的不可变汇总 Excel 报告：

- `异常汇总`：文件、来源类型、物理行数、正常行数、过滤行数、重复行数、链接行数和原因统计。
- `调拨异常明细`：调拨过滤行的来源位置、业务键、ReconID、错误码、原因和全部原始列。
- `测试付款异常明细`：测试付款过滤行的来源位置、业务键、ReconID、错误码、原因和全部原始列。

没有对应来源时可省略该明细 Sheet。超过 Excel 单 Sheet 上限时按固定序号拆分，不得截断。

为保证逐文件事务可以独立恢复，sealed ledger 同时冻结文件级审计报告：

- 多个文件含过滤行时，最后一个过滤文件引用完整批次报告，其余过滤文件各自引用只包含本文件数据的审计分片。
- 文件级分片和批次报告都记录所依赖的输入文件路径、SHA-256、大小和报告行数。
- 正常全部提交时，导入提醒仍只提供完整批次报告；极端部分提交恢复时，仅展示并归档已提交文件对应的报告，存在多份时提供多个导出按钮。
- 运行过滤数据合并必须按墓碑冻结的 `report_key` 读取；即使批次报告与文件分片包含相同 `report_row_key`，也不得重复或从错误报告取行。

### 6.2 输出约束

- 长编号、订单号和 ReconID 按文本输出，禁止科学计数法或精度丢失。
- 报告包含全部过滤物理行，不得只导出界面预览。
- 导入结果中的导出和存档中心下载必须引用同一文件字节及同一哈希，不重新计算。
- 完整异常原始内容仅保存在报告中；数据库墓碑只保存轻量索引与审计字段。

### 6.3 归档与保留

- 成功过滤后，输入文件和异常报告归入同一“平盘对账数据处理”批次。
- 报告方向为 `output`，角色显示为“异常数据”，操作类型标记为 `source-import-anomaly-report`。
- 数据库提交前必须建立可恢复的归档意图；提交后归档中断时由现有恢复机制补齐。
- 每个报告输出必须声明其输入依赖；恢复只保留依赖集合全部出现在 side DB 文件级提交凭证中的报告。旧 pending 若缺少依赖声明且只完成部分提交，必须失败关闭，禁止形成误导性成功存档。
- 活动墓碑或 pending run 引用的报告批次保持锁定，避免保留期清理破坏审计链。
- 用户手工导出的本地副本不改变存档状态、墓碑状态或来源 revision。

## 7. 对平盘资金性质校验的影响

### 7.1 运行流程

用户选择 Channel 和月份并点击开始后直接执行资金校验：

`选择 Channel / 月份 → 开始运行 → 直接执行校验 → 自动打开结果确认`

不新增运行前过滤确认，不实现：

- `needs-filtered-source-confirmation`
- `基于当前版本继续校验`
- 过滤来源确认 token 或确认快照

现有待确认运行替换提示、银行范围就绪检查和普通来源缺失硬错误保持不变。

### 7.2 全量过滤阻断

后端根据所选银行行的 FundType 确定本次必要来源，并逐个检查“必要来源 × 目标月份”。若任一组合：

- 有活动过滤墓碑；且
- 有效原始/链接数据为 0；

则返回 `position-source-all-filtered` 并阻断运行，提示具体来源、月份、有效行数和过滤行数。不存在“继续校验”按钮。

禁止先合计多个目标月份再判断：其他月份存在有效行，不得掩盖某个月份“有效 0 行且存在活动过滤墓碑”的状态。

部分来源行被过滤但仍有有效候选时直接运行，不弹二次确认。

### 7.3 运行快照

创建运行时冻结：

- 所选 Channel 和月份。
- 必要来源类型及其 source revision。
- 规则集和调拨账户映射 revision。
- 当前范围内的活动过滤墓碑和异常报告引用。

来源、规则或映射变化后，未确认运行继续沿用现有 stale 规则失效；已确认历史运行保持可读。

## 8. 结果确认与过滤数据导出

### 8.1 结果确认入口

- 资金校验成功后自动打开“平盘资金性质校验结果确认”弹窗。
- 主页面 `结果确认`按钮保留，用于用户点击“稍后”、关闭弹窗或重启软件后重新打开同一个 pending run。
- 重新进入只读取已经保存的运行，不重新执行匹配。
- 无 pending run、run 已 stale 或已确认时，主页面按钮禁用。

### 8.2 `过滤数据导出`

结果确认弹窗始终显示`过滤数据导出`按钮：

- 当前运行包含过滤数据时启用。
- 当前运行没有过滤数据时禁用，并提示`本次运行没有过滤数据`。

导出范围固定为本次运行实际涉及的月份和必要来源类型。Channel 只决定银行范围及必要来源，不用于猜测来源行 Channel。

多个导入报告合并为一个 Excel，并按运行冻结的墓碑 ID 去重。默认文件名：

`时间戳_平盘资金性质校验过滤数据_Run{runId}.xlsx`

工作表至少包括：

- `运行与过滤汇总`
- `调拨过滤数据`
- `测试付款过滤数据`

同一来源明细超过 Excel 单 Sheet 数据行上限时，按`_2`、`_3`固定后缀继续拆分，不得截断或生成超限工作表。

### 8.3 与现有确认门禁的关系

- `过滤数据导出`为可选操作，不是最终确认的前置条件。
- 不更新现有运行的 `exported_at`，不替代普通结果的`导出文件`或合法结果回导。
- 用户未点击过滤导出也可以按现有规则确认。
- 但底层异常报告必须存在且哈希正确；报告丢失或损坏时因审计链不完整阻断最终确认。
- 结果页顶部不显示“本次校验基于部分缺失来源数据”等持续警告。

## 9. 数据库与接口变更

### 9.1 数据库

新增 `position_filtered_source_rows`，保存第 5.2 节的墓碑字段，并建立：

- 来源类型 + 月份 + 活动状态索引。
- 来源类型 + ReconID + 活动状态索引。
- 来源类型 + 业务单号 + 活动状态索引。
- `source_type + row_hash` 活动记录唯一约束。

新增 `position_run_filtered_sources`：

- `run_id`
- `filtered_source_id`
- 报告文件引用及冻结哈希
- 运行时来源 revision 快照
- 绑定运行、过滤墓碑、报告引用和 revision 的完整性哈希

`run_id + filtered_source_id`唯一，运行删除时级联删除关联记录。读取、导出和确认运行时必须复算完整性哈希，关联被改写时失败关闭。迁移必须幂等，并兼容 3.1.3 现代来源身份。

### 9.2 服务与 IPC

- 来源导入结果增加 `filteredRowCount`、原因统计、异常报告文件引用和逐文件处理状态。
- 多文件过滤结果增加 sealed `anomalyReports` 文件级报告集合；每个 output 携带 `requiredInputPaths`，完整批次报告继续通过 `anomalyReport` 暴露给正常导入提醒。
- 每个成功文件结果同时返回提交后的 source revision 和 linked revision，供日志与故障恢复核对。
- 不新增过滤确认 token，也不增加 `filter-and-import/skip-anomaly-files` 应用接口。
- 增加异常报告保存接口；只复制已生成并校验过的报告。
- `status().pendingRun`增加 `filteredRowCount`和`hasFilteredRows`。
- 新增 `position-reconciliation:run:export-filtered`，按运行冻结引用生成合并 Excel。
- 运行快照和普通结果导出增加中性来源 revision 信息，不增加持续警告字段。

## 10. 失败、恢复与可观测性

- 报告生成失败、报告哈希不一致或无法建立归档意图时，当前文件禁止写库。
- 数据库事务失败时，正常行、链接、墓碑和 revision 全部回滚。
- worker 在提交后退出时，沿用 3.1.3 的 checkpoint、input proof 和数据库事实恢复真实结果，禁止重复提交。
- worker 在多文件中途退出时，恢复结果与存档输出只保留已提交输入及其依赖闭合的文件级异常报告；未提交文件从结果报告引用中移除。
- 重启后，已提交过滤批次必须能从墓碑和存档引用恢复导出入口。
- 导入结果和日志至少记录：扫描行、正常行、过滤行、重复行、链接行、文件状态、来源 revision 和报告引用。
- 全量过滤、输出 0 行、同业务单号碰撞和报告损坏必须用户可见，不得只写后台日志。

### 11.2 自动化测试

- 第一条过滤异常不会终止扫描，报告包含全部过滤行。
- 混合文件自动落正常行、过滤异常行，无前置确认调用。
- 白名单外错误和成功调拨缺证据继续整文件拒绝。
- 库内已有同业务单号正常记录时，异常文件整文件拒绝且旧数据不变。
- 同文件、跨文件的正常行/过滤行同业务单号碰撞行为确定且无顺序依赖。
- 完全相同异常重导只有一条活动墓碑，历史审计保留。
- 后续正常导入解除活动墓碑并正常派生链接。
- 全量过滤显示有效落库 0 行，运行时必要来源全量过滤被阻断。
- 报告、数据库事务、归档和 worker 故障均保持原子或可恢复。
- 成功过滤提升 source revision，并使旧 pending run stale；查看和导出不提升 revision。
- 选择范围后直接运行并自动打开结果确认。
- `结果确认`可在稍后、关闭和重启后重入同一 pending run，不重新计算。
- `过滤数据导出`始终显示；无数据禁用，有数据按本次运行范围合并并去重。
- 过滤导出不满足普通结果确认门禁，不更新 `exported_at`。
- 报告缺失或损坏时过滤导出和最终确认均失败关闭。
- 结果页顶部不出现来源缺失持续警告。

## 13. 决策、假设与资金红线

### 13.1 已确认决策

- 异常行采用物理过滤，不写原始表或链接表。
- 过滤在解析/校验后自动执行，不在写数据库前弹确认框。
- 导入完成后提供过滤统计和异常数据导出，导出不是写库前置条件。
- 同业务单号已有正常数据时整文件拒绝，不自动删除旧数据，也不保留旧行后继续过滤。
- 资金校验选完 Channel、月份后直接运行，不增加过滤来源二次确认。
- 结果确认页始终显示`过滤数据导出`；无数据时禁用。
- 结果页顶部不显示持续缺失来源警告。

### 13.2 保守假设

- “异常数据”仅指第 3.2、3.3 节白名单覆盖的问题，不代表未来所有行级错误。
- 过滤报告属于落库审计契约；无法生成可靠报告时宁可拒绝当前文件，也不做无审计过滤。
- 不引入新第三方依赖，优先复用 3.1.3 流式导入、Excel writer、存档与恢复能力。

### 13.3 ⚠️ 资金红线，请人工复核

发布前必须由业务负责人确认：

1. 调拨过滤白名单只覆盖不应形成有效匹配腿的非付款成功记录。
2. 测试付款缺源金额或源币种的记录确实不得参与资金性质校验。
3. 自动过滤并直接落库符合操作预期，导入完成提示足以让用户识别部分数据未落库。
4. 同业务单号碰撞整文件拒绝不会阻断合法的日常补数方式。
5. 六份真实文件的正常候选、金额、币种、方向和严格 1:1 结果不存在非预期变化。
