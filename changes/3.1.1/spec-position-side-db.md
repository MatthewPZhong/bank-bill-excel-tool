# v3.1.1 子规范 1：平盘空旧侧库初始化兼容修复

## 1. 背景

在开发环境首次打开 v3.1.0 平盘对账功能时，状态框可能提示：

```text
平盘对账侧库不完整，已停止初始化以避免历史消费关系丢失
```

已对本次异常文件进行只读检查，确认：

- SQLite 文件可以正常打开，`quick_check` 结果正常。
- 文件包含 v3.1.0 定稿前创建的旧版平盘侧库表结构。
- 所有业务表、运行表、差异表、消费关系表和元数据表均为 0 行。
- 主库只有本次首次初始化生成的 generation 0 bootstrap，不存在已绑定 checkpoint 或待完成操作。
- 该库不存在银行数据、链接数据、运行草稿、差异记录或历史消费关系。

当前实现只要发现侧库缺少新版 checkpoint 历史表，就统一按“侧库不完整”阻断。该规则能保护真实历史数据，但也误拦了上述可证明完全为空的旧版侧库。

## 2. 目标

在不削弱平盘数据防丢保护的前提下，允许“结构可识别且所有相关表完全为空”的旧版平盘侧库完成首次初始化，并与主库 generation 0 bootstrap 建立绑定。

修复后，符合条件的开发环境重新打开软件时应正常初始化平盘对账功能，不再显示“侧库不完整”；任何不能证明为空或不能证明来源安全的侧库仍必须停止初始化。

## 3. 适用范围

本次只调整平盘侧库首次 bootstrap 的兼容判断，涉及：

- 平盘侧库打开前的结构识别。
- 空库证明。
- generation 0 首次绑定。
- 对应的初始化与防丢回归测试。

本次不修改平盘匹配规则、FundType、金额币种口径、结果确认、跨运行消费规则、Excel 契约、UI 页面或业务 IPC。

## 4. 空旧侧库的准入条件

只有同时满足以下全部条件，才允许把已有文件视为“可安全初始化的空旧侧库”：

1. 主库不存在已绑定的平盘侧库 checkpoint。
2. 主库不存在待完成的平盘操作。
3. 主库存在合法的 generation 0 首次 bootstrap，且 identity、generation、token 均可通过现有格式校验。
4. 侧库文件存在且 SQLite 完整性检查通过。
5. 侧库没有可读取的现代 checkpoint，也没有 checkpoint 历史表。
6. 侧库用户表集合与受支持的旧版平盘侧库结构完全一致，不缺少必需表，也不存在未知业务表。
7. 下列所有表均为 0 行：
   - `position_meta`
   - `position_revisions`
   - `position_bank_rows`
   - `position_source_rows`
   - `position_link_rows`
   - `position_account_mappings`
   - `position_runs`
   - `position_run_rows`
   - `position_differences`
   - `position_consumed_sources`
8. 旧运行明细表不存在需要迁移的历史行；新增完整性字段只能在空表上补齐。

判定必须采用 SQLite 结构查询和逐表存在性/行数检查，不得只根据文件大小、创建时间、文件名或单个 marker 推断为空。
完整证明必须执行两次：第一次在事务前预检，避免明显失败的旧库被切换日志模式；第二次在取得
`BEGIN IMMEDIATE` 写锁后、执行任何 `SCHEMA` 或 checkpoint 写入前复检，以关闭外部 SQLite
连接在“预检完成—取得写锁”之间插入数据的竞态。两次任一失败都必须回滚并拒绝接管。

对于首次检查时磁盘上**不存在**侧库文件的新建候选，也不能把 `exists=false` 当成持续成立的事实。
Store 打开候选文件后必须先取得 `BEGIN IMMEDIATE` 写锁，并在任何 `SCHEMA` 写入前证明候选库
不存在非 SQLite 内置的表、索引、视图或触发器。若其它进程在“路径不存在检查—Store 打开文件”
之间抢先创建了任意用户 schema 对象，必须回滚并按侧库缺失/来源不可信阻断；不得把该外部库
接管成新的平盘侧库，也不得在拒绝前持久切换该外部库的 journal mode。正式 `WAL` 切换只能
发生在锁内证明及 schema/checkpoint 初始化事务成功提交之后。

## 5. 初始化行为

满足第 4 节全部条件时：

1. 保留原侧库文件路径，不删除、不替换用户文件。
2. 取得 `BEGIN IMMEDIATE` 写锁，并在同一事务内再次完成第 4 节的全部结构与空表证明。
3. 只有锁内复检通过，才在原空库上补齐当前版本需要的表、索引和空表字段。
4. 使用主库已有的 generation 0 bootstrap 写入侧库 identity、generation 和 checkpoint token。
5. 写入 generation 0 checkpoint 历史记录。
6. 继续执行现有主库/侧库 checkpoint 一致性检查。
7. 初始化成功后提交事务，由现有主进程流程保存正式 checkpoint，并清除首次 bootstrap。

不得在兼容过程中生成业务行、消费关系、差异记录或运行草稿。

全新建库同样必须把“锁内证明候选没有用户 schema → 写入当前 schema/checkpoint”放在同一
`BEGIN IMMEDIATE` 事务中。不存在路径由 Store 自己打开形成的空 SQLite 文件可以继续初始化；
一旦锁内证明发现外部对象，就不得写入任何平盘表或 checkpoint。

## 6. 必须继续阻断的情况

出现以下任一情况时，不得自动迁移、清空、删除、覆盖或重新绑定，继续显示恢复同批备份的错误提示：

- 主库已经存在侧库 checkpoint，但侧库缺失、为空、结构残缺或 checkpoint 不一致。
- 主库存在待完成平盘操作，而恢复证据不完整或不一致。
- 旧侧库任一元数据表、业务表、运行表、差异表或消费关系表存在至少 1 行。
- 侧库只存在旧 marker，缺少完整的受支持旧表结构。
- 侧库缺少任一受支持旧表，或存在未知用户表、未知视图或未知触发器。
- SQLite 完整性检查失败，或读取 schema/行数时发生异常。
- 已有现代侧库试图被另一份 generation 0 bootstrap 接管。
- checkpoint generation、identity、token、父链或 operation token 不符合现有约束。
- 空文件、非 SQLite 文件或被替换的侧库文件。
- 路径首次检查为不存在，但 Store 打开前被其它进程抢先创建且包含任意用户 schema 对象。

失败判断必须保持 fail-closed；检查过程中的异常不得降级为“按空库继续”。

## 7. 数据与兼容性约束

- 不新增数据库表以外的持久化位置，不迁移主库业务数据。
- 不删除现有平盘侧库文件，也不自动生成用户侧备份副本。
- 不为非空旧库提供迁移路径；此类数据必须恢复同一备份批次或另行制定迁移方案。
- 已初始化的现代侧库行为保持不变。
- 新安装且磁盘上不存在侧库时，使用锁内“无用户 schema”证明后的全新建库流程。
- 主库无 checkpoint/bootstrap、磁盘却已有侧库时，继续拒绝接管。
- 回滚到 v3.1.0 时，已补齐的现代侧库仍按 v3.1.0 的既有 checkpoint 契约处理。

## 8. 可观测性

- 自动兼容成功后，平盘状态页应正常读取，不再显示侧库不完整。
- 自动兼容不得显示“已恢复历史数据”等容易误解的文案，因为旧库已被证明没有历史数据。
- 阻断时继续提供异常文件路径和恢复同批软件数据目录的操作提示。
- 成功日志只记录初始化模式：`new`、`empty-legacy-upgrade` 或 `existing`。
- 非空/未知旧库拒绝接管时只记录结构化错误 `code/reason`；不得记录数据库路径、账户、订单或银行明细。

## 9. 验收标准

### 9.1 成功场景

- 完整受支持旧结构且十张相关表全部为空，在合法 generation 0 bootstrap 下可初始化成功。
- 初始化后的 checkpoint 与主库 bootstrap 完全一致。
- 新增 checkpoint 历史表、操作输入表及运行明细完整性字段存在。
- 初始化前后业务表、差异表和消费关系表行数均为 0。
- 完成一次关闭和重新打开后，现代侧库可按正式 checkpoint 正常加载。

### 9.2 阻断场景

- 十张相关表中任意一张存在数据时必须阻断。
- 第一次预检后、取得写锁前由第二连接插入任意一行时，锁内复检必须阻断，且不得创建现代 schema 或 checkpoint。
- 路径检查为不存在后，故障注入在 Store 打开前创建外部表及数据时必须阻断；外部表和数据保持原样，
  journal mode 保持原值，不得创建任何平盘 schema/checkpoint。
- `position_meta` 仅有旧 marker 时必须阻断。
- 缺表、加未知表、加未知视图或触发器时必须阻断。
- 空文件、损坏文件、SQLite 检查失败时必须阻断。
- 主库已有 checkpoint 时，侧库缺失或被替换为空库必须阻断。
- 不相关现代侧库不得被新的 bootstrap 接管。

### 9.3 回归验证

- 现有侧库缺失、空库替换、旧 marker、checkpoint 父链、同 generation 分叉、高 generation 分叉和待完成操作恢复测试继续通过。
- 使用本次异常侧库的隔离副本验证兼容成功，不直接修改正在使用的真实侧库。
- 执行平盘侧库定向单测、position side DB 集成回放、`release-check`、`scan:vars` 和 `check:vars -- --include-minor`。

## 10. 风险与人工复核

⚠️ 资金红线，请人工复核：本次不改变匹配或金额口径，但改变了平盘持久侧库的首次初始化分支。合并前必须确认：

- 自动放行条件要求所有业务、审计、消费和元数据表都为空，不存在只检查部分表的旁路。
- 空表证明在事务前和取得写锁后各执行一次，不存在 TOCTOU 竞态旁路。
- 新建候选也在写锁内证明无用户 schema，不存在“先判断路径不存在、后无条件接管”的竞态旁路。
- 任一检查失败都保持阻断，不会因异常回退为新建空库。
- 已有正式 checkpoint 的环境绝不会进入空旧库兼容分支。
- 隔离副本升级前后行数均为 0，checkpoint 与主库 generation 0 bootstrap 一致。

## 11. 非目标

- 不迁移任何包含历史数据的旧版平盘侧库。
- 不提供“一键删除侧库”或自动清空功能。
- 不修改历史消费关系、运行草稿或差异记录。
- 不处理其它模块的 SQLite 兼容问题。
- 本 spec 不包含提 PR、合并、tag 或 GitHub Release。
