## 2. 审查发现

### R1 · P2：生产 capability / strategy 校验使用待校验数据生成期望，不能拒绝语义漂移

定位：[composition.js:119](/Users/pzhong/Desktop/Project/bank-bill-excel-tool/tmp/worktrees/v3210-execution-descriptors/src/main-process/execution-descriptors/composition.js:119)，相关代码为 119–124 行。对应 **G7-AC-02、G7-AC-04**，Spec §2、§3.8 及 TechDoc §3、§6。

`validateProductionExecutionDescriptors` 从 `compiled.policies` 创建 manifest、capability inventory 和 effective production strategy，随即用同一份 `compiled.policies` 调用各自 validator。私有 action/task authority 仍能限制 canonical action 与绑定关系，但这里没有独立对照“哪些 canonical action 应有 runtime policy、哪些应保持 legacy-only、哪些允许 production”。因此，待校验 descriptor 的错误声明同时成为预期值。

在独立进程中仅替换 Toolbox factory 的返回值，再调用正式 `composeExecutionDescriptors`，没有改动私有 authority、catalog、manifest 文件或源码，得到以下结果：

| factory 返回内容 | 应有结果 | 实际结果 |
| --- | --- | --- |
| 原始 descriptor | 接受 | 接受，49 runtime / 13 production |
| 删除 `toolbox:merge` policy 及相应 Main binding | 拒绝漏注册 | **接受，48 / 13** |
| 将 `toolbox:merge` 改为 production enabled，并填入一致的有效模式/worker 数 | 拒绝未经批准的启用 | **接受，49 / 14** |
| 给原 legacy-only 的 `toolbox:split-large` 增加完整 runtime policy、Main binding 并启用 production | 拒绝扩大后台能力 | **接受，50 / 14** |

后两种情况下，实际 `policyRegistry.assertRunnable(action, { production: true })` 也通过；catalog 对目标 action 仍返回 false，私有 action/task authority 内容保持不变。由此形成 catalog 与实际 runtime 注册/生产状态不一致的合法装配结果。

影响是本分支所承诺的启动阶段独立校验失效：漏注册或误启用不能在创建 generation 前被识别。当前 49/13 基线本身没有漂移；探针也不证明 Renderer 可以注入 descriptor，更没有启动真实业务 worker 或执行生产文件操作。

建议将 compiled action 集合、capability 和 effective production strategy 与独立、经批准的基线比较，并检查 catalog 与 compiled 集合的一致性。不能先由待校验 descriptor 生成 expected 再自证。保留现有未知 action 与非法 action/task pair 的拒绝逻辑，补充上述三种负向注册回归。

证据：[可执行探针](review-2026-09-21-evidence/authority-drift.cjs)、[复现输出](review-2026-09-21-evidence/authority-drift.json)。探针退出码 0 表示成功复现“错误配置被接受”，不表示该负向验收通过。执行方式：

### R2 · P3：非生产关闭观察在未提供 dispatch hook 时由允许执行变为拒绝

定位：[runtime.js:77](/Users/pzhong/Desktop/Project/bank-bill-excel-tool/tmp/worktrees/v3210-execution-descriptors/src/main-process/background-execution/runtime.js:77) 与 [contract.js:300](/Users/pzhong/Desktop/Project/bank-bill-excel-tool/tmp/worktrees/v3210-execution-descriptors/src/main-process/execution-descriptors/contract.js:300)。对应 G7-AC-02、G7-AC-05 的兼容性要求。

给 runtime 设置 `carrierClosureActionKeys: ['toolbox:merge']`，使用 `production: false`、有效 operation context，且不提供 `beforeCarrierDispatch`，旧 runtime 会给 Supervisor 传 undefined。原 Supervisor 只对 production 关闭观察强制要求 dispatch hook，因而该非生产请求可以进入 worker adapter。

新 runtime 始终传入聚合后的 `beforeCarrierDispatch` 函数；Supervisor 调用它后，contract 发现该 action 的 `beforeDispatch === null` 即抛出 `CARRIER_DISPATCH_BINDING_REQUIRED`。探针用可控 adapter 在启动点抛错，不创建真实 worker：旧实现 `spawned: 1 / PROBE_REACHED_ADAPTER`，新实现 `spawned: 0 / CARRIER_DISPATCH_BINDING_REQUIRED`。production=true 时，两边仍先拒绝未启用的 Toolbox policy。

此项影响非生产载体观察/测试入口，当前 Main 只为 BizOP 设置 closure action keys 且存在本域 hook，没有证据说明现有用户业务路径受损，故列为非阻断 P3。若保持原契约，应显式保留该非生产路径，同时继续强制 production dispatch authority；不能把所有缺 hook 情形统一改成 no-op。

证据：[旧/新 runtime 差分与边界探针](review-2026-09-21-evidence/runtime-diff.cjs)、[原始输出](review-2026-09-21-evidence/runtime-diff-output.txt)。
