## 额外探针与结论边界

### 执行恢复期间，外部程序直接改写 index

合成 probe 通过真实 dispatcher/worker 和测试 `fsImpl.renameSync` hook，在 execute 最后移除一个合法记录后、结束 snapshot 前追加一个未知 owner 的有效 journal entry。`toolbox-output-publication.js:2147–2149` 将这份结束 snapshot 的 digest 返回，dispatcher `:162–163` 将它用于下一步 preflight；新增 entry 未重新经过 Main identify，随后新发布成功，下次显式恢复才返回 `PUBLICATION_RECOVERY_OWNER_UNKNOWN`。因此，本次证据不支持“执行期间任意外部改写都已覆盖”的更强声明。

这次注入绕过正常应用的单实例锁和唯一 dispatcher FIFO；本轮未找到正常生产入口会并发直接追加该 index。因此未将其列为生产 P2 finding，也未把该 probe 的 exit 0 解释为安全断言通过。它记录的是容错边界；若后续正式支持外部恢复材料同步或多个 index writer，应针对该情形重新明确并验证授权闭环。

探针：[race-probe.js](evidence/review-2026-09-20/race-probe.js)、[race-worker.js](evidence/review-2026-09-20/race-worker.js)、[实测输出](evidence/review-2026-09-20/external-index-probe.log)。脚本引用文首的冻结快照，命令为 `node <该证据目录>/race-probe.js`。

### receipt 缺失后的不可变身份被直接改写

另外用临时 SQLite 构造 receipt 已清理、acknowledged 尚未写入的窗口，再直接改写 Archive batch 的不可变 parentRunId；重试确认仍可成功。基线原路径完全没有新增的 Archive proof 复验，比本分支更宽；未找到合法业务入口改写该身份。本轮未将人为破坏不可变 DB 身份的结果当作新增生产回归，也未据此推断资金损失。

### transport-error 与 deferred 的保留标志

交叉核查了 dispatcher 重抛原 transport error 时未增加保留标志的候选。BizOP export 持有 read admission，写 HOLD/RECOVERY_BLOCKED 的恢复路径需要 exclusive admission；本次 borrowed capability 也不会因自身 `closed=false` 自阻塞。未证明正常路径下本任务发生此 deferred，且 exporter 不存在仅因该标志缺失而无条件清理 generation 的 finally。后续 settlement 仍要求 durable fact 与 closure，故没有足够证据上报误清理缺陷。
