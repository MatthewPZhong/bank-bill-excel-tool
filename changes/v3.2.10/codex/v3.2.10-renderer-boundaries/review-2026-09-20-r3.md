## 2. 新增发现

### R3-01 · P2 · 配套写部分成功后，仍展示并使用已删除的发生额规则

**代码位置：**[configuration.js:4620](/Users/pzhong/Desktop/Project/bank-bill-excel-tool/tmp/worktrees/v3210-renderer-boundaries/src/renderer/dialogs/configuration.js:4620)，定位范围 4620–4626。关联：规则编辑器使用当前缓存的 [configuration.js:4641](/Users/pzhong/Desktop/Project/bank-bill-excel-tool/tmp/worktrees/v3210-renderer-boundaries/src/renderer/dialogs/configuration.js:4641)。

将「按字段区分发生额」从“是”改为空时，处理器依次执行 `saveBillSplitAmountRules([])` 和 `saveBillSplitMeta(...)`。本轮统一 `runWrite` 后，把 `currentAmountRules = []`、隐藏规则管理按钮和重新计算控件状态，都延迟到了整条写链最终成功的 `onSuccess`。

当第一步清空规则成功、第二步元数据保存失败时，Main 已完成的规则删除不会回滚，但仍存活的窗口保留旧 `currentAmountRules`。失败告警关闭后，界面显示未启用按字段规则，却仍显示规则管理按钮、禁用按正负号选择；再打开管理窗还会带入已删除的旧规则。

**最小复现：**

1. 使用真实拆分管理工厂，初始化已有的按字段发生额规则。
2. 将「按字段区分发生额」改为空。
3. 第一条规则保存成功并实际清空有状态 API 存储；第二条元数据保存返回失败。
4. 确认错误告警，再点击仍显示的「发生额映射关系管理」。

| 可观察事实 | R2 对照 | 当前 R3 |
| --- | --- | --- |
| 规则存储 | `[]` | `[]` |
| 规则管理按钮 | 隐藏 | **仍显示** |
| 按正负号选择 | 可用 | **仍禁用** |
| 重新打开规则管理 | 不再有此入口 | **编辑器仍带入旧“入金”规则** |
| 第二步失败反馈 | 此旧路径未提示该失败 | 当前正确显示失败，但没有同步已成功的第一步 |

因此这是本轮将状态更新移到整体成功分支后产生的新回归，不是上轮删行问题尚未修复。R2 的错误反馈不足不影响上述状态一致性对照，也不建议恢复其忽略错误的行为。

**持久化依据：**[main.js:9182](/Users/pzhong/Desktop/Project/bank-bill-excel-tool/tmp/worktrees/v3210-renderer-boundaries/src/main.js:9182) 与 [main.js:9219](/Users/pzhong/Desktop/Project/bank-bill-excel-tool/tmp/worktrees/v3210-renderer-boundaries/src/main.js:9219) 分别保存规则和元数据；[template-repository.js:835](/Users/pzhong/Desktop/Project/bank-bill-excel-tool/tmp/worktrees/v3210-renderer-boundaries/src/backend/database/template-repository.js:835) 的规则保存自行 `COMMIT`，两次 IPC 不在同一事务中。主审另用实际仓储函数和内存 SQLite，在第二步注入数据库拒绝写入：最终规则确为 `[]`，元数据仍保留旧目标 `[1]`，证明第二步异常不会恢复规则。这个仓储探针没有加载产品 Main，也没有访问真实数据库。
