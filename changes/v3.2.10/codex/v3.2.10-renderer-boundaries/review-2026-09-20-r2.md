## 2. 仍需处理的问题

### RR01 · P2 · 拆分管理的单行删除仍绕过提交锁，旧预检可在窗口关闭后续发删除

**位置：**[configuration.js:4333](../../../../src/renderer/dialogs/configuration.js:4333)、[删除确认回调 :4359](../../../../src/renderer/dialogs/configuration.js:4359)。关联预检 :4322、无合并组时直删 :4364。

整改新增的 `rowCountSaving` 只覆盖 `saveBillSplitRowCount`。同一 `createBillSplitRowsDialog()` 内的 `deleteBillSplitRow`、删除确认层以及预检续接没有共享提交锁或句柄存活校验。两个独立真实 Electron 工厂序列已确认：

1. **写入中重复删除和关闭。** 点击某行删除，预检返回需要确认；延迟真实工厂所调用的删除 API 回包，再连续两次普通点击确认。相同的 `{templateId:7, seqNo:1}` 发送 **2 次**，确认按钮没有禁用；父 handle 在写入中 `close()` 返回 **`closed`**。
2. **已关闭视图仍发起新写入。** 点击删除后让 `previewDeleteBillSplitRow` 等待；关闭原管理窗，再打开其他窗口；旧预检返回 `dissolvedGroups: []` 后，旧处理器继续发送一次 `deleteBillSplitRow`。此时 `oldOpen=false`，新窗口仍为顶层。

后者发生在删除命令尚未发送之前，不是已提交业务必须继续结算的情形。它使用户关闭的旧编辑会话仍能在后台改变配置；前者也违反 G3-AC-03 / 14 的 busy 关闭和单次提交合同。测试 API 只记录调用，未删除真实模板或配置。

**归类：**R06 相邻入口的未完成治理。原报告明确复现的“收纳”和“增减份数”已经修复，本轮不重复声称这些旧反例仍失败。同一删行探针在 R1、R2 快照的结果一致，不能称为本轮整改新引入。

**建议：**把删行纳入对应父子 handle 的写入资格和同步防重；预检返回后核对原会话仍有效，关闭/替换后的旧视图不得开始新的删除；已发送删除则保留真实结算并限制旧 DOM 续接。用真实工厂覆盖有合并组确认、无合并组直删、预检迟到、重复点击及失败重试。

**证据：**[独立 Electron 探针](review-2026-09-20-r2-evidence/review-modal-r2-probe.cjs)、[R2 输出](review-2026-09-20-r2-evidence/review-modal-r2-probe-output.log)、[R1 对照](review-2026-09-20-r2-evidence/review-modal-r2-before-output.log)。两次进程均退出成功，表示两种缺陷已确认；不是产品测试通过。探针记录的“份数变化后未提交行内草稿被重绘”在两版也一致，未作为本次整改回归列入发现。

### RR02 · P3 · 状态读取已恢复，资金对账／ReconID 仍显示旧读取失败

**位置：**[bank-statement.js:105](../../../../src/renderer/controllers/bank-statement.js:105)，同类 [recon-id-fix.js:94](../../../../src/renderer/controllers/recon-id-fix.js:94)。关联两域 `render()` 消费 `resultFeedbackInvalidated`、`enter()` 使用静默刷新。

页面可见时收到确定失效，立即重绘已消费失效标记。若随后自动 `sessionStatus()` 读取失败，catch 显示错误，却没有保留“成功恢复后需要替换该读取错误”的事实。用户离开再进入，状态读取已经成功、`enter()` 返回 `ready`、按钮资格恢复，但 `updateStatus:false`、`lostResult:false`、失效标记为 false，错误文案保持不变。

已在两域分别通过真实 controller、Main handler/SQLite harness、一次状态读取故障注入复现：

```text
bank enter() → { status: "ready" }
仍显示：资金对账状态读取失败：暂时无法读取

recon enter() → { status: "ready" }
仍显示：对账单修复状态读取失败：暂时无法读取
```

**影响与分级：**这是恢复状态与提示不一致，容易使用户误认为重新进入仍未恢复；没有证据显示它使数据错误、导出越权或按钮不可用，因此按 P3 反馈缺陷记录。故障是受控注入，不代表实际产品已经发生该 IPC 故障。对应 Spec §4“进入时同步按钮和状态”；保留成功/欢迎反馈不应保留已恢复的读取错误。

**归类：**上轮未覆盖、R1 已存在的恢复反馈缺口，不是本轮 R03/R05 修复回归。R1/R2 两个快照各两方向均可复现。对整个 `11086a3c` 基线未做完整行为对照，尤其 ReconID 旧代码已有静默刷新，故不将两域一概称为本分支新引入。

**建议：**单独跟踪状态读取错误，下一次有效成功读取后清除/替换该错误；保留未命中域原成功反馈，避免每次导航都无条件重写文案。

**证据：**[独立 7 项探针](review-2026-09-20-r2-evidence/renderer-boundaries-r2-scenario-review.test.js)、[R2 日志：5 PASS / 2 FAIL](review-2026-09-20-r2-evidence/renderer-boundaries-r2-scenario-review.log)、[R1 对照：2 FAIL](review-2026-09-20-r2-evidence/renderer-boundaries-r1-scenario-recovery-check.log)。失败的仅是恢复后错误文案撤回断言，`ready` 断言均先通过。
