## 1. 目标与需求清单

本版本完善 VCC 财务 OP 的导入和人工核查流程，并修复安装版读取内置结果模板时的误报。

| 编号 | 需求 |
| --- | --- |
| VCC-329-01 | 支持一个 XLSX 工作簿包含多张业务 Sheet，包括同类型和混合类型 |
| VCC-329-02 | 在结果确认页左下角增加【导出待确认表】 |
| VCC-329-03 | 一次导出一个工作簿；Sheet1 对应确认页全部主体的完整表格，差异关联原表放在后续 Sheet |
| VCC-329-04 | 使用原生另存为对话框，由用户选择文件位置和名称 |
| VCC-329-05 | 数据管理中的结果表在确认归档前显示“待确认” |
| VCC-329-BF01 | 修复 ASAR 内置结果模板被误判为“读取期间发生变化”的问题 |

本版确定以下业务口径：

- 确认页不增加主体选择。
- 待确认表包含确认页展示的全部主体。
- 默认文件名为 `{YYYY-MM}_VCC财务OP校验待确认表.xlsx`，单主体与多主体使用同一规则。
- Sheet1 的字段、主体顺序、明细顺序、调整行及汇总顺序，以确认页为准。
- 系统财务 OP 的完整九币种快照必须在同一 Sheet 内成立，不增加跨 Sheet 碎片重组。
- “待确认”是结果状态的展示文案，沿用现有 `calculated / archived` 数据库状态。

## 2. 多 Sheet 导入

### 2.1 支持范围

支持以下输入：

1. 一个文件、一张业务 Sheet。
2. 一个文件、同类型多张业务 Sheet。
3. 一个文件、不同类型的业务 Sheet。
4. 多个文件，各文件包含一张或多张业务 Sheet。

业务类型按正式表头、列数、列顺序和既有识别规则确定，不根据 Sheet 名称推断。

| 原表类型 | 当前正式列数 |
| --- | ---: |
| VCC 充值清退明细 | 49 |
| VCC 费用及换汇明细 | 36 |
| VCC 通道明细 | 38 |
| 移除归档 Pending 账单 | 46 |
| 系统财务 OP | 16 |

新增导入继续拒绝旧 48 列 Pending 模板。历史数据的读取兼容不等于允许旧模板重新导入。

### 2.2 逐 Sheet 预检

提交业务数据前，列出每张 Sheet 的：

- 文件名、Sheet 名、工作簿内顺序及隐藏状态。
- 识别类型、表头原行号。
- 是否需要补充主体。
- 可导入、空白、无法识别或结构错误的结果及原因。

处理规则：

| 情况 | 处理 |
| --- | --- |
| 完全空白 Sheet | 自动跳过，在摘要中列明 |
| 合法业务 Sheet | 纳入导入，包括隐藏 Sheet |
| 非空且无法识别的 Sheet | 默认阻止提交；用户明确排除说明页后可继续 |
| 近似正式表头但缺列、错列、旧版模板 | 结构错误，不能作为说明页排除后绕过 |
| 同一 Sheet 出现多个独立业务表块 | 拒绝该输入，定位 Sheet 和表头位置 |
| 工作簿损坏、Sheet 引用缺失或读取失败 | 拒绝，不能按空表处理 |
| 排除说明页后没有任何业务 Sheet | 不创建导入任务，提示没有可导入数据 |

说明页排除只作用于当前导入计划，不修改原始工作簿。

分类按固定顺序执行：先匹配完整正式表头，再检查旧模板、近似表头和疑似表头证据，最后才允许归为 `unrecognized`。五类表采用 TechDoc §2.2.1 的固定匹配阈值、特征列和判定顺序；不能仅因精确匹配失败，就给出“可排除说明页”。无法唯一确定类型但命中业务表头证据的 Sheet 归为 `invalid`，展示候选类型和具体行列，由用户修正输入。

预检中的 `ready` 只代表结构可读，不代表每条业务数据均合格。表头和表块结构错误与业务行、主体快照错误分别按 §2.4 处理。

### 2.3 主体处理

有主体字段的原表继续使用正式字段。

通道原表的补充主体按“文件 + Sheet”绑定。同一工作簿的不同通道 Sheet 可以指定不同主体；允许批量填入相同主体，但每张通道 Sheet 在提交时都必须有明确主体。

这里的主体补充属于导入预检，不在结果确认页增加主体选择。

### 2.4 分组、幂等与事务

- Sheet 是读取和错误定位单位。
- 导入记录继续按“批次 + 原表类型”组织。
- 同批次同类型的多个 Sheet 进入同一业务导入组。
- 同一工作簿同类型的多个 Sheet 共用该类型的一条文件来源记录。
- 同一工作簿包含不同类型时，各类型来源记录引用同一个已冻结的原始文件。
- 跨 Sheet 的同一业务键参与现有幂等和冲突判定，不因 Sheet 不同重复计账。
- 成功行、幂等跳过、异常过滤和回滚数量沿用既有业务规则。

可在预检发现的结构性错误必须在业务写入前全部发现。业务写入继续使用现有按来源类型分组的事务边界；某组失败时，已经提交的其他组必须在结果中明确列示。

以下为错误处置合同；“其他组”指同批次其他原表类型，“当前组”包括该类型的全部文件和 Sheet。

| 编号 | 情况 | 拒绝或过滤单位 | 其余数据、计数与状态 |
| --- | --- | --- | --- |
| IE01 | 损坏文件、缺失 Sheet 引用、坏表头、旧 Pending、疑似表头无法判定、独立多表块 | 整个导入计划，业务写入前拒绝 | 不创建业务批次、导入记录或有效事实；只展示预检诊断，不计入业务回滚数 |
| IE02 | 非空说明页未排除、通道 Sheet 主体未补齐 | 暂停整个计划的提交 | 用户修正后可重试预检计划；排除后无业务 Sheet 时不创建任务 |
| IE03 | 结构可信的普通明细存在行级格式错误、重复或业务冲突 | 沿用既有 mapper、幂等分类及类型组事务规则 | 错误定位至原 Sheet/行；保留既有成功、跳过、异常过滤、冲突和回滚计数，不改为工作簿整体事务 |
| IE04 | 系统 OP 结构可信，可确定主体，但其候选快照缺币种、币种重复或业务字段不合法 | 当前系统 OP 组内的该主体 | 过滤该主体在组内所有 Sheet 的候选；其他合法主体和其他类型可提交。格式异常按主体校验单位计数，不按九条币种行计数 |
| IE05 | 系统 OP 表块可信，但个别行缺少主体、无法归属主体 | 该 Sheet 的未知主体异常单位 | 不猜主体、不从别的 Sheet 补齐；保留既有可识别主体的校验结果，异常按该 Sheet 的未知主体单位计数 |
| IE06 | 写入阶段发生不能局部过滤的组级错误，Importer 已返回失败记录 | 当前原表类型组 | 当前组按既有事务回滚；其他组继续，批次为 `completed_with_errors`，明确列出已提交、过滤、回滚数量 |
| IE07 | 取消、Worker 退出或未被 Importer 收口的运行异常 | 当前未提交事务及尚未执行的组 | 停止后续组；保留已提交组，沿用现有失败/中断收口及 `partialCommitted`，不把已提交数据计成已回滚 |

一个组有新增成功并伴随幂等跳过或异常过滤时为 `success_with_skips`。系统 OP 无新增且只有幂等跳过时为 `all_skipped`；无新增且有异常时为 `failed_validation`，含冲突时按既有优先级为 `failed_conflict`。批次没有失败组时沿用 `success`，即使某组是 `success_with_skips`；界面仍必须显示“含跳过/异常过滤”及具体数量，不能展示为“全部数据成功”。

### 2.5 系统财务 OP

沿用现有账期、主体、快照和九币种完整性规则：

```text
AUD / CAD / CNY / EUR / GBP / HKD / JPY / SGD / USD
```

允许多张 Sheet 各自包含完整、合法的主体快照。一个 Sheet 内可包含哪些主体和快照，继续由既有系统 OP 解析合同决定。

同一快照的九币种被拆到不同 Sheet 时，按快照不完整处理，过滤范围为 §2.4 的 IE04；不跨 Sheet 补齐、不将重复币种求和、不把不同快照合成一份。同一主体即使在另一张 Sheet 有完整候选，也不能用它掩盖本组内该主体的不完整候选。表头重复、独立表块或无法信任的表块边界适用 IE01，在业务写入前拒绝整个计划。

确定性样例：新账期、没有已有重复或冲突，Sheet A 含甲主体完整九币种，Sheet B 含乙主体八币种，Sheet C 含一条合法充值明细。系统 OP 组应为 `raw_count=2`、`inserted_count=1`、`format_error_count=1`、`skipped_count=0`、`rolled_back_count=0`、`success_with_skips`；充值组导入一条并为 `success`；批次沿用 `success`，摘要明确乙主体被过滤。业务读取阶段另计 18 条数据行，不重复累计预检扫描，也不能与两个快照校验单位混算。若 B 是缺列或独立多表块，则适用 IE01，三个 Sheet 均不得开始业务写入。

### 2.6 进度与追溯

进度至少区分：

1. 预检文件与 Sheet。
2. 读取指定文件、指定 Sheet。
3. 校验并提交原表类型。
4. 汇总导入结果。

物理文件数、业务 Sheet 数、实际读取行数分别统计；预检扫描与提交读取分别显示阶段进度，不叠加成业务数据量。来源继续保留原 Sheet 名和原行号，不能用合并后的行号替代。

原文件、来源类型、Sheet 定位及逐 Sheet 通道主体必须在业务写入前持久化；重启后不依赖旧窗口的预检缓存或文件名猜测。具体保存位置、绑定身份和崩溃恢复顺序见 TechDoc §3.4。恢复只保留并协调已提交数据，不自动重放尚未执行的业务组。

## 3. 待确认表导出

### 3.1 入口与交互

确认弹窗左侧操作区顺序为：

```text
【导出待确认表】 【修改结果】
```

右侧保留：

```text
【关闭】 【确认归档】
```

不增加主体选择框、主体选择弹窗或按主体拆文件步骤。

可导出条件：

- 当前结果存在，状态为 `calculated`。
- 页面结果版本与数据库一致。
- 当前输入仍与该结果对应。
- 没有正在进行的互斥操作或未完成的调整保存。

流程：

```text
点击导出待确认表
→ 原生另存为
→ 核验输出位置
→ 核验结果及输入版本
→ 生成结果快照和差异原表附页
→ 校验文件
→ 保存成功
```

导出过程中锁定会改变当前结果的操作。取消、失败或成功后都留在结果确认页；成功导出不等于确认归档。

已归档结果不提供本入口，继续使用正式结果表导出。

### 3.2 文件名

默认文件名：

```text
{YYYY-MM}_VCC财务OP校验待确认表.xlsx
```

示例：

```text
2026-08_VCC财务OP校验待确认表.xlsx
```

用户可在另存为时修改文件名和位置。覆盖已有文件必须经过明确的覆盖确认；目标文件在生成期间发生变化时，停止发布并提示重新保存。

禁止将本次导出保存到应用数据库及关联文件、存档中心受管原件、内置模板和任务内部资源所在的受管路径；也禁止覆盖本次结果已知的外部原始输入文件。普通用户导出文件可以在明确确认后覆盖。覆盖确认不解除上述保护。Main 在开始生成前和最终保存前均核验路径及文件身份，不能通过别名路径绕过；不为本功能扫描用户所有目录或推测无关文件的用途。

### 3.3 Sheet1：待确认表

工作簿第一张 Sheet 固定命名为 `待确认表`。

以导出请求对应版本的确认页为内容合同，包含全部主体。每个主体的结构为：

1. 主体标题。
2. 该主体表头。
3. 当前页面顺序的全部明细行和人工调整行。
4. `期初财务OP`。
5. `当月计算财务OP`。
6. `系统财务OP`。
7. `差异`。

固定十四列：

```text
主体 | 大类 | 分类 |
AUD | CAD | CNY | EUR | GBP | HKD | JPY | SGD | USD |
调整值 | 调整原因
```

具体要求：

- 主体顺序、行顺序与确认页一致。
- 保留分类中的来源提示和“人工调整”标识。
- 保留已保存的调整值、调整原因及生效金额。
- 页面显示的空值占位和差异为零时的 `-` 保持一致。
- 保留币种差异提示及汇总行区分。
- 不只导出差异行，也不使用正式结果表的其他汇总顺序替换确认页顺序。
- 页面按钮、确认复选框等操作控件不写入工作簿。

结果调整通过独立弹窗保存。调整弹窗打开或保存进行中时不能同时导出；不隐式保存未提交的编辑。

为区分同账期的不同导出版本，在 `待确认表!A1` 的批注中记录结果 ID、结果 revision、输入指纹、导出时间和应用版本。批注不改变主体标题、十四列或行序，不增加说明 Sheet，也不包含本机完整路径。此项为本次评审采纳的追溯增强，具体字段见 TechDoc §6.5。

### 3.4 差异判定

对全部主体逐币种判定当前生效差异，复用 `isEffectiveDifferenceZero()`。

不得：

- 使用调整前的初始差异。
- 根据单元格显示的小数位判零。
- 将不同主体或币种互相抵销。
- 新增浮点容差。
- 在导出时自动重算并替换用户正在核对的结果。

全部主体全部币种均无差异时，仅生成一张 `待确认表`。

### 3.5 差异关联原表附页

附页输出的是参与当前结果、与差异坐标相关的有效原始记录，用于人工核查，不代表系统已经定位具体错误流水。

分组依据：

```text
主体 + 币种 + 原表类型 + 原始结构版本 + 表头结构
```

来源选择：

| 来源 | 关联规则 |
| --- | --- |
| 充值清退、费用换汇、通道 | 当前有效事实的主体和计算使用的统计币种 |
| Pending | 当前计算使用的流水币种或 Pending 币种命中差异币种 |
| 系统财务 OP | 当前采用的主体快照中，该币种对应的原始记录 |

补充规则：

- Pending 同一行涉及两个有差异币种时，可以分别出现在两个币种附页。
- 同一来源行在同一分组内只输出一次。
- 不按整行内容去重，不误删内容相同的两笔合法记录。
- 不额外过滤金额为零的关联有效行。
- 不包含幂等重复、被过滤或已回滚的数据。
- 历史币种兼容只用于匹配和核验，附页保留原始币种值。
- 不同原始结构必须拆页，历史 Pending 不能被改造成新表头后冒充原表。
- 保留原表表头、列顺序和原始数据值，不追加业务列。

期初初始化和人工调整保留在 Sheet1，不伪造相应“原表”。某类来源经核验确实为空时不建空附页；来源丢失、损坏或无法验证时必须停止导出。

先按持久来源关系确定读取依据：已有绑定或曾绑定原件时，必须验证指定原件，不能用同时存在的 `raw_json` 或备用数据掩盖损坏。只有历史合同明确允许且可以证明从未绑定的来源，才允许读取合法历史值；来源模式不明时停止导出。

提取原表前，必须从同一数据库快照独立确定每个附页应有的记录身份、顺序和数量，再与实际提取结果、最终 XLSX 逐层比较。不能用“实际只取到了多少行”反推期望行数。漏行、多行、同组重复、漏掉一类来源或错分币种、分页均必须阻止发布。

### 3.6 Sheet 命名、分页与数据完整性

正常名称为：

```text
{主体}-{币种}-{校验原表名称}
```

名称非法、超长或重名时，使用可读短名和稳定后缀；完整名称通过表头批注保留。工作表名不超过 31 字符，按大小写不敏感方式保证唯一。[Microsoft 工作表命名规则](https://support.microsoft.com/en-us/excel/rename-a-worksheet)

附页每页保留一行原表表头，最多容纳 1,048,575 条数据，超限按原顺序续页。Sheet1 不拆成多个结果 Sheet；如果完整确认页超过 Excel 行容量，明确拒绝导出，不能丢弃主体或明细。[Microsoft Excel 容量限制](https://support.microsoft.com/en-us/excel/excel-specifications-and-limits)

长编号、前导零、原始文本和金额不得因类型推断失真。以 `=` 等字符开头的原始文本不得变成公式。

原始字面值、存储类型和显示格式分别处理，遵循 TechDoc §6.3、§8.3.1 的固定对照表。真实公式不得在导出中重算；既有导入禁止的公式、错误值继续拒绝，历史合法缓存值只按明确规则输出。历史数据未保存的类型或格式不能猜测补造，也不能宣称恢复了原 Excel 的全部样式。

待确认导出新增 VCC 业务编排层，复用从现有 Biz OP Writer 抽取的共享有界流式写入组件，底层沿用项目锁定的 ExcelJS `4.4.0`。共享组件负责写入、缓冲和可取消等待；确认页布局、差异附页及内容校验由 VCC 负责。默认直接流式生成 XLSX，不额外增加逐 Sheet XML 落盘层；原表分流和校验清单的任务暂存仍按 TechDoc 执行。共享抽取须保持既有 Biz OP 导出行为，并通过慢盘、取消和大数据验收。

## 4. 数据管理中的结果状态

“数据管理 → 结果表 → 处理状态”采用以下规则：

| 业务情况 | 数据库结果状态 | 显示文案 |
| --- | --- | --- |
| 已计算，尚未确认归档 | `calculated` | 待确认 |
| 保存结果调整后，尚未确认归档 | `calculated` | 待确认 |
| 导出待确认表成功、取消或失败 | `calculated` | 待确认 |
| 已勾选确认复选框，但尚未成功归档 | `calculated` | 待确认 |
| 确认归档成功 | `archived` | 已归档 |
| 归档失败且事务回滚 | `calculated` | 待确认 |
| 解归档成功 | `calculated` | 待确认 |

没有结果时保留空态，不生成一条虚假的“待确认”结果。

该需求仅调整结果表的状态展示。原表和校验表继续使用各自的数据集状态合同。

## 5. Bugfix：VCC-329-BF01

### 5.1 问题来源与现象

来源为用户提供的[ASAR 模板报错排查对话](https://chatgpt.com/share/6aabe483-52bc-83e9-ae3d-bf70485937b8)。

对话描述了 `3.2.8` 安装版读取内置结果模板时，出现 `result-template-contract-mismatch`，提示“读取期间模板文件发生变化”。

代码核验表明，模板加载器比较读取前后的：

```text
dev / ino / size / mtimeMs / ctimeMs
```

Electron 为 ASAR 内文件生成的 `stat` 信息不能用作普通磁盘文件的稳定身份。该机制会使模板字节未变时也被拒绝。[Electron ASAR 文档](https://www.electronjs.org/docs/latest/tutorial/asar-archives#fake-stat-information-of-fsstat)

### 5.2 修复要求

对应用内置的固定结果模板：

1. 读取模板 Buffer。
2. 校验该 Buffer 的固定 SHA-256。
3. 使用同一 Buffer 解析并验证模板结构。
4. 缓存身份使用规范化模板路径和内容哈希。
5. 不再用 ASAR 的 inode、时间戳等字段判定模板读取稳定性。

以下约束继续成立：

- 模板文件和固定哈希不因本修复而改变。
- 表头、范围、样式锚点等模板校验继续执行。
- 模板缺失、无法读取、哈希不符或结构错误必须阻止导出。
- 修复范围限定于内置固定结果模板，不放宽导入文件、存档原件和输出目标的完整性校验。
- 正式结果导出与待确认表导出都必须覆盖对应回归。

## 6. 数据兼容与副作用

混合类型工作簿需要允许多个业务来源绑定同一个原始文件。现有存储合同对此有唯一性限制，因此本版包含 VCC 存储合同 `v2 → v3` 的来源绑定迁移。

迁移必须：

- 保留现有业务数据、来源 ID、哈希、结果、调整和归档关系。
- 原子更新索引、合同版本及写保护。
- 迁移期间关闭业务写入口；提交前失败回滚持久结构，提交后连接初始化失败则保留已提交的新合同。两者均关闭能力状态不确定的连接，重新核验版本并恢复连接后才能开放相应入口，不能将已提交 v3 降级。
- 兼容历史单来源文件的读取和恢复。
- 阻止不支持新合同的旧程序写入。
- 对历史非空 v1 数据继续使用既有维护迁移流程，不在普通启动中清空或重建业务数据。

“待确认”文案本身不需要新增数据库状态。

待确认导出不写入结果、调整、输入 revision 或归档状态，不登记为正式结果文件批次，不触发确认归档。允许产生用户选择的输出文件、任务临时文件和操作日志。
