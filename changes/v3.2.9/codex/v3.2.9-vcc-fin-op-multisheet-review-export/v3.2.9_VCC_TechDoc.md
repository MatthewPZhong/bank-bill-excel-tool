## 1. 架构与实施边界

采用以下实现分工：

| 子系统 | 实现职责 |
| --- | --- |
| Workbook Reader | 工作簿预检、显式选择 Sheet、共享读取上下文 |
| Import Service / Importer | 按类型分组、逐 Sheet 主体、幂等与来源记录 |
| Storage Contract / Archive Lineage | v3 迁移、一个原件对应多个来源、保护与恢复 |
| 共享确认页投影 | 同时服务页面和 Sheet1，统一字段、行序与显示值 |
| Review Export Planner | 版本校验、差异坐标、有效来源和附页计划 |
| 共享有界 XLSX Writer | 从现有 Biz OP Writer 抽取；负责流式写入、背压、可取消等待及错误收口 |
| Review Writer / Worker | VCC 行布局与附页编排、调用共享 Writer、回读校验及任务资源清理 |
| Main / Service / Preload | IPC、另存为、任务互斥、最终发布 |
| Result Template Contract | ASAR 模板修复及内容缓存 |
| Data Manager | 结果状态展示映射 |

三个必须避免的复用错误：

1. `inspectSourceFile()` 当前返回单业务表描述，不能只删除“多 Sheet”报错。
2. 正式 Writer 的 `buildSubjectRowPlan()` 将期初放在明细前，与确认页顺序不同，不能作为待确认表行计划。
3. 新版有效事实表不普遍保存 `raw_json`，原表附页不能设计成直接全量读取该字段。

## 2. 多 Sheet 导入协议

### 2.1 工作簿计划

新增工作簿级识别结果。主进程保存完整计划，renderer 只接收展示所需字段。

```ts
type SheetSource = {
  sourceId: string;
  physicalFileId: string;
  fileName: string;
  sheetName: string;
  sheetIndex: number;
  visibility: 'visible' | 'hidden' | 'veryHidden';
  status: 'ready' | 'empty' | 'unrecognized' | 'invalid';
  sourceType?: string;
  rawContractVersion?: number;
  headerRow?: number;
  requiresSubject: boolean;
  diagnostics: Array<{ code: string; message: string }>;
};

type WorkbookImportPlan = {
  planId: string;
  physicalFiles: Array<{
    physicalFileId: string;
    fileName: string;
    sheetCount: number;
  }>;
  sources: SheetSource[];
};

type CommitImportPlanRequest = {
  planId: string;
  subjectBySourceId: Record<string, string>;
  excludedSheetIds: string[];
};
```

完整文件路径、SHA-256、大小、文件身份及 Sheet 定位信息只保存在 Main/Worker 的内部计划中。

约束：

- `sourceId` 为计划内的不透明标识，不使用文件 basename。
- `excludedSheetIds` 引用上述 `sourceId`，只允许排除 `unrecognized` 项。
- 合法业务 Sheet、结构错误 Sheet 不能通过排除字段绕过规则。
- Main 根据缓存计划解析类型、路径和表头，不信任 renderer 回传的描述。
- 同一窗口重新选择文件时替换旧计划；窗口关闭或开始业务导入后，旧计划失效。
- 提交前校验失败可修正主体后重试；已经开始业务写入的任务重试必须重新预检。
- 提交时重新核对文件指纹和完整 Sheet 计划；变化则要求重新预检。

同一规范化输入路径只登记一次；不同输入文件即使同名，也不能只凭文件名合并。

### 2.2 Reader 改造

统一提供工作簿读取上下文：

```text
打开 ZIP / workbook relationships / shared strings
→ 枚举全部 Sheet
→ 指定 Sheet 预检或读取
→ 关闭 ZIP、游标及 shared strings 临时资源
```

`streamDetailRows()` 等读取函数增加显式 Sheet 定位参数，禁止默认读取第一个匹配 Sheet。

所有识别调用方和原表重建调用方同步适配，避免新导入成功后旧数据管理导出只读第一张。

识别规则：

- 表头使用正式定义精确匹配。
- Sheet 前部预览可用于快速定位，但不能据此宣称整张 Sheet 没有第二个独立表块。
- 在业务写入前完成结构扫描，识别后续重复表头及独立表块。
- relationship 指向不存在的 Sheet 文件属于损坏。
- 隐藏 Sheet 与可见 Sheet 使用相同业务识别规则。

系统 OP 改为读取指定 Sheet，并保留既有日期、公式、余额原始 token、快照边界及精度校验。不能通过全量展开混合工作簿来读取其中一张小型系统 OP 表。

#### 2.2.1 可排除说明页与坏业务表的固定判据

表头归一化只复用 `definitions.js::normalizeHeaderRow()` 的首尾空白处理；不调整列序、不按 Sheet 名猜类型。对全 Sheet 的每个非空行按下列顺序分类，预览仅作加速，最终结论必须来自完整结构扫描：

1. 行与唯一当前正式表头精确相等：该行是正式表头；同一行命中其他类型的近似条件不产生第二个候选。
2. 精确匹配旧 48 列 Pending：`invalid`，提示升级模板。
3. 非精确匹配行满足下表的交集阈值，或至少命中两个特征列：近似业务表头，`invalid`。
4. 尚未达到第 3 条，但同一行命中一个特征列及另一个该类型正式列名：证据不足以确认类型，仍为 `invalid`，诊断 `vcc-sheet-header-uncertain`，不得作为说明页排除。
5. 整张 Sheet 没有上述任何表头证据，且确实非空：`unrecognized`，必须由用户明确排除才能继续。完全没有值、公式或错误单元格的 Sheet 才是 `empty`；仅有样式的空单元格不算业务内容。

| 类型 | 当前列数 | 正式列名去重交集最少数量 | 特征列（同一行匹配） |
| --- | ---: | ---: | --- |
| `recharge_refund` | 49 | 25 | `穿透节点ID`、`订单号`、`我方金额` |
| `fee_fx` | 36 | 18 | `穿透节点ID`、`订单号`、`我方金额` |
| `channel` | 38 | 19 | `通道名称`、`渠道订单号`、`清算净金额` |
| `pending_archive_removal` | 46 | 23 | `pending类型`、`PendingBizId`、`流水_对账金额` |
| `system_op` | 16 | 8 | `OP发生额`、`财务余额`、`财务主体余额` |

交集按不同列名计数，重复写同一列名不能提高得分。充值/费用近似表头可能同时命中，直接列明两个候选并拒绝，不能按最高分猜一个可导入类型。诊断稳定排序为“交集数降序、原位置匹配数降序、上表类型顺序”，保留文件、Sheet、原行号、缺列/错序/额外列证据。

整 Sheet 只有一个正式表头且没有其他近似/疑似表头时，结构状态才能为 `ready`；正式表头之外出现第二个正式、近似或疑似表头按 `vcc-sheet-ambiguous` 拒绝整个计划。没有正式表头但有上述证据时也不能提交。所有结构错误统一适用 Spec IE01，不能靠 `excludedSheetIds` 绕过。

基线的 `systemHeaderCandidate()`、`pendingHeaderCandidate()` 已使用半数列名交集定位；其他类型的同等检查及上述弱证据判据为本版新增设计。实现时抽成一个纯分类器并保留精确匹配优先级，不把诊断阈值用于放宽正式模板。

### 2.3 导入顺序与分组

```text
选择物理文件
→ 逐 Sheet 预检
→ 排除说明页、补充通道主体
→ 冻结物理文件和来源成员清单
→ 按来源类型首次出现的顺序执行
→ 组内按文件选择顺序、Sheet 顺序读取
→ 原有 mapper、幂等分类和组级事务
→ 汇总
```

持久化单位：

- `import_records`：每个批次、每个 `source_type` 一条。
- `import_sources`：每条 import record 下，每个物理文件一条。
- 同类型的多个 Sheet 共用一个 `import_source_id`。
- 混合类型建立不同来源记录，但共享原始 artifact。
- 有效行保留真实 `sheet_name` 和 `source_row`。
- revision 沿用既有组级提交语义，不因 Sheet 数额外递增。

“首次出现”按用户文件选择顺序、文件内 Sheet 顺序展开后确定，保持基线 `import-service.js` 的分组插入顺序；不以异步预检完成顺序决定。

### 2.4 系统 OP 快照边界

每张 Sheet 独立调用既有快照解析和完整性校验。

候选快照缺失九币种或币种重复属于可定位主体的业务校验错误，适用 Spec IE04；独立表块、多个表头及表块边界不可信属于 IE01。各 Sheet 的合法候选可以送入同一系统 OP 导入组，但不得先将各 Sheet 行合并后再校验。

重复完整快照进入既有快照幂等流程。

#### 2.4.1 失败单位、计数和状态

以 Spec §2.4 的 IE01–IE07 为业务处置矩阵，实现不得另行解释“拒绝”：

- `system-op-importer.js::readSystemOpSnapshotCandidates()` 按 Sheet 产出候选与诊断；`importSystemOpGroup()` 继续汇总 `rejectedSubjects`。一个主体有业务格式错误，该组内其余 Sheet 的同主体候选一并过滤，不能由另一个完整候选补救。
- 有主体的格式异常键仍为 `(batchId, system_op, subject)`；无法归属主体的异常键明确为 `(batchId, physicalFileId, sheetIndex, unknown-subject)`，避免同名文件或不同 Sheet 的异常被合并。异常列表可有多条行级明细，但 `format_error_count` 按去重后的校验单位计数。
- 系统 OP 的 `raw_count` 沿用“剩余候选快照数 + 格式异常单位数”，不是 Excel 行数；实际读取数据行数另有进度字段。成功、幂等、冲突、回滚沿用基线分类器，Spec §2.5 的 A/B/C 样例必须精确得到所列数值。
- 无新增时，系统 OP 状态优先级为：有冲突 `failed_conflict`，否则有格式异常 `failed_validation`，否则 `all_skipped`；有新增且存在跳过、冲突或格式异常为 `success_with_skips`，其余为 `success`。
- 能预检的结构错误必须先发现；提交后若发生读取失败或身份变化，不得改为局部业务过滤。Importer 已收口并返回失败记录时按 IE06 继续其他组；运行异常抛出时走 `failImportBatch()`，批次为 `failed`、响应为 `error` 并带真实 `partialCommitted`，后续组不执行。
- 无运行异常时，`import-service.js` 只在存在 `failed*` 组时将批次写为 `completed_with_errors`；`success_with_skips` 不单独改变批次状态。UI 必须展示组级异常，不能只依据批次 `success` 隐藏失败明细。

基线回归依据为“系统财务OP跨文件格式异常只过滤异常数据并提升完整快照”和“系统财务OP同文件多主体部分格式错误时提升完整主体并过滤异常主体”两项测试；多 Sheet 对应场景、新结构分类和 RV02 数值样例仍需新增测试。

## 3. 存储合同 v3 与原文件共享

### 3.1 迁移原因

当前 `vcc_fin_op_import_sources.archive_artifact_id` 存在全局唯一索引，无法表达同一个混合类型工作簿对应多个业务来源。

本版升级：

```text
VCC_STORAGE_CONTRACT_VERSION = 3
```

该升级只改变来源绑定能力，不改变结果状态枚举、金额或业务幂等键。

### 3.2 索引变化

将全局 artifact 唯一约束调整为：

```sql
DROP INDEX idx_vcc_fin_op_import_sources_artifact;

CREATE INDEX idx_vcc_fin_op_import_sources_artifact
ON vcc_fin_op_import_sources(archive_artifact_id)
WHERE archive_artifact_id IS NOT NULL;

CREATE UNIQUE INDEX idx_vcc_fin_op_import_sources_record_artifact
ON vcc_fin_op_import_sources(import_record_id, archive_artifact_id)
WHERE archive_artifact_id IS NOT NULL;
```

继续保留：

```text
UNIQUE(import_record_id, source_ordinal)
UNIQUE(batch_id, source_type)
```

实际迁移先验证旧索引和合同身份，再执行对应版本步骤；上述 SQL 不作为无条件启动脚本。

### 3.3 原子迁移与写保护

分开处理持久结构事务与连接能力，不能把 SQLite 函数注册当成可由 SQL `ROLLBACK` 撤销的状态。

1. 由现有存储维护协调器关闭受影响的写入口，等待或按既有规则终止 VCC 任务；停止来源协调，关闭旧业务写连接和 Worker。启动迁移完成前不暴露 VCC 写服务。
2. 创建专用迁移连接，验证 v2 marker、表结构、索引和 canonical guard；仅在该连接注册迁移所需的 v2/v3 版本能力。注册发生在连接层，不作为事务回滚保证的一部分。
3. 在同一明确事务中替换索引、将持久 guard 及其要求的 token 切换为 v3、写入 v3 marker，并验证全部受保护表的 INSERT/UPDATE/DELETE guard、索引和外键，然后提交。
4. 成功后关闭迁移连接；Main、generic/dedicated 写 Worker、维护及 COW 候选连接分别按实存 v3 合同重新初始化，只注册其被授权的 v3 写能力。全部验证完成后恢复业务入口。
5. 第 3 步提交前失败时，回滚持久变更，并关闭迁移连接及能力版本不确定的连接。重新打开只读检查连接，确认仍为完整 v2 后只恢复适用的读取/维护入口；本版本的 v3 业务写须待重试迁移成功后开放。无法确认合同则保持写入关闭，报告原错误及恢复状态。

若第 3 步已经提交，但后续 v3 连接初始化失败，持久合同仍是 v3，不能声称已回滚到 v2；关闭失败连接、保持业务写关闭，重新按 v3 初始化。测试分别覆盖提交前回滚与提交后恢复连接，不能把两种失败混为一项断言。

成功路径不得复用先前的 v2 写连接；失败路径不得在原迁移连接上继续业务。v1 COW 迁移中间形成 v2、再执行 v3，只有最终候选库合同完整通过后才能交付替换；不能将半完成候选库投入使用。

v3 使用：

```text
vcc_storage_write_capability_v3()
vcc-storage-contract-v3
vcc_storage_contract_v3_guard_
```

不能仅修改版本常量或宽泛忽略未知 trigger。marker、索引和 guard 不允许处于混合版本状态。

不同来源版本的处理：

| 来源合同 | 处理 |
| --- | --- |
| v1 空库 | 沿既有空库建表步骤形成 v2 结构，再执行 v3 迁移 |
| v1 非空库 | 沿用既有维护入口和 COW 迁移，成功形成 v2 后执行 v3；新多 Sheet 导入在完成前不开放 |
| v2 | 执行保留全部业务数据的增量迁移 |
| v3 | 校验合同后使用 |
| 高于 v3 | 拒绝写入，不擅自修复或降级 |

既有 v1→v2 步骤需要保留明确的中间版本，不允许通过全局替换常量使旧迁移错误跳到 v3。

### 3.4 输入文件交接协议 v2

新增版本化的物理文件与来源成员关系：

```ts
type ImportArchiveHandoffV2 = {
  version: 2;
  taskRunId: string;
  files: Array<{
    physicalFileId: string;
    filePath: string;       // 仅 Main / Worker
    fileName: string;
    archiveArtifactId: number;
    sha256: string;
    sizeBytes: number;
    members: Array<{
      sourceType: string;
      sourceOrdinal: number;
      sheets: Array<{
        sheetName: string;
        sheetIndex: number;
        headerRow: number;
        rawContractVersion: number;
        subject?: string;  // 通道补充主体
      }>;
    }>;
  }>;
};
```

要求：

- 物理文件只冻结、复制和登记一次。
- 同一 `sourceType` 的 `sourceOrdinal` 按该类型涉及的文件顺序生成。
- 交接必须验证批次身份、artifact 身份、SHA-256、大小和成员关系。
- 已持久化的 artifact 绑定优先使用；身份不符时不能转而按文件名或哈希寻找其他文件替代。
- 老版单成员 metadata 保持兼容读取，不批量改写历史 artifact。
- 新版恢复通过持久成员清单定位多个来源，不能把共享 artifact 误报为重复来源。
- 既有 exact-seven `BatchContext` 保持其固定字段；上述清单作为独立版本化数据传递。

#### 3.4.1 持久化落点和唯一绑定

复用 `archive_artifacts.metadata_json`，不新增业务大表。由 Main 的 `buildVccImportArchiveHandoffFiles()` 构造 v2 成员；新增 `persistVccImportHandoffV2()` 负责校验并经 ArchiveRepository 的事务写入接口保存到已分配的 input artifact。此函数是本版拟新增接口，不代表基线已存在。

每个物理文件的 metadata 固定包含：

```ts
type PersistedVccImportHandoffV2 = {
  vccImportHandoffVersion: 2;
  vccTaskRunId: string;
  vccImportBatchId: string; // 沿用业务 batchId = taskRunId
  vccPhysicalFileId: string;
  vccSourceSha256: string;
  vccSourceSizeBytes: number;
  vccSourceMembers: ImportArchiveHandoffV2['files'][number]['members'];
  vccMembersDigest: string;
};
```

artifact 的数据库主键、所属 archive batch、角色、`artifactKey` 与 `sourceOperation` 继续使用现有列及 manifest 身份，不重复写入可独立漂移的副本。业务 batchId 等于 taskRunId，不假定 archive batchId 也等于它。完整路径沿用内部 artifact/file-plan 字段，不进入 renderer 或导出批注。

成员按 `sourceType` 的固定枚举顺序、`sourceOrdinal`、`sheetIndex` 排序后，以固定字段顺序 UTF-8 JSON 计算 `vccMembersDigest`；无主体使用字段缺省，不使用任意空串占位。原 Sheet 名、索引、表头行、结构版本及通道主体均参与摘要。Main 提交前确认的主体在该时点冻结，不允许 Worker 或恢复流程重新猜测。

绑定键固定为 `(vccImportBatchId, sourceType, sourceOrdinal)`：先通过 `(batch_id, source_type)` 找到唯一 `import_record_id`，再通过 `(import_record_id, source_ordinal)` 找到唯一 `import_source_id`，核对持久 artifact ID、哈希、大小及成员集合。ID 由既有表生成，不要求回填到成员 metadata；不能按 basename 或只有 SHA-256 反查来源。一个成员代表该类型在此文件下的一个来源，内部可含多张 Sheet。

v2 成员清单提交后不可因某组失败而删掉该成员。重复持久化只有在全部身份和摘要完全相等时才视为幂等；缺失、未知版本、重复成员、摘要或主体不符均报 `vcc-import-handoff-mismatch`。读取由 `reconcileVccImportArchiveLineage()`、启动恢复和受控原表重建共同复用只读解析函数；v1 metadata 按原单成员模式读取，不猜补 v2 多 Sheet 成员。

#### 3.4.2 持久化与业务提交时序

| 顺序 | 负责方与落点 | 后续阶段准入条件 |
| --- | --- | --- |
| 1 | Main 完成预检、补主体、指纹及完整 Sheet 计划复核；按物理文件建立冻结的 file plan | 尚未写业务数据 |
| 2 | 现有任务生命周期分配唯一 input manifest/artifact；Main 按 manifest 身份原子保存全部 v2 metadata 并回读核对 | 每个文件有且只有一份耐久成员清单；未齐全时不能启动业务 |
| 3 | Main 调用现有 `settleArtifacts()`，每个物理文件复制一次并核验 SHA-256/大小 | 所有输入均返回 `ok=true`、`durable=true`、ready artifact；将同一 artifact ID 交给全部成员 |
| 4 | Import Service 在业务来源创建事务中写批次、各类型记录、各文件来源及 artifact ID，同时为每个来源预先建立独立 hold | hold 与来源在同一主数据库连接/事务提交；Worker 不得先写有效事实再等待 Main 建保护 |
| 5 | Importer 按 §2.3 顺序执行各类型事务 | 只读指定 artifact 的冻结字节及清单中的 Sheet；成功组即按原规则提交 |
| 6 | Main/恢复协调器按每个来源核对 ready artifact 和成员，幂等完成 `bound_at`、`archive_state`、fallback 清理及 hold 协调 | 每个来源的绑定、清理和 hold 更新在同一数据库事务完成；不改其他成员 |
| 7 | 现有生命周期收口业务与 archive task | 已提交事实保留；没有有效引用的失败/全跳过来源可释放自身 hold，原件按现有存档保留规则管理 |

第 4 步通过同一数据库连接上的 ArchiveRepository hold API 完成，不另建跨库事务；这是既有“导入结束后才协调 hold”流程需要补齐的持久性边界。任务尚未收口前保留现有任务保护，第 4 步开始再由来源 hold 接续，不能出现已提交事实无人保护的窗口。

#### 3.4.3 崩溃恢复结果

| 崩溃位置 | 重启后的确定行为 |
| --- | --- |
| metadata 未完整提交或原件尚未 ready | 不执行业务；由原任务的持久 manifest/终态恢复入口收口，不新建替代文件或猜成员 |
| 原件与 metadata ready，业务来源尚未创建 | 没有业务事实需要恢复；收口中断任务，原件按现有任务/存档规则保留，不自动创建或重放业务组 |
| 来源及 hold 已创建，但尚无组提交 | 回滚未提交事务，收口 importing 记录；按有效引用核对后释放无引用来源自己的 hold |
| 第一组已提交，下一组未完成 | 保留第一组及其 hold；回滚/收口未完成组，补齐各来源绑定；不得再次导入第一组或以失败文件为单位释放全部 hold |
| 业务已提交，Main 来源协调中断 | 仅凭持久成员清单、来源 ID、artifact ID 恢复绑定和 hold；原事务中的 fallback 清理与绑定要么均已提交，要么均未提交 |

以上恢复由 `recoverInterruptedImports()` 与现有启动来源协调按既有顺序执行，并在开放新的 VCC 操作前完成；恢复不依赖 Main 缓存，不自动继续未完成的业务导入。缺失已持久化的 artifact 或匹配到多个候选时失败并保留证据，不用新 artifact 覆盖原绑定。

### 3.5 来源保护和删除

继续按每个 `import_source_id` 建立独立的 artifact hold。

同一 artifact 可以有多个来源 owner。删除某个数据集、回收某条来源或处理失败组时，只释放该来源对应的 hold；其余仍被使用的来源继续保护同一原始文件。

迁移及恢复需要覆盖：

- 同一文件的两个来源均成功。
- 一个成功、一个失败。
- 一个被删除、另一个仍在使用。
- 崩溃后重新协调绑定。
- 已持久化绑定丢失或被替换。
- 多个候选 artifact 匹配同一来源。

## 5. 一致性、取消和文件发布

### 5.1 执行顺序

1. 快速检查 run 存在、状态为 `calculated`、页面 revision 合法。
2. 打开原生另存为；取消直接返回 `cancelled`。
3. 用户确认路径后，Main 按 §5.5 执行目标准入、记录覆盖授权及目标快照，再获取 VCC 任务占用并核对 generation。
4. 在只读数据库连接中开启一致性事务。
5. 读取生效结果、已保存调整、输入版本和来源集合。
6. 使用现有计算预检生成的指纹规则，比较 run 保存的输入 revision 和 `input_fingerprint`。
7. 生成完整确认页投影、差异坐标及独立的应输出身份清单；将后续所需的历史值、来源描述和全部期望信息落入任务暂存，再关闭读取事务。
8. Main 核对计划中的全部已知输入路径均受目标保护；按冻结清单读取并验证原始来源，流式写入任务暂存，不再查询最新业务行补数。
9. 生成 XLSX 并回读校验。
10. 完成所有异步校验后，Main 保持任务占用并进入短暂发布保护阶段。
11. 在同一同步调用链内重新检查 run、revision、输入指纹、任务身份、目标准入及目标文件快照，随即执行文件发布；不经过异步 callback。
12. 返回成功并释放任务；失败或取消统一清理本次临时产物。

另存为等待期间不持有数据库事务或 VCC 长任务锁。

### 5.2 结果与输入绑定

必须同时验证：

```text
runId
run.status
result_revision
input_revisions_json
input_fingerprint
```

输入指纹继续使用既有计算规则，包含数据集、系统快照、期初及前期归档相关信息。不能只比较输入行数或单个 revision。

读取生效行、系统快照和调整必须来自同一个数据库快照。释放该快照后不能再按“当前最新数据”补附页。

Worker 持有专用只读连接，启用 `query_only` 并显式开启读取事务；取得快照后，所有期望身份、来源权威模式、原件描述、历史 raw/fallback 值、投影、调整和指纹均从此连接读取。以游标和任务磁盘清单保存，完成后正常结束只读事务并关闭连接，再开始大规模原表提取和 XLSX 写入，避免长时间保留业务数据库快照。

正常完成、协作取消及异常路径由 Worker 的单一 `finally` 停止游标、结束未结束的读取事务、关闭连接、ZIP 和文件流。超时强制终止不能假设 `finally` 一定执行，必须验证 Worker 环境销毁时连接和句柄确实释放；Main 等待退出后再回收其负责的暂存，不在 Worker 仍写文件时抢删。任务占用保留到发布或清理完成，不随读取事务结束而释放。最终 Main 的新鲜度核验是独立只读检查，不允许在该阶段修补来源或补生成数据。

### 5.3 生命周期修正

当前通用 Worker 包装在收到结果时会释放任务，新导出需要把占用延续到最终发布结束。

只扩展该任务所需的生命周期：

- Worker 完成表示暂存文件就绪，不表示用户文件已保存。
- Main 负责最终 freshness 检查和发布。
- 从最后一次同步 freshness 检查到同步发布动作之间，不留下可让其他 VCC 操作插入的异步间隙。
- 发布保护阶段不接受强制终止。
- 每个任务只返回一次最终结果。

新任务的取消和关闭清理不能调用 `recoverInterruptedImports()`，避免只读导出附带导入恢复 DML。

基线 `vcc-financial-op-output-publication.js::writeXlsxAtomically()` 使用 `await beforePublish(...)`；即使传入同步函数，调用者仍会让出执行权，因此不能直接用于承诺“最后检查到发布之间无异步间隙”。本版抽出同步的最终发布段 `commitValidatedReviewOutputSync()`，或提供等价的明确同步接口：仅接收已验证暂存、目标快照和同步 freshness 检查函数，拒绝 Promise/thenable 返回值，在同一调用栈完成检查、备份、rename 及必要回滚。异步写入、回读、哈希准备和提示均在它之前完成；原有正式导出语义保持不变并补回归。

### 5.4 副作用限制

导出路径不得调用会修改来源关系的 `syncImportArchiveLineage()`。只读取已经存在的绑定和允许使用的历史 fallback。

允许读取存档原件并验证完整性，但不能为完成导出临时修改业务来源、清理 fallback 或推进归档状态。

发布保留现有同目录暂存、备份及回滚方式，但需补齐 §5.3 的同步最后检查、§5.5 的目标准入和目标变化核验；不能将基线 helper 视为已具备这些保证。不能在校验完成前替换目标文件。回滚本身失败时保留恢复文件，并在错误结果中提供可恢复路径。

### 5.5 输出目标准入

新增 Main 专用 `assertReviewOutputTargetAllowed()`；路径来自原生另存为，renderer 无权提交替代路径。生成前与最终发布前执行同一准入合同：

| 目标类别 | 规则 |
| --- | --- |
| 应用数据库、WAL/SHM、维护候选库及备份、应用受管数据/存档目录 | 拒绝，不受覆盖确认影响；以现有实际配置的受管根目录和已登记文件身份为依据 |
| 安装目录内模板、ASAR/解包资源以及任务暂存、原表重建暂存 | 拒绝，不能将任务自身输入或内部资源作为用户输出 |
| 本次结果已知的外部原始输入路径 | 拒绝覆盖，即使已有受管副本；不扫描不相关目录寻找可能的输入 |
| 受管目录外的普通用户 XLSX，包括以前的待确认导出 | 可新建；已存在时要求对该目标的明确覆盖确认及未变化快照 |

先检查扩展名和路径归属，再创建暂存或目录。规范化目标父目录的真实路径，并按目标卷的路径比较规则判断归属；已存在的目标还核对普通磁盘文件身份，防止硬链接别名指向受保护文件。目标自身为符号链接/Windows reparse alias 或不能可靠确认目标身份时拒绝，提示选择普通文件路径；父目录解析结果及目标身份纳入最终复核。不存在的目标若在生成期间被创建，停止并要求重新保存，不继承原来的“新建”授权。

目标快照沿用可用的文件保护能力，记录存在性、文件身份、大小、时间及内容校验结果；异步计算哈希后复核身份，最终同步提交前再比较身份与父目录。普通磁盘文件的身份校验不因 §9 的 ASAR 模板修复而删除。检查目标保护集合必须包含本次快照给出的全部来源；若初次准入尚未取得完整来源集合，在 Worker 写 XLSX 前补齐准入。

拒绝受保护路径返回 `vcc-review-target-protected`，目标改变返回 `vcc-review-target-changed`；原目标字节保持不变。该合同复用已有路径/文件身份工具，不新增通用存档删除机制，也不将任意用户文件都视为受管文件。

### 5.6 互斥覆盖清单

基线实际入口位于 `vcc-financial-op-service.js`。本版采用整个 VCC 服务的 `activeTask/taskGeneration` 互斥，不能只锁当前 run；前期归档或其他月份输入也可能影响当前指纹。

| 入口/路径 | 可能改变的内容 | 导出期间的处理 |
| --- | --- | --- |
| `importSelectedFiles()` | 有效事实、系统快照、输入 revision 和来源记录 | 同一任务占用，禁止并发提交 |
| `calculate()` | run、结果 revision、输入绑定 | 同一任务占用，禁止并发计算/重算 |
| `addRunAdjustment()` | 已保存调整、结果 revision | 同一任务占用；renderer 调整弹窗与导出也互斥 |
| `initializeOpening()` | 期初及相关输入版本 | 同一任务占用，不绕过 Main 直接写入 |
| `archive()`、`unarchiveMonth()` | 当前及前期归档、结果状态、依赖版本 | 同一任务占用，按整个 VCC 服务互斥 |
| `deleteDataTarget()`、`deleteDatasetData()` 别名 | 数据集、run、来源引用 | 统一经 `runResultWriteWorker()` 的任务占用 |
| `syncImportArchiveLineage()`；`listImportRecords()`、`previewDatasetExport()` 中的隐式调用 | artifact 绑定、fallback、hold | 导出期间跳过协调写操作，仅返回已持久化的查询结果；来源待协调则如实显示不可用，不能在导出中修复 |
| `recoverInterruptedImports()`、启动来源协调 | 导入收口、来源和保护关系 | 只在服务开放前执行；导出取消/关闭路径禁止调用 |
| 存储合同迁移、COW/恢复替换、数据库/存档根目录切换 | 数据库连接、合同、原件位置 | 复用维护协调器：先拒绝新任务并等待/终止既有任务；与导出占用不能同时进入维护阶段 |
| 存档保留清理、删除任务 | 原件可用性 | 继续服从已持久化来源 hold 和现有维护保护；导出不临时新增/释放业务 hold |

普通读入口可以继续，但不得附带恢复或协调 DML。VCC 服务必须在导出入口开放前完成初始化；服务未就绪时拒绝导出，不能由导出请求惰性创建服务并顺带执行恢复。其他模块对自身数据的写入不需一律阻塞；只核对其是否实际触及上述 VCC 依赖或共享存档维护入口。测试必须逐入口调用，不能只模拟 generation 数字变化。

上述“无异步间隙”保证以本应用受控连接和 Worker 为边界；不新增跨进程锁协议，不承诺与外部 SQLite 编辑器或不受支持的多个独立写进程协作。真实文件替换仍按原件及目标完整性校验处理，不能以进程内互斥代替文件核验。

## 6. Sheet1 与确认页共享投影

### 6.1 数据来源

以 `getEffectiveRunResult()` 返回的 `review.currencies` 和 `review.subjects` 为基础，抽取共享纯函数，供 renderer 与 Review Writer 使用。

投影负责：

- 固定十四列表头。
- 全部主体的顺序。
- 明细和调整行顺序。
- 分类、来源提示和人工调整标识。
- 四类汇总的顺序与标签。
- 每个单元格的语义值和展示值。
- 差异状态及主体分块位置。

renderer 不从 DOM 反向提取数据；Writer 不另建一套结果排序规则。

### 6.2 行布局

每个主体按以下顺序写入同一张 `待确认表`：

```text
主体标题行：A:N 合并
表头行：十四列
明细与人工调整行：review.subject.rows 原顺序
期初财务OP
当月计算财务OP
系统财务OP
差异
```

主体之间增加一行空行，最后一个主体后不额外添加空主体或辅助表。

汇总行的 B:C 合并。分类单元格通过换行保留分类名称、来源提示和“人工调整”文字。结果表格外的按钮、提示操作区和复选框不写入。

不使用正式 `buildSubjectRowPlan()` 的行序；可复用模板的列宽、字体、边框及正常/异常填充锚点。

### 6.3 数值与显示

- 金额计算和差异判定始终使用既有规范十进制字符串。
- 页面格式继续采用当前千分位规则，保留已有小数精度。
- 缺失明细值及非调整行的调整字段显示 `-`。
- 差异行为零时显示 `-`；普通金额零按页面正常金额规则显示。
- 可以无损写成 Excel 数值的金额使用数值单元格及对应显示格式。
- 超出 Excel 安全精度，或无法无损往返的金额，写入完整显示文本并右对齐，由导出清单记录单元格类型。
- 不允许为了通过校验先舍入；正式结果 Writer 的原校验合同不因此放宽。

Sheet1 保存结果值，不依赖 Excel 重算得到金额。

复用 `src/backend/toolbox-format/number-date.js` 的 `classifyNumericOutput()`；VCC 如需 `canWriteReviewAmountAsNumber()`，仅作为该分类器与确认页显示合同之间的薄封装，不另写一套精度算法。写数值必须同时满足：

1. 既有分类器返回 `outputType: 'number'`。保留其有效数字和整数位数均不超过 15 位、数值有限、非零值不下溢为零、十进制精确往返及生成格式长度等限制；不能修改全局分类器或绕开较严格的拒绝条件。
2. VCC 为该数值设置的 numFmt 与确认页的千分位、小数位和符号一致，不能直接把分类器的通用格式当成页面格式，也不执行 `toFixed()`、四舍五入或容差比较。
3. 按锁定 Writer 的数值序列化形式可无损回读；最终 XLSX 校验独立比较实际数值 token 与原十进制值，并核对 numFmt 对应的页面显示精度。

任一条件不成立则写完整页面显示文本，不能直接使用分类器返回的规范数值文本替代页面显示；清单另存精确语义值。`Number.isFinite()` 仅是必要条件。测试至少覆盖普通小数、恰好 15 位、16 位及以上、极小数、正负零、带尾零和科学计数法，禁止通过改写期望金额使断言通过。原始附页按 §8.3.1 保留原 token，文本金额不会因满足该分类器而自动转为数字。

### 6.4 调整引用

VCC Review 编排层根据全部主体的实际行偏移生成调整 lineage 引用：

```text
'待确认表'!$M$<实际调整行号>
```

defined names、合并区域及打印范围都按实际投影建立并验证。打印范围包含 A:N 的调整值和原因，不套用正式模板仅到 L 列的打印范围。

新校验器允许本版明确生成的引用，拒绝越界、错 Sheet 或重复绑定。不能通过全局替换 XLSX XML 字符串改名。

### 6.5 离线版本批注

采纳 R10，在 `待确认表!A1` 的主体标题主单元格写固定批注，前缀为 `VCC Review Export`，正文为下列字段的固定顺序 JSON：

```ts
type ReviewExportProvenance = {
  schemaVersion: 1;
  runId: number;
  resultRevision: number;
  inputFingerprint: string;
  exportedAt: string; // 冻结导出快照时的 UTC ISO-8601 时间
  appVersion: string; // 实际运行的应用版本
};
```

字段在快照准备完成时冻结，IPC 成功响应的 revision 必须相同；`exportedAt` 表示本次内容生成时间，不冒充最终文件落盘时间。A1 可见标题不变，批注随行提交前写入，不新增业务列、说明 Sheet、外链或完整路径。回读验证批注字段与任务清单完全一致；无差异、只有一个 Sheet 时也保留此批注。

## 7. 差异坐标与原表重建

### 7.1 差异集合

遍历全部主体的 `effectiveDifference`：

```text
坐标 = (subject, currency)
纳入条件 = !isEffectiveDifferenceZero(effectiveDifference)
```

接口使用明确的生效差异字段，不用 truthy/falsy 方式在多个字段之间兜底。

### 7.2 有效记录选择

| 类型 | 选择条件 |
| --- | --- |
| 普通明细 | 目标账期 + 主体 + 归一化后的统计币种 |
| Pending | 目标账期 + 主体，且归一化后的流水币种或 Pending 币种命中 |
| 系统 OP | 当前主体有效快照中命中币种的原始行 |

Pending 的现有贡献关系为：

```text
流水币种 ← flow_amount
Pending币种 ← pending_amount
```

两个币种相同时，两项贡献进入同一坐标，但原始行在该附页只输出一次。两个币种都存在差异时，原始行可以分别进入两个附页。

金额符号沿用 mapper 和计算器，不在导出阶段重新解释借贷方向。

### 7.3 原始值来源

先根据同一数据库快照中的持久关系确定权威来源模式，再选择读取方法；不按哪个字段非空就优先读取哪个。按下表自上而下判定：

| 来源证据 | 权威来源及行为 |
| --- | --- |
| 有 `archive_artifact_id`、`bound_at`、ready 状态或其他明确的曾绑定证据 | 只能验证并读取指定 artifact；绑定、成员、ready 状态或原件任一不合法即失败，不能读取 raw_json/fallback 降级 |
| 无上述绑定证据，且历史合同与审计关系确认是未建立来源绑定的旧记录，保存完整合法 `raw_json` | 允许按其原始结构、键及哈希版本验证后读取历史值；不能只凭 `import_source_id IS NULL` 宣称是合法旧记录 |
| 来源记录存在，可确认从未绑定，历史合同允许 fallback，且对应 fallback 完整可核验 | 允许读取该来源的合法 fallback；只读，不在导出中推进绑定或清理 fallback |
| 来源 ID 指向不存在的记录、绑定证据互相矛盾、历史合同不支持或无法证明合法模式 | `vcc-review-source-unavailable` 或既有更具体的完整性错误；停止导出 |

`archive_artifact_id` 已分配但 `archive_state` 尚未 ready 的新来源也不能降级；需由独立恢复/协调流程完成后重试。存在合法旧 `raw_json` 不会覆盖表中第一行的强制原件规则。

ready 原件必须验证：

- 持久 artifact 身份、来源成员关系。
- 文件 SHA-256 和大小。
- Sheet 名、原始行号及原始结构版本。
- 按原 hash 版本重建的业务键和内容哈希。
- 系统 OP 的快照内容和币种原行位置。

不能用残留 fallback 掩盖已经绑定原件的损坏。

“该类来源确实为空”只指 §7.6 从数据库快照得到的应输出集合为空；不能把读取失败、未找到 Sheet/原行、没有绑定或匹配失败解释为空。若数据库中有应输出身份而无可验证来源，导出失败。

### 7.4 历史结构保真

普通明细原始表头使用 `getRawContractHeaders(sourceType, rawContractVersion)`；系统 OP 使用对应版本的 `SYSTEM_OP_HEADERS` 合同，不能假定基线的普通明细 helper 已覆盖系统 OP。未知版本或缺少可验证表头时失败，不默认套用当前模板。

Reader 的历史结构读取能力只开放给受控的原表重建流程。新导入仍只接受当前正式模板。

重建时同时保留：

- 原始值：用于附页输出。
- 规范化副本：用于 hash、业务键和计算归属核验。

例如历史 Pending 的 48 列原始记录仍按 48 列输出，不调用会将其转换为当前 46 列的展示转换函数。历史 `CNH` 可按既有规则匹配 CNY 坐标，但原表值保留 `CNH`。

### 7.5 顺序、去重与资源

分组键：

```text
(subject, currency, sourceType, rawContractVersion, headerFingerprint)
```

附页顺序：

1. 确认页主体顺序。
2. 固定九币种顺序。
3. 正式来源类型顺序。
4. 原始结构版本和表头指纹顺序。
5. 续页顺序。

组内记录按来源导入顺序、文件序号、Sheet 顺序、原行号和持久 ID 排列。

有效事实 ID 用于同组去重；系统快照使用快照 ID 与对应原始行身份。不能用文件名、行值或单独原行号作为全局去重键。

每个物理文件在一次导出中只进行一次业务行提取扫描，按命中的附页组分流到磁盘暂存；哈希校验读取另计。使用游标和有界缓冲，不为每个差异坐标重读整个文件，也不在内存中保存百万行数组。

### 7.6 独立应输出集合与三层核对

提取原表之前，在 §5.2 的同一数据库快照内按 §7.1/§7.2 独立枚举应输出身份，写入任务级磁盘清单 E。分组的表头由原始结构合同及已核验的来源描述确定，不能根据“本次提取成功的行”建立组或推导行数。

```text
E：数据库快照给出的 (分组键, 来源实体身份, 来源定位, 顺序号)
→ A：原件/合法历史值实际提取的身份、原始单元格证据和行内容
→ X：XLSX 的实际坐标、单元格类型/值、数量及内容摘要
```

- 普通事实身份使用 `effective_row_id`，并保留所属 `import_source_id`、artifact/legacy 身份、Sheet、原行、键及 hash 版本；系统记录使用 `(snapshot_id, 原始币种行身份)`。分组键必须参与身份比较。
- E 中每个 `(分组, 实体身份)` 只能一次；Pending 命中两个不同差异币种时在 E 中明确有两个不同组的条目，命中同一币种时只有一个。两条内容完全一样但事实 ID 不同的记录在 E 中是两条。
- E 的行数、分页边界和有序身份摘要在 A 开始前冻结。提取时将 A 与 E 按来源定位归并校验，必须逐项匹配，既没有未消费的期望身份，也没有额外、重复、误分组的身份；不能把 A 的条数回填成 expected。
- 重建 A 时先核对业务键、内容 hash、主体/币种归属及原始结构，再生成带身份和序号的行信封。身份、原始值和规范化副本分开保存，不在序列化前覆盖原始值。
- 从 E 的固定顺序和分页规则预先建立“Sheet/行坐标 → E 身份”的映射 P；Writer 消费每个 A 信封时再次核对 P 中的身份与序号。不能由 Writer 随意变更顺序后重新生成 P。
- XLSX 不增加事实 ID 列，回读不能从相同格值反推出数据库 ID。身份完整性在 E/A 和 Writer 消费阶段核验；X 按 P 的坐标与已核验 A 的单元格类型、值及顺序摘要比较。不能声称只靠最终 XLSX 就恢复了隐藏的事实身份。

E、A、P 均是任务暂存，不写业务数据库、不追加隐藏 Sheet；使用排序游标及磁盘索引/清单实现。摘要采用版本化的 UTF-8、类型标签和长度前缀编码，明确区分空值、空串、文本零和数值零；每条记录含分组及顺序号，避免只比较无序总数。每组每页均校验，汇总计数再比较一次。

测试的应输出身份和 Sheet1 顺序使用独立手写的小样例，不通过调用被测 Planner 或共享投影生成 expected。百万级样本可以有独立生成器的公式化计数，但仍需有 RV07/RV08 的定向漏数、重复及错位故障。

## 8. Sheet 计划、写入和校验

### 8.1 附页清单

```ts
type ReviewSheetPlan = {
  subject: string;
  currency: string;
  sourceType: string;
  rawContractVersion: number;
  headers: string[];
  headerFingerprint: string;
  fullLogicalName: string;
  actualSheetName: string;
  partNumber: number;
  expectedRowCount: number;       // E 确定的本页数据行数
  sourceIdentityDigest: string;    // E 的本页有序身份摘要
  expectedManifestRef: string;     // E/P 的任务内不透明引用
  extractedRowCount: number;      // A 的实际行数，必须等于 expected
  extractedIdentityDigest: string; // A 的身份摘要，必须与 E 相同
  contentDigest: string;           // A 的类型化有序内容摘要，供 X 比较
  serializationContractVersion: 1;
};
```

清单只放元数据、计数和摘要，明细存于任务暂存文件。它不新增业务数据库表，也不增加“说明 Sheet”。

`expected*` 在原表提取前生成且不可变；`extracted*` 与 `contentDigest` 是完成核对后的独立提取结果，不允许用它们覆盖期望值。任务内引用由 Main/Worker 解析并验证归属，不作为任意文件路径接受 renderer 输入。

### 8.2 名称算法

1. 生成完整逻辑名。
2. 清理非法字符、控制字符和不合法首尾字符。
3. 合法、未超长且唯一时直接使用。
4. 超长或清理后重名时，追加分组键 SHA-256 的稳定短后缀，并预留后缀空间。
5. 从 6 位哈希开始，冲突时逐步扩到 12 位；仍冲突则按完整分组键排序追加稳定序号。
6. 需要分页时，所有分页加 `-p1`、`-p2` 等后缀，后缀计入长度。
7. 对最终全部名称执行大小写不敏感唯一校验，同时避开保留名称及 `待确认表`。

截断不能切开 Unicode 代理对。完整逻辑名、结构版本和分页关系写入该页表头批注。

### 8.3 Writer

新增 VCC Review 导出编排层，复用从现有 Biz OP Writer 抽取的共享有界流式写入组件，底层沿用项目锁定的 ExcelJS `4.4.0`。

基线 `src/main-process/biz-op-v327/export-writer.js` 已包含 `SheetStream` 和 `BoundedWorkbookWriter`：通过标准 `PassThrough` 替换 ExcelJS 的内部 Sheet 缓冲流，将 XML 直接送入 ZIP，并在提交行后等待背压排空。该类目前是模块私有实现，只导出 `writeExportWorkbook()`，不能将其写成现成可直接导入的公共 API。

拟新增共享模块 `src/main-process/bounded-xlsx-writer.js`，先抽取已有流实现，再让 Biz OP 与 VCC 分别调用。模块名为实施约定，本文修订不会创建该源码文件。职责边界如下：

| 组件 | 复用或新增范围 |
| --- | --- |
| 共享有界 Writer | 抽取 `SheetStream`、`BoundedWorkbookWriter`、依赖版本检查、行提交后的背压等待、Sheet/工作簿完成与错误关闭流程；补充可取消等待，提供中立错误，由调用方映射业务错误码 |
| 既有 Biz OP Writer | 保留六类导出的表头、分页、类型化单元格、精度说明、业务错误码和任务合同；改为调用共享组件，不把这些业务规则搬进共享层 |
| VCC Review 编排层 | 使用确认页投影和 E/A/P 清单，负责结果与附页布局、表名、样式、批注、合并、调整引用及 VCC 错误映射；调用共享组件完成写入 |
| VCC 回读与 Main | 独立校验 E/A/P/X；Main 继续负责结果新鲜度、任务互斥和最终发布，共享 Writer 不访问业务数据库、归档或用户目标 |

继续复用项目已有的中立基础能力：`classifyNumericOutput()` 负责数值安全分类，`excel-text.js` 的文本长度检查与 OOXML 文本编码负责文本保真，已有流式 XML Reader 可提供回读基础。避免重复编码文本；以回读原文一致作为断言。

VCC 数据集 Writer 的来源重建、分页等能力可按现有合同抽取；其中旧 Pending 转换、缺源时导出说明页等行为不能带入 Review。正式结果 Writer 只复用合适的模板样式和 lineage 基础函数，不能复用其结果行序或 Pending 辅助页。Biz OP 的整套业务 Writer、NOTES 页和面向平面表格的校验器也不能直接承担 Review 导出。

VCC Review 编排按以下规则输出：

- 首先写 `待确认表`。
- 再逐组、逐页写原表附页。
- 原表使用一行表头。
- 不自动生成正式结果的 Pending 计算辅助页。
- 原始编号、前导零和特殊文本按文本写入。
- 不生成非预期公式、外链或超链接。

清单提前计算 Sheet1 总行数及附页分页数。无法合法容纳的 Sheet1 在生成前报错。

#### 8.3.1 原始单元格与输出类型合同

Reader 为可验证原件保留原始 token、OOXML 类型、必要 numFmt、公式标记及缓存值；这些是任务暂存证据，不新增业务列或全量 raw_json 存储。类型化读取是原表重建专用能力，不改 mapper 接受范围。原始字面值用于保真，规范化值用于键/hash/业务匹配，显示格式只控制用户看到的形式。

| 已核验的原始证据 | XLSX 输出 | 回读断言 |
| --- | --- | --- |
| 文本，包括长编号、前导零、文本金额、文本 `0`、以 `=`/`+`/`-`/`@` 开头的普通文本 | 明确写文本，不解析成数值、日期、公式或超链接，不添加会改变原值的前置单引号 | 原文逐字符一致，文本类型，XML 不含公式节点 |
| 数值零及普通数值/金额 token | 通过 §6.3 精度判定才写数值；否则按完整原始 token 写文本。编号语义列保持文本 | 语义十进制值精确相等；类型与清单一致，数值零与文本零不混淆 |
| 日期/时间原本为文本或 OOXML ISO 日期 token | 保留原始日期文本，不经本机时区转换 | 原文及文本类型一致 |
| 数值日期/时间，原件能证明日期系统及日期 numFmt | 本版新输入沿用 1900 日期系统；保留原始序列值及对应日期 numFmt。无法无损写数值则写原 token 文本，并在清单记录；不猜时区或补造格式 | 比较序列值、类型、numFmt 与日期系统；Excel/WPS 核对显示，不经 JS Date 往返 |
| 不存在的单元格、显式空单元格或历史 null | 写空单元格；不变为 `0`、`null` 字符串或 `-` | 按该模式的空值语义比较；明细附页不套用 Sheet1 的占位符 |
| 原件明确记录的空字符串 | 写显式文本空串 | 检查 XML 中的文本类型及空值，与缺失单元格分别记录；若库序列化不能区分，该能力未通过，不能悄悄合并 |
| 原件布尔值 | 写布尔类型及其真/假值 | 比较类型和值；历史文本 `TRUE`/`1` 仍按文本处理 |
| 错误单元格 | 业务合同已拒绝的不得进入有效记录；历史合法非计算字段允许的错误仅写错误码文本 | 错误码原文一致，无公式求值；不能转成零或空值 |
| 真实公式单元格 | 既有合同不接受的形态继续拒绝。已合法进入有效记录、且存在能按原合同验证的缓存值时，只写该缓存值，按本表选择类型；公式表达式不写入，不重算 | 无公式节点；缓存值和原键/hash/金额证据一致；无缓存、缓存错误且业务不允许或无法核验时失败 |
| 合法旧 raw_json/fallback 只保存值，未保存原始类型或 numFmt | 使用该历史合同确实保存的值；字符串仍为字符串，历史 null/缺失统一为空；不猜测原先是数值、日期、公式还是空串 | 对历史合同可证明的值断言；不可恢复的类型差异在清单记录，不伪称原件级类型还原 |

这里的“原始 token”是 XML 实体解码后的原始字面值或历史合同保存值，不是重新格式化后的 JS Number。数值单元格本来就未保存的前导零不能猜造；文本中的前导零必须保留。原有日期、金额、币种和必要字段的导入限制继续执行，不为导出新增公式执行器或放宽错误接受范围。

Sheet1 的数值和占位符仍执行 §6.3；附页按此表，不把全部原始值套进页面格式化函数。类型转换、历史能力范围和拒绝原因均参与回读清单及 RV09 手写预期。

#### 8.3.2 落盘、提交和有界缓冲

共享组件先检查 ExcelJS 版本为 `4.4.0`，通过后才创建任务暂存输出流，沿用 `flags: 'wx'`、`mode: 0o600`。构造 `BoundedWorkbookWriter` 时显式传入该磁盘流，使用 `useSharedStrings: false`、`useStyles: true`；不省略输出流。样式复用有限的模板/列格式，不为每个数据行创建不同样式。

保留现有 `_openStream()` 实现中的 `SheetStream`：使用 `highWaterMark: 65536` 的 `PassThrough`，及时将 ExcelJS `StringBuf` 转成 Buffer，再交给 ZIP；保留所需的 `pause/end/finish/zipped` 兼容行为。默认路径为“行 XML → SheetStream → ZIP → 任务 XLSX 文件”，不新增逐 Sheet XML 磁盘落盘层，不复制第二份流适配类，也不修改 `node_modules`。输入原表分流和 E/A/P 磁盘暂存继续保留。

提交顺序固定为：等待 Writer 初始化完成 → 按计划设置当前行的值、样式、批注和合并 → `row.commit()` → 检查并等待真实背压 → 完成本 Sheet → 在提交前注册完成监听 → `worksheet.commit()` 并等待其流完成 → 下一 Sheet → `await workbook.commit()` → 确认输出流关闭 → 回读。Sheet 的 `finish` 只代表该流的提交阶段结束，不能作为整个 XLSX 或用户文件保存成功的依据。

标题合并、汇总合并和批注在相关行 commit 前建立；使用计划中的明确行号 `getRow(rowNumber)` 填写 Sheet1。合并操作可能预先创建行，不能随后混用无行号的 `addRow()` 导致表头、调整行或引用整体偏移，也不应在写入前一次创建全部未来行。defined names 和打印范围按实际行号规划并在 workbook commit 前完成，禁止修改已提交行。

背压、取消和资源合同如下：

- `row.commit()` 不是 Promise。每行提交后检查当前 `SheetStream.writableNeedDrain`，需要时等待真实 `drain`，再消费下一行。标准流的 64 KiB 水位不是进程内存上限；可读端、可写端、ZIP 及文件输出队列都纳入观测。
- 现有 `await once(stream, 'drain')` 不能单独满足 VCC 取消合同。共享等待接口接收任务 AbortSignal，在 `drain`、完成或输出关闭等待期间，取消、流错误或提前关闭都必须使等待及时结束；注册监听前后检查状态并在收口时移除监听，不能只在等待前后调用 `safePoint()`。Worker 将实际取消消息接入该信号，最终发布阶段仍遵循 §5.3 的不可强杀规则。
- 原表 Reader、暂存游标到 Writer 的消费链必须能 `await` 行写入；现有同步回调需要适配为可等待消费，不能靠不等待的异步回调堆积写入。每 256 行主动让出一次事件循环，沿用既有 Biz OP 处理消息的方式。
- 输入行批次最多 512 行或 4 MiB，先到者先排空；超过批次字节阈值的单行单独处理，编码后单行上限 16 MiB，超过则明确报资源错误。所有活动 XML/ZIP 写队列合计水位仍为 8 MiB，允许至多一条上述单行的瞬时超额；达到水位即停止读取，不积累待写 Promise。共享抽取必须暴露实际队列指标，不能仅凭单个 PassThrough 配置宣称总预算成立。
- 输入 shared strings 复用现有磁盘 provider，显式设置内存预算 64 MiB；落盘后的 LRU 同时显式设置 `cacheMaxBytes=64 MiB`，不能仅限制 8,192 条而漏计长文本的字节。缓存指标按实际条目字节计量，超过上限逐出；不为每个附页重建全量字典。SST 临时目录与文件的创建/清理身份使用同类 BigInt stat，区分 Number 范围外的不同对象，替换后拒绝清理。E/A/P 使用磁盘索引和游标，活跃源文件、分流暂存句柄采用固定上限，默认最多 8 个，切换时 flush/close。
- 仅保留当前页的行缓冲。Sheet、批注、合并和调整命名元数据允许随实际主体/Sheet/调整数增长，但必须计入资源测量；不能宣称这些元数据也与输入规模完全无关。
- 取消或异常时终止当前 Sheet 流、ZIP 和输出流，等待输出句柄关闭，再由任务所有者清理候选文件和暂存。错误只收口一次；既有 Biz OP 调用方保持原业务错误码，VCC 使用本任务的错误合同。

该共享实现依赖锁定版本的内部 `_openStream()` 接口，升级 ExcelJS 必须重跑既有 Biz OP 导出及 VCC 的流、批注、defined names、合并和回读集成。共享抽取、可取消等待或队列观测未完成，或 §12.4 实测超预算时，R09 不能判为通过；先定位实际积压点并修正，若确需更换写入方案则修订设计并复审，不能默默退回全量内存写入。临时磁盘不足、数据超过单元格/工作簿能力或达到运行资源上限时明确失败并清理，禁止截断后返回成功。

#### 8.3.3 选型依据与验收边界

本次选型核验已运行既有 Biz OP 导出的两个专项用例，均通过；另用基线私有 `BoundedWorkbookWriter` 进行了两张 Sheet、5,000 条附页数据的小样本探针，验证合并、批注、defined name、A:N 打印范围、格式、前导零、高精度文本和公式外观文本可以写入并回读。探针观察到 13 次背压等待，当前 Sheet 流读写缓冲合计峰值为 131,240 字节；该值不是进程 RSS，也不能证明整个 ZIP 的总内存上限。

这些记录用于说明现有组件值得复用；共享抽取后的行为、VCC 实际任务取消、百万行、Windows 安装版及 Excel/WPS 仍需按 §12 执行，不以基线用例或小样本探针标记 RV12 已通过。

### 8.4 回读校验

使用 ZIP 条目与流式 XML 校验，避免把包含百万行附页的整个 XLSX 再加载到内存。

必须验证：

- 工作簿 Sheet 数、顺序、名称及唯一性。
- Sheet1 全部主体、十四列、行序、合并区域、显示值与金额语义。
- 调整值、原因及 lineage 引用。
- 每个附页的表头、原始列顺序、数据类型、行数及内容摘要。
- 每组 E/A 的身份与顺序一致，再按 P 比较 X 的各坐标；分页前后记录数量及顺序守恒。
- E 的来源身份摘要与 A 相同；X 的类型化内容摘要与已核验 A 相同，不能只检查 X 与自身提取数。
- §8.3.1 的类型转换、原值能力边界及 §6.5 的版本批注。
- 无差异时恰好一个 Sheet。
- 不存在非预期公式、外链或隐藏附加数据页。

验证通过后才能进入最终发布。

回读必须独立解析 XML token、类型及 numFmt，不能只调用 Writer 的格式化函数再比较字符串。小样本还与人工固定的预期表格对照，防止页面与 Writer 共用的投影函数同时写错却互相比对通过。RV07 在提取、Writer 消费和回读三个边界分别注入错误，记录具体组、预期/实际数量及首个不符坐标或身份。

## 9. ASAR 模板修复

### 9.1 根因和改动范围

修改 `result-template-contract.js` 中的 `readStableTemplate()` 与 `loadResultTemplateContract()`。

Electron `36.9.5` 的 ASAR wrapper 为虚拟文件构造 `Stats`，其 inode 采用生成值；不能将连续 `stat` 的 inode 差异解释为模板内容变化。[Electron 36.9.5 源码](https://raw.githubusercontent.com/electron/electron/v36.9.5/lib/node/asar-fs-wrapper.ts)

### 9.2 内容校验流程

```text
规范化模板路径
→ 读取 Buffer
→ 计算 SHA-256
→ 与固定模板哈希比较
→ 查询 path + hash 缓存
→ 缓存未命中时解析同一 Buffer
→ 校验模板结构
→ 缓存并返回深拷贝
```

固定模板：

```text
VCC财务OP校验结果表_模板.xlsx
```

固定 SHA-256：

```text
48c8161484128e63a6e3e60724336f2433a8f23687695d980720c59a9dec2053
```

具体变化：

- 删除读取前后 `statIdentity` 相等要求。
- 缓存键不再包含 inode、时间戳等 stat 身份。
- 每次加载均先读取并校验内容哈希，不能仅凭路径直接使用旧缓存。
- ExcelJS 解析已经验证的同一 Buffer，不能重新按路径读第二次。
- 缓存继续返回深拷贝，调用方修改不能污染缓存。
- 不再向内部合同附加没有实际用途的 `statIdentity` 字段。
- 若保留文件类型检查，stat 只用于 `isFile()` 等类型判断。

保留原模板结构验证：

```text
Sheet：财务OP校验结果表
业务范围：A1:N45
物理范围：A1:N51
正式模板打印范围：A1:L45
十四列表头及既有样式锚点
```

### 9.3 错误分类

| 原因 | 错误码 |
| --- | --- |
| 模板不存在或目标不是有效文件 | `result-template-missing` |
| 权限不足、I/O 等读取失败 | `result-template-read-failed` |
| SHA-256、XLSX 内容或模板结构不符 | `result-template-contract-mismatch` |

该修复不增加关闭校验开关，不通过把模板移出 ASAR 来代替修复，也不修改其他文件完整性函数。

### 12.4 真实环境与性能

使用锁定的 Electron 版本建立真实 ASAR 测试包，在 Electron 进程中读取包内模板。普通 Node 测试和模拟变化的 stat 不能替代此项。

- 原生另存为、覆盖确认和文件占用。
- 中文路径、长文件名。
- Excel/WPS 打开及完整表格核对。

性能验收固定使用 Windows x64、16 GiB 内存、SSD、本地同卷另存为，锁定 Electron `36.9.5`、ExcelJS `4.4.0` 及本版依赖。记录实际 CPU、Windows/Excel/WPS 版本、磁盘可用空间和运行构建 SHA；比较两种规模时使用同一台机器、同一构建与相同启动条件。其他环境的结果可以补充，但不能替代这一基准。

| 样本 | 固定输入/用途 | 通过门槛 |
| --- | --- | --- |
| PF01 | 100,000 行与 1,000,000 行等比例样本，文件数、主体数、差异坐标、结构版本及 Sheet 数相同；每行有唯一长编号和高基数文本，含 Pending 双币种 | E/A/X 全部匹配；百万行的导出 Worker 峰值 RSS 相比十万行增加不超过 256 MiB，不能随行数增加约十倍；报告测得绝对峰值 |
| PF02 | 一个附页组恰好 1,048,576 条数据，另有其他正常组 | 该组分成 1,048,575 + 1 条数据，两页各一行表头；身份及顺序守恒，其他组不被挤掉 |
| PF03 | 200 个主体、至少 500 个有数据附页、10,000 条已保存调整，包含长表名、页批注和调整引用 | 完整生成、回读并由 Excel/WPS 核对；记录元数据占用，不能通过少建 Sheet、丢调整或省引用来满足内存要求 |
| PF04 | PF01 百万行样本，输出限速为 1 MiB/s，并注入一次暂时停写 | 观测 SheetStream、ZIP 和文件输出队列，行缓冲、XML/ZIP 队列和 SST 满足 §8.3.2 固定预算；停止写入时上游停止读取，恢复后无丢行、不积累无界待写 Promise |
| PF05 | 在准备、提取、写入、回读阶段分别取消，写入覆盖已进入 `drain` 等待且输出停写；另在最终保存阶段发取消请求 | 前四阶段在当前有界批次/可中止等待处停止，等待不依赖慢盘恢复，不继续消费下一批或写完整个 Sheet 才响应；最终保护阶段完成提交/回滚后收口，不强杀 |

每 500 ms 采样 Main、Worker 和进程合计 RSS，另记录任务开始基线、峰值、缓冲高水位、SST 内存/磁盘模式、各阶段耗时、输入/输出/暂存大小和每个物理文件业务扫描次数。PF01 的行数放大判据只比较固定元数据规模，PF03 单独检验元数据增长，不能混在一起解释超标。

共享 Writer 原有 `peakBufferedBytes` 只统计当前 Sheet 流的读写积压；扩展记录时须分别列出各队列和总量，不能将此单项当作进程内存或全部 ZIP 缓冲。记录使用的是直接流式 ZIP 路径，并核对没有逐页全量 XML 字符串或 Buffer 驻留。

取消时记录请求、Worker 收到信号、停止读取、连接/游标关闭、暂存清理及 UI 解除忙态的时间；drain/限速等待必须可取消，不能等慢盘无限恢复。报告主线程响应与实际取消耗时，不编造固定总导出秒数或提速比例。资源门槛在执行前固定；未通过则修正实现或正式修订设计并复审，不能事后降低样本规模冒充通过。
