## 1. 背景

用户需求（2026-10-27）：余额取值为"通过发生额计算"时，如果账单日期不连续，弹出提醒框询问是否导入前一日的期末余额，并提醒不导入的话算出来的余额可能是错的。

## 2. 代码现状（基线 v3.2.12）

| 位置 | 当前行为 | 与本次的关系 |
| --- | --- | --- |
| `src/main-process/statement-generation-business.js`，`deriveBalanceRecords` | 发生额计算模式下，每个 MerchantId + Currency 的日期升序逐日接着算；中间缺日直接用上一个出现日期的期末余额 | 文件内断档无提示 |
| 同上，`seededBalance` | 只有首日完全没有可用种子时才抛 `BALANCE_SEED_REQUIRED`（"因首次导入余额，请导入上一个账单日余额"） | 保留，优先级最高 |
| `src/backend/balance-seed-store.js`，`findPreviousBalanceSeed` | 取目标日期之前最近的一条种子，不检查是否为前一日 | 种子与首日之间的断档无提示 |
| `src/main-process/statement-generation.js`，`generateStatementFiles` | 生成余额后用 `storeGeneratedBalanceSeeds` 以 `overwrite: true` 写入每个日期的计算种子 | 未确认的断档不得先写入种子 |
| `src/main.js`，`file:save-balance-seed` | 补录一条人工种子后重算余额；重算仍缺种子时返回下一个补录 prompt | 复用为补录与"不补录"的通道 |

## 3. 已确认决策（用户，2026-10-27）

| 编号 | 决策 |
| --- | --- |
| D1 | 断档判定只在模板 Balance 取值为"通过发生额计算"时进行；"账单里的余额"等其他取值不判定，行为不变 |
| D2 | 按自然日判定：缺任何一天都算断档，包括周末、节假日和无交易日；不引入节假日日历 |
| D3 | 一次生成中的全部断档合并在一个弹窗里，可以一键全部不补录 |
| D4 | 不补录：照常生成余额账单并可导出；状态框提示 N 处断档未补录、余额可能不准确，活动日志逐条记录；余额账单格式不变 |
| D5 | 纳入 v3.2.14，独立分支，以上一正式标签为基线 |

## 4. 功能规则

### 4.1 锚点与断档

- 每个 MerchantId + Currency 分组按日期升序，确定每个账单日的锚点，即用来接着算的上一期末余额：
  - 首日：首日之前最近的一条余额种子（沿用现状）。完全没有种子时仍走"首次导入"补录。
  - 后续日期：在"文件内上一个账单日"和"种子库中日期落在两者之间、生成方式为人工录入的最新一条"中取日期更晚的；同一天时以文件内本次计算为准。断档内的计算种子不作锚点（见 §8 T7）。
- 锚点日期的下一个自然日早于当前账单日，就是断档。缺失区间为锚点日期次日至当前账单日前一日，建议补录日期为当前账单日前一日。
- 锚点来自种子时，余额附加值按首日现有规则累计。

### 4.2 交互

1. 生成时发现未处理的断档，不产出余额账单，也不写入计算种子；明细账单照常可导出。
2. 弹出"账单日期不连续"确认框，逐条列出：银行账号、币种、断档前最后一个有余额的日期、断档后第一个账单日、缺失区间；提示不补录的话断档后的余额会直接接着断档前的余额计算，可能是错的，之后导入的余额也会接着这个结果计算。按钮为【补录期末余额】【不补录，继续生成】。
3. 【补录期末余额】：按断档顺序打开现有补录弹窗，日期预填为建议补录日期（可修改），保存后重算；还有断档时直接切到下一处。断档类补录弹窗另有【不补录此处】。
4. 【不补录，继续生成】/【不补录此处】：在本次账单会话中记住这些断档，然后重算。结果按 D4 提示并记录日志。
5. 关闭确认框视为暂不处理：状态框显示"账单日期不连续，点击处理"并可点击重新打开，余额导出保持禁用。
6. 补录日期早于建议日期时，断档仍然存在，会再次提示；用户可以选择不补录。

### 4.3 "不补录"的记忆范围

只保存在主进程账单会话的内存中，不跨重启，不落盘。确认键包含模板、账号、币种、锚点日期和断档后首日，本次运行期间对完全相同的断档有效；锚点日期或断档后首日变化后视为新的断档，需要重新确认。

## 5. 非目标

- 不改"账单里的余额"模式、新开账户余额账单、月度余额导出。
- 不改余额账单的输出列和文件格式，不给种子记录加字段。
- 不改首日"首次导入"补录的规则与文案。

## 6. 验收标准

- 发生额计算模式，日期连续：结果与基线一致，不提示。
- 文件内断档、种子与首日之间断档：都能提示，断档信息准确；确认前不产出余额账单，也不写入种子。
- 补录断档前一日后：不再提示，断档后首日余额 = 补录余额 + 当日贷方 − 当日借方（叠加适用的余额附加值）。
- 不补录：余额账单可导出，数值与基线一致；状态框与活动日志符合 D4。
- 多账号、多币种、多模板（按文件名映射）的断档合并在一次确认中；同时缺首次种子时先走"首次导入"补录。
- "账单里的余额"模式不受影响。
- 日期按自然日计算：12-31 → 01-01、非闰年 02-28 → 03-01 视为连续；闰年 02-28 → 03-01 视为断档。

## 7. 数据与资金影响

- 计算口径只有一处变化：断档中存在人工录入的种子时，用它作锚点。没有这类种子时，数值与基线完全一致。
- 新增的"不补录"记忆只在内存中，不新增持久化格式。
- 涉及余额金额，合并前做对账专项审查。

## 8. 实现决策（技术，2026-10-27）

| 编号 | 决策 | 理由 |
| --- | --- | --- |
| T1 | 断档判定放在 `deriveBalanceRecords`，全部分组算完后统一抛 `BALANCE_GAP_CONFIRM_REQUIRED`；种子解析器改为返回整条种子记录 | 抛错早于写余额表和计算种子；唯一的计算口径改动集中在一处 |
| T2 | 断档结果复用 `status: 'manual-balance-required'`，以 `manualBalancePrompt.reason === 'gap'` 区分 | 存档任务的结果分类已把该状态审计为成功，不新增状态，不改任务策略与执行描述基线 |
| T3 | "不补录"复用 `file:save-balance-seed`，payload 为 `skipBalanceGapKeys`；预检只接受当前 prompt 列出的断档，不生成种子写入计划，新鲜度守卫在无计划时跳过种子证据核对 | 不新增 IPC 通道，沿用同一套 FilePlan、新鲜度与存档登记 |
| T4 | 确认键挂在内存中的账单会话对象上（没有会话时挂在当前 importContext 上），生成时通过注入的 `getAcknowledgedBalanceGapKeys` 查询 | 不新增主进程全局状态，不改 E09 状态足迹的六项全局清单 |
| T5 | 断档类补录 prompt 未经确认时，`createManualBalanceSeedDialog` 先渲染确认框；补录流程内的下一处直接进补录弹窗 | 状态框点击、导入、导出全部、大账号选择后都走同一入口，不扩展弹窗导出链 |
| T6 | 断档补录日期必须晚于断档前最后一个账单日 | 更早的种子不会被采用，避免反复提示 |
| T7 | 文件内断档只把人工录入的种子作锚点；`findPreviousBalanceSeed` 新增可选 `generationMethod` 过滤，未指定时行为不变 | 对账专项审查发现：计算种子已含余额附加值，按首日口径从 0 起累计会重复叠加（同 backlog B32），且可能来自另一条计算链而被静默采用。只认人工录入后，这类断档会照常提示，由用户补录或确认不补录 |
