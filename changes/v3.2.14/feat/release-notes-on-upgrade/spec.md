> status: in-progress
> created: 2026-10-28
> updated: 2026-10-29
> 目标版本：v3.2.14
> 适用分支：`feat/release-notes-on-upgrade`
> 分支创建基线：`v3.2.13` → `e68089cc46c88c3eaed87b942fcd8badef00dff7`

## 1. 背景

用户需求（2026-10-28）：每次成功升级到新 release 后，用户打开客户端即弹出一个页面，列出上一个 release 至最新 release 的简要更新功能。

## 2. 代码现状（基线 v3.2.13）

| 位置 | 当前行为 | 与本次的关系 |
| --- | --- | --- |
| `src/main-process/app-updater.js` | electron-updater 在线升级，仅 NSIS 且用户开启时可用；`isStrictStableUpgrade` 比较稳定版本号 | 复用版本比较；不改升级流程 |
| 便携版 / 手动安装包 | 用户自行替换或重装升级 | 同样需要弹出 |
| `app_settings`（`src/backend/database/settings-repository.js`） | 键值设置表，无“上次运行版本”记录 | 新增一个键，无需迁移 |
| `CHANGELOG.md`、`docs/VERSION_FEATURE_HISTORY.md` | 不随包打包，内容偏技术、偏长 | 不作为弹窗数据源 |
| `app:get-info` | 渲染层启动时读取版本等信息 | 附带更新说明数据，不新增读通道 |
| 设置 →「版本管理」 | 显示当前版本、自动更新、更新状态 | 新增再次查看入口 |

## 4. 功能规则

### 4.1 版本记录

- `app_settings` 新键 `release_notes_acknowledged_version`：用户最后确认过更新说明的版本。
- 主进程启动、主库初始化后计算一次，结果只在本次运行内缓存：
  1. 记录为空或不是合法稳定版本号：
     - 主库文件在本次启动前不存在（全新安装）：写入当前版本，不弹。
     - 主库已存在（从本功能之前的版本升级）：基线取 `3.2.13`（最后一个不含本功能的正式版），来源版本记为未知。
  2. 当前版本不是基线的严格升级（同版本、降级、带预发布号）：不弹。记录为空时补写当前版本；降级不改记录。带构建元数据（如 `3.2.14+build.7`）的正式版按对应正式版（`3.2.14`）判定、查说明和写入记录。
  3. 取版本在（基线, 当前版本] 内的说明条目；没有条目时写入当前版本，不弹。
  4. 否则本次启动有待显示的更新说明。

### 4.2 交互

1. 渲染层初始化完成后，有待显示内容时弹出“更新说明”弹窗；已有其他弹窗时等它关闭后再弹。
2. 正文首行写“已从 vX 更新到 vY”，来源未知时写“已更新到 vY”；下面按版本从新到旧分节，每节显示版本号、发布日期和要点；内容过长时正文滚动。
3. 底部【知道了】；右上角 ×、Esc 也可关闭；点击背景不关闭。用户以上述任一方式关闭即视为已确认，写入当前版本；被其他弹窗替换或页面卸载导致的关闭不确认，下次启动再弹。
4. 弹窗属于应用级，切换模块不关闭。
5. 确认写入失败只记录日志，下次启动再弹。
6. 设置「版本管理」页新增“更新说明”行，【查看本版更新说明】在设置之上打开同款弹窗，只显示当前版本条目，不改变确认记录。当前版本没有条目时显示“本版暂无更新说明”。
7. 预览截图（`previewModal` / `previewCapture`）运行时不弹。

### 4.3 说明数据

- 文件：`src/main-process/release-notes/release-notes.json`，随 `src/**/*` 打包。
- 格式：数组，每项 `{ "version": "X.Y.Z", "date": "YYYY-MM-DD", "highlights": ["…"] }`，按版本从新到旧排列，版本唯一。
- 编写规范：面向用户、中文纯文本（不含 Markdown）；每版 1–5 条，每条不超过 120 字；不写内部流程、验证记录、分支或审查信息。
- 运行时只采用通过校验的条目，不合格条目跳过并记录日志。
- 发版门禁：单测要求 `package.json` 当前版本必须有条目；发版清单 C2 增加编写本版条目。本分支回填 v3.2.13 条目，v3.2.14 条目在发版时编写。

## 5. 非目标

- 不联网读取 GitHub Release 说明，不改 electron-updater 的检查、下载与安装流程。
- 不推断本功能上线前的实际旧版本；从更早版本直接升级时，只显示 v3.2.13 之后的条目。
- 不改 CHANGELOG、版本功能清单和使用手册的编写方式（发版时照常更新）。

## 6. 验收标准

- 全新安装首次启动：不弹，记录写入当前版本。
- 已有数据、无记录（从 v3.2.13 或更早升级）：弹出 v3.2.13 之后到当前版本的条目，标题行为“已更新到 vY”。
- 记录为旧版本：弹出（记录, 当前]，跨多个版本时全部按新到旧列出。
- 关闭后再次启动不弹；同版本重启、降级不弹。
- 启动时已有其他弹窗：等其关闭后再弹；在线升级“已下载”提示与本弹窗不互相覆盖。
- 切换模块不关闭弹窗；设置入口可再次查看且不影响记录。
- 预览截图运行不弹。

## 7. 数据与兼容影响

- 只新增一个 `app_settings` 键，不新增表、不改迁移；不涉及账单、对账、金额或币种。
- 旧版本读取到该键不会使用，降级后再升级按记录判断，不重复弹出已确认版本。

## 8. 实现决策（技术，2026-10-28）

| 编号 | 决策 |
| --- | --- |
| T1 | 版本比较复用 `app-updater.js` 导出的 `isStrictStableUpgrade`，区间判断为 `isStrictStableUpgrade(from, v) && !isStrictStableUpgrade(to, v)` |
| T2 | 全新安装判定：`initializeApplication` 在 `new AppDatabase` 之前检查 `tool-data.sqlite` 是否存在 |
| T3 | 读取走 `app:get-info` 的 `releaseNotes: { current, pending }`；写入新增 `settings:acknowledge-release-notes`，只接受当前版本且仅在有待显示内容时写入，归入 `ui-navigation` 排除策略 |
| T4 | 渲染层新增 `src/renderer/dialogs/release-notes.js` 工厂，登记架构边界 `renderer-dialog-release-notes`；设置弹窗工厂 `ui` 新增 `openReleaseNotes`，按 `policyChanges` 登记放宽 |
| T5 | 弹窗以 `owner: 'application'` 打开；等待其他弹窗关闭的方式与在线升级“已下载”提示一致（`modalRoot` MutationObserver） |
| T6 | 当前版本去掉构建元数据后再判定与查找说明（`toStableVersion`），与 `app-updater.js` 的稳定版解析同口径；预发布号仍排除。2026-10-29 Codex 第三轮审查 `release/v3.2.14` 发现原先只认纯 `X.Y.Z`，带构建元数据的正式版既不弹窗、设置入口也显示暂无说明。仓库历史版本号都不带构建元数据，现行发版不会触发；新增单测 2 项，已确认修复前失败、修复后通过 |
