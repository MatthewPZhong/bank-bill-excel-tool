# v3.2.x 后台执行平台版本拆分决策

| 项目 | 内容 |
| --- | --- |
| 决策日期 | 2026-08-21 |
| 评审状态 | Implementation Ready（action 生产启用仍按独立门禁） |
| 结论 | 新增 v3.2.4 与 v3.2.5；v3.2.3 不再承担最终全量收口 |
| 前置条件 | E00 Platform Contract v1 冻结并合并 |
| 适用文档 | v3.2.0～v3.2.5 Spec / TechDoc |

## 1. 决策

需要新增 **v3.2.4** 和 **v3.2.5**。

原因不是为了把文档拆得更细，而是当前 v3.2.3 同时包含六类性质完全不同的工作：

1. Statement 长驻大状态 Service 与多轮用户交互；
2. NewAccount 单工作簿生成与 managed artifact；
3. ReconFix 长驻状态、JPM 资金写回和跨重启恢复；
4. VCC Financial OP 多主体只读输出图；
5. Pending、BizOP、PreFund、Position 等剩余只读导出；
6. Pending、BizOP、Acquiring、Position 成熟执行器适配与全 Action Coverage 收口。

这些工作同时涉及：

- 长驻内存所有权；
- waiting-user 生命周期；
- 资金写入和 critical intent；
- 只读工作簿生成；
- utility process 适配；
- 全局 ResourceGovernor；
- 最终 Registry / Inventory / release gate。

若继续放在一个版本中，任何一个资金恢复 BLOCK 都会拖住其他低风险只读能力；同时一个版本内的 Windows、RSS、故障注入和人工资金复核范围过大，无法形成清晰、可回滚的发布证据。

## 2. 不新增更多版本的当前判断

目前 **不建议继续新增 v3.2.6**。

v3.2.3～v3.2.5 按下述边界拆分后，每个版本都可以形成独立的控制面主题、独立 feature flags 和独立回滚面。只有出现以下任一事实时，才重新评估 v3.2.6：

- ReconFix JPM 必须新增复杂数据修复 UI，而不只是恢复 hold；
- Statement Session Artifact 最终需要跨重启持久化，而不是 Worker 内存状态；
- 成熟 adapter 发现必须重写现有内部池或 utility process；
- 现有 Action Inventory 数量和依赖关系远超当前预估，v3.2.5 无法在一个稳定观察版本内完成。

在这些事实出现以前，不预先创建空版本。

## 3. 新的版本边界

### E00 — Platform Contract v1 Freeze（非产品版本，所有 v3.2.x 的合并前置）

目标：冻结唯一的平台合同，关闭跨版本协议、资源和恢复语义漂移。

必须交付：

- `platform-contract-v1.md`；
- `platform-contract-v1.schema.json`；
- `platform-lifecycle-mapping.md`；
- Background Execution Policy/Protocol v1；
- 完整 ResourceGovernor：base、persistent、phase、compound、atomic replace；
- Critical Intent Store、Recovery Hold、startup scan；
- TaskLifecycle `interrupted` 映射；
- action-level receipt / inspector probe 结果。

E00 合并前：

- 可以开发纯 Parser Core、只读 validator、benchmark fixture；
- 不允许新平台承载 DB mutation、正式发布终态或自动 crash recovery；
- 新增多 Worker 生产策略固定 `effectiveWorkerCount=1`。

### v3.2.0 — 平台核心、成熟样板适配、VCC OP 解析并行

保留范围：

- Action Inventory 与基线；
- Supervisor / Registry / adapters；
- ResourceGovernor 实现；
- Critical Intent Store 和 lifecycle mapping 落地；
- 通用大表导入与 Toolbox 大文件拆分的既有 transport 适配样板；
- VCC OP Parser Core、Parser Pool、有序 Reducer；
- VCC `saveRun` operation receipt。

生产门禁：

- VCC Parser Pool 可先上线；
- `saveRun` 只有在稳定 `operationKey` 和同事务 receipt 可唯一查询后，才通过“提交后回包前崩溃”门禁；
- 未完成 receipt 时，计算可以后台化，保存仍走 legacy/blocked 策略。

### v3.2.1 — Toolbox 后台生成与 PreFund MPT 有序导入

保留范围：

- Toolbox merge / 普通拆分单 Worker 后台隔离；
- 证明必要后再启用单 Scanner + sealed Route DB + 最多两个只读 Writer；
- PreFund MPT Parser Core、spool、有序 Coordinator；
- 单一 Writer 和逐文件事务；
- `inserted / replaced / noop-existing-batch` receipt 语义。

生产门禁：

- Toolbox Publisher 继续是唯一正式发布者；
- Route DB 必须完成 sidecar sealing 合同；
- PreFund Writer 必须能按 `operationKey + fileIndex` 唯一判断 committed / not-committed / unknown。

### v3.2.2 — FundRecon、Duplicate、BankBU 后台隔离

保留范围：

- FundRecon 长驻单 Service；
- Duplicate 长驻单 Service；
- BankBU one-shot 单 Worker；
- Duplicate paired parser 和 BankBU dual parser 作为独立性能门禁；
- Service base/persistent/phase lease；
- side/main 提交恢复。

生产门禁：

- Duplicate 必须先做 startup recovery scan 和独立只读 inspector，再执行 compensation，最后才构造 Service；
- BankBU side run 和 main mirror 必须共享 `operationKey`，main mirror 保存 `sideRunId`；
- 两个模块在 receipt/inspector 未关闭前保持 `legacy-preserved` 或 `blocked`；
- FundRecon 纯内存状态迁移不受这两个 mutation BLOCK 牵连。

### v3.2.3 — Statement 与 NewAccount

本版本只处理“交互式大状态 Service”和“单工作簿生成”两类能力。

范围：

- Statement 长驻 Service；
- Statement pending interaction reservation；
- 大账号、余额和 scope opaque token；
- `waiting-user` Task phase；
- token TTL、数量上限和 crash/quit 终结；
- current/all 工作簿生成；
- manual balance seed 的 main-settlement 原子写与 inspector；
- NewAccount 单 Worker 生成；
- NewAccount 另存为 `inline-async`。

明确不做：

- ReconFix；
- VCC Financial OP output pool；
- 成熟 adapter 最终收口；
- 全 Action Coverage Release Gate。

这样拆分后，Statement 的 RSS、token、waiting-user、业务锁释放与重新获取可以在独立版本中充分验证，不与 JPM 资金写回共享发布风险。

### v3.2.4 — ReconFix 与 VCC Financial OP 输出图

范围：

- ReconFix 长驻 Service；
- 普通和 BOC 只读 run；
- JPM ID-aware ADM reader；
- JPM no-op 识别；
- JPM pre/post image、critical intent、同事务 operation marker/receipt、inspector；
- ReconFix 多 artifact 全有或全不发布；
- VCC Financial OP 单 Writer 新合同；
- subject filter 下推；
- 最多两个主体 Writer；
- 所有主体完成后单一 Publisher。

独立 action 门禁：

- ReconFix 普通/BOC 可在 JPM blocked 时独立启用；
- VCC 单 Writer可先启用；
- VCC 双 Writer必须通过 15% 性能、RSS 和 subject filter pushdown 门禁；
- JPM 资金写回必须完成人工复核，不能被 VCC 的低风险输出能力替代。

### v3.2.5 — 剩余只读导出、成熟 Adapter 与全量策略收口

范围：

- Pending 差异/汇总/错误报告；
- BizOP 单日/区间导出；
- PreFund 渠道/平账/不平/审计输出；
- Position 银行/Linked/Raw/Run/筛选结果；
- VCC Financial OP 非主体类只读导出；
- Acquiring“复制现有差异文件”与“重新生成工作簿”的 action 分类；
- Pending/BizOP/Acquiring/Position 成熟 transport adapters；
- Action Inventory 100% coverage；
- Capability Inventory 与 Effective Production Strategy Snapshot；
- CI / release-check 的 action manifest gate；
- legacy seam 的保留/后续删除决策。

本版是平台收口版本，不新增高风险资金匹配算法。

## 4. 依赖关系

```mermaid
flowchart LR
    E00["E00 Platform Contract v1"] --> V320["v3.2.0 平台核心 + VCC OP"]
    V320 --> V321["v3.2.1 Toolbox + PreFund"]
    V321 --> V322["v3.2.2 FundRecon + Duplicate + BankBU"]
    V322 --> V323["v3.2.3 Statement + NewAccount"]
    V323 --> V324["v3.2.4 ReconFix + VCCFin"]
    V324 --> V325["v3.2.5 Exports + Adapters + Closure"]
```

版本依赖不表示所有 action 必须在前一版生产启用。被 action-level BLOCK 阻止的能力可以保持 legacy，而平台和无关模块继续推进；但任何后续版本不得绕过未解决的 recovery hold 或用“版本已发布”代替 action 门禁。

## 5. 为什么不把 VCC Financial OP 留到 v3.2.5

VCC Financial OP 多主体输出具备清晰的 read-only 分片边界，适合作为 v3.2.4 中与 ReconFix 并行的低风险工作流：

- 即使 JPM 暂时 blocked，VCC 单 Writer和双 Writer仍可独立验证；
- v3.2.5 应专注外围 adapter 与全量策略收口，避免再加入新的输出引擎；
- VCC 的 subject filter pushdown 和 artifact join 需要在最终 adapter 收口前形成稳定样板。

因此 v3.2.4 同时包含 ReconFix 和 VCCFin，但它们必须使用独立 PR、独立 feature flag、独立 release evidence，不允许互相替代门禁。

## 7. 发布与回滚原则

- 每个 action 通过 Registry 独立开关，不以整个模块作为最小启用单位；
- active job 不动态切换实现；
- action 被 blocked 时继续使用明确的 legacy path，不执行 silent fallback；
- 任何 `commitState=unknown` 产生 Recovery Hold，阻断冲突 mutation；
- read-only export 和 parser 能力不得自动解除 mutation hold；
- 发布说明必须区分：
  - capability 已实现；
  - production effective mode；
  - Worker count；
  - recovery status；
  - legacy 是否仍可用。

## 8. 最终决策

- **新增 v3.2.4：需要。**
- **新增 v3.2.5：需要。**
- **当前不新增 v3.2.6。**
- **下一步不是继续扩写模块流程，而是先完成 E00 Platform Contract v1。**
