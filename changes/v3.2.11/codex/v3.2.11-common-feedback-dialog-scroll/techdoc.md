## 三、实现方案：公共默认保护，不全局改所有弹窗

### 3.1 最小调用链与边界

```text
业务控制器／对话框包装函数
  → createAlertDialog(message, options)
    或 createConfirmDialog(options)
  → 原 card 增加 feedback-dialog-card
  → 原 overlay／描述符经既有 bridge／host 挂载
  → 正文独立滚动，操作区不随正文滚动
  → 原按钮事件、日志及关闭链
```

不新建第二套弹窗工厂，不新增必须由调用方选择的公共 `scrollable` 选项，不移动业务状态，不搜索全仓后机械替换所有 `createAlertDialog` 调用。

### 3.2 实施前的调用／包装盘点

在实际开发基线检索两个工厂的定义、返回导出、依赖注入别名及包装函数。仅搜索原函数名不够，还需顺着 `ui.alert`／`ui.confirm` 等实际注入路径核对来源，不能按变量名猜测。

对每个生产包装入口记录：所属模块、原工厂、是否修改 card 类名、是否重排正文与 footer、是否已有局部滚动、是否存在显式焦点／关闭描述符、测试归属。调用清单记在本 TechDoc 实施记录或现有对应测试资料，不再建立另一份需求正文。

重点排查：

- `card.className = ...` 覆盖新标记；普通 `classList.add()` 应保留兼容。
- 把 footer 搬进 `.alert-body`，或在外层重复包一个纵向滚动容器。
- 内联高度／overflow、较高优先级专用规则覆盖公共保护。
- 工厂返回后继续 `registerModal()`，是否保持已有描述符合并约定。
- 预览或测试直接构造了另一份假 DOM，导致没有覆盖真实公共工厂。

确有问题只修对应包装的布局兼容；若发现完全独立工厂，记录为范围外并做必要负向回归。实施阶段已完成 [调用／包装清单](./call-inventory.md)。静态盘点不等于逐入口运行验收，不能宣称“所有模块已逐一验证”。

**已知范围外入口 OOS-01：**平盘对账 `openMappingsDialog()` 内的 `showNestedAlert()`（`src/renderer-position-reconciliation.js` 约 1275 行）直接创建 `section.modal-card.alert-card`、正文和“确认”操作区；`api.saveMappings()` 抛异常或返回非 `ok` 时均会调用它。[S10] 同事报告已用实际控制器与虚构长消息复现裁剪，临时套用公共方案后仍未覆盖。[RV1] 本次不在该入口调用公共布局辅助函数，也不迁移其宿主、关闭或保存流程。将其记入已知残留问题；负向回归检查没有新增误命中／行为退化，不要求该旧缺陷永久保持。

### 3.3 公共布局辅助函数与焦点接入

以下为待实施的关键示意，不是已应用补丁：

```javascript
// createRendererDialogs() 内部工具，不新增公开工厂参数。
function applyCommonFeedbackLayout(overlay, card) {
  const body = card.querySelector('.alert-body');
  if (!body) throw new Error('公共反馈弹窗缺少正文容器');

  card.classList.add('feedback-dialog-card');
  body.setAttribute('role', 'region');
  body.setAttribute('aria-label', '弹窗内容');

  // 当前 host 先安排首次初始焦点，再调用描述符 onMount。
  // 此时增加正文 Tab 入口，不额外 focus()，避免抢占原按钮／输入焦点。
  registerModal(overlay, {
    onMount(handle) {
      if (!handle.isOpen()) return;
      if (!body.hasAttribute('tabindex')) body.tabIndex = 0;
    }
  });
  return overlay;
}
```

两个公共工厂在原有 `overlay.appendChild(dialog)` 后返回：

```javascript
return applyCommonFeedbackLayout(overlay, dialog);
```

必须保留原 `.modal-card.alert-card` 类，不复制或替换 overlay；保留同一个 DOM 节点及所有已经绑定的事件。`applyCommonFeedbackLayout` 仅限两个结构已知的公共工厂使用，不成为对任意 `.modal-card` 的全局自动装饰器。

当前 `createAlertDialog()` 已注册日志用 `onMount`。`registerModal()` 会合并并串接同名挂载回调，因此装饰注册必须走现有 bridge，不能手工覆盖旧描述符、重复调用旧日志逻辑或重新 `registerModal` 一个业务关闭合同。[S1][S6]

该方式不新增计时器、resize 监听器或直接 `.focus()`，不复制宿主的可聚焦元素筛选算法。当前宿主顺序是 `mount → scheduleFocus → onMounted`；若实际开发基线已改变顺序，必须调整接入以继续满足“首次初始焦点保持”，而不是默默让原删除按钮／确认按钮的键盘行为变化。

正文 Tab 可达后，原宿主会将其纳入焦点环。滚动键在正文获得焦点时滚动正文；在按钮获得焦点时维持该按钮原生键盘动作。不要拦截整张弹窗的空格／Enter，也不要新增任何自动确认逻辑。

### 3.4 标记限定 CSS

保留生产 CSS 中原有卡片高度、裁剪、宽度、圆角、颜色、图标和 footer 背景。推荐新增如下规则作为实现起点，最终按真实级联验收：

```css
/* 仅两个公共反馈工厂生成的卡片。 */
.modal-card.feedback-dialog-card {
  min-height: 0;
  min-width: 0;
}

.feedback-dialog-card > .alert-body {
  flex: 1 1 auto;
  min-height: 0;
  min-width: 0;
  overflow-y: auto;
  overscroll-behavior-y: contain;
}

.feedback-dialog-card > .alert-body > .alert-message {
  min-width: 0;
  overflow-wrap: anywhere;
}

.feedback-dialog-card > .dialog-actions {
  flex: 0 0 auto;
  flex-wrap: wrap;
}

.feedback-dialog-card > .dialog-actions > button {
  min-width: 0;
  max-width: 100%;
  min-height: 36px;
  height: auto;
  white-space: normal;
  overflow-wrap: anywhere;
}

.feedback-dialog-card > .alert-body:focus-visible {
  outline: 2px solid var(--primary);
  outline-offset: -3px;
}
```

卡片仍继承 `.modal-card` 已有的 `max-height: calc(100vh - 56px)` 与 `overflow: hidden`，不盲目增加第二套不一致的高度常量。现有单行 `.small` 按钮高度为 36px；该值作为最小高度，长标签允许增高，内边距、边框和按钮视觉由原类继承。[S2][S7]

样式只匹配专用标记及其直接正文／操作区，避免命中消息内容内部恰好同名的后代节点。不要使用全局 `!important`、固定 footer 浮层、统一增大所有弹窗宽高或移除外层裁剪来规避问题。

短内容不能被 `height: 100%`／固定高度强制撑满；长内容必须有正的可用正文高度。窗口小到无法容纳任何实际按钮的极端尺寸不在本次变更中虚假承诺，按应用现有最小窗口边界与明确压力用例验收，不修改产品窗口下限。

连续长文本应换行且可读，不能靠横向裁剪隐藏一部分内容。富文本中的 `<br>`、表格和既有局部滚动保持原语义；不要全局改所有消息子节点的 `white-space` 或移除业务已有的内层滚动。

### 3.6 业务合同逐项不变

前置资金保留原可修复项筛选与 `repairTokens` 映射，保留 `repairMptErrors(repairTokens)`、`exportMptErrors(repairTokens)`，以及“删除错误数据并重跑／导出错误数据／关闭”的顺序与 `data-action`。打开、滚动、窗口调整、取消或关闭均不新增业务调用。[S3]

资金对账保留链接表导入结果与 ADM／BOC 链式反馈顺序，保留“现在导入／稍后”等既有分支，不修改派生或入库语义。[S3]

工具箱保留成功／失败状态、文件名／路径、warning 生成规则及原有样例上限；普通多文件拆分成功和所有失败反馈仅获得默认布局保护。[S4]

公共工厂保留现有签名、返回 overlay、日志 options、confirmSecondary、按钮文案和事件。`createAlertDialog` 的既有“关闭成功后再回调”与 confirm 的“业务回调决定提交链”不能被统一重写为新的关闭时机。对于参数声明与历史实际行为的差异，本次不顺带修复。[S1]

不新增业务 busy 锁或二次确认，不声称所有调用方都已有同样锁。回归当前关闭资格与重复点击路径；如发现独立业务漏洞，记录并另行界定范围，不静默扩大本次变更。

### 4.4 几何与真实输入断言

长结果弹窗为栈顶时，读取视口、card、body、footer、各按钮的实际矩形，允许约 1 CSS px 的取整误差：

1. card 和 footer 在视口内；每个按钮矩形均在 card 可见范围内，不仅中心点在内。
2. 长正文 `scrollHeight > clientHeight` 且 `clientHeight > 0`；正文可见底边不越过 footer 顶边。
3. 将正文滚动到顶／中／底，footer 与按钮位置在无 resize 时稳定；到底后最后一项实际进入正文可视区。
4. 调整窗口／zoom 之后再次测量；按钮换行允许 footer 高度改变，但新的布局仍完整可操作。
5. `elementFromPoint` 命中各按钮或其子节点，随后用隔离窗口的真实鼠标输入触发受控回调；DOM `button.click()` 只用于逻辑测试，不能证明“未被遮挡”。
6. 键盘进入正文后滚动有效，按钮获得焦点时保留原键盘操作；背景与非顶层不响应业务事件。
7. 打开、滚动、resize、Tab、关闭对业务 API 的调用计数保持原预期；单次受控按钮输入对应原回调。

几何与业务回调断言使用独立实例，避免一次点击关闭弹窗后污染后续测量。真实输入测试必须保证隔离窗口可接收输入；若环境无法提供真实输入，不用 `.click()` 代替后声称通过，而是记录缺口并保留 Windows 人工验收项。
