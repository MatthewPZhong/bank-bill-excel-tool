## 1. 背景

本功能分支只调整两组设置的默认值，不新增设置项，不重做设置页面：

| 设置项 | 目标默认值 |
| --- | --- |
| 启用定时深色模式 | 开启 |
| 深色模式开始时间 | 17:30 |
| 深色模式结束时间 | 07:00 |
| 输入/输出文件保留期限，使用模块＝默认 | 永久 |
| 存档服务内部未注入策略解析器时的默认保留期限 | 永久 |

用户输入的 `1730`、`0700` 在方案及配置中规范表示为 24 小时制 `17:30`、`07:00`。界面现有字段名称是“适用模块”，默认选项文案为“默认（未单独设置的模块）”；本次不改文案。

**需求与方案补充的区分：**上表为用户明确要求。已有配置是否覆盖、历史批次是否迁移未由用户单独指定；本方案按“仅改变默认值、保留有效既有配置、保留已建批次快照”的保守范围设计，详见 §4.3。这不是一次面向所有老用户的强制配置迁移。

2026-09-29 用户追加要求：`archive-service.js` 内部独立的 60 天默认也改为永久。因此本方案同时调整策略层和服务层默认，并同步服务构造参数对 `null` 的支持。

## 4. 功能点

### 4.1 功能点 1：定时深色模式默认开启

**入口：**设置 → 外观设置。

未保存有效配置时，开关默认开启，开始时间为 `17:30`，结束时间为 `07:00`。沿用电脑本地时间和现有调度器，区间包含开始、不包含结束：

| 本地时间 | 新默认配置的实际主题 |
| --- | --- |
| 07:00 ≤ 当前时间 < 17:30 | 浅色 |
| 17:30 ≤ 当前时间，或当前时间 < 07:00 | 深色 |

软件启动即按当时的时间确定主题，不要求用户先进入设置页；跨午夜连续保持深色。开启开关不等于全天深色，白天仍应显示浅色。用户关闭开关后沿用现有浅色行为，并保留其时间设置。

设置读取、主进程主题、窗口底色及前端展示必须一致。休眠恢复、窗口重新聚焦和本地时间变化继续沿用现有重判能力，不在 Renderer 新建第二套调度器。

### 4.2 功能点 2：默认输入/输出文件保留期限改为永久

**入口：**设置 → 存档中心 → 存档设置 → 输入/输出文件保留期限。

当“适用模块”为“默认（未单独设置的模块）”，且未保存有效全局保留期限时，保留期限默认为“永久”。输入文件和输出文件均遵循其所属批次的期限，不能只更改其中一种方向。

未单独设置期限的模块继续继承默认值，不把这些模块逐个写为显式永久。模块已有 30、60、90、180、365 天或永久配置时，继续采用各自配置。业务建批入口已有显式期限参数的，继续保留其原有优先级，不因本次更改而强制永久。

存档服务未注入 `resolveRetentionDays` 时，同样默认永久。`defaultRetentionDays` 省略、为 `undefined` 或显式为 `null` 均表示永久；显式传入合法有限期限继续作为无解析器路径的默认值。服务层有限期限沿用 1–36500 天范围和既有数值转换行为，不收窄为设置页的五个枚举。已注入解析器时继续采用解析结果；合法 `null` 不得被转换成 0 或重新回退为 60 天。

**“永久”的范围：**不因保留期限到期而自动清理；不等于锁定，不禁止用户按既有授权流程手动删除，也不改变失败任务、临时文件等其他独立生命周期规则。

### 4.3 兼容性与生效范围（方案补充）

| 场景 | 本方案处理 |
| --- | --- |
| 新安装 / 对应设置键缺失 | 使用本次新默认值 |
| 老版本曾读取默认值，但没有持久化该设置 | 升级后使用新默认值 |
| 已保存完整、有效的深色配置，包括关闭状态 | 原样保留开关和两个时间，不覆盖 |
| 已保存 60 天等有效全局保留期限 | 保留原值，即使它恰好等于旧默认值 |
| 已保存模块独立期限 | 保留，不清空、不批量改为永久 |
| 深色 JSON 损坏、配置缺字段或整体无效 | 沿用整组规范化回退，使用新默认对象；不新增逐字段拼接，不在读取时覆盖原始记录 |
| 全局保留设置缺失、空或无法解析为合法期限 | 沿用读取回退机制，回退到新的永久默认值 |
| 非法设置提交 / 设置保存失败 | 继续返回失败，不把非法提交当成有效默认值保存，不修改已生效状态 |
| 已建批次、预留批次、已持久化的归档待办快照 | 保留原期限，不新增扫描或回填迁移；幂等重入不能重新套用新默认值 |
| 新批次无显式期限、无模块覆盖，且全局设置缺失或无效 | 使用新的永久默认值 |
| 服务未注入解析器，构造默认期限省略、为 `undefined` 或为 `null` | 新批次采用永久默认 |
| 服务未注入解析器，显式提供合法有限构造默认期限 | 新批次采用该有限期限；批次显式期限仍优先 |

不以“值等于旧默认”推定“用户没有设置过”。因此，**已保存关闭或 60 天的老用户升级后不会自动变为开启或永久**。若产品目标是让这部分用户也强制变更，需要另行明确迁移范围；不纳入本方案。

## 6. 技术决策

采用“共享深色默认 + 策略层和服务层保留默认同步 + 前端初值同步”。深色调度沿用原算法，保留期限沿用现有永久表示；服务构造器先区分 `undefined`、`null` 和有限期限，再校验数值，避免默认改为 `null` 后初始化失败。不新增依赖，不做配置格式迁移。

不采用仅修改页面选中项的方案，因为它不会改变真实建批策略；不采用启动时强制覆盖方案，因为它会改变用户已保存的偏好与保留期限；不采用把所有模块写成永久的方案，因为它会破坏模块继承。

详细改动和回归任务见 [TechDoc](./techdoc.md)。

## 7. 数据 / 状态 / 安全影响

无新增表、字段、设置键或批量数据迁移。永久期限将延长采用新默认值的新批次的存档时间，磁盘占用可能持续增长；继续沿用存档容量展示和手动删除功能，不额外增加自动清理兜底。

永久的业务值 `null` 不得在数值转换时变成 `0`，也不得通过 `?? 60` 或 `|| 60` 重新回退成 60 天。全局设置的数据库未命中 `null` 与已解析业务期限 `null` 位于不同层，不能混用。

回滚代码时，已明确保存的新时间及永久值仍使用原有合法格式；缺失配置将重新采用旧代码默认值。已建永久批次不得在回滚中批量缩短期限或触发补删。回滚验证见 TechDoc。

服务构造器对 `null` 的支持属于本次运行时合同变化；若新增显式传入 `defaultRetentionDays: null` 的调用方，回滚时须与构造器实现同步处理，避免新调用方配旧构造器而初始化失败。
