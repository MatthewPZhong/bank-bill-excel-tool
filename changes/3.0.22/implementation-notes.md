# Implementation Notes - v3.0.22 设置页内存档中心

> updated: 2026-07-20
> branch: `codex/v3.0.22-archive-center`

## Baseline

- 目标：在设置页增加存档中心，保存 11 个模块的业务输入和第一次结果。
- 原型：`changes/3.0.22/archive-center-settings-prototype.html`。
- 非目标：不新增主模块、不改变任何资金计算和 Excel 内容、不提供恢复或重跑。

## Decisions

| ID | 决定 | 原因 |
|---|---|---|
| D-01 | 设置弹窗改为双导航，默认自动更新。 | 保留既有入口并避免增加第 12 个主模块。 |
| D-02 | 成功运行/成功生成才建批。 | 与“只导入不存档”一致，避免留下无业务结果的档案。 |
| D-03 | 输入只在当前启动周期内暂存路径。 | 不为 11 个异构模块新增跨重启 receipt 和迁移。 |
| D-04 | 链接表和临时 MPT 成功导入独立成批。 | 这些持久数据会被多次运行复用，不应在每个运行批次重复挂接。 |
| D-05 | 活动批次按 `moduleId + moduleCode + runKey` 隔离。 | 同一主模块下正式运行、链接表和临时表会并存，仅按 moduleId 会错绑。 |
| D-06 | 共享 `recon-id-fix:run` 显式携带 `originModuleId`。 | 资金对账页和专用修复页复用 IPC，按通道名无法判断实际模块。 |
| D-07 | 业务返回后才排队复制，队列只保留轻量结果快照。 | 归档 I/O 不阻塞业务，也不因排队持有大批银行行。 |
| D-08 | Blob 使用 SHA-256 内容寻址，逻辑引用保留原文件名。 | 满足全局去重，同时保留用户可识别的批次文件清单。 |
| D-09 | 设置损坏时网银模板排除按隐私优先处理。 | 无法确认排除策略时不应擅自保存网银文件。 |
| D-10 | 没有本次周期文件的历史运行不建空批。 | 避免“存档完成但没有任何可证明文件”的误导状态。 |
| D-11 | 日流水使用独立 `archive_batch_sequences` 游标表。 | 从现存批次取最大值会在删除最高批次后复用用户已见号码。 |
| D-12 | 仅 39 个归档相关 IPC 进入 AsyncLocalStorage 和归档队列。 | 防止无关 IPC 参数被闭包持有，也避免所有请求都追加空队列任务。 |
| D-13 | 重启后的历史单次导出必须存在当前周期活动批次才可追加。 | 当前版本不持久化 run/result receipt，禁止生成来源不完整的 output-only 批次。 |
| D-14 | 模板排除设置损坏时先排除全部当前模板，保存时同步当前模板集合。 | 采用隐私优先默认，同时保证新模板不会因旧集合遗漏而被意外存档。 |
| D-15 | 删除元数据成功、物理文件清理失败时显式返回部分成功。 | UI 应刷新已删除批次，同时提示残留文件待启动修复，不能误导用户重复删除。 |
| D-16 | 存档目录暂不可写时仍登记失败批次，恢复后允许原批次重试。 | 存储故障不应让业务失败，也不能丢失用户可见的失败记录和补救入口。 |
| D-17 | “另存为”目标禁止位于存档根目录内。 | 防止用户覆盖内容寻址 Blob、只读副本或内部元数据目录。 |
| D-18 | 批次号筛选下沉到 SQLite 查询。 | 避免先截取最近 1000 条再在内存筛选，导致较早的精确批次无法找到。 |
| D-19 | 批次详情公开对象同时剥离源路径和 Blob 内部相对路径。 | Renderer 只持有不可反查磁盘布局的文件引用 ID，内部目录结构不跨 IPC。 |
| D-20 | 显式 run key 只做精确批次绑定，找不到时不回退 latest。 | 历史导出不能被静默挂到当前运行批次。 |
| D-21 | 业务成功后立即记录轻量文件身份，后台复制前再次核对。 | 串行队列等待期间同路径文件可能被覆盖，不能把新内容冒充原输入/结果。 |
| D-22 | 同批全部 artifact 在首个文件复制前登记，正常退出等待归档队列排空。 | 确保中断后的启动修复拥有完整重试清单，不丢失尚未开始复制的后续文件。 |
| D-23 | 临时 MPT 修复按源文件与结果下标绑定，不按 basename 集合筛选。 | 不同目录可存在同名文件，按名称会把失败文件误记为成功。 |
| D-24 | 月度余额批次不写入普通网银账单 latest 活动槽。 | 避免随后余额补录结果被追加到无关月度余额批次。 |
| D-25 | 另存目标同时做词法路径和 realpath 目录检查。 | 阻止 symlink/junction 绕过“不能写入存档内部”的保护。 |

## Deviations

### DEV-01 规格基线曾扩展为跨重启 receipt 和失败运行批次

- 原基线：内部 UUID、持久输入 receipt、失败/取消运行也建批、跨重启 result CAS、保留期追溯既有批次。
- 实际：内部使用 SQLite 数字主键；输入与首次结果绑定为当前启动周期内存状态；仅成功运行/生成建批；保留期只用于新批次。
- 原因：上述扩展没有用户确认，且会显著改变 11 个模块的数据模型与业务生命周期。
- 影响：旧持久数据不补档；重启后无法把历史导出绑定到旧运行；这些能力明确列入非本轮范围。
- 已反向同步：`spec.md`、`test-spec.md`、`tasks.md`。

### DEV-02 持久链接数据不重复挂到每次运行

- 原基线：每次运行归档所有实际消费的持久链接表源文件。
- 实际：成功导入链接表/临时 MPT 时建立所属模块独立输入批次；运行批次只保存本次直接导入文件和结果。
- 原因：当前链接表没有稳定“源文件 -> 当前每行 -> 每次 run”跨重启血缘，重复挂接会依赖猜测。
- 影响：可证明“某文件成功进入链接表”，但不宣称每次运行批次包含全部持久源文件。

### DEV-03 退出策略由固定 5 秒上限改为完整排空

- 原计划：正常退出最多等待后台存档 5 秒，超时后依赖下次启动修复。
- 实际：超过 5 秒仅写慢退出告警，正常退出和升级重启继续等待归档队列排空。
- 原因：尚在主队列等待的操作还未登记到 SQLite，固定超时会永久丢失整批血缘，启动修复无从恢复。
- 影响：大文件存档时正常退出可能多等待一段时间；强制结束进程仍由“复制前整批登记 + 启动一致性修复”兜底。
- 已反向同步：`spec.md`、`test-spec.md`、`tasks.md` 和三份版本文档。

### DEV-04 首次发布暴露 Windows 测试可移植性假设

- 原状态：两条单测分别写死 POSIX 路径和 LF 换行，在 macOS 与 PR workflow 中通过。
- 实际：首次 `v3.0.22` Windows 发布 workflow run `29814335578` 在打包前的 release-check 失败，未生成 Release 或发布资产。
- 修复：路径快照与输入统一使用 `path.resolve`，源码契约断言读取后先将 CRLF/LF 统一为 LF；不修改业务实现或发布契约。
- 证据：相关定向测试 `34/34` 通过，完整 release-check 再次通过 unit `3780/3780`、integration `1955/1955` 和 Smoke。

## Rollback

- 代码回滚后旧版本会忽略新增 SQLite 表和存档目录，不影响原业务模块。
- 不自动删除已有存档文件；需要清理时先在新版本存档中心删除，或由用户人工处理 Documents 下存档目录。
- 本迭代没有业务数据迁移或金额/匹配规则变更。
