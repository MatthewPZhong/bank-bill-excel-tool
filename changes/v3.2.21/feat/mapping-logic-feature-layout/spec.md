# Spec — 映射关系管理迭代：逻辑取值候补支持特征值、「启用」列与布局调整

> status: in-progress
> created: 2026-11-19
> 目标版本：v3.2.21（暂定，发版时按 weekly-release 调整）
> 适用分支：`feat/mapping-logic-feature-layout`
> 分支基线：正式标签 `v3.2.20`（`08d1fb41`）
> 依据：2026-11-19 用户需求（网银账单生成模块 · 映射关系管理）及同日确认的两项决策
> 格式来源：`changes/v3.2.20/feat/retire-recon-modules/spec.md`、`changes/v3.2.19/feat/bill-split-fee-amount/spec.md`

## 1. 背景

1. 映射字段「逻辑取值」（v3.2.19）的候补只能选源字段，用户需要把模板的特征值（「字段筛选特征值」v3.2.18 的具名特征值）也作为候补。
2. 映射关系管理「账单拆分合并设置」的排序、「原始账单预处理」等勾选行的布局需要调整；勾选后按钮出现使行高跳变；Windows 端模板字段名「Transaction Description」「By Order Of/Beneficiary」换行。

## 3. 规则

### 3.1 逻辑取值的特征值候补（D1、D2）

- 存储：特征值候补在映射行 `mapped_fields_json` 中存为 `\u0000__FEATURE_FILTER__:<特征值 id>`（以 NUL 开头，id 去首尾空白），源字段候补仍存列名；顺序即优先级。按 id 引用，特征值改名不影响。
  - 冲突与旧包提示不带候补原文与特征值 id（含 NUL，id 也可能是模板包带入的任意字符串，提示框按 HTML 渲染）。
  - 以 NUL 开头的原因：v3.2.19/v3.2.20 的候补都是源列名，没有标记可区分；表头不会含 NUL，旧候补即使形如 `__FEATURE_FILTER__:1` 也照常按源列读取，不会升级后改从同 id 特征值取值（资金红线）。构造的表头（如 XLSX 以 `_x0000_` 转义写出的 NUL）与特征值候补写法相同时无法区分：保存（按原写法与规范写法都检查）与生成都拒绝，不任选其一；模板【更新】在当前或新表头出现这种列名时，预览与确认都拒绝（更新后无法再判断该候补原是源列），要求先重选候补。
  - 已知残余风险（不处理，见 `knowledge/backlog.md` B112）：v3.2.19/v3.2.20 时若用过构造的含 NUL 列名作候补、且升级前已经【更新】删掉该列，升级后该失效候补会被认作同 id 的特征值。只有当时的列名恰好是这种写法才会发生。彻底排除需要一次性启动迁移，按「不因假想风险增加流程」未做。
  - 界面下拉框中特征值选项的 value 用 DOM 属性赋值（NUL 经 HTML 解析会被替换）。
- 界面：【设置】弹窗的候补下拉框分「源字段」「特征值」两组（模板没有特征值时不分组）；选中的特征值显示名称；映射行预览显示「名称（特征值）」，【特征值管理】改名后跟着刷新；找不到的特征值候补显示「特征值（已删除）」并标红，映射行预览也标红并在最前提示「（含已删除的特征值，请重新设置）」（不被 80 字截断）。
- 保存校验：至少 2 个候补、不重复（重复提示按显示名称）不变，特征值候补先统一为规范写法再查重（同一特征值的不同写法算重复）；特征值候补不按表头校验，改为校验特征值存在且条件有效（与「字段筛选特征值」同一校验，标签为「字段（逻辑取值）」）。拆分/合并映射仍不支持逻辑取值。
- 生成：逐行按候补顺序取第一个去首尾空白后非空的值；特征值候补取该行筛出的特征值，未筛出为空。没有 id 的特征值候补按特征值不存在拒绝生成（配置无效不等于未筛出）。逻辑取值引用的特征值按所在映射是否生效启用（同「字段筛选特征值」），筛选源字段不在源文件表头时拒绝生成。
- 未筛出提示：只为直接选「字段筛选特征值」的字段记录；同一特征值另被直接选用时，直接选用的字段照常提示。
- 合计行识别（资金红线）：BillDate 为逻辑取值且候补含特征值时，合计标签会被筛成空、落到下一个候补；按候补顺序检查**实际查看过的**特征值候补（到第一个取到值的候补为止）的筛选源单元格，任一为合计标签（且带金额）即按合计行跳过并记入 `summary-row-skipped`（生成结果提示行数与明细），不把合计金额当普通交易导出。原始账单预处理过滤掉的行不套用这一判定，沿用 v3.2.19 口径（任一 BillDate 映射取到有效日期即算上一段的交易行，作为桥接候选的界线）；直接识别不受该界线裁剪，属既有问题 B113。
  - 多账户分段的大账号识别口径不变（与 v3.2.20 一致）：这里识别出的合计行与其他合计行一样只是不进明细，识别时的处理同既有合计行。既有合计行在识别中的问题（合计行上的上一段账号可能被当成下一段的账号）与本功能无关，见 `knowledge/backlog.md` B113，需单独立项并人工复核。已取到值之后的候补不检查，避免把真实交易误判为合计行而少记。直接选「字段筛选特征值」的识别口径（只看第一个特征值）不变。
- 删除保护：被逻辑取值候补引用（已保存映射或当前草稿）的特征值不能删除，提示「特征值「X」正被 字段（逻辑取值） 使用」。新特征值的 id 避开已保存映射（主映射、拆分映射）仍引用但特征值已不存在的 id（数字 id 按 BigInt 比较递增，超出安全整数也不会复用），悬空引用不会被绑定到新规则；导入模板包时，包内映射引用的 id 同样不分配给未带 id 的特征值。特征值 id 按自有属性解析，与对象原型属性同名（如 `constructor`）也照常生效。
  - 行切到其他映射值时暂存的候补不算引用，特征值可以删除；特征值增删改后，从这些已切走行的暂存候补中去掉已不存在的特征值，避免之后新建、复用同一 id 的特征值被当成原先的选择。去掉后不足 2 个候补时，保存映射时照常提示重新设置。仍选着逻辑取值的行不去掉，显示「特征值（已删除）」，由保存时校验要求重选。
- 模板【更新】：特征值候补不计为源字段引用；被候补引用的特征值视为启用，其筛选字段失效时列出并在生成前拦截。
- 模板包：导入 v8 及更早的包时，形如特征值候补的值按旧语义是源列名：表头中没有该列（失效的旧候补）时拒绝该模板，不改认作特征值（跳过的模板名与原因写入活动日志）。任一模板的逻辑取值候补含特征值时写 **v9**（固定的功能版本 `LOGIC_VALUE_FEATURE_BUNDLE_VERSION`，与能读取的最高版本 `SUPPORTED_BUNDLE_VERSION` 分开）（`SUPPORTED_BUNDLE_VERSION` 8 → 9），v3.2.20 及更早版本按版本整包拒绝（否则会把 token 当源字段名报「映射字段不存在」跳过模板）；其余情况版本规则不变（v5～v8）。包内特征值保留 id，导入后候补引用不变。

### 3.2 映射关系管理布局（D3～D7）

- 排序（D3）：`BILL_SPLIT_GROUP_FIELDS` 调整顺序；映射按字段名读写，顺序只影响展示，不影响已存数据。
- 「启用」列（D4、D5）：
  - 「启用」12px（同分组标题）、浅色主题暗绿 `#006400`，夜间亮绿 `#7fcf97`；文字盒右边缘 = 映射字段列内容左边缘 = 【规则设置】左侧，落在两列之间的内边距中，不挤占字段名与按钮。
  - 两条竖线与「启用」文字盒左右边缘重合（文字盒两侧各留 3px，文字不贴线），从「启用」文字顶部开始，贯穿「原始账单预处理」「个性化映射设置」「账单拆分合并设置」各行，止于「复用模块字段的映射关系」文字下方 4px；竖线颜色同「启用」。
  - 勾选框水平居于两条竖线中间、垂直居于所在行中心；点击文字或勾选框照常切换。
  - 旧载荷没有「原始账单预处理」标题行或其后没有勾选行时不显示该列，勾选框回到文字右侧。
- 行高（D6）：勾选行的编辑区最小高度 = 按钮高度（36px），无按钮的行（如「重复账单过滤」）同高。
- 宽度（D7）：模板字段列 220px → 240px，弹窗 780px → 800px，映射字段列宽度不变。Windows 端英文为 Courier New（14px 约 8.4px/字符），两段 23 字符约 193px，列内容宽 208px。

## 4. 非目标

- 不改「字段筛选特征值」本身的规则、未筛出提示文案与【特征值管理】交互。
- 不改拆分/合并账单映射（仍不支持逻辑取值）。
- 不调整其他弹窗（如拆分/合并账单映射关系设置）的宽度。
