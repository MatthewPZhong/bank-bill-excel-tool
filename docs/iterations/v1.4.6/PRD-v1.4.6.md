## 一、需求概述

本版本包含 5 项需求：

1. **多币种枚举缺失 + 币种大写强制** -- 维护大账号"自己输入"模式下多币种下拉枚举不全，且币种输入需强制转大写
2. **模板选择框初始值** -- 每次重新打开应用时，模板选择下拉框恢复为"请选择模板"
3. **按钮文本溢出** -- 映射关系管理里"选择字段"按钮文本溢出，所有相同样式按钮不允许溢出
4. **维护大账号新增两个功能按钮** -- 导入银行账号信息、余额管理
5. **新开账户余额账单逻辑** -- 生成从开户日期到当前系统日期每一天的余额

### 需求 1：多币种枚举缺失 + 币种大写强制

#### 1.1 功能说明

**Bug 描述 -- 多币种枚举缺失：**

维护大账号对话框（`createBigAccountManagerDialog`）中，当用户勾选"多币种"后，点击下拉按钮弹出的币种浮动面板（`big-account-currency-floating-panel`）中的币种选项不全，只有少量币种。

**根因分析：**

- 经评审确认，`src/renderer-dialogs.js` 的 `createBigAccountManagerDialog` 只有一套实现路径（约第 799-1204 行），已使用 `getCurrencyOptionEntries()` 获取币种列表，`renderCurrencyDropdownOptions`（第 858 行）也正确遍历 `currencyOptionEntries`。当前实际运行走的是新版路径（`renderer-dialogs.js` 的工厂函数内，通过 `renderer.js:184` 调用）。文件中不存在旧版 legacy 的 `createBigAccountManagerDialog`，无需清理。
- **代码路径本身无 bug**。如果用户确实看到币种不全，原因可能是 `state.currencyOptions` 在 `app:get-info` 返回时数据不完整（如 `assets/币种映射表.xlsx` 文件缺失或内容不全），属于数据源问题而非代码逻辑问题。
- **处理方式**：开发在实施时先排查数据源，如确认 `assets/币种映射表.xlsx` 和 `getAvailableCurrencyCodes()`（`src/main.js:793-824`）返回值完整，则枚举缺失部分标记为"已确认无代码修改"，仅保留币种大写强制的修改。
- **QA 验证手段**：测试时可通过开发者工具控制台执行 `console.log(state.currencyOptions.length)` 与 `assets/币种映射表.xlsx` 的数据行数对比，确认 `getAvailableCurrencyCodes()` 返回值完整。

**目标行为 -- 枚举缺失：**

- 维护大账号对话框中，勾选"多币种"后弹出的币种选择面板应展示完整的币种枚举列表（与 `assets/币种映射表.xlsx` 中的数据一致）。
- 币种选项的显示格式为 `{英文代码} {中文名}`（如 `CNY 人民币`），与新开账户模块多币种面板、大账号选择对话框的币种格式保持一致。

**Bug 描述 -- 币种大写强制：**

维护大账号对话框中，单币种模式下的文本输入框（`big-account-currency-input`）允许用户输入小写字母（如 `cny`），点击"完成"后保存的值是小写的，不会自动转为大写。

**目标行为 -- 币种大写强制：**

- 用户在维护大账号对话框中点击"完成"（行级别的完成按钮，即 `toggle-complete`）时，如果币种输入框中有值，强制将其转换为大写后再保存。
- 即 `currencyInput.value = currencyInput.value.trim().toUpperCase()` 在 `toggleCompleteBtn` 的 click handler 中、`row.dataset.mode === 'edit'` 分支的 `validateRowDraft()` 之前执行。
- **关于对话框级"完成"按钮**：当前代码（`renderer-dialogs.js:1177`）在对话框级"完成"点击时，如果存在任何 `mode === 'edit'` 的行，会提示"请先完成或删除当前编辑行"并阻断操作。因此用户无法跳过行级"完成"直接保存，币种大写转换只需在行级"完成"处理即可。

### 需求 2：模板选择框初始值

#### 2.1 功能说明

**做什么：**

每次重新打开应用时，模板选择下拉框（`#templateSelect`）应恢复为初始值"请选择模板"，而不是自动选中某个模板。

**当前实现：**

- 文件：`src/renderer.js` 约第 1595-1619 行 `updateTemplateSelect` 函数
- 当前逻辑：如果存在之前选中的 `state.selectedTemplateId` 对应的模板，则恢复选中该模板；否则自动选中第一个模板（`fallback = state.templates[0]`）
- 这意味着应用启动后，模板选择框总会自动选中一个模板（要么是上次选中的，要么是第一个）

**目标行为：**

- 应用启动时，`state.selectedTemplateId` 应初始化为空字符串 `''`
- `updateTemplateSelect` 在启动时首次调用时，不应自动选中第一个模板作为 fallback
- 下拉框显示 placeholder option "请选择模板"
- 用户手动选择模板后，`state.selectedTemplateId` 正常更新
- 在同一次应用会话中，如果用户导入了新模板或执行了模板管理操作导致 `refreshTemplates` 被调用，应保留当前用户已选中的模板；但如果之前未选中任何模板（`previous === ''`），则仍然显示"请选择模板"

**实现要点：**

- 修改 `updateTemplateSelect` 函数中的 fallback 逻辑：当 `previous === ''`（初始状态或用户未选择）时，不自动 fallback 到第一个模板
- 具体改动：将 `const fallback = state.templates[0]` 改为仅在 `previous` 有值且 `preserved` 不存在时才使用 fallback（即用户曾经选过但该模板已被删除的场景）

#### 2.2 交互流程

1. 用户启动应用
2. 模板选择下拉框显示"请选择模板"，未选中任何模板
3. 用户手动选择一个模板（如"CNCB-CN"）
4. 导入文件等操作正常执行
5. 用户关闭应用并重新打开
6. 模板选择下拉框再次显示"请选择模板"

#### 2.3 UI 说明

```
启动时：
  [请选择模板         ▾]   <- 显示 placeholder，value 为空

用户选择后：
  [CNCB-CN-3973       ▾]   <- 正常显示所选模板

重新启动后：
  [请选择模板         ▾]   <- 再次显示 placeholder
```

### 需求 3：按钮文本溢出

#### 3.1 功能说明

**Bug 描述：**

映射关系管理对话框中，拼接字段选择器的"选择字段"按钮（`.concat-picker-trigger`，class 为 `secondary-btn small`）在某些情况下文本溢出按钮边界。

**目标行为：**

- 所有使用 `.secondary-btn.small` 样式的按钮，其文本不允许溢出按钮容器
- 超出时应截断并显示省略号（`text-overflow: ellipsis`），或确保按钮宽度足以容纳文本

**根因分析：**

- `.concat-picker-trigger` 设定了 `min-width: 80px; height: 34px`（`src/styles.css:870-872`）
- 但"选择字段"四个中文字符加上按钮的内边距可能超过 80px 的最小宽度
- `.secondary-btn.small` 的基础样式为 `min-width: 108px; height: 38px`，但 `.concat-picker-trigger` 覆盖了高度为 34px 且 min-width 缩小为 80px

**修复方案：**

- 优先在 `.secondary-btn.small` 基类上统一添加 `overflow: hidden; text-overflow: ellipsis; white-space: nowrap`，一次性保护所有 small 按钮，无需单独处理 `.concat-picker-trigger`

#### 3.2 交互流程

无交互变更。纯 UI 样式修复。

#### 3.3 UI 说明

```
修复前：
  [ 选择字段 ] <- 文本可能超出按钮边界

修复后：
  [选择字段]  <- 文本完全在按钮内部，不溢出
```

| AC 编号 | 验收条件 |

| AC3-4 | 不影响其他 `.secondary-btn` 样式按钮的外观 |

#### 4.1 功能说明

在维护大账号对话框（`createBigAccountManagerDialog`）的底部操作区域（`.big-account-footer-actions`），在现有"新增"按钮右侧，新增两个平行等距的功能按钮：**导入银行账号信息** 和 **余额管理**。

---

#### 4A：导入银行账号信息

##### 4A.1 功能说明

**做什么：**

点击"导入银行账号信息"按钮，弹出文件选择器选择一个 Excel 文件。系统读取 Excel 内容，按指定条件提取银行账号和币种数据，分两个用途存储：

- **客资账号** -> 写入当前模板的大账号表（`bigAccounts`）
- **自有账号** -> 独立 JSON 文件存储（按 bankName 区分）

**IPC 设计说明：**

IPC handler（`big-account:import-bank-info`）的职责为：在主进程中弹出文件选择对话框 → 读取 Excel → 解析 → 返回 `{ clientAccounts, ownAccounts }` 给渲染进程。渲染进程收到后负责重新渲染 tbody。这与 `template:import`、`file:import` 等现有 handler 的模式一致。

**Excel 解析模块位置：**

Excel 解析逻辑应放在新模块 `src/backend/bank-account-import.js`（职责单一），不放在 `file-service.js`（该模块专注于网银账单的读取/映射/导出）。

**Excel 解析规则：**

系统读取 Excel 文件的表头行，按以下列名匹配字段。列名匹配规则：trim 后精确全等匹配（不做包含匹配、不区分"账"/"帐"等同音字、不处理换行符——如匹配失败则视为缺少该列）：

| 需要的字段 | 对应列名 |
|-----------|---------|
| 账户性质 | `账户性质` |
| 账户状态 | `账户状态` |
| 是否参与对账 | `是否参与对账` |
| 银行账号 | `银行账号` |
| 币种 | `币种` |

**提取条件 A -- 客资账号：**
- `账户性质` = `客资` **且** `账户状态` = `正常` **且** `是否参与对账` = `是`
- 提取 `银行账号` + `币种` 字段
- 同一银行账号出现多次（不同币种行），合并为一个大账号条目下的多币种（`currencies` 数组）
- 如果同一银行账号只有一个币种，`isMultiCurrency = false`；有多个币种则 `isMultiCurrency = true`
- 结果写入大账号表，**替换**当前模板的全部 `bigAccounts` 数据

**提取条件 B -- 自有账号：**
- `账户性质` = `自有` **且** `账户状态` = `正常` **且** `是否参与对账` = `是`
- 提取 `银行账号` + `币种` 字段
- 同一银行账号出现多次（不同币种行），同样合并币种
- 结果存储到独立 JSON 文件（路径：`{storageRoot}/own-accounts/{bankName}.json`），按 bankName 区分（bankName 由 `splitTemplateName` 取模板名第一段）
- 数据格式与 `bigAccounts` 相同：`[{ merchantId, currencies, isMultiCurrency }]`
- **已知限制**：删除模板不会清理对应的自有账号 JSON 文件（与 balance-seeds 的行为一致）。孤儿文件不影响功能，本版本不处理清理

**币种值的标准化：**
- 从 Excel 读取的"币种"列值不经过 `resolveCurrencyValue` 映射（不做中文→英文代码转换）。
- 但需做 **trim + toUpperCase** 处理，与需求 1 的币种大写强制保持一致。例如 Excel 中的 `" cny "` 处理为 `"CNY"`。
- 如果用户发现导入的币种格式不符预期，可在大账号表中手动修改后保存。

**关于"替换"行为和持久化时机的说明：**
- 导入客资账号时，替换当前模板的全部 `bigAccounts`。用户现有手动维护的大账号数据将被覆盖。
- 导入前不弹出确认对话框（因为导入后用户可以在大账号表中继续编辑修改再完成保存）。
- **客资账号**：导入操作仅修改对话框内存中的大账号列表（重新渲染 tbody），不直接写入数据库，需用户点击"完成"后才真正持久化。
- **自有账号**：也在用户点击"完成"后才持久化到 `{storageRoot}/own-accounts/{bankName}.json`，与客资账号保持一致的持久化时机。如果用户导入后不点击"完成"（如点击关闭），自有账号也不保存。
- **关闭对话框（点击 X）的行为**：调用 `onCancel()`，丢弃所有导入数据，恢复到打开对话框时的状态。导入后的客资账号和自有账号均不保存。

##### 4A.2 交互流程

1. 用户在维护大账号对话框中，点击"导入银行账号信息"按钮
2. 系统弹出文件选择对话框（仅 Excel 格式：`.xlsx`、`.xls`）
3. 用户选择文件后，系统解析 Excel
4. 如果 Excel 中找不到必要的列名（如缺少"账户性质"列），弹出提示"导入的文件中缺少必需列：{缺少的列名}"
5. 如果没有匹配到任何满足条件的行，弹出提示"未找到符合条件的银行账号信息"
6. 解析成功后：
   - 客资账号自动填充到对话框的大账号表中（替换现有行，以"view"模式渲染）
   - 自有账号静默存储到 JSON 文件
   - 状态栏显示"已导入 {n} 个客资账号、{m} 个自有账号"
7. 用户可在大账号表中继续编辑、新增、删除
8. 点击"完成"后保存（与现有保存逻辑一致）

#### 4B：余额管理

##### 4B.1 功能说明

**做什么：**

点击"余额管理"按钮，弹出余额管理对话框。用户可为大账号录入"余额附加值"，该附加值将参与余额导出计算。

**弹窗内容：**

余额管理弹窗包含一个表格，每行五列 + 右侧一个"删除"按钮：

| 列名 | 控件类型 | 说明 |
|------|---------|------|
| 大账号 | 单选下拉框 | 选项来自当前模板的大账号列表（`bigAccounts` 中的 `merchantId`），去重 |
| 币种 | 自动带出 / 下拉框 | 若所选大账号仅有单个币种，自动填充且不可编辑；若多币种，显示为下拉框供选择 |
| 日期 | 日期输入框 | 复用现有日期输入框样式（与新开账户的开户日期输入框行为一致：点击弹出 date picker） |
| 余额附加值 | 文本输入框 | 仅允许输入数字（含负数和小数） |
| 备注 | 文本输入框 | 自由文本 |

每行右侧有"删除"按钮，可删除该行。

弹窗左下角有"新增"按钮（新增空白行），右下角有"完成"按钮。

**"余额附加值"参与余额导出的规则：**

- 余额附加值存储后，在生成余额账单时被使用
- 规则：对于填写日期当日及之后的所有余额记录，余额 = 原始余额 + 余额附加值
- 即余额附加值是一个"从某日起叠加的永久偏移量"
- **累加规则**：同一大账号 + 币种可以有多条不同日期的余额附加值，它们**累加**生效。例如：A 账号有两条附加值——3月1日 +100、3月15日 +50，则 3月20日的余额 = 原始余额 + 100 + 50 = 原始余额 + 150
- 具体计算方式：对于某一天的余额，汇总该大账号+币种下所有 `effectiveDate <= 当天` 的附加值之和，加到原始余额上

**余额附加值的代码注入点：**

- 在 `deriveBalanceRecords`（`src/main.js:1733-1934`）中，`endBalance` 计算完成后（约第 1902 行）、写入 `records` 之前（约第 1906 行），叠加当日生效的余额附加值总和
- **关键决策：叠加后的值作为 `previousEndBalance` 传递给下一天的余额推导**（即第 1904 行 `previousEndBalance = endBalance` 使用叠加后的值）。这意味着余额附加值会影响后续所有日期的余额链式计算，符合"永久偏移量"的语义

**大账号列表的数据来源：**

- 余额管理弹窗中"大账号"下拉的选项来自**数据库中已保存的大账号数据**（非对话框内存中正在编辑的 tbody 数据），原因是余额附加值的生命周期独立于大账号编辑会话，应引用已持久化的稳定数据

**数据存储：**

- 余额附加值数据存储到独立 JSON 文件：`{storageRoot}/balance-adjustments/{bankName}.json`
- 其中 `bankName` 为模板名称按 `-` 分隔后的第一部分（复用 `splitTemplateName` 逻辑）
- **已知限制**：如果用户重命名模板导致 `bankName` 变化，历史余额附加值文件会丢失关联（与 `balance-seeds` 存在相同的限制）。本版本不处理重命名迁移
- **bankName 共享说明**：如果两个不同模板的 bankName 相同（如 `CNCB-CN-3973` 和 `CNCB-HK-1234` 都是 `CNCB`），它们会共享同一个余额附加值文件。这是**有意的设计**，与 `balance-seeds` 的行为一致——同一银行的余额附加值在不同模板间共享

**余额附加值的边界规则：**

- **同一大账号+币种+同一日期有多条附加值**：允许存在，累加生效（即两条都计入总和）。用户可通过余额管理弹窗自行合并或删除多余记录
- **余额附加值的 effectiveDate 晚于最后一条余额记录日期**：静默忽略（不报错），该附加值在当前导出中不产生效果，待后续有该日期或之后的余额记录时自动生效

**余额管理弹窗的保存行为：**

- 余额管理弹窗的"完成"按钮**独立保存**到 JSON 文件，不依赖外层"维护大账号"对话框的"完成"。这意味着用户在余额管理中保存后、在外层点击 X 取消，余额附加值已保存但大账号列表未保存。这是预期行为——余额附加值的生命周期独立于大账号编辑会话，允许两者不同步
- 数据格式：

```json
[
  {
    "merchantId": "1234567890",
    "currency": "CNY",
    "effectiveDate": "2026-03-01",
    "adjustmentValue": 100.50,
    "remark": "调整说明",
    "templateName": "CNCB-CN-3973",
    "updatedAt": "2026-03-27T12:00:00.000Z"
  }
]
```

### 需求 5：新开账户余额账单逻辑

#### 5.1 功能说明

**做什么：**

修改新开账户余额账单的日期生成逻辑，从当前的"开户日期 + 每月月末日期"改为"从开户日期到当前系统日期的每一天"。

**当前实现：**

- 文件：`src/main.js` 约第 1940-1962 行 `buildNewAccountBillDates` 函数
- 当前逻辑：生成开户日期 + 从开户日期所在月到今天所在月的每月月末日期
- 例如：开户日期 2026-03-15，今天 2026-03-27 -> 生成 `[2026-03-15]`（因为 3月月末 3月31日大于今天，所以不包含）

**目标行为：**

- 生成从开户日期到当前系统日期（含两端）的每一天的余额记录
- 例如：开户日期 2026-03-25，今天 2026-03-27 -> 生成 `[2026-03-25, 2026-03-26, 2026-03-27]`
- 开户日期当天的余额为 0（与现有逻辑一致：`期末余额: 0`）
- 开户日期之后每一天的余额也为 0（因为新开账户未发生交易）

**实现要点：**

- 修改 `buildNewAccountBillDates` 函数
- 从开户日期开始，每天递增一天，直到（含）当前系统日期
- 返回所有日期的数组
- 保留开户日期不能晚于今日的校验

**性能考量：**

- 最大可能的天数：理论上用户可能输入很早的开户日期，但实际业务场景中，新开账户通常是近期开户。为安全起见，如果生成的天数超过 3650 天（约 10 年），抛出错误"开户日期距今超过 10 年，不支持生成"。
- 3650 天的上限检查应在循环之前通过日期差计算完成（`Math.floor((today - openDate) / 86400000)`），避免不必要的循环开销。
- **错误展示方式**：与现有的"开户日期不能晚于今日"报错保持一致（通过 `setStatus` 显示在状态栏，同时弹出 alert 对话框）。

#### 5.2 交互流程

1. 用户在新开账户模块中填写银行名称、所在地、币种、银行账号、开户日期
2. 点击"生成"
3. 系统按开户日期到今天每一天生成余额记录
4. 每天的余额为 0
5. 成功后提示"新开账户余额账单可导出"
6. 用户点击"导出"导出 Excel

#### 5.3 UI 说明

无界面变更。仅影响生成的数据量（从每月月末扩展为每天）。

导出的 Excel 中每天一行，余额值为 0。
