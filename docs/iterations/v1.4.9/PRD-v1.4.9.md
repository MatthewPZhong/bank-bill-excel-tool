## 一、需求概述

本版本包含 1 项需求：

1. **账单拆分合并管理** —— 在「模版管理 → 映射关系管理 → 映射关系设置」下方新增一个「账单拆分合并管理」分组。该分组由两行开关构成：
   - 「是否拆分/合并明细账单」（是 / 否，默认 **否**）
   - 「复用模块字段的映射关系」（是 / 否，默认 **是**）

   开启「是否拆分/合并明细账单」后，原本在「映射关系管理」主界面中直接映射的 `Currency` / `Credit Amount` / `Debit Amount` 三个字段会迁移到一个独立的「拆分/合并账单映射关系管理」弹框中（弹框 2）配置；该弹框支持把一行原始账单拆分成 N 份账单，并允许把其中若干份账单合并成一行输出。

   「复用模块字段的映射关系」决定拆分后的账单其它字段（非 Currency / Credit Amount / Debit Amount）的映射关系是否复用主模板的映射。置为「否」时开放一个独立的「拆分/合并账单映射关系设置」弹框（弹框 1），允许用户为拆分账单单独配置字段映射。

   **互斥关系**：该功能与 v1.4.7 的「按正负号拆分的发生额」、v1.4.8 的「按字段区分发生额」以及「Credit Amount / Debit Amount 的直接映射」**4 选 1 完全互斥**（见 §4.5 和 Q-B1 确认结果）；但弹框 2 内部的「发生额映射关系管理」副区域可以**重新**使用这两种发生额模式作为拆分后账单内部的子配置，在数据层独立（UI 复用 + 数据独立，见 Q-B3 / Q-E1 确认结果）。

## 二、背景与目标

### 2.1 背景

当前 v1.4.x 已经支持以下「一行原始数据 → 一行输出行」的发生额配置方式：

1. **直接映射**（v1.4.x）：`Credit Amount` / `Debit Amount` 分别映射到源文件的两个独立金额列。
2. **按正负号拆分**（v1.4.7）：`SIGNED_AMOUNT_MAPPING_FIELD` 把单个金额列按正负号自动拆分为收入和支出。
3. **按字段区分发生额**（v1.4.8）：通过"条件字段 + 条件值 → 目标字段"的通用形式，根据某个辅助列的取值把金额列映射到 `Credit Amount` 或 `Debit Amount`。

但仍有部分银行账单的一行原始数据需要**拆成多行输出**（或者反过来，需要把多行原始数据**合并成一行**），且这些"拆分份"之间可能需要不同的 Currency / Credit Amount / Debit Amount 映射。例如：

- **拆分场景**：某行原始数据同时包含本币和外币两种币种的发生额（`CNY_AMT` 和 `USD_AMT` 两列），需要拆成 2 行输出，一行 Currency=CNY 取 `CNY_AMT`，另一行 Currency=USD 取 `USD_AMT`。
- **合并场景**：原始账单的某些连续行语义上属于同一笔交易（例如手续费和交易本金被拆成两行记账），需要把它们合并为 1 行输出，Credit Amount / Debit Amount 按正负号相加得到最终值。

当前三种发生额模式都无法表达"一拖多"或"多合一"的结构，故新增本 feature。

### 2.2 目标

- 在「模版管理 → 映射关系管理 → 映射关系设置」下方新增一个独立的「账单拆分合并管理」分组。
- 通过两个单选下拉框开启：是否拆分/合并、是否复用主模板的字段映射。
- 通过弹框 1（映射关系设置）允许用户为拆分账单中的**非金额字段**配置独立映射。
- 通过弹框 2（映射关系管理）允许用户配置：
  - N 份拆分账单各自的 Currency / Credit Amount / Debit Amount / 发生额来源；
  - 合并规则：把 N 份拆分账单中的若干份合并成 1 条输出行。
- 开启本 feature 时与既有三种发生额模式互斥。
- 数据需要持久化到模板（DB schema 迁移），导入文件时按规则生效。

## 三、术语

> **术语统一（重要）**：用户确认原始需求文案里「合成」是笔误，**本 PRD 统一使用「合并」**。任何地方若看到「合成」一词均应替换为「合并」。

| 术语 | 含义 |
|------|------|
| 拆分账单 | 一行原始数据被展开成 N 行输出；每一份叫一个"拆分账单"，编号为 1..N |
| 账单序号 | 每一份拆分账单的序号，1..N，与弹框 2 六列表格中的第一列一一对应 |
| 合并账单 | 把若干份拆分账单合并为 1 条输出行（合并是"事后"动作，先拆再并） |
| 弹框 1 | 「拆分/合并账单映射关系**设置**」弹框（对应入口「复用模块字段的映射关系」置为"否"后出现的按钮） |
| 弹框 2 | 「拆分/合并账单映射关系**管理**」弹框（对应入口「是否拆分/合并明细账单」置为"是"后出现的按钮） |
| 发生额模式 | 决定一行数据的 Credit Amount / Debit Amount 如何产生的方式，目前包括：①直接映射、②按正负号拆分、③按字段区分发生额（v1.4.8） |

> **命名约定**：本 PRD 使用「按钮『设置』」「按钮『管理』」来区分两个弹框。"设置"对应字段映射的配置（弹框 1），"管理"对应拆分/合并规则本身（弹框 2）。该措辞源自用户的需求原文，本 PRD 保留。

## 四、功能详细描述

### 4.1 入口：映射关系设置下方新增「账单拆分合并管理」分组

**位置：**

在「映射关系管理」对话框（`createMappingDialog`，`src/renderer-dialogs.js:1470`）的「映射关系设置」分组**下方**新增一个独立分组 **"账单拆分合并管理"**。该分组**不属于**「映射关系设置」，是一个平级的新分组。

**分组标题：** `账单拆分合并管理`

**UI 元素（由两行开关组成）：**

| 行号 | 左侧标签 | 右侧控件 | 默认值 | 说明 |
|------|---------|---------|-------|------|
| 第一行 | `是否拆分/合并明细账单` | 单选下拉框（选项：`是` / `否`） | **`否`** | 置为 `是` 时启用拆分/合并 feature |
| 第二行 | `复用模块字段的映射关系` | 单选下拉框（选项：`是` / `否`） | **`是`** | 置为 `否` 时启用独立的字段映射设置（弹框 1） |

**交互：**

#### 4.1.1 「复用模块字段的映射关系」开关（第二行）

**开关只作用于"非金额字段"**。所谓"非金额字段"是指模板映射字段中**除 `Currency` / `Credit Amount` / `Debit Amount` 之外**的所有字段（如 `MerchantId` / `BillDate` / `ValueDate` / `Drawee Name` / `Payee Name` / `Drawee CardNo` / `Payee CardNo` / `Description` 等）。

- 默认为 **`是`**：拆分后 N 份账单的**非金额字段**直接复用主模板的映射关系，不做独立配置，下拉框右侧无按钮。每一份拆分账单的非金额字段值都取自**同一行原始数据**按主模板映射计算出的结果（因此 N 份拆分账单的非金额字段值完全一致）。
- 置为 **`否`** 时：下拉框右侧立即出现按钮 `拆分/合并账单映射关系设置`，点击该按钮 → 弹出**弹框 1**（详见 §4.2）。
  - 此时拆分后 N 份账单的非金额字段走弹框 1 中配置的**独立映射**（**一套弹框 1 配置对所有 N 份拆分账单共享**，不按每份独立配置）。

> **重要（Q-D5 确认）**：`Currency` / `Credit Amount` / `Debit Amount` 三个金额字段**永远**由「是否拆分/合并明细账单」开关 + 弹框 2 管辖，**与「复用模块字段的映射关系」开关无关**。即：无论"复用"开关是 `是` 还是 `否`，只要「是否拆分/合并明细账单 = 是」，这三个字段就走弹框 2 的 N 行配置。

#### 4.1.2 「是否拆分/合并明细账单」开关（第一行）

- 默认为 **`否`**。置为 `否` 时：`Currency` / `Credit Amount` / `Debit Amount` 三个字段仍由「映射关系管理」主表格直接配置，下拉框右侧无按钮。
- 置为 **`是`** 时：
  1. 立即**互斥清空**主模板里的以下几个配置（见 §4.5 互斥关系）：
     - 模板字段 `Credit Amount` 的 `mappedField`
     - 模板字段 `Debit Amount` 的 `mappedField`
     - 「按正负号拆分的发生额」（`SIGNED_AMOUNT_MAPPING_FIELD`）的 `mappedField`
     - 「按字段区分发生额」（`AMOUNT_SPLIT_BY_FIELD_MAPPING_FIELD`）的开关值及其 6 条规则
  2. 主表格里的 `Currency` 行此时**也需要互斥清空 + disabled**（因为 Currency 已迁移到弹框 2 的六列表格内按拆分份单独配置）。
  3. 下拉框右侧立即出现按钮 `拆分/合并账单映射关系管理`。
  4. 点击该按钮 → 弹出**弹框 2**（详见 §4.3）。
- 置为 `是` 后切回 `否` 的行为（Q-C9 确认）：
  - 按钮 `拆分/合并账单映射关系管理` 立即隐藏。
  - 主表格中的 `Currency` / `Credit Amount` / `Debit Amount` 行的 disabled 解除，但值**已被清空**（与 v1.4.8 的切回行为保持一致，需要用户重新填写）。
  - 弹框 2 中已落库的拆分/合并规则**草稿保留**（草稿跟模板走，与外层下拉框状态无关；与 v1.4.8 §3.3.4 等价）。
- 置为 `是` 时，主表格中以下 4 行**保留显示但 disabled**（**Q-E3 确认**），不隐藏整行，并加 tooltip 提示 `已开启拆分/合并明细账单，本字段不可用`：
  - `Credit Amount`
  - `Debit Amount`
  - 「按正负号拆分的发生额」
  - 「按字段区分发生额」

  此外 `Currency` 行同样按 **Q-C8 确认** 互斥清空 + disabled + 同款 tooltip。

**「导入当前映射关系」按钮（Q-C1 确认）：**

- 点击后把主模板的映射配置**复制**一份到弹框 1 的表格中，**排除** `Currency` / `Credit Amount` / `Debit Amount` 三个字段（这三个字段属于弹框 2 管辖）。

#### 4.3.1 弹框右上角：`合并账单` 勾选框（Q-G6 确认）

- 位置：弹框**右上角**（标题栏右侧）。
- 默认值：**未勾选**。
- 勾选后：立即在其右侧显示一个**多选下拉框** + `完成` 按钮（见 §4.4 合并账单逻辑）。
- 取消勾选后：

  - 所有被合并的行从"灰显不可选"恢复到"可选取状态"。

#### 4.3.2 弹框右上角下方一行：`需要拆分成几份账单` 数字输入框（Q-G6 确认）

- 位置：弹框右上角下方**单独一行**（与 §4.3.1 的勾选框分行，避免排版冲突）。
- 由从左到右的 3 个元素组成：
  - 标签：`需要拆分成几份账单`
  - 数字输入框：3 个占位符宽度，**仅支持数字输入**（非数字字符在输入时被拒绝；Q-C3 确认取值范围 **1 ≤ N ≤ 99**，超出范围的输入被拒绝或弹错误提示）。
  - 按钮：`拆`（**2026-04-08 fix2 override**：原文案为 `完成`，按用户反馈改名为 `拆`，并将按钮宽度缩窄为原宽度的 66%，以减少视觉冲突并与 Fix #7 新增的右下角"完成"按钮文案区分；详见变更记录 2026-04-08 fix2 行）
- 交互：
  - 用户输入数字 N 并点 `拆`，六列表格立即生成（或同步到）N 行（详见 §4.3.3 的"生成 / 同步 N 行的行为"）。

#### 4.3.3 下方：六列表格

| 列名 | 控件类型 | 说明 |
|------|---------|------|

| Currency | 单选下拉框 | 选项来自 `template.headers`（Q-C4 确认），**排除**特殊枚举（`MERCHANT_ID_SELF_INPUT_OPTION` / `CONCAT_FIELDS_MAPPING_FIELD` 等），**不允许**"自己输入"固定值 |
| Credit Amount | 单选下拉框 | 同上 |
| Debit Amount | 单选下拉框 | 同上 |
| 发生额 | 单选下拉框 | 同上。**默认禁用**。启用条件：见下方"发生额列启用条件" |
| 执行操作 | 两个文字按钮：`完成` / `删除` | 语义见下方"执行操作语义" |

**生成 / 同步 N 行的行为（Q-C2 确认）：**

- 初次打开弹框 + 输入 N + 点 `完成`：生成 N 行空白行，账单序号 1..N。
- 已经有 M 行，修改 N 为更大值（N > M）：追加 N − M 行空白行，已有 M 行保留。
- 已经有 M 行，修改 N 为更小值（N < M）：**先弹二次确认** `确认删除最下方的 (M − N) 行？已填数据会丢失`，用户点 `确认` 后删除，点 `取消` 不动作。若被删除的行中有已经参与合并的行，同步按 §4.3.3「执行操作语义」的"删除"规则**解散所在合并组**（组内其它行回退为未合并状态）。

**执行操作语义（Q-C6 / Q-C7 确认）：**

- **`完成` 按钮**：锁定该行不可编辑 + **行级落库**（把该行的 5 列值写入 `template_bill_split_rows` 表，`row_status = completed`）。锁定后该行整行置为只读（四个字段下拉框 disabled），`完成` 按钮变为 `编辑` 按钮；点 `编辑` 解除锁定并把 `row_status` 改回 `draft`，允许继续修改。
- **`删除` 按钮**：
  - 删除该行后，**后续行序号自动前移填补**（例：原 5 行，删除第 3 行后变 4 行，原第 4 行变成第 3 行、原第 5 行变成第 4 行）。
  - 右上角「需要拆分成几份账单」数字输入框的值 N **自动 −1**。
  - 若被删除的行已参与合并：**解散所在合并组**（组内其它行的 `merged_group_seq` 清空，回退为未合并状态；**不**级联删除其它行）。
  - 删除操作**不弹二次确认**（与 Q-C2 的"修改 N 触发删除"路径区分：用户显式点 `删除` 视为明确意图）。

**字段约束（Q-C10 确认）：**

- **同一行内**：`Credit Amount` ≠ `Debit Amount`（逻辑上一列不能既收又支；违反时弹错误提示 `同一份拆分账单的 Credit Amount 和 Debit Amount 不能是同一列`）。
- **跨行**：允许同字段。两份拆分账单可以选取同一列作为 Credit Amount / Debit Amount / Currency / 发生额。
- `Currency` 和其它三个下拉框的"同字段"约束：不禁止 Currency 与 Credit Amount 或 Debit Amount 用同一列（实际使用意义极少，但 PRD 不主动拦截）。

**发生额列启用条件（Q-C11 确认）：**

- 默认禁用。
- 启用条件：**弹框 2 副区域（§4.3.4）** 的「按正负号拆分的发生额」或「按字段区分发生额」**任一有值**时立即启用。
- 用户若在副区域配好发生额模式、已在六列表格的「发生额」列填入值、然后又把副区域的两个配置全部清空：六列表格「发生额」列**保留已填的值**但变为 disabled（不清空），下次副区域再有值时 disabled 解除、值自动回显。
- 切换发生额模式时对六列表格「Credit Amount」/「Debit Amount」列的影响见 §4.3.4 弹框 2 内部互斥规则。

#### 4.3.4 页面中线下侧：`拆分/合并账单——发生额映射关系管理`

副标题：`拆分/合并账单——发生额映射关系管理`

副标题下方两行（**完全复用**「映射关系管理」主弹框中这两个同名行的交互形式）：

| 行 | 说明 |
|----|------|
| 按正负号拆分的发生额 | 单选下拉框，选项来自 `template.headers` |
| 按字段区分发生额 | 单选下拉框（选项：空 / 是）；置为「是」后右侧出现按钮 `发生额映射关系管理`，点击弹出 v1.4.8 的「发生额映射关系管理」弹框 |

**关键点（Q-B3 / Q-E1 / Q-E2 确认）**：这两行在弹框 2 内部是**独立配置**（与主模板的同名字段 **不共享** 配置数据），用于决定六列表格里的"发生额"下拉框如何产生 Credit / Debit Amount。UI 复用 + 数据独立，Dev 在 TechDoc 阶段决定具体复用方式（参数化 / 子类化 / 工厂等）。数据层面新建独立表 `template_bill_split_amount_rules`（详见 §4.6 和 Q-A4）。

- 当「按正负号拆分的发生额」有值**或**「按字段区分发生额 = 是」时：
  - 六列表格中的 `Credit Amount` 列和 `Debit Amount` 列下拉框**禁用且清空**（因为 Credit/Debit 由副区域的发生额模式产生）。
  - 六列表格中的「发生额」下拉框**启用**。
- 当「按正负号拆分的发生额」和「按字段区分发生额」都为空时：
  - 六列表格中的 `Credit Amount` / `Debit Amount` 下拉框启用。
  - 六列表格中的「发生额」下拉框禁用（值保留，不清空，详见 §4.3.3「发生额列启用条件」）。
- 副区域内部：「按正负号拆分的发生额」和「按字段区分发生额」**二选一**互斥（任一有值时禁用另一个并清空，与 v1.4.8 外层主模板的二选一互斥语义一致）。

#### 4.3.5 弹框 2 的完成 / 落库策略（Q-C12 确认 — **行级"完成"即落库**）

弹框 2 的落库策略依旧是**行级"完成"即落库**。落库发生在下列三种时机：

1. **`需要拆分成几份账单` 右侧的 `拆`**（**2026-04-08 fix2 override**：按钮文本从 `完成` 改为 `拆`，宽度为原按钮的 66%，详见 §4.3.2 尾部注解）：生成 / 同步六列表格 N 行。这一步会把 N 的当前值持久化到 `template_bill_split_rows` 表（增加 N − M 行新纪录，`row_status = draft`；或按 §4.3.3 的二次确认后删除多出的 M − N 行）。
2. **六列表格每一行「执行操作」里的 `完成`**：锁定该行并把该行的 5 列值**行级落库**到 `template_bill_split_rows` 表的对应记录，`row_status` 从 `draft` 改为 `completed`；点 `编辑` 解锁时改回 `draft`（行数据保留，标志位回退）。
3. **`合并账单` 勾选框右侧的 `完成`**：落库合并组关系，把被选中的行的 `merged_group_seq` 字段更新为组内最小 seq_no；取消勾选时清空这些行的 `merged_group_seq` 字段。

**外层「映射关系管理」对话框的「完成」/「取消」/「关闭」均不影响弹框 2 中已落库的配置**，与 v1.4.8 的弹框草稿语义一致。

**弹框 2 的关闭方式**（**2026-04-08 fix2 override**）：
- **原决定**：只能通过右上角 `x` 按钮或 ESC 键关闭；弹框 2 没有弹框级整体「完成」按钮（行级落库已涵盖所有数据写入）。
- **新决定**：在弹框 2 **右下角新增一个「完成」按钮**，按钮语义**等同 × 关闭**——点击触发关闭 + `onClose` 回调，**不做任何额外落库动作**（所有改动仍然是行级落库，该按钮只是提供另一个关闭入口，方便用户在操作完成后显式确认"我已完成"）。× 按钮和 ESC 键仍然保留。

关闭时**不做额外落库动作**（因为一切都已行级落库）。未完成的 `draft` 行保留在 DB 中，下次打开弹框时回显，允许用户继续编辑。

**副区域的落库时机**（§4.3.4）：
- 「按正负号拆分的发生额」下拉框值改变时立即落库到 `template_bill_split_amount_rules` 表的 meta 记录（或等效位置，Dev 在 TechDoc 决定）。
- 「按字段区分发生额」的开关值 + 其 `发生额映射关系管理` 弹框（v1.4.8 组件）里的两行规则按照 v1.4.8 §3.3.4 的语义落库到 `template_bill_split_amount_rules` 表。

**Sub-question（Q-C12-a 确认）— 合并多选下拉框的候选值**：

- 当用户勾选 `合并账单` 并打开多选下拉框时，**候选值只显示六列表格中已落库（即 `row_status = completed`）且未被合并的行**。
- 未完成的 `draft` 行**不出现**在合并下拉框中。这强制用户先点完每一行的 `完成`（行级落库）才能进入合并流程，避免对"半成品"行做合并导致的数据不一致。

### 4.4 合并账单逻辑（Q-D2 / Q-D3 / Q-D4 / Q-C13 / Q-C14 / Q-C15 / Q-F4 确认）

**触发：** 勾选右上角的 `合并账单` 勾选框。

#### 4.4.1 UI 交互

1. 勾选 `合并账单` 后，右侧出现 **多选下拉框** + `完成` 按钮。
2. **多选下拉框的候选值**（Q-C12-a 确认）：六列表格中**已落库**（`row_status = completed`）**且** `merged_group_seq IS NULL`（即未参与任何合并组）的行的账单序号。`draft` 状态的行和已参与其它合并组的行不出现。
3. 用户在多选下拉框中至少选择 **2 个** 账单序号（Q-C15 确认），点击 `完成`：
   - 若选中数量 < 2 → 弹错误提示 `合并账单至少需要选择 2 个账单序号`，不执行合并。
   - 否则：把被选中的这些行的「账单序号」**全部变成其中的最小值**（例：选了 `{2, 4, 5}` → 三行的序号都显示 `2`）。
   - **DB 层**：把被选中的这些行的 `merged_group_seq` 字段写入组内最小 seq_no（即 `2` 对应的原 seq_no）。
   - **UI 层**：被合并的**所有 K 行**（含序号最小的代表行）**变灰 + 不可选取**（Q-C13 确认：所有 K 行都灰，含代表行）。合并组在视觉上由相同的账单序号数字和灰显样式共同识别。
4. **多组独立**（Q-C14 确认）：支持多个独立合并组。用户可以取消勾选 `合并账单` 后再次勾选，针对另一组未合并的行执行第二次合并。不同合并组的 `merged_group_seq` 值不同，互不影响。不支持合并组再合并（嵌套合并）。
5. **取消勾选 `合并账单` 勾选框**：
   - 多选下拉框和完成按钮隐藏。
   - **所有**被合并的行恢复到可选取状态，`merged_group_seq` 字段在 DB 中**清空**（所有合并组被**一次性解散**）。
   - 被合并行的「账单序号」恢复到原值（Q-C5 确认：还原为 1..N 的原始 seq_no）。

#### 4.4.2 合并后的输出计算（Q-D2 / Q-D3 / Q-D4 / Q-F4 确认）

**合并只发生在导入阶段**（UI 上只保存合并组关系，不预先计算金额）。导入时对同一组的 K 条拆分输出行执行以下计算：

**步骤 1 — Currency 一致性校验**（Q-F4 确认）：

- 如果合并组内 K 条拆分输出行的 `Currency` 字段值**不完全一致**（即存在任意两行 Currency 不同），**导入时报错阻断**：
  - 错误码：`BILL_MERGE_CURRENCY_MISMATCH`
  - 文案：`合并账单的 Currency 不一致，无法合并`（具体文案见 Q-G2 / Q-G3 确认）

**步骤 2 — 金额求和**（Q-D2 确认）：

- 合并组内 K 条拆分输出行的 `Credit Amount` **分别求和** → Σ(Credit_i)
- 合并组内 K 条拆分输出行的 `Debit Amount` **分别求和** → Σ(Debit_i)
- 若当前是"发生额"列主导模式（弹框 2 副区域配置了发生额模式）：合并组内 K 条拆分输出行的 `发生额` 列先按副区域规则计算出各自的 `Credit_i` / `Debit_i`，再按上述规则求和。

**步骤 3 — 净值与方向判定**（Q-D3 确认 — 净值法）：

- 净值 = Σ(Credit_i) − Σ(Debit_i)
- 若 **净值 > 0** → 合并后 `Credit Amount = |净值|`，`Debit Amount = 空`。
- 若 **净值 < 0** → 合并后 `Debit Amount = |净值|`，`Credit Amount = 空`。
- 若 **净值 = 0** → **静默跳过整个合并组**，该合并组不产生任何输出行；导入流程继续处理其他行/组，不报错不提醒（**2026-04-08 fix2 override**：原决定为"报错阻断 + `BILL_MERGE_NET_ZERO`"，基于用户反馈改为静默过滤，详见变更记录 2026-04-08 fix2 行）。

**步骤 4 — 非金额字段合并**（Q-F4 确认）：

- `Currency`：步骤 1 已保证一致，取任一行的值（取代表行 `merged_group_seq` 对应的最小 seq_no 行的值）。
- **所有其它非金额字段**（MerchantId / BillDate / ValueDate / Drawee Name / Payee Name / CardNo / Description / ...）：**取合并组代表行**（即 `merged_group_seq` 对应的最小 seq_no 行）的值。
  - 代表行的非金额字段来源：若「复用模块字段的映射关系 = 是」→ 取自主模板映射；若「复用模块字段的映射关系 = 否」→ 取自弹框 1 的独立映射。

**合并后的输出行数**：

- 合并组 G 内的 K 条拆分输出行 → 合并为 **1** 条输出行（**或 0 条**：若合并组净值 = 0 则整个组被静默过滤）。
- 未被任何合并组包含的拆分输出行 → 各自保留为 1 条独立输出行（**或 0 条**：若该行 Credit 和 Debit 同时为 0 / 空 / NaN，则该行被静默过滤，详见下方"2026-04-08 fix2 0 值静默过滤"说明）。
- 最终输出行数 = (未合并独立行中 credit/debit 非全 0 的行数) + (合并组中净值非 0 的组数)。

> **2026-04-08 fix2 override — 0 值静默过滤语义**（影响 §4.4.2 步骤 3、§4.7.5、AC1-62、ACI-7）：
>
> - **单行拆分输出 0 值过滤**：对每条原始行展开出的 N 条拆分输出行，若某拆分行的 `Credit Amount` 和 `Debit Amount` 都为 0（或空、或 NaN），该行被**静默丢弃**，不输出也不报错。
> - **合并组净值 0 过滤**：合并组内 K 条拆分行求和后净值 = 0 时，整个合并组被**静默跳过**，不产生输出行，导入流程继续处理其他行/组。
> - **保留不变**：合并组内 `Currency` 不一致仍然**报错阻断**导入（错误码 `BILL_MERGE_CURRENCY_MISMATCH`）。
> - **原决定**（已 override）：净值 = 0 时报错阻断，错误码 `BILL_MERGE_NET_ZERO`；详见变更记录 2026-04-08 fix2 行。

### 4.5 互斥关系（本 feature 与既有发生额模式）

#### 4.5.1 外层（主模板）4 方互斥 — Q-B1 确认

**4 种发生额模式只能启用其中一种**：

1. **直接映射 Credit Amount / Debit Amount**（v1.4.x）
2. **按正负号拆分的发生额**（v1.4.7，`SIGNED_AMOUNT_MAPPING_FIELD`）
3. **按字段区分发生额**（v1.4.8，`AMOUNT_SPLIT_BY_FIELD_MAPPING_FIELD`）
4. **拆分/合并明细账单**（v1.4.9 新增，即「是否拆分/合并明细账单 = 是」）

| 模式组合 | 合法性 |
|---------|-------|
| 只启用 1 种 | 合法 |
| 启用 2 种及以上 | **非法**，`template:save-mappings` 校验阶段报错，错误码 `AMOUNT_MODE_CONFLICT` |
| 全都不启用 | 合法（Currency / Credit / Debit 都为空的模板，现有场景保留） |

**UI 层互斥（Q-E3 确认）**：选择任一种模式时，**立即清空**其余 3 种模式的相关字段值，并在其行上 **disabled + tooltip** `已开启拆分/合并明细账单，本字段不可用`（类似的反向 tooltip 用于其它三种模式被禁用时显示 `已开启 {被选中的模式}，本字段不可用`）。参考 v1.4.8 「选『是』后互斥清空 Credit/Debit/按正负号」的机制。

**保存层互斥（Q-B2 确认）**：`validateTemplateConfiguration`（`src/main.js:2579`）的 `enabledAmountModes` 数组从 3 方扩展成 4 方（新增一个 `usesBillSplitMerge` 布尔），`> 1` 时报错：

- 错误码：`AMOUNT_MODE_CONFLICT`
- 错误文案：`Credit Amount / Debit Amount 直接映射、按正负号拆分的发生额、按字段区分发生额、拆分/合并明细账单 四者只能启用其中一种`

#### 4.5.2 内层（弹框 2 副区域）互斥

弹框 2 §4.3.4 描述的副区域内部有自己的"2 方互斥"：

- 「按正负号拆分的发生额」和「按字段区分发生额」二选一。
- 任一有值时：
  - 六列表格中的 `Credit Amount` / `Debit Amount` 列下拉框禁用 + 清空。
  - 六列表格中的「发生额」列下拉框启用。
- 均为空时：
  - 六列表格中的 `Credit Amount` / `Debit Amount` 列下拉框启用。
  - 六列表格中的「发生额」列下拉框禁用（值保留不清空，见 §4.3.3）。

#### 4.5.3 主模板互斥 vs 弹框 2 内部配置的关系（Q-B3 / Q-E1 / Q-E2 确认）

用户启用 v1.4.9 feature 后：

- 外层主模板里的「按正负号拆分」「按字段区分」「Credit Amount」「Debit Amount」「Currency」配置被**清空**且 disabled（§4.5.1 / §4.1.2）。
- **弹框 2 内部的副区域**允许用户**独立地**再次配置「按正负号拆分的发生额」和「按字段区分发生额」作为拆分账单的子配置。
- 这两个机制**在 DB 层是两套独立的数据**：
  - 外层主模板的发生额配置 → `template_mappings` + `template_amount_split_rules`（v1.4.8 既有表，**本 feature 不动**）
  - 弹框 2 副区域的发生额配置 → `template_bill_split_amount_rules`（v1.4.9 新建表，schema 参考 `template_amount_split_rules`）
- 前端通过给 v1.4.8 的 `createAmountSplitRulesDialog` 传入 `context` 参数（`'main'` vs `'bill-split'`）区分两种上下文，具体复用方式（参数化 / 子类化 / 工厂）由 Dev 在 TechDoc 决定。

### 4.7 导入时的行为（Q-D1 / Q-F1 / Q-F2 / Q-F3 / Q-F4 / Q-F5 确认）

当模板的「是否拆分/合并明细账单 = 是」且弹框 2 的 N 行配置完整时，导入文件的预期效果：

#### 4.7.1 拆分语义（Q-D1 确认 — **feature 灵魂**）

对每一行原始数据（以下称"原始行"）：

1. 按弹框 2 六列表格的 N 行配置，产生 **N 条拟输出行**（后续称"拆分输出行"，编号 1..N）。
2. 第 i 条拆分输出行的 Currency / Credit Amount / Debit Amount / 发生额 值的取法：
   - 弹框 2 第 i 行配置中的每个下拉框值都是**源文件的列名**（即 `template.headers` 中的某一列），语义与主模板的「映射字段」列完全一致。
   - 从**同一条原始行**中，按该列名的列索引取值，套用 `sanitizeAmountValue` / 发生额规则得到最终数值（与 v1.4.8 的金额处理管线一致）。

**举例**：

```
原始数据（1 行）：
  {DATE: 2026-04-07, AMT1_CUR: CNY, AMT1_C: 100, AMT1_D: 0,
                      AMT2_CUR: USD, AMT2_C: 14,  AMT2_D: 0, ...}

弹框 2 六列表格配置（N=2）：
  第 1 行: Currency=AMT1_CUR, Credit=AMT1_C, Debit=AMT1_D, 发生额=（禁用）
  第 2 行: Currency=AMT2_CUR, Credit=AMT2_C, Debit=AMT2_D, 发生额=（禁用）

拆分后的 2 条拟输出行：
  Row1: Currency=CNY, Credit=100, Debit=0, ...  ← 从原始行取 AMT1_CUR/AMT1_C/AMT1_D
  Row2: Currency=USD, Credit=14,  Debit=0, ...  ← 从原始行取 AMT2_CUR/AMT2_C/AMT2_D
```

> **关键概念**：拆分的本质是"一行原始数据 × N 份配置 = N 条拟输出行"，每份配置告诉系统"从原始行的哪几列取值"。所有 N 份拆分输出都**取自同一条原始行**，只是取的列不同。

#### 4.7.2 发生额列的导入语义（Q-F2 确认）

当弹框 2 **副区域**（§4.3.4）配置了发生额模式时，六列表格的「发生额」列**启用**，`Credit Amount` / `Debit Amount` 列 disabled。此时第 i 行拆分输出的 Credit/Debit 取法：

- **副区域配了「按正负号拆分的发生额」**：
  - 第 i 行「发生额」列的值是源字段名（同 Q-D1 语义）。从原始行取该列的原始字符串值，经过 v1.4.7 的 `splitSignedAmountValue` 逻辑按正负号拆成 Credit / Debit。
- **副区域配了「按字段区分发生额」**（即副区域弹出了 v1.4.8 的「发生额映射关系管理」弹框并配好两行规则）：
  - 第 i 行「发生额」列的值是 `mapped_field`（目标金额源字段名）。
  - 导入时对原始行评估副区域的 2 行规则（condition_field + condition_value）。若 Credit 规则命中，从第 i 行「发生额」列指向的源字段取金额作为第 i 条拆分输出的 Credit；Debit 规则同理。

> **注**：副区域的 2 行规则是**子区域级**（所有 N 份拆分输出共用同一套副区域规则），而不是"每份拆分一套"。这与 v1.4.8 主模板的同名机制语义一致。

#### 4.7.3 合并阶段（调用 §4.4.2）

若弹框 2 配置了合并组：

- 每一组合并组内的 K 条拆分输出行 → 按 §4.4.2 的求和 + 净值法计算，合并为 **1** 条输出行。
- 未被任何合并组包含的拆分输出行 → 各自保留为 1 条独立输出行。

#### 4.7.4 非金额字段的映射（Q-D5 确认）

对每一条最终输出行（合并后或未合并的拆分输出行）：

- 若「复用模块字段的映射关系 = 是」：**非金额字段**按主模板映射计算，取自对应的原始行（合并情形下取代表行对应的原始行）。
- 若「复用模块字段的映射关系 = 否」：**非金额字段**按弹框 1 中的独立映射配置计算，取自对应的原始行（合并情形下取代表行对应的原始行）。

#### 4.7.5 异常处理

- **合并组 Currency 不一致** → 报错阻断，错误码 `BILL_MERGE_CURRENCY_MISMATCH`，文案 `合并账单的 Currency 不一致，无法合并`（Q-F4 确认）。
- **合并后净值 = 0** → **静默跳过整个合并组**，不产生输出行，不报错不提醒，导入流程继续（**2026-04-08 fix2 override**：原决定为"报错阻断 + `BILL_MERGE_NET_ZERO`"，Q-D4 原采纳方案 D4-2，本次改为方案 D4-3（导入时过滤）；详见变更记录 2026-04-08 fix2 行）。
- **单行拆分输出 Credit/Debit 全 0** → **静默丢弃该拆分行**，不输出也不报错（**2026-04-08 fix2 新增**）。
- **源文件 headers 中不存在弹框 2 配置中选定的列** → 报错 `映射字段不存在：{字段名}`（与 v1.4.8 一致）。
- **开关 = 是但弹框 2 无任何已落库行** → 保存外层「映射关系管理」对话框时报错，错误码 `BILL_SPLIT_CONFIG_MISSING`，文案 `请先在"拆分/合并账单映射关系管理"中配置至少一行拆分账单配置`（模仿 v1.4.8 的 `AMOUNT_SPLIT_RULES_MISSING` 校验模式）。
- **全部行未命中（Q-F3 / Q-F5 确认 — 沿用 v1.4.8 §3.4.3）**：
  - 多文件批量导入时，逐文件独立判定"是否全部行均未命中任何拆分 / 合并规则"。
  - 合并为一个告警框统一弹出，文案格式：
    ```
    以下文件全部未命中拆分/合并规则，请检查规则配置：
    file1.csv
    file5.csv
    ```
  - 不阻断导入，对应文件生成的输出为空，由用户判断。

#### 4.7.6 多文件 / 多账号粒度

- 「账单拆分合并管理」配置是**模板级**的，不按账号 / 文件细分。
- 一个模板的配置对该模板所有导入的文件 / 所有大账号生效。

### Q-D 业务语义（最关键）

**Q-D1 — 拆分的本质：每份拆分账单的字段从哪里取？** ✅ 已确认（2026-04-08）— **feature 灵魂**

需求原文完全没有讲清楚：一行原始数据 → N 份拆分账单，每份拆分的 Currency / Credit Amount / Debit Amount 的值是怎么来的？

**PM 推测**：

弹框 2 的六列表格每一行的 Currency / Credit Amount / Debit Amount / 发生额 下拉框选择的是 `template.headers` 中的某一列。导入时从原始数据的该列读取值，走 sanitize（可能还要经过副区域的发生额规则）得到最终输出。

举例（CNY/USD 双币种拆分）：
```
原始数据一行：{DATE: 2026-04-07, CNY_AMT: 100, USD_AMT: 14, TYPE: 转出}
弹框 2 配置：
  第1行：Currency=「固定值 CNY」, Credit Amount=CNY_AMT, Debit Amount=（空）, 发生额=（禁用）
  第2行：Currency=「固定值 USD」, Credit Amount=USD_AMT, Debit Amount=（空）, 发生额=（禁用）
拆分结果：
  Row1: {DATE: 2026-04-07, Currency: CNY, Credit Amount: 100, Debit Amount: 0}
  Row2: {DATE: 2026-04-07, Currency: USD, Credit Amount: 14, Debit Amount: 0}
```

但这个推测依赖"Currency 下拉框允许固定值"（见 Q-C4），也依赖"Credit Amount 下拉框允许选具体列"（而不只是 template.headers 的语义）。

**需要用户明确**：
1. 六列表格每个下拉框选中的值，对应到导入文件的什么数据？
2. 是从原始数据行的对应列取，还是固定值？
3. 如果是"从对应列取"，那所有 N 份拆分账单都取自**同一行原始数据**，只是取不同列？

> **最终答案（2026-04-08）**：
> 1. 六列表格每个下拉框的值都是 `template.headers` 中的某一列名（即源文件列名）。
> 2. **从原始数据行的对应列取**，**不允许**固定值（与 Q-C4 答案一致）。
> 3. **是的** — 所有 N 份拆分账单都从**同一条原始行**取值，只是取的列不同。
>
> 因此 Q-D1 的 PM 推测中"固定值 CNY"的例子需要修正为"取一个 Currency 列名（如 AMT1_CUR）从原始行的该列值得到 CNY"。本 PRD §4.7.1 已用修正后的 CNY/USD 例子。详见 §4.7.1 与 ACI-1 / ACI-2。

**Q-D2 — 合并的计算规则：求和？加权？** ✅ 已确认（2026-04-08）— **feature 灵魂**

需求原文："Credit Amount、Debit Amount 或发生额**需要计算得到一个值**"。但没说是什么计算。

候选：

- **方案 D2-2**：加权求和。权重如何指定？需求原文没提权重。
- **方案 D2-3**：按币种分组求和（同一币种才合并）。如果合并组里 Currency 不同怎么办？

**补充问题**：合并组内如果 Currency 不同（比如合并 CNY 行和 USD 行），是直接报错、还是按方案 D2-3 分别计算、还是直接相加（明显错误的语义）？

> **最终答案（2026-04-08）**：采纳 **方案 D2-1（简单求和）**。合并组内 Σ(Credit_i) 与 Σ(Debit_i) 分别求和；不做加权。补充问题：合并组内 Currency 不一致 → **报错阻断**（错误码 `BILL_MERGE_CURRENCY_MISMATCH`），不允许跨币种合并。详见 §4.4.2 与 AC1-60 / AC1-61 / ACI-6。

**Q-D3 — 正负号如何判断？** ✅ 已确认（2026-04-08）— **feature 灵魂**

需求原文："根据**正负号**决定填到 Credit Amount 还是 Debit Amount 里"。

候选：
- **方案 D3-1**：净值 = Σ(Credit_i) − Σ(Debit_i)。若净值 > 0 → 合并后的 Credit = 净值，Debit = 空；若净值 < 0 → 合并后的 Debit = |净值|，Credit = 空。
- **方案 D3-2**：每行的 Credit 和 Debit 本身就有正负号（比如存在 `Credit = -100` 的情况），合并时需要先按行正负号归一化再求和。

**PM 建议**：方案 D3-1（因为 v1.4.x 的惯例是 Credit/Debit 都是正数）。需要用户确认。

> **最终答案（2026-04-08）**：采纳 **方案 D3-1（净值法）**。净值 = Σ(Credit_i) − Σ(Debit_i)；净值 > 0 → Credit = |净值|, Debit = 空；净值 < 0 → Debit = |净值|, Credit = 空；净值 = 0 → 走 Q-D4 处理路径。详见 §4.4.2 与 AC1-61。

> **2026-04-08 fix2 override**：Q-D4 的"报错路径"已改为"静默过滤路径"（见下方 Q-D4 最终答案更新），因此此处"走 Q-D4 报错路径"实际含义现为"整个合并组被静默跳过，不输出"。

**Q-D5 — 「复用模块字段的映射关系」的精确语义** ✅ 已确认（2026-04-08）— **feature 灵魂**

需求原文的字面意思是：开关控制"是否复用主模板的字段映射"。但"模块字段"这个词在既有术语中没有明确定义。

**PM 理解**：该开关决定拆分账单的**非金额字段**（除 Currency / Credit Amount / Debit Amount 外的所有字段）是否复用主模板。

- 若「是」：拆分后 N 份账单的非金额字段（MerchantId / BillDate / Drawee Name 等）**全部相同**，都等于主模板 mapping 的结果。
- 若「否」：进入弹框 1，用户为拆分账单单独配置非金额字段的映射。**每一份拆分账单的非金额字段都共享**这一套弹框 1 的映射（而不是每份再独立一套），对吗？

**需要用户确认**：
1. 「模块字段」是否指"非金额字段"？
2. 弹框 1 的配置是**所有拆分份共享一套**，还是**每份一套**（若每份一套，UI 应该是 N 个弹框 1 或者一个多 tab 的弹框 1）？

> **最终答案（2026-04-08）**：
> 1. **是的** — 「模块字段」即"**非金额字段**"，指除 Currency / Credit Amount / Debit Amount 之外的所有模板字段。
> 2. **所有 N 份拆分账单共享一套**弹框 1 配置 — UI 是单个弹框 1，不是 N 个或多 tab。
>

## 十二、Release Note 草稿

> 本文案面向最终用户，已锁定。Tester 可在测试阶段对照本草稿验证功能完整性。

### 新功能

- **账单拆分合并管理**：在「映射关系管理」对话框中新增「账单拆分合并管理」配置分组。该分组由两个开关组成：
  - **是否拆分/合并明细账单**（默认 否）：开启后可以将**一行原始账单**按 N 种发生额配置**拆分成 N 条输出**，每一份拆分账单的 Currency / Credit Amount / Debit Amount / 发生额来源单独配置；并支持将其中若干份**合并为 1 条输出行**（合并后按净值正负号自动落入 Credit 或 Debit 列）。开启后原本由主映射关系管理的 Currency / Credit Amount / Debit Amount 三个字段会迁移到新的「拆分/合并账单映射关系管理」弹框内独立配置。
  - **复用模块字段的映射关系**（默认 是）：决定 N 份拆分账单的非金额字段（除三个金额字段外）是否复用主模板。置为「否」时可在「拆分/合并账单映射关系设置」弹框中为拆分账单单独配置一套字段映射（所有 N 份共享一套）。
- **典型适用场景**：
  - "一行含多币种"：原始账单的一行同时包含本币和外币的发生额（CNY_AMT + USD_AMT 两列），需要拆成 2 行输出，分别用 Currency = CNY / USD。
  - "多行组成一笔交易"：原始账单的连续若干行属于同一笔交易（手续费 + 本金），需要合并为 1 行输出，按净值符号自动落 Credit/Debit。
- **互斥关系**：本功能与 v1.4.x 的「Credit/Debit 直接映射」、v1.4.7 的「按正负号拆分的发生额」、v1.4.8 的「按字段区分发生额」**4 选 1 完全互斥**。任意两种同时启用时保存模板会报错；启用本功能时会自动清空其它三种模式的配置。

### 已知限制

- **v1.4.8 及以下版本的应用无法打开 v1.4.9 及以上版本导出的模板 bundle**（报错拒绝，由 v1.4.8 预埋的 `bundleVersion = 3` 校验机制生效）。如果需要跨版本共享含此配置的模板，请确保接收方也升级到 v1.4.9 或更高版本。
- v1.4.7 及以下版本仍会**静默忽略**新字段（已知限制，继承自 v1.4.8 Release Note）。
- 合并账单要求合并组内 `Currency` 必须一致：跨币种合并会报错 `合并账单的 Currency 不一致，无法合并`，需要先按币种分组再合并。
- **合并账单的净值为 0 时该合并组被静默跳过**：若 Σ(Credit) − Σ(Debit) = 0，该合并组不会产生任何输出行，但导入流程**不报错不中断**，继续处理其他行/组。同理，若某条原始行展开出的单条拆分行 Credit/Debit 都为 0（或为空），该行也会被静默丢弃（**2026-04-08 fix2 override**：原定报错阻断策略已改为静默过滤；详见 PRD §4.4.2 末尾的 override 说明）。
