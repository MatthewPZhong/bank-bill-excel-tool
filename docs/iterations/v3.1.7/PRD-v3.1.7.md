# PRD v3.1.7：Payment 与 R5s2-recon 调拨回填调整

## 一、背景

Payment 线下调拨回填和普通 R5s2-recon 原先使用不同输入形态和独立消费过程，可能让同一银行行或调拨业务事实在两个引擎间重复成为候选。本版将两者收口到同一份调拨对账单运行工作副本，并补充付款账户和订单周边界核对。

## 二、目标

1. 开启 Payment 时固定 Payment 先运行、R5s2-recon 后运行。
2. 两个引擎共享派生行使用状态和银行消费集合。
3. Payment 必须核对调拨付款账户与银行 `Drawee CardNo`。
4. Payment 按连续 ISO 订单周建立左闭右开的银行候选窗口。
5. 输出完整展示实际配对、原始银行行和原始调拨派生行。

## 三、业务规则

- 开启 Payment 时强制使用中台调拨派生表；Payment 关闭时保持既有来源行为。
- 调拨派生新增“付款方式”和运行态“是否被使用”；使用状态每次运行重置，不写回数据库。
- Payment 只消费 `FundTransfer-in`；同订单 `FundTransfer-out` 可继续供 R5 使用。
- Payment 已消费银行 `_rowId` 必须从 R5 排除；同值命中仍消费双方。
- Payment 候选必须同时满足状态、付款方式、方向、渠道、地区、大账号、金额、币种、付款账户和非空 ReconID。
- 同周多个订单日期取最早值；订单周断档或日期非法时，在两个引擎写值前整体阻断。
- R1/R2 使用订单周窗口，R3 保留相同核对要素且日期差不超过 7 天的兜底。

## 四、输出与非目标

- Payment 核对 sheet 固定为“匹配对照”“银行行-原始”“调拨对账单行-原始”。
- “未命中场景”不新增异常说明列；“命中场景”保留既有异常说明与多对多审计。
- 不新增最终 ReconciliationId 重复检测、重复统计或重复提示。
- 不改变 R5s2-recon 的付款账户核对要素，不把 Payment 条件扩散到普通 R5。

## 五、验收基线

固定样本为 CITI LU 银行账单 1,831 行和中台调拨订单 223 行。生产链路应得到：派生 446 行；Payment 匹配 220（R1=218、R2=0、R3=2），实际改写 190；R5 后续改写 2；命中 192、未命中 1,639；三个 Payment 核对 sheet 各 220 条，且付款账号 220/220 等于 `Drawee CardNo`。

## 六、风险与发布

本功能写入银行 ReconciliationId，属于资金红线。自动化和固定样本 baseline 只能证明规则按代码执行，不能替代业务逐笔判断。技术 Release 可按受控 tag workflow 生成，但正式业务启用和公告前必须完成人工复核 220 条 Payment 配对与 2 条 R5 回填。

正式发布还要求：完整 release-check、主页面布局、重要变量检查、Windows Release workflow、四项公开资产摘要和 `latest.yml` 契约全部通过，并通过独立证据 PR 回写。

## 七、发布状态

v3.1.7 已于 2026-08-03 通过受控 Windows Release workflow 发布为 latest stable，四项公开资产及 updater 元数据已独立回读通过。技术 Release 不解除第六节人工资金门禁；业务启用和公告仍须完成 220+2 逐笔复核及 Windows 实机 canary。
