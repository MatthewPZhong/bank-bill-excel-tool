## 一、需求概述

本版本包含 5 项需求：

1. **发生额精度提升到小数点后 12 位** —— 网银原始账单映射为 `Credit Amount`、`Debit Amount` 和发生额的值支持保留小数点后 12 位，支持输出到对应明细账单的 `Credit Amount`、`Debit Amount` 和余额账单的余额里。
2. **大账号确认页标题和文案改动** —— 页面标题改为「网银账单解析大账号确认」，「记住大账号选择顺序」改为「记住顺序」，「定位大账号」和编辑框向右平移补缺。
3. **"记住顺序"持久化增强** —— 在「账号顺序固定」模式下勾选「记住顺序」时，持久化本次导入文件的文件个数、每个文件里的账户个数、每个文件里所有的账户号、每个文件里账户的排序。导入时自动匹配，匹配失败弹提醒框。
4. **"提取大账号顺序"功能** —— 原「检查排序」按钮改为「提取大账号顺序」，点击后弹出新对话框，左侧显示文件顺序，右侧显示从文件中提取出的大账号信息排序，支持编辑，完成后填入主页面。
5. **删除"文件顺序"帮助图标** —— 去掉「文件顺序」右侧的圆形问号帮助图标。

## 二、背景与目标

### 2.1 背景

**需求 1**：当前金额处理流程中 `sanitizeAmountValue`（`src/backend/file-service/normalizers.js:91`）将原始值清洗为纯数字字符串后不做截断，但 `parseNumericValue`（同文件 :19）使用 `Number()` 转换，其浮点精度约为 15-17 位有效数字。此外 `roundAmount`（同文件 :41）显式调用 `toFixed(2)` 将金额四舍五入到 2 位小数用于余额推算。对于某些银行账单（如外汇交易）原始数据包含超过 2 位小数的金额值，当前 2 位精度会造成数据丢失。

**需求 2~5**：当前大账号选择页（`createBigAccountSelectionDialog`，`src/renderer-dialogs.js:503`）存在以下问题：
- 页面标题和文案不够简洁准确。
- 「记住大账号选择顺序」（当前 `big-account-order-store.js`）仅存储 `assignments`（merchantId + currency 的列表），不记录文件个数、各文件的账户个数和账户号。导入新文件时无法自动判断文件结构是否匹配，用户每次都需要手动确认。
- 原「检查排序」功能只做匹配校验弹提醒，不能自动提取文件中的大账号信息并填入。用户需要手动一个个勾选。
- 「文件顺序」右侧的帮助图标不再需要。

### 2.2 目标

- 需求 1：`Credit Amount`、`Debit Amount` 和发生额（含余额账单的余额）支持保留小数点后最多 12 位精度，不补零。
- 需求 2：更新页面标题和文案。
- 需求 3：在「账号顺序固定」+ 勾选「记住顺序」时，持久化完整的文件-账户映射信息到模板文件中，导入时自动匹配并跳过手动确认，匹配失败时弹框提醒。
- 需求 4：用「提取大账号顺序」替代原「检查排序」，自动从文件提取大账号信息并填入主页面。
- 需求 5：删除帮助图标。

## 四、功能详细描述

### 4.1 需求 1：发生额精度提升到小数点后 12 位

#### 4.1.1 影响范围

以下字段的值需要支持保留小数点后最多 12 位：

| 输出位置 | 字段 |
|---------|------|
| 明细账单 | `Credit Amount` |
| 明细账单 | `Debit Amount` |
| 余额账单 | 余额值（通过发生额计算或直接映射） |

#### 4.1.2 当前精度瓶颈分析

| 环节 | 当前行为 | 是否需要修改 |
|------|---------|-------------|
| `sanitizeAmountValue` (normalizers.js:91) | 清洗为纯数字字符串，**不截断小数位** | 不需要（已保留原始精度） |
| `parseNumericValue` (normalizers.js:19) | 使用 `Number()` 转换，浮点精度约 15-17 位有效数字 | **需要评估**：12 位小数 + 整数部分若不超过 3-5 位，总有效数字在 15-17 位内可满足；但边界情况可能需要字符串运算 |
| `roundAmount` (normalizers.js:41) | `toFixed(2)` 四舍五入到 2 位小数 | **需要修改**：新增高精度版本用于余额推算，原 `roundAmount` 保留用于余额比对容差（Q-A3 已确认） |
| `splitSignedAmountValue` (normalizers.js:274) | 内部调用 `parseNumericValue` 后 `String(Math.abs(numericValue))` | **需要评估**：`Math.abs` + `String()` 可能丢失尾部零 |
| Excel 输出 (`writers.js`) | 写入 Excel 单元格时的数值格式 | **需要修改**：默认数字格式，超 15 位有效数字时自动切文本格式（Q-A2 已确认） |

#### 4.1.3 预期行为（Q-A1 已确认：最多 12 位，不补零）

- 原始账单中 `Credit Amount` / `Debit Amount` 映射字段的值若包含小数点后 12 位及以内的数字，输出到明细账单时**完整保留**，不截断、不四舍五入。
- 小数点后不足 12 位的值（如 `100.50`）**保持原样输出，不补零**。
- 小数点后超过 12 位的部分：截断或四舍五入到 12 位（具体策略由 Dev 在 TechDoc 决定）。
- 余额账单中通过发生额计算得出的余额值（`calculateEndingBalanceFromAmounts`，normalizers.js:85）同样保留到小数点后最多 12 位精度。

#### 4.1.4 Excel 输出格式（Q-A2 已确认：A2-3 自动切换）

- **默认**以**数字格式**写入 Excel 单元格。
- 当检测到某个金额值的**有效数字超过 15 位**时（如整数部分 4 位 + 小数 12 位 = 16 位有效数字），自动切换为**文本格式**写入该单元格，确保所有位数完整保留。
- 切换粒度为**单元格级别**（不是整列），仅对超出 15 位有效数字的单元格启用文本格式。

#### 4.1.5 `roundAmount` 修改策略（Q-A3 已确认：A3-2 新增高精度版本）

- **保留**现有 `roundAmount`（`toFixed(2)`），继续用于 `inferEndingBalance` 中的余额比对容差逻辑（`< 0.005` 判断）。
- **新增**一个高精度版本（如 `roundAmountHighPrecision`），使用 `toFixed(12)` 或等效的高精度四舍五入，用于需要保留 12 位精度的场景（如 `calculateEndingBalanceFromAmounts` 的最终输出）。
- 具体函数签名和调用点由 Dev 在 TechDoc 决定。

### 4.3 需求 3："记住顺序"持久化增强

#### 4.3.1 触发条件

当「多账号账单导入解析模式」= **账号顺序固定**，且用户勾选了「记住顺序」checkbox 时触发。

#### 4.3.2 持久化的数据内容

勾选「记住顺序」后，除了现有的大账号分配列表（`assignments`）外，**额外持久化**以下信息：

| 数据项 | 说明 |
|-------|------|
| 文件个数 | 本次导入的文件总数 |
| 每个文件里的账户个数 | 各文件中识别到的账户块数量 |
| 每个文件里所有的账户号 | 各文件中识别到的所有账户号列表 |
| 每个文件里账户的排序 | 各文件中账户号的排列顺序（从上到下） |

> **数据结构示例**（PM 建议，Dev 可在 TechDoc 调整字段名）：
> ```json
> {
>   "fileCount": 3,
>   "files": [
>     {
>       "fileIndex": 0,
>       "accountCount": 2,
>       "accounts": [
>         { "merchantId": "62001234567890", "currency": "CNY" },
>         { "merchantId": "62009876543210", "currency": "USD" }
>       ]
>     },
>     {
>       "fileIndex": 1,
>       "accountCount": 1,
>       "accounts": [
>         { "merchantId": "44001234567890", "currency": "HKD" }
>       ]
>     },
>     ...
>   ],
>   "assignments": [ ... ]
> }
> ```

#### 4.3.3 存储位置

- 该配置存入**模板文件**（与当前 `big-account-order-store.js` 的存储机制对齐或扩展）。
- 之后对该配置做修改时需**联动修改模板文件**中相关数据。
- **导出模版文件**（bundle）时需**包含**该配置。导入 bundle 时需还原。

#### 4.3.4 导入时自动匹配流程

每次导入文件时，如果该模板的「多账号账单导入解析模式」= 账号顺序固定 且用户有勾选「记住顺序」（即存在记住顺序配置），执行以下匹配流程：

**步骤 1：检查文件个数**

- 若导入文件个数 **不等于** 记住顺序配置中的文件个数 → **自动降级**：进入页面后的「多账号账单导入解析模式」切换为「账号顺序不固定」，由用户手动确认。

**步骤 2：文件个数相同时，逐文件匹配**

- 记录导入文件里各文件中的账户个数和账户号。
- 将各文件中的账户个数和账户号与记住顺序配置中的各文件的账户个数和账户号做**内容匹配**（**不按文件位置对位**，而是按账户个数 + 账户号集合做匹配——即导入的文件 A 可能匹配到配置中的文件 B，只要它们的账户个数和账户号相同）。

**步骤 3：匹配结果判定**

- **全部文件匹配成功**（账户个数和账户号都匹配）→ 对应导入的文件按记住顺序配置中对应文件的账户的排序去**直接输出**明细和余额账单（跳过大账号确认页）。
- **有任一文件匹配失败** → 弹出提醒框（见 §4.3.5）。

#### 4.3.5 匹配失败提醒框

**提醒框内容**：

显示文本：`{文件名}的账户个数或账户号匹配不上（账户个数和账户号都匹配不上），请检查。`

> **说明**：提醒文本需明确指出**哪个文件**匹配不上。如果多个文件匹配不上，逐行列出（见 Q-D1）。

**提醒框按钮**（置于提醒框中间下方）：

| 位置 | 按钮文本 | 行为 |
|------|---------|------|
| 左侧 | `变更配置` | 点击后进入「网银账单解析大账号确认」页面，供用户编辑大账号顺序 |
| 右侧 | `确认` | 点击后返回主页面（不做导入） |

### 4.4 需求 4："提取大账号顺序"功能

#### 4.4.1 按钮位置

原「检查排序」按钮（大账号确认页左下角）**文本改为** `提取大账号顺序`。按钮位置不变。

#### 4.4.2 弹出框布局

点击「提取大账号顺序」按钮后弹出一个新对话框：

| 区域 | 内容 |
|------|------|
| 左上角 | 标题文本：`确认大账号顺序` |
| 右上角 | 关闭按钮（`×`），点击关闭弹出框返回大账号确认页 |
| 左侧 | 显示上级页面（大账号确认页）里的文件顺序（复用上一级的文件顺序样式）。左侧文件名较长时做省略显示（truncate），并显示行号后缀（如 `第3行`） |
| 右侧 | 显示根据上级页面里文件顺序的行数据**提取出来的大账号信息**做好的排序（复用上一级的大账号顺序样式）。每行左侧带**数字序号**（1. 2. 3. ...） |
| 右下角 | `完成` 按钮 |

**提取数据来源**：不固定模式下，提取使用前端传递的左侧面板文件数据（`frontendFileRows`）驱动，确保提取的账户数量和左侧文件顺序面板展示的行数**一致**。

**左右同步滚动**：弹出框左侧和右侧面板**同步滚动**——当用户滚动其中一侧时，另一侧同步跟随滚动，保持左右行对齐。

#### 4.4.3 右侧行数据的编辑交互（Q-E2 确认：E2-3 双输入框 + 精准匹配校验）

右侧的每一行数据的**最右侧**带有「编辑」文字按钮。

- 点击「编辑」→ 对应行数据变为可编辑状态：行内出现**两个输入框**（账户号 + 币种），分别编辑。
- 编辑完成后点击「完成」→ 执行以下校验：
  1. 将输入框中的账户号和币种与模板维护的**大账号表**做**精准匹配**。
  2. **匹配成功**：行数据**文本化**（回到只读显示状态）。
  3. **匹配失败**：弹出提醒框，显示文本 `大账号信息不存在，请重新输入。`，用户点击「确认」后保持编辑状态，允许重新输入。

#### 4.4.4 提取失败处理

如果某些文件/行数据**提取不到大账号信息**：

- 弹出提醒框，显示是**哪些行数据**提取不到大账号信息。
- 用户点击「确认」后返回上一级（大账号确认页）。

#### 4.4.5 "完成"按钮行为（Q-E3 确认：条件覆盖）

点击弹出框右下角的「完成」按钮后：

1. **检查大账号确认页右侧是否已有已勾选选项**：
   - **有已勾选选项** → 弹二次确认框，确认后**覆盖**现有勾选，用提取结果替换；取消则不动作，保持弹出框打开。
   - **无已勾选选项** → **直接覆盖**（不弹确认）。
2. 将弹出框右侧的做好排序的大账号信息**填入**主页面（大账号确认页）右侧的「大账号顺序」表里。
3. 按照排序填入，与左侧文件顺序的序号**对齐**（第 1 个提取出的大账号对应文件顺序的第 1 行，以此类推）。
4. 填入后，大账号确认页右侧的「大账号顺序」面板按填入的序号**从上到下排序**显示（已勾选的按序号排前面，未勾选的按原序排后面）。
5. 关闭弹出框。

#### 4.4.6 主页面左右面板同步滚动

大账号确认页的左侧「文件顺序」面板与右侧「大账号顺序」面板**同步滚动**——当用户滚动其中一侧时，另一侧同步跟随滚动，保持左右行对齐。

## 八、非功能性要求

| 类别 | 要求 |
|------|------|
| 向下兼容 | 需求 1 的精度提升不应改变小数位 ≤ 2 位的金额的现有输出格式 |
| 向下兼容 | 需求 3 的 bundle 格式扩展需保证旧版本 app 打开新 bundle 时不崩溃（可忽略新字段，但不应报错阻断） |
| 性能 | 需求 3 的自动匹配流程和需求 4 的大账号提取不应显著增加导入等待时间 |
| 鲁棒性 | `.csv` 文件如果实际内容是 XLS/XLSX 二进制格式（magic bytes 检测），应自动走 XLSX 库解析而非纯文本 CSV 解析（v1.4.7 回归 bug 修复） |
