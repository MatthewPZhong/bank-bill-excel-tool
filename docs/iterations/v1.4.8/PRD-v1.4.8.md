## 一、需求概述

本版本包含 1 项需求：

1. **按字段区分发生额** -- 在「映射关系设置」中新增一行配置项「按字段区分发生额」，配合一个新对话框「发生额映射关系管理」，允许用户通过「条件字段 + 条件值 → 目标字段映射为 Credit Amount / Debit Amount」的方式配置发生额来源。本配置与现有的「直接映射 Credit/Debit Amount」「按正负号拆分的发生额」**三者互斥**。

---

## 二、背景与目标

### 2.1 背景（业务场景）

当前 v1.4.x 已经支持以下两种「发生额」配置方式：

1. **直接映射**：模板字段 `Credit Amount` / `Debit Amount` 分别映射到源文件的两个独立金额列。
2. **按正负号拆分**：通过「按正负号拆分的发生额」（`SIGNED_AMOUNT_MAPPING_FIELD`）将单个金额列按正负号自动拆分为收入和支出。

但仍有部分银行的流水文件采用如下结构，无法通过上述两种方式覆盖：

- **场景 A**：单金额列 + 类型列。例如某 CSV 中只有一列 `AMOUNT`，配合一列 `TXN_TYPE`，其中 `TXN_TYPE = C` 表示收入、`TXN_TYPE = D` 表示支出。
- **场景 B**：两个金额列 + 类型列。例如 CSV 中存在 `AMOUNT1`、`AMOUNT2`、`TXN_TYPE` 三列，根据 `TXN_TYPE` 的取值决定是 `AMOUNT1` 当作 Credit Amount 还是 `AMOUNT2` 当作 Debit Amount，或反之。
- **其它变种**：基于"条件字段 + 条件值 → 目标字段"的通用形式可表达的所有结构。

本需求通过统一的"条件 + 字段映射"形式覆盖以上所有场景，让用户可以告诉系统：在何种条件下，把哪一列当作 Credit Amount，把哪一列当作 Debit Amount。

### 2.2 目标

- 在「模版管理 → 映射关系管理 → 映射关系设置」对话框中，新增一个名为「按字段区分发生额」的配置项。
- 提供一个独立的「发生额映射关系管理」对话框，允许用户配置 Credit Amount 和 Debit Amount 各自的条件式映射规则。
- 数据需要持久化到模板（DB schema 迁移），导入文件时按规则生效。
- 与现有的「直接映射 Credit/Debit Amount」「按正负号拆分的发生额」三者互斥。

## 三、功能详细描述

### 3.1 映射设置新增行「按字段区分发生额」

**位置：**

新增行插入在「映射关系管理」对话框（`createMappingDialog`，`src/renderer-dialogs.js:1444`）的「映射关系设置」分组的**末尾**（位于现有 advanced 字段之后）。该字段属于 `ADVANCED_MAPPING_FIELDS` 范畴（即与「按正负号拆分的发生额」「根据发生额做映射的户名」「根据发生额做映射的账户号」同组）。

**UI 元素：**

| 元素 | 说明 |
|------|------|
| 左侧标签 | 文本：`按字段区分发生额` |
| 右侧下拉框 | **复用** 现有映射设置行使用的同款单选下拉控件（`.mapping-select`），包含两个选项：<br>① 空白（默认值）<br>② `是` |
| 右侧按钮（条件显示） | 当下拉框选中 `是` 时，在下拉框**右侧**立即出现一个按钮，标签为 `发生额映射关系管理`；其余情况隐藏 |

**交互：**

1. 用户首次进入对话框时，下拉框为空白（默认值），按钮隐藏。
2. 用户在下拉框中选择 `是`：
   a. 下拉框右侧立即出现 `发生额映射关系管理` 按钮（同行渲染）。
   b. 同时**彻底清空**另外两种发生额相关配置（互斥处理 — 不仅清空 UI，也清空将要写入 DB 的值）：
      - 模板字段 `Credit Amount` 的映射值（设为空）
      - 模板字段 `Debit Amount` 的映射值（设为空）
      - advanced 字段「按正负号拆分的发生额」的映射值（设为空）
   c. 这三行在视觉上**保持显示**（不隐藏整行），下拉框被重置为空，并禁用 / 灰显，提示用户当前互斥（具体禁用方式由 Dev 在 TechDoc 中决定，PM 建议加 disabled 样式 + tooltip 提示"已开启『按字段区分发生额』，本字段不可用"）。
3. 用户将下拉框由 `是` 切回空白时：
   a. `发生额映射关系管理` 按钮立即隐藏。
   b. 之前在弹框中配置的两行规则**草稿保留**（不清空），下次重新选择 `是` 时回显（详见 Q12）。
   c. 上一步被互斥清空的三行（Credit Amount、Debit Amount、按正负号拆分的发生额）解除 disabled，但其值已经被清空，需要用户重新配置。
4. 用户点击 `发生额映射关系管理` 按钮，弹出 3.2 节描述的对话框。

**数据：**

- 该下拉框的当前值（空白 / 是）随其它映射一并保存到模板。
- 该下拉框的取值是一个**新枚举概念**（"是 / 空白"），不复用任何已有 `mappedField` 取值。

### 3.2 弹框「发生额映射关系管理」

**触发：** 点击 3.1 节中描述的 `发生额映射关系管理` 按钮。

**对话框结构：**

| 区域 | 内容 |
|------|------|
| 左上角 | 标题文本：`发生额映射关系管理`（无副标题） |
| 主体 | 两行规则（详见下方），**固定 2 行，不可增删** |
| 右下角 | `完成` 按钮 |

**主体两行规则：**

> 下列描述中：`""`（双引号）= 单选下拉框，`[]`（方括号）= 输入框。

- **第一行**（固定映射到 Credit Amount）：`当 "1" 的值为 [1] 时， "2" 映射为 Credit Amount`
- **第二行**（固定映射到 Debit Amount）：`当 "3" 的值为 [2] 时， "4" 映射为 Debit Amount`

> "映射为 Credit Amount" 和 "映射为 Debit Amount" 是**固定文案**，不可修改、不可调换顺序。

**枚举值来源：**

| 占位符 | 类型 | 取值来源 | 说明 |
|--------|------|---------|------|
| `"1"` | 下拉框 | `template.headers` | 该模板从源文件中识别到的所有列名 |
| `"3"` | 下拉框 | `template.headers` | 同上 |
| `"2"` | 下拉框 | `template.headers` | 同上 |
| `"4"` | 下拉框 | `template.headers` | 同上 |
| `[1]` | 输入框 | 用户自由输入 | 必填，匹配规则见 3.2.1 |
| `[2]` | 输入框 | 用户自由输入 | 必填，匹配规则见 3.2.1 |

**特殊值排除：**

下拉框选项中**不**包含以下特殊枚举值：
- `自己输入`（`MERCHANT_ID_SELF_INPUT_OPTION`）
- `需要拼接字段`（`CONCAT_FIELDS_MAPPING_FIELD`）
- 其它非真实列的"控制项"占位

仅展示真实存在于源文件 headers 中的列名。

**字段同/异约束：**

- **同一行内**：条件字段与目标字段**不能是同一个**字段（即第一行的 "1" ≠ "2"，第二行的 "3" ≠ "4"）。
- **跨行**：第一行的条件字段 "1" 和第二行的条件字段 "3" **可以是同一个字段**（典型场景：两行都用 `TXN_TYPE`）。
- **跨行**：第一行的目标字段 "2" 和第二行的目标字段 "4" **可以是同一个字段**（典型场景：两行都用 `AMOUNT` 列）。

**完成按钮语义：**

- 点击 `完成` **直接落库**到数据库（不走外层「映射关系管理」对话框的草稿模式）。
- 落库前先做校验（详见 3.2.2 校验规则）。校验通过则写入 DB 并关闭弹框；校验失败则弹错误提示，**用户点确认后保留弹框打开状态、不丢失已填字段**，让用户重新编辑。
- 外层「映射关系管理」对话框的「完成」/「取消」/「关闭」均不影响弹框中已落库的配置。

#### 3.2.1 条件值匹配规则（输入框 `[1]` `[2]`）

输入框的值被解释为以下两种语法之一（**二选一**，不支持多值组合）：

##### A. 字面值精确匹配（默认）

| 规则 | 内容 |
|------|------|
| 匹配方式 | **整串精确匹配**（不是包含 / 前缀 / 后缀） |
| 大小写 | **大小写敏感** |
| Trim | 比较前**先 trim 源数据字段值的首尾空白**（用户输入框的值在保存时也 trim） |
| 数字归一化 | **不做归一化**。保持原字符串精度比较，例如源值 `1.0` 与用户输入 `1` **不视为匹配** |
| 空字符串 | 输入框空值不允许保存，详见校验规则 |

##### B. 正则表达式

| 规则 | 内容 |
|------|------|
| 触发条件 | 输入框内容**以 `/` 开头**且**包含结尾 `/`**（结尾 `/` 后可选带正则 flag），例如 `/^C$/`、`/^C.*/`、`/c/i` |
| 语法 | 标准 JavaScript `RegExp` 字面量语法 `/pattern/flags`，flags 可选，支持 `i` / `g` / `m` / `s` / `u` |
| 匹配方式 | `regex.test(trimmedSourceValue)`（整串 test），不使用 `match` / `exec` |
| 大小写 | **遵循 Q4 大小写敏感原则**：**默认不自动加 `i` flag**。用户如需大小写不敏感，必须显式写 `/C/i` 等带 `i` flag 的形式 |
| Trim | 与字面值模式一致，先 trim 源字段值首尾空白后再做 `regex.test` |
| 无效正则 | 在配置时校验：保存时若 `new RegExp(pattern, flags)` 抛异常，则报错 `正则表达式语法错误`，保留弹框打开、不丢失已填字段 |
| 数字归一化 | 不做归一化（与字面值模式一致） |

##### 关于多值

**不支持**在单个输入框中表达多个候选值（如 `C,CR,Credit` 这种逗号分隔形式）。如果用户希望匹配多种值，请使用正则的分组语法（例如 `/^(C|CR|Credit)$/`）来表达。

##### 注意事项

- 正则触发依据是"字符串以 `/` 开头并含结尾 `/`"。如果用户希望把字面值的 `/foo/` 当作普通字符串匹配（即真的想匹配源字段值就是 `/foo/` 这一串字符），目前**没有转义机制**，必须使用正则形式 `/^\/foo\/$/`。这是已知的语法限制。

#### 3.2.2 校验规则（点击「完成」时执行）

| 错误场景 | 提示文案 |
|---------|---------|
| 任一条件字段下拉框 ("1" / "3") 未选择 | `请为两行规则分别选择条件字段` |
| 任一目标字段下拉框 ("2" / "4") 未选择 | `请为两行规则分别选择目标字段` |
| 任一条件值输入框 (`[1]` / `[2]`) 为空 | `请填写条件值` |
| 任一条件值输入框被识别为正则模式（即以 `/` 开头并包含结尾 `/`）但 `new RegExp(pattern, flags)` 抛异常 | `正则表达式语法错误` |
| 同一行内条件字段与目标字段相同（即 "1" == "2" 或 "3" == "4"） | `条件字段与目标字段不能相同` |
| 用户在外层下拉框选了 `是` 后打开弹框却完全不填，点击「完成」 | 同上述各错误，按字段顺序提示 |
| 「按字段区分发生额 = 是」但 `template_amount_split_rules` 表中该模板无记录（即外层下拉框选了「是」但弹框中的两行规则未配置）。**触发时机**：保存外层「映射关系管理」对话框时校验 | `请先在"发生额映射关系管理"中配置完整的两行规则`<br>（错误码：`AMOUNT_SPLIT_RULES_MISSING`） |

错误提示通过弹窗（如 `createAlertDialog`）展示，用户点确认后**保持弹框打开**，已填字段不丢失。

> 注：上面最后一行（`AMOUNT_SPLIT_RULES_MISSING`）的校验时机不在「发生额映射关系管理」弹框的「完成」按钮，而是在**外层「映射关系管理」对话框保存时**触发。这是为了防止用户开了开关却始终没打开过弹框配规则就直接保存外层对话框，从而留下"开关=是 + DB 规则空"的不一致状态。

### 3.3 数据持久化

#### 3.3.1 模板字段层

「按字段区分发生额」下拉框的当前值（`空白` / `是`）按模板维度持久化。该字段在模板的 `mappings` 列表中以一个独立行的形式存在（`templateField` = `按字段区分发生额`，`mappedField` 取值为空字符串或 `是`）。

#### 3.3.2 弹框规则层

「发生额映射关系管理」弹框中两行规则的**全部 6 个值**（4 个下拉框 + 2 个输入框）需要按模板维度持久化。

#### 3.3.3 DB schema 迁移

需要走 DB schema 迁移，给现有 `template_mappings` 表（或新建关联表）增加新列以容纳"条件字段 + 条件值 + 目标字段"的二元组数据结构。**具体 SQL 由 Dev 在 TechDoc 阶段决定**，本 PRD 不做实现层选型。

迁移要求：
- 旧模板（升级前生成的）的「按字段区分发生额」字段默认填 `空白`。
- 旧模板的两行规则字段默认填空，不影响打开映射关系管理对话框。
- 迁移脚本必须幂等，可重复执行。

#### 3.3.4 弹框草稿与下拉框状态的关系

- 用户在弹框里配置两行规则后，**草稿跟着模板走、跟外层下拉框的「空白/是」状态无关**。
- 用户在弹框中配好规则 → 点「完成」落库 → 关闭外层对话框 → 把外层下拉框切回 `空白` → 再切回 `是`：弹框中**仍能回显**之前配的规则。
- 只有用户在弹框里**主动清空**字段并点「完成」时，规则才真正丢失。
- 该行为在 DB 层等价于：「按字段区分发生额」下拉框值 `是 ↔ 空白` 的切换不会清除关联的 6 个规则字段，只是控制规则是否在导入时生效。

#### 3.3.5 Bundle 版本字段（`bundleVersion`）

本版本在模板 bundle 文件顶层新增 `bundleVersion` 字段：

| 项目 | 内容 |
|------|------|
| 字段名 | `bundleVersion` |
| 类型 | integer |
| 本版本取值 | `2`（v1.4.8 起统一写入） |
| 写入行为 | 本版本导出 bundle 时一律写入 `bundleVersion = 2`（即使 bundle 中不含「按字段区分发生额」配置也写） |
| 读取行为 | **本版本写入但不校验拒绝**（因目前没有更高版本可校验拒绝），主要为后续版本预埋机制 |
| 后续版本 | v1.4.9+ 版本读取 bundle 时会校验此字段：若其值 > 自身支持的最大版本，则报错拒绝并提示"bundle 来自更高版本的 app，请升级" |

> **背景说明**：v1.4.7 的 `readTemplateBundleFile` 不读取 / 不校验任何版本字段，遇到未知字段静默忽略。我们无法"追溯"让一个已经发布的旧版本 app 开始报错拒绝新 bundle。因此 v1.4.7→v1.4.8 这一方向的"旧版应用打开新 bundle"是**已知不兼容**（详见 AC1-20、Open Questions Q9-b、第十一节 Release Note 草稿）。本字段的目的是从 v1.4.8 开始建立版本约定，让 v1.4.9+ 起的所有未来版本都能正确识别并拒绝更高版本的 bundle。

### 3.4 导入时的行为

当模板的「按字段区分发生额」= `是` 且「发生额映射关系管理」中两行规则均有效时，导入文件的预期效果：

#### 3.4.1 规则匹配

对每一行原始数据，**并行**评估两行规则（互不依赖）：

- **Credit 规则**：取该行中条件字段 `"1"` 的原始值，按 3.2.1 节匹配规则与条件值 `[1]` 比较。若匹配，则取该行中字段 `"2"` 的值，写入到目标列 `Credit Amount`。
- **Debit 规则**：取该行中条件字段 `"3"` 的原始值，按 3.2.1 节匹配规则与条件值 `[2]` 比较。若匹配，则取该行中字段 `"4"` 的值，写入到目标列 `Debit Amount`。

两行规则相互独立，可以同时命中（如条件字段都是 `TXN_TYPE`、条件值都是 `Both` 等极端场景），也可以全部不命中。

#### 3.4.2 与现有发生额方案的互斥（强制）

「按字段区分发生额」与以下两种模式**强制互斥**：
- 直接映射 Credit Amount / Debit Amount（即模板字段 `Credit Amount` 或 `Debit Amount` 的 `mappedField` 非空）
- 按正负号拆分的发生额（`SIGNED_AMOUNT_MAPPING_FIELD` 的 `mappedField` 非空）

互斥在两层强制：

1. **UI 层 + 待保存值**：3.1 节描述的"选『是』后立即彻底清空另外两种模式的下拉框值并 disabled"。所谓"彻底清空"包括 UI 上的展示和将随『完成』动作落库的待保存值，**不是**仅 UI 隐藏而 DB 仍保留旧值。
2. **保存层**：在 `template:save-mappings` 的校验中（`src/main.js:2924`），仿照 `src/main.js:2590` 的现有检查模式，加入新的互斥校验。如果待保存的 mappings 中同时存在「按字段区分发生额 = 是」和上述任一其它模式的非空 `mappedField`，保存时报错：`「按字段区分发生额」与 Credit Amount / Debit Amount 直接映射、按正负号拆分的发生额三者不能同时设置`。

#### 3.4.3 未匹配行的处理

- 当某一行原始数据**两行规则都未命中**时：Credit Amount 和 Debit Amount 列均为空（即视该行为非交易行 / 非有效金额行）。
- 由于 3.4.2 已强制互斥（UI 层 + 待保存值层 + 保存校验层共同保证），DB 中**不可能**同时存在「直接映射 Credit/Debit」配置作为 fallback，因此**没有"回落到直接映射"的路径**。这一行为已在 Q13 中由用户最终确认（理解 B：彻底清空，未匹配行为空，无 fallback）。

**单文件 / 多文件批量导入的"全部未命中"告警语义：**

- **逐文件独立判定**：每个被导入的文件**独立**评估"是否全部行均未命中任何规则"（即对该文件的 `命中的 Credit + Debit 行数 == 0` 这一布尔值独立计算）。
- **聚合告警**：在一次导入操作（无论是单文件还是多文件批量）结束后，收集所有被判定为"全部未命中"的文件名，**合并为一个告警框**统一弹出。
- **告警文案**（多行，文件名按原导入顺序排列）：
  ```
  以下文件全部未命中收支规则，请检查规则配置：
  file1.csv
  file5.csv
  ```
  - 若只有 1 个文件全部未命中，文案格式相同（标题行 + 一行文件名），不退化为单行文案。
  - 若只导入了 1 个文件且该文件全部未命中，仍使用此格式。
- **不弹告警的场景**：本次导入的所有文件均至少有 1 行命中（无论 Credit 还是 Debit），则**不弹告警**。
- **不阻断导入**：导入流程不因告警阻断；告警只是提示用户检查配置，文件仍正常生成（被未命中的文件其 Credit/Debit 列为空，由用户判断是配置错了还是文件确实不含有效交易行）。

#### 3.4.4 与「根据发生额做映射的户名 / 账户号」的联动

「根据发生额做映射的户名」（`AMOUNT_BASED_NAME_MAPPING_FIELD`）和「根据发生额做映射的账户号」（`AMOUNT_BASED_ACCOUNT_MAPPING_FIELD`）当前依赖 `hasCreditAmount` / `hasDebitAmount` 标志（`src/backend/file-service.js:160-178`）。

- 在「按字段区分发生额」模式下，`hasCreditAmount` / `hasDebitAmount` 标志需要根据本节 3.4.1 计算出的 Credit/Debit Amount 值正确感知（即按规则匹配后的实际写入值判断，与现有"直接映射"模式下的语义保持一致：只要该行 Credit Amount 非空且非 0，则 `hasCreditAmount = true`，Debit 同理）。
- 因此「根据发生额做映射的户名 / 账户号」在新模式下可以正常工作，无需用户额外配置。
- 具体实现由 Dev 在 TechDoc 中决定。

#### 3.4.5 多文件 / 多账号粒度

- 「按字段区分发生额」配置是**模板级**的，不按账号 / 文件细分。
- 一个模板的配置对该模板所有导入的文件 / 所有大账号生效。

#### 3.4.6 源文件中条件字段不存在的处理

- 若导入的源文件 headers 中不存在配置中选定的条件字段或目标字段（如用户配了 `TXN_TYPE` 但该次导入的文件没有这一列），导入时报错：`映射字段不存在：{字段名}`，参考现有 `src/main.js:2594-2596` 的错误模式。

#### ✅ Q4-多值-已确认（2026-04-07）

**最终结论：不支持多值。** 用户最后一轮回复明确将多值能力撤销。

- 输入框 `[1]` / `[2]` 只接受**单个值**（一个字面值或一个 `/.../` 正则）。
- 不支持任何分隔符语法（如逗号分隔 `C,CR,Credit`）。
- 如果用户希望匹配多种值（如 `C` 和 `CR`），请用正则的分组语法（如 `/^(C|CR)$/`）来表达。

#### ✅ Q4-正则-已确认（2026-04-07）

**最终结论：只支持 `/.../` 包裹的 JavaScript 正则字面量**，不支持独立通配符。本项目技术栈为 Node.js，可直接复用原生 `RegExp`。

具体行为：

1. **触发条件**：输入框内容**以 `/` 开头**且**包含结尾 `/`**（结尾 `/` 后可选带 flag）。例如：`/^C$/`、`/^C.*/`、`/c/i`。
2. **语法**：标准 JavaScript `RegExp` 字面量 `/pattern/flags`，flags 可选，支持 `i` / `g` / `m` / `s` / `u`。
3. **匹配方式**：`regex.test(trimmedSourceValue)`（整串 test，不使用 `match` / `exec`）。
4. **大小写默认**：**不自动加 `i` flag**（遵循 Q4 整体的大小写敏感原则）。用户如需大小写不敏感匹配，必须显式写 `/C/i`。
5. **无效正则**：在配置时校验。保存时若 `new RegExp(pattern, flags)` 抛异常，弹错误提示 `正则表达式语法错误`，弹框保持打开、已填字段不丢失。
6. **与多值混用**：因多值已不支持（见 Q4-多值-已确认），不存在"正则与多值混用"的场景。
7. **字面值含 `/` 的边缘情况**：目前**没有转义机制**。如果用户希望把字面值 `/foo/` 当作普通字符串匹配（即源字段值就是这一串），必须改用正则形式 `/^\/foo\/$/`。这是已知的语法限制，已在正文 3.2.1 节注意事项中说明。

正文 3.2.1 节、3.2.2 节、AC1-29a / AC1-29b 均已按此结论锁定。

## 十一、Release Note 草稿

> 以下文案面向最终用户，由发布时整理到 release notes 中。措辞可后续微调。

### 新功能

- **按字段区分发生额**：在「映射关系管理 → 映射关系设置」中新增配置项「按字段区分发生额」。开启后可在「发生额映射关系管理」对话框中配置两行规则，按"条件字段 + 条件值 → 目标字段映射为 Credit Amount / Debit Amount"的形式描述账单结构，覆盖此前直接映射和按正负号拆分两种模式无法表达的银行流水格式（如单金额列 + 类型列、双金额列 + 类型列等）。规则的条件值支持字面值精确匹配（大小写敏感）以及 `/pattern/flags` 形式的正则表达式。

### 已知限制

- **v1.4.7 及以下版本的应用在打开 v1.4.8 及以上版本导出的模板 bundle 时，新增的「按字段区分发生额」配置会被静默忽略**（不会报错），bundle 中其它已有字段仍可正常导入。如果需要跨版本共享含有此配置的模板，请确保接收方也升级到 v1.4.8 或更高版本。
  - 技术原因：v1.4.7 的 bundle 读取逻辑不校验版本字段，已发布版本无法追溯阻断。
  - 本版本起在 bundle 顶层写入 `bundleVersion = 2`，v1.4.9+ 将基于此字段在打开过新版本 bundle 时显式报错拒绝；v1.4.7 老用户应升级到 v1.4.8 或更高版本以获得正确的版本识别能力。
