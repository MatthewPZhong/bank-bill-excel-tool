- 用户测试未启动

**风险**：
- 无（保持现状）

- PR review 发现 finding 修复后需要新 β 标识
- 改动量较大（≥ 5 SR-FIX commit）且需在 PR review 中区分版本

**适用条件**：
- ✅ Phase 0-6 完成
- ❌ 需有 SR-FIX commits（当前未有 PR review 触发 SR-FIX，N4-cont-1 sentinel v0.3 修订已在 beta.1 内完成）
- ❌ 需用户明确指示

**当前评估**：**不推荐 bump 到 beta.2** — Phase 0-6 已闭环 + 无 SR-FIX backlog；如果直接进 stable 也可直接跳。

### 选项 C：bump stable `2.1.10`

- ✅ Phase 0-6 完成 + release-check 全绿

## 三、推荐方案

### 🟢 推荐：保持 `2.1.10-beta.1` 不动

**理由**：

1. **流程未走完**：按 memory `workflow_no_tester_no_auto_pr` — 用户测试循环未启动；按用户 spec → dev → review → manual test → SR-FIX → PR → merge 流程，β.1 是测试期版本号，不应在测试前 bump
2. **测试已闭环**：Phase 0-6 已闭环（35 commits / release-check 全绿 / check-vars 全过 / 文档三件套完整 / important-variables 升格完成）；β.1 本身已是可测版本
3. **SR-FIX 可在 beta.1 内消化**：v2.1.9 经验 — SR-FIX-1 round 1/2/3 三次修复全部在 beta.1 内提交（PR #53），合并时才 bump stable；如果用户测试发现 bug，可继续在 beta.1 内修复 commit
4. **stable bump 触发条件待满足**：用户测试 + PR review + finding 全修 + 用户拍板合并 — 这是 stable bump 的硬前置；当前 stable bump 前置不满足

**下一步**（按推荐方案）：

1. **主线程通知用户**：Phase 6 完成；β.1 可启动用户手动测试（按 `manual-test-checklist.md` 4 主线 ≥ 20 case + 0 regression 9 主题）
2. **用户测试 → SR-FIX 循环**（如发现 bug）：在 beta.1 内修复 commit，不 bump 版本号
3. **用户测试通过 + 拍板提 PR** → team-lead 提 PR + check-vars / preview 回归（已完成）
4. **PR review 通过 + finding 修复**（如有）→ 用户拍板合并
5. **合并 main + bump stable `2.1.10`** — 此时执行 `npm run scan:vars` 重跑 + 三件套同步 + 提 release commit

### 🟡 备选：bump `2.1.10-beta.2`（仅在以下场景）

- 用户主动指示"提 PR 前需要 β.2 标识"
- 发现 ≥ 5 SR-FIX commit 且需在 PR body 中明确区分 beta.1 → beta.2 修复范围

### 🔴 不推荐：bump stable `2.1.10`（流程前置未满足）

- 跳过用户测试 → PR review → finding 修复路径，资金红线 + DB 不可逆 + worker 跨进程 三类高危改造未经用户实测就 stable 发版，违反 CLAUDE.md 规则 7
