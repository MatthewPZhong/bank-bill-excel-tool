# v3.1.0 技术设计

## 数据边界

- 批量银行、链接、运行和差异数据保存在独立 `position-data.sqlite`。
- 主库只保留既有应用配置和轻量运行能力，不保存平盘批量明细或个人信息。
- 首次初始化由主库先保存 generation 0 bootstrap，再创建完全一致的侧库；已有侧库但主库没有 checkpoint/bootstrap、仅旧 initialized marker、文件缺失或空库均 fail closed。
- 后续由主库保存 checkpoint 和当前待完成 operation token，侧库保存身份、generation、事务 token、父 token 与 operation token 历史。侧库领先时只有主库预登记操作与完整父链同时吻合才追平；旧主库单独恢复或新旧代次分叉均阻断。
- 平盘业务全局串行，待完成记录、checkpoint 同步和清理均验证 operation token 所有权。
- 备份恢复以完整应用数据目录为单位，主库与 `run-data/` 不得混用不同批次。
- 银行、账户确认导入和结果回导使用应用私有暂存副本，保证解析、写库和存档来源一致；未完成存档引用的副本跨重启保留，直至重试成功或批次删除。

## 状态与失效

- 银行数据按 `Channel + 月份` 原子替换，BizId 不允许跨范围迁移。
- 运行草稿绑定银行、来源、映射 revision 和规则版本。
- 银行、链接、映射或规则变化后，旧草稿禁止导出、回导和确认。
- 草稿 scope、snapshot、summary 采用严格结构校验；每条运行行保存覆盖索引与 JSON 的完整性 hash，来源、结果、差异、消费标记和血缘均重新推导，再与当前银行/链接记录及汇总计数交叉核对。已确认运行还会把运行血缘反推的消费关系与持久消费表双向核对。

## 匹配与确认

- 订单类匹配执行单次运行及跨已确认运行的双向严格 1:1。
- 匹配金额使用十进制字符串计算，不使用 JavaScript 浮点数。
- 回导固定 49 列，只允许在原 FundType 基础/FX 二元组内修改。
- 结果、链接和原始表的标识符格式写到列定义，`客户号`、`accountReference`、`Account Reference`、大额行号、VA 等非典型标识符和零数据工作簿仍保持文本列。
- 未解决差异确认不认领链接来源，只有唯一成功匹配血缘写入消费表。

## 存档与退出

- 成功输入、回导和每次结果导出均独立立即接入存档中心；业务 IPC 返回成功前完成存档或形成正式失败批次/持久文件 outbox，跨重启不依赖未持久化内存任务。
- 待完成操作记录业务成功状态、文件清单和输出写入前快照；侧库已推进、业务已成功或输出已发布时，启动恢复及同进程部分提交失败都必须先重建存档意图，再同步 checkpoint。
- outbox 重放成部分失败正式批次时，只释放已解决且没有其它未完成引用的源文件；失败 artifact 的源文件继续保留供重试。
- 清结算银行账户表 prepare 阶段只有待确认 token 时标记为延迟存档，不算业务提交；用户确认后的 apply 才推进侧库并登记输入文件。
- 历史 owner 只有在已确认运行的完整行血缘可证明同一消费关系时，才可为重导银行 BizId 提供幂等消费；无关 owner 立即阻断当前运行读取。
- pending、存档结果和 checkpoint 清理由可注入生命周期 helper 编排，覆盖正式批次、outbox 和双失败行为级测试。
- 正式建批、追加和 outbox 重放共享 artifact 完整性门禁；全部文件取得正整数 artifact ID 才算有正式重试能力，否则写入或保留同一 operation key 的 outbox 并保护源文件。
- 启动暂存清理合并正式失败 artifact、outbox 与主库 pending 文件保护集；pending `archiveFiles` 缺失、非数组或含非法路径，以及 provider 返回非数组、抛异常等保护集不完整场景，均不执行过期清理。清理与恢复共享严格解析器；损坏文件清单不写 outbox、不清 pending、不推进 checkpoint，outbox 存储层二次拒绝非法路径。
- 退出先禁止新业务并等待活动业务结束，再排空存档任务，最后关闭 side DB。
